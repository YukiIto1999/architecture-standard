# canonical 層

canonical 層は、外部へ公開する契約の意味の正本を定める層である。
操作・型・エラー・制約を、媒体に依らない意味として記述する。
canonical は [layout](./layout.md) の依存に従う。

## 意味の定義

canonical は、公開する操作の入出力、型の field、直和の variant、値の制約、エラーを定義する。
公開契約に必要な共有の field、variant、制約を、利用側の手書き DTO にだけ持たせない。
canonical は HTTP や protocol の詳細を含まず、媒体固有の表現は binding が所有する。
emitter の注釈は、名前空間や import の名前だけで媒体依存と判定せず、定める内容と変更理由で配置する。
型の制約や直和の意味を各出力へ保つ注釈は canonical に置き、HTTP の path、method、header、status などを定める注釈は binding に置く。
core の業務モデルは canonical の写しではなく、各コンテキストが所有する責務と保証で定める。
業務の区分を公開する契約は、選択肢の意味と公開する値域を定め、内側の区分との対応を明示する。
同じ意味と保証を持つ公開区分の定義は共有し、operation ごとに独立した一覧を保守しない。

## 単一の正本

canonical は、契約の意味の唯一の正本である。
http と protocol は canonical から導き、generated は canonical と binding から導く。
言語の型を、正本にしない。

## 分割

canonical は、業務のコンテキストや host の技術契約など、意味の所有者ごとのファイルに分け、一枚のファイルへ集約しない。
host 固有の技術操作を業務の契約と区別し、core の操作を呼ばないことを理由に公開契約の正本を手書きの言語型へ置き換えない。

## 記述

canonical は、単一の契約記述言語で記述し、その記述を契約の単一の正本とする。
契約記述言語と生成器の採用は、[tools/build/typespec](../../tools/build/typespec.md) が定める。
生成した DTO が公開契約を具体的に表せない場合は、意味の欠落を canonical で、wire への写像の欠落を binding で、生成表現の欠落を生成器で直す。

## 集合の操作

集合を返す操作は、最初から頁を持つ。
続きは opaque な cursor で表し、client はその中身を解釈しない。
cursor は続きの位置だけを表し、認可を含めない。
頁の大きさは任意指定とし、既定値と上限を定義へ書く。
頁の大きさと cursor の入力は optional かつ NonNullable とし、前者の未指定は既定値、後者の未指定は最初の頁を意味する。
上限を超える指定は上限へ丸める。
終端は、次の cursor の不在で表す。
並びは安定とし、同値は一意の鍵で順序を固定する。
絞り込みと並び替えは、操作の定義で宣言した項目に限る。
相対日付などの条件は、評価に使う基準時点と暦の文脈、未指定時の意味を定義し、条件本体と区別する。
UTC offset とタイムゾーンの違いは [RFC 9557](https://www.rfc-editor.org/rfc/rfc9557) の定義に従い、夏時間や過去の規則を必要とする暦の解釈を offset だけで代用しない。
総数は、既定で返さない。
総数の選択を提供する操作は、その入力と返す場合と返さない場合の結果の形を定義し、選択だけでは頁の要素と順序を変えない。

## 更新の操作

更新の操作は、対象の全体の上書きでなく、関心の単位で分けた部分への操作にする。
関心の単位で分けた更新対象について、その操作は更新対象の完全な desired state を定義する。
取得と対にした全項目の上書きを、機械的に提供しない。
更新の項目は必須にし、全項目が任意の更新を作らない。
変更できない項目は、検証で弾くのでなく、契約から除く。

## 直和の型

直和は、判別子と各 variant の対応を契約に持つ判別付き直和として定義する。
判別のない直和は、媒体と生成先を越えて variant を一意に復元できないため canonical に置かない。

## 値の不在

項目の必須性と、存在する値の null の許容は、独立に定める。
required は項目の存在を必須とし、optional は未指定を許し、Nullable と NonNullable は存在する値の null の許容を表す。
任意指定の入力は未指定時の意味または既定値を canonical に定義し、binding と生成先でもその意味を保持する。
既定値も型と制約を満たすものとし、未指定時に一か所で適用して、null や不正値の補完に使わない。
未指定と、値の削除は、別の意味であり、別の表現で表す。
対象の不在と、要素が零の集合は、別の意味であり、別の表現で表す。
リクエストは必要な項目だけを必須で受け、レスポンスは確定した形で返す。

## 命名

操作・型・エラーの名前は、その契約が表す業務または技術の意味の語彙で付ける。
command・query・result・view の別を、名前で表す。
HTTP の request・response の語彙を、canonical に持ち込まない。
名前の規則性は、契約の公開範囲に依らず保つ。

## 進化

互換のある変化は、追加で行い、読み手は未知の項目を無視する。
破壊的な変化は、独立した版として分け、移行の期限を定める。
恒久的な互換ラッパーや互換専用の層を作らない。
版を、URL の path へ刻まない。
互換は、契約の進化と移行の期限で扱う。
破壊的な変化の切り替えは、受け入れの拡張、既定の切り替え、旧の収縮の順に進める([principles/evolution](../../principles/evolution/README.md) に従う)。
この移行の期限は現行の公開契約を切り替えるために定め、保存事実の保持・回復に必要な旧版の解釈の撤去期限にはしない。
保存事実の版の解釈は [concerns/persistence](../../concerns/persistence/read-time-upcasting.md) の「追記した事実の版を読み出しで現在へ変換する」に従う。
制約の変更の互換性は、リクエストとレスポンスで向きが逆になる。
リクエストの受け入れを広げる変更と、レスポンスの確定を強める変更は互換である。
リクエストを狭める変更と、レスポンスを広げる変更は破壊的であり、版を分ける。
