# tests の方法

methods は、検証に用いる技法と、規範から検証への割当を定める。
技法は、検証する対象の性質で選ぶ。
この file は、どの対象へ検証を割り当てる場合にも使う、検査の選択、性質と入力領域、規範から検証への割当、テストの有効性を定める。
特定の対象にだけ使う技法は次の file に分け、その対象へ検証を割り当てる場合は、この file と合わせて読む。

| 対象 | file |
|---|---|
| ドメイン型の計算・比較・区分判断・集合の操作、権限の matrix | [methods-domain](./methods-domain.md) |
| 実依存の adapter、生存と準備の面、故障の注入による再現、永続化・transaction・messaging の保存と再構築 | [methods-persistence](./methods-persistence.md) |
| 契約の意味と生成、信頼できない入力と公開 API の契約への適合、protocol と HTTP binding の適合 | [methods-contracts](./methods-contracts.md) |
| 利用者面の受入と smoke、利用者面の自動検査の境界(accessibility を含む)、CLI と terminal | [methods-surfaces](./methods-surfaces.md) |
| 依存方向・公開面・配置・命名などの構造の規則と、循環・規模・複雑さのアーキテクチャ特性 | [methods-structure](./methods-structure.md) |

methods は [layout](./layout.md) の配置に従う。
ダブルとフィクスチャの扱いは [doubles](./doubles.md) に従う。

## 変更と影響範囲

製品の振る舞いを確かめる検査と、検査の検出力を評価する分析を分ける。
検査ごとに、保証する性質、入力領域、期待する観測、失敗条件を定め、分析では評価する性質と得たい判断を定める。
例示テスト、PBT、mutation という技法の名から実行資源や承認条件を決めず、それぞれの役割に割り当てる。
変更ごとの検査は、比較元と検査する source の同一性を確定し、変更入力の所有単位と、その依存先・逆依存の consumer から選ぶ。
変更入力には、production code、テスト、契約、設定、依存の版、生成器と生成元を含める。
index、worktree、未追跡の入力、削除、移動と改名を検出し、実行する source と同じ内容の差分で対象を導く。
削除と改名の影響は、変更前の参照と変更後の参照から追い、現在存在する file の参照だけで非影響としない。
影響範囲は、宣言された依存から影響する単位を返す build graph、入力の閉包・command・toolchain・宣言した環境を鍵にする内容 cache、道具に備わった差分選択で選ぶ。
project の検証入口に、変更入力から影響範囲を導く独自の planner や影響の判定を実装しない。
検査の証跡の保存、照合、再利用は、同じ build graph の内容 cache に担わせ、project の検証入口に証跡の保存、鍵の算出、照合を実装しない。
後段の検証入口は、前段の task を build graph の task として含め、同じ source と入力に対する前段の task の結果を同じ内容 cache から再利用する。
build graph と内容 cache を持つ道具の採用は、[tools/build](../../tools/build/README.md) が定める。
静的参照だけでは表せない設定、生成物、登録、実依存と scenario の結び付きは、build graph の依存と cache の鍵の入力として宣言する。
lockfile と依存の版、toolchain、build 設定、検証入口、生成器、契約と契約 profile、migration、認証・認可の policy、設定 schema の変更は、build graph の依存に現れない形で多くの保証へ届く。
これらの変更では、変更ごとの検査の対象を、その入力を使う保証の全範囲へ広げ、広げた理由を記録する。
依存関係や所有者を確定できない場合も、未確定の関係が影響する保証の全範囲へ対象を広げ、理由を記録する。
影響する保証の全範囲は、その入力または未確定の関係が届きうる保証と境界の全体であり、無関係な保証も含む全量ではない。
一つの関係を解決できないことを、無関係な保証も含む全量入口の反復実行の理由にしない。
製品の受入に必要な検査を省けるのは、必要な保証への非影響を示せる場合か、同じ対象と入力の有効な証跡を再利用できる場合だけである。
選択実行は、実行した検査の一覧、省いた検査とその区分(非影響、cache の有効な証跡)、全範囲へ広げた変更と理由、比較元と選択した source の同一性を記録し、全量回帰との照合に使えるよう保存する。
被覆した行だけで契約の入力領域を決めず、既存テストが到達しない分岐と拒否も対象へ含める。
mutation の候補は、変更した production の箇所と、変更入力の依存先・逆依存の consumer、契約、設定、生成物との関係から振る舞いまたは検出力へ影響が届く production の箇所から導く。
未変更の caller への影響も候補に含め、production の diff が空でも、テスト、契約、設定、依存、生成器または生成元の変更を追う。
候補から、調べる性質、検査の変更、過去の見逃しと有効な既存証跡に基づいて生成対象と変異演算子を選び、選択理由と未分析の範囲を残す。
mutation の影響部分の生成対象と再判定する mutant の選択も、道具に備わった差分選択、build graph と内容 cache に限る。
それらで選べない影響部分は、届く関係とともに未分析として記録し、検証入口で補わず、道具の実装課題として扱う。
変更部分の結果で、影響部分を分析済みとしない。
変更部分と影響部分の全候補を、各変更で生成・実行し尽くすことを要求しない。
生成対象と、各 mutant を観測するテスト群を別に選び、被覆テストの選択を生成対象全体の分析と同一視しない。
被覆テストが無い mutant を検出済みとせず、選んだ範囲の結果から未分析の範囲の検出力を保証しない。
変更入力が振る舞いまたは検出力へ影響する範囲の既存証跡は、production の箇所が未変更でも無効化する。
source の依存閉包と失効する証跡は検査別に対応付け、必要な保証への非影響を示せる検査の証跡を、木全体が変わったことだけで失効させない。
分析候補は既存証跡の有無と独立に導き、無効化された証跡の一覧だけで影響範囲を決めない。
影響を確定できない関係は、影響しうる保証と境界とともに記録し、非影響または分析済みとして扱わない。
影響範囲から選んだ実行の正しさは、選択によらない全量回帰の結果で確かめる。
全量回帰で失敗し、同じ source で再現した検査を、その source に含まれる変更を検証した選択実行の記録が省いていた場合は、選択の誤りとして記録する。
選択の誤りは、非影響として選ばなかったことによる見逃しと、cache の証跡が失効しなかった不備に分けて集計する。
見逃しは見逃した関係を build graph の依存として、失効の不備は cache の鍵に欠けた入力として宣言する。
選択の記録が無いか source の同一性を照合できない失敗は、照合不能として別に数え、選択の正しさの証拠にしない。
製品の検証と分析の実行時点、結果の取込と再利用は [process/verification](../../process/verification.md) に従う。


## ロジックと状態

純粋なロジックは、stateless の property-based testing で検証する。
そのうち、入力のすべてが列挙型や真偽値のように取りうる値の一覧で定義された型である純粋なロジックは、入力を生成する代わりに、全組み合わせを列挙して性質を検証する。
列挙は型の定義から導き、人が値を書き並べない。
列挙の到達集合が型の定義から導いた全入力集合と一致し、入力の欠落と重複がないことを確かめる。
件数の積との一致だけを網羅の証拠にせず、0 件の実行と集合の不一致を不合格とする。
全組み合わせの実行が検証の段の予算を超える場合の扱いは、[process/verification](../../process/verification.md) が定める。
状態の遷移は、状態を持つ property-based testing で検証する。
性質は、公開契約の入力条件、結果、拒否、状態への効果から導き、不変条件、冪等性、往復、metamorphic な関係、独立したモデルとの一致を、その保証の判定に使える条件に応じて選ぶ。
性質の名前から強弱の序列を作らず、異なる保証を一つの性質で代替しない。
use-case の判断や効果の組立のうち、実依存を必要としない性質は、port を fake に置き換えて検証する。
冪等性は、同じ command の識別子の再実行が同じ結果を生むことで確かめる。
これらはプロセスの外への依存を持たない Small である。
配置は [layout](./layout.md) に従う。
形式手法で、コードの全面は検証しない。
symbolic と concolic の実行を、標準の検証に組み込まない。
これらは、対象を限れば成果が出る一方で、全面へ広げると実行の費用と結果の読み替えが検証入口に見合わないためである。

## 性質と入力領域

性質ごとに、入力領域、適用条件、観測結果、失敗条件を定める。
外部入力の領域は、handler の型が受けたい値だけでなく、その channel が運べる表現から定める。
文字列、byte 列、構造化データのどれを入口で受けるか、encoding、長さ、欠落、余分な項目、境界値の扱いを契約と照合する。
有効入力は、相互に依存する値を独立生成して後から大量に捨てるのでなく、先に生成した値から従属する値を構築して制約を満たす。
拒否する入力は別の領域として生成し、想定内の拒否、その理由、状態と副作用の不変を観測する。
拒否領域を、有効入力の constructor を通した値だけで代替しない。
独立した検証を蓄積する入口は、違反を一つだけ持つ入力に加えて、複数の独立した違反を同時に持つ入力を拒否領域に含め、全ての違反が一つの結果に残り、状態と副作用が変わらないことを観測する。
後段が前段の出力に依存する経路は、前段が想定内の失敗で終える入力を与え、後段とその効果が実行されないことを観測する。
蓄積の途中で起きた欠陥と取り消しが、蓄積した失敗に混ざらず、それぞれの終了として返ることを観測する。
外部の状態や時刻に依存する性質を型の保証にする入口は、有効範囲の外で使用する入力を作り、使う時点または確定の中で再検査されることを観測する。
再検査でも性質が成立する場合は受理でき、成立しなくなった場合は拒否して状態を変えないことを、それぞれ独立した期待値で確かめる。
型が構築できることだけで、使う時点でその性質が成り立つことを示したとしない。
生成器、適用条件の判定、oracle が検証対象と同じ誤りを共有しないことは [principles/verification](../../principles/verification/test-reliability.md) の「テストの信頼性を保つ」に従う。
schema の検証対象と、その schema から作る生成器だけの一致を、schema 自体の意味の正しさの証拠にしない。
往復は対応する二つの変換の整合を調べるが、両方に同じずれがあれば通るため、外部表現の契約には独立した期待値も割り当てる。
入力の変化と出力の関係は、契約が保証する場合に限って使い、順序や重複が意味を持つ処理へ順序不変や冪等を要求しない。
定数を返す実装でも通る比例関係など、契約違反を許す性質だけで値の正しさを判定しない。
実行は、生成数、適用条件で捨てた数、性質を判定した数、契約から分けた入力区分の通過数を残す。
性質を判定した入力が 0 件の実行は、不合格とする。
契約の適用区分を通過していない場合は、反復数を増やすだけでなく、区分別の生成か性質の分割で検査する。
空の集合や空文字列は、契約が受け入れるなら検査する入力であり、実行した入力が 0 件であることとは区別する。

## 操作列と観測

状態を持つ検証は、初期状態、独立した参照モデル、状態ごとに実行できる操作、引数、状態の変化、利用者が観測する結果を持つ。
操作の生成は、参照モデルの状態から有効な操作と引数を構築し、前提のない操作を捨て続ける形にしない。
無効な操作の拒否は別の検査として扱い、正しい状態遷移の検査から抜け落ちないようにする。
実体とモデルは、操作の契約が定める観測点で、戻り値、公開された状態、発生した効果を、その保証に必要な範囲で比較する。
観測点は、同期の結果、非同期の受理、処理中、完了のうち、契約が保証するものから定め、同期の操作は返った直後を観測点に含める。
受理は完了と別の観測点であり、受理の直後に完了後の状態を要求せず、未完了を拒否や失敗と判定しない。
処理中は契約が公開する状態だけを比較し、内部の事象の順序や通知を条件にしない。
完了は、契約が公開する通知または状態の遷移で観測し、成功、拒否、期限超過を含む失敗、取り消しの終了を区別する。
非同期処理の最終結果は完了を観測して判定し、受理の応答だけで業務上の拒否や失敗がないと判定しない。
到達した観測点の誤りは、後続の操作、clear、reset の前に判定して残し、未到達の完了を待つために処理中の取り消しなどの操作を止めない。
最後の状態だけの比較は、その前の誤りを後続の clear や reset が消しうるため、途中の観測の代替にしない。
契約が完了までの期限を定める場合は、公開された完了時刻や期限時点での未完了の観測など、契約の時間軸と観測境界に対応する証拠から、期限内に完了したかを判定する。
runner の観測が遅れたことだけを、業務の完了が遅れた証拠にしない。
runner の待機の上限は契約の期限と別であり、その上限や観測の不足で契約の成否を確かめられない実行は、契約違反でも合格でもなく未確認に分ける。
完了の保証を検査するのに必要な公開の観測が契約にない場合は、検査側で内部の通知を足して補わず、未確定の仕様として返す。
時刻、乱数、外部応答などを操作列の入力として制御する場合は、その範囲を記録し、制御していない process や資源の振る舞いまで検証済みにしない。
状態モデルの検証が process 内で閉じても、terminal、datastore、別 process との実結合の保証は実依存の検査へ別に割り当てる。

## 反例の縮小と分類

失敗した入力と操作列は、破る性質を保って縮小し、縮小後にも入力制約と操作の前提が成り立つことを確かめる。
縮小で前提を失った操作列を、元の失敗の小さい再現として扱わない。
反例は、縮小した値または操作列、seed と replay に必要な情報、生成器と検証器の版、失敗した観測を残して再現する。
見つけた反例を固定する回帰は、入力の生成による性質の検査を残したまま加える。
失敗は、製品の契約違反、誤った性質、生成器またはモデルの欠陥、未確定・矛盾・実現不能な仕様、実行環境の不成立に分ける。
失敗を緑へ戻すために生成領域を狭めたり、未確定の仕様を実装の現状だけで決めたりしない。
矛盾する仕様や必要な成功を実現できない仕様は、実装を曲げて緑にせず、[principles/requirements](../../principles/requirements/specification-quality.md) の「仕様自体の欠陥を実装の合否と別に確かめる」に従って仕様を直す。
成功は、実行した領域と観測で反例を見つけなかった結果として報告し、全入力での正しさの証明としない。

## 反実仮想で検証を選ぶ

隠れた制約を探す場合は、現在の producer と consumer を読み、開発者が合理的に行いうる小さい変更を一つ仮定する。
値の追加、順序の変更、既定値の変更、早期 return、境界の緩和などから、その対象の実際の関係を崩す変更を選ぶ。
変更から、暗黙の不変条件、その条件が破れた入力または操作列、consumer が観測する失敗、検出する判定へ因果関係を辿る。
変更だけを危険と呼んだり、起きていない障害を実際の incident の文体で記録したりしない。
不変条件の強制は型、境界の検証、所有する状態の操作へ割り当て、違反の検出はこの file の「規範から検証への対応」に従う。
既存の判定が仮定した違反を検出するなら、その入力と実測結果を使い、検出しないなら許可された範囲で保証または判定を補う。
実装がない設計では、検出する具体的な入力と観測を完了条件へ渡し、検出済みとしない。
型や静的検査で変更を拒否する場合と、契約違反の実行結果をテストが検出する場合を分ける。
思考実験だけ、適用した変更だけ、赤だけを有効性の証拠とせず、変更、保証の違反、判定結果を対応させる。

## テストの単位

検証の単位は、公開の振る舞いであり、実装の単位ではない。
class や関数ごとに 1:1 の単体テストを置かない。
振る舞いの検証は、公開 API を通し、内部の協力者を実物のまま含めて行う。
局所の単体テストは薄く保ち、仕様と振る舞いの検証を厚くする。
実装の詳細に結合したテストはリファクタリングで壊れ、振る舞いに結合したテストだけが構造改善の安全網になる。
ダブルの範囲は [doubles](./doubles.md) に従う。

## 決定性と隔離

テストは、実行順序に依存せず、単体でも他のテストと並べても同じ結果を返す。
テストどうしが共有する状態は、実行の前に用意し、後始末を次の実行へ持ち越さない。
並列実行への耐性は、テストごとに独立した資源(接続・スキーマ・一時領域)を割り当てて確かめる。
繰り返し実行して結果が変わる不安定なテストは、隔離の区分へ移し、通常のゲートから外す。
隔離の区分に残せる期間は期限で区切り、期限の値は project が定める。
不安定さを断つ原因の分類と対処は [principles/verification](../../principles/verification/README.md) に従う。

## 性質別の技法

oracle が得にくい対象は、metamorphic な関係で検証する。
移行と置換は、旧と新の経路の差分で検証する。
段の差し替えでは、旧と新の差分を、後段と呼び出し側が観測する出力・想定内の失敗・効果で比べ、型が合うことだけで同値としない。

## 規範から検証への対応

標準の要求と禁止事項は、観測できる性質ごとに次の検証へ割り当てる。
比較する適用対象・入力集合は、各検証の自己申告から採らず、割り当て先である標準の要求と禁止事項が要求する全範囲から導く。
その範囲を欠かさない非空の集合を標準本文から定められなければ、同じ性質とは判定しない。
二つの検証を同じ性質の判定とみなせるのは、同じ規範命題へ割り当てられ、そこから導いた非空の適用対象・入力集合が一致し、その集合の全要素で一方の合格が他方の合格を含意し、かつ逆方向も成り立つ一つの観測可能な述語として示せる場合だけである。
規範が要求する適用対象・入力集合が一致しない、一方が適用不能になる、または一方だけが不合格となる対象・入力を作れる場合は、別の性質として両方を残す。
反例をまだ見つけていないことだけを、同じ性質の根拠にしない。
実装の欠陥または更新漏れだけで生じる不一致は、別の性質の根拠にしない。
同じ性質を複数の道具で重複して判定せず、最も内側で確定できる型、静的検査、実行テスト、計測の順に一つの判定を選ぶ。
共有の道具が保証する性質は、その道具の検証入口を持ち主とし、持ち主が道具の版ごとに確かめる。
共有の道具は、言語に欠ける compile 時の検査と生成を補う機構、契約の生成器、mutation の道具のように、利用する製品の code と別に自身の検証入口と版を持つ道具を指す。
利用する project は、使う版と設定に対する持ち主の有効な証跡を参照し、自身の検証入口では、道具との接続、設定、生成物の drift、自身の型や契約と道具の入出力との写像、実際の binding、業務の受入だけを確かめる。
持ち主が版ごとに確かめる性質を、利用する project の検査へ複製しない。
持ち主の有効な証跡がない版は、持ち主の検証入口で確かめてから使い、利用する project の検査で代替しない。
利用する project で道具の保証の違反を見つけた場合は、その違反を検出する検査を持ち主の検証入口へ加え、利用する project の再検証で補わない。
道具の版、設定、道具へ渡す入力の変更で影響する保証は、「変更と影響範囲」に従って再選択する。

transaction の検証は、application が開始から確定または中止までを制御すること、確定前の各終わりでの中止、確定結果不明の保持、確定後の後始末の失敗で確定済みの結果が失われないことを含める。

## テストの有効性

mutation は、人工的な変異に対するテストの反応から、検出力の弱点と改善箇所を調べる分析である。
未検出 mutant は元の製品の欠陥を直接示さず、全 mutant の検出も、仕様の正しさ、要求の網羅、製品の成立を証明しない。
分析の目的は契約上意味のある誤りを検出するテストの改善であり、全件検出、未検出 0 件、mutation score を製品の承認条件にしない。
分析対象は「変更と影響範囲」に従って選び、全量分析は必要な調査の選択肢とし、変更ごとの義務にしない。
生成対象、変異演算子、選択したテスト、選択理由と未分析の範囲を記録し、対象を狭めた結果を全量分析と表示しない。
diff の取得に失敗した分析は、変更が無い分析と区別して不成立を報告する。
分析の成立は、選択した範囲で生成、テストの発見と実行、結果の記録ができたかで判断し、mutant をすべて検出したかと区別する。
未完了の分析は未完了として残し、判定できた変異と未判定の変異を分ける。
同じ対象、性質、入力、検証器の組で違反を検出した既存の証跡は、有効性の確認にも使い、同じ欠陥の手動変異や全量実行を重ねない。
証跡の再利用と失敗後の実行範囲は、[process/verification](../../process/verification.md) に従う。
手動で検証対象を変える場合は、試す差分だけを隔離した入力へ加え、利用者や他の作業の変更を戻さず、その差分だけを取り除く。
mutation の結果は、道具が返した report の mutant の識別子、変異の差分、status、選択したテストの実行結果と終了 status を残して判断し、集約 score や手作業の status の書換えで置き換えない。
未検出または判定が成立しなかった結果は、契約と元の実装の観測に基づいて次の原因へ分類し、生存したという理由だけで一律にテストを足さない。

| 原因 | 判定の根拠 | 対処 |
|---|---|---|
| 元の実装の欠陥 | 変異を加える前の実装が、独立した期待値に対して契約を破る | この file の「見つけた欠陥」に従って回帰を確定し、製品を直す |
| 検証の不足 | 元の実装は契約を満たすが、契約を破る mutant の経路を実行しないか、誤った結果を判定しない | 破った性質に割り当てた技法で、入力領域と oracle の不足を補う |
| 等価変異 | 契約の入力領域で、元の実装と mutant の観測が変わらない | 根拠と範囲を残し、検出しにくいことを等価の理由にしない |
| 契約内の観測差 | 元の実装と mutant の結果は異なるが、どちらも契約が許す結果である | 未検出の status と根拠を残し、契約にない一意の結果を期待値へ追加しない |
| 別の保証への影響 | 機能の観測は同じだが性能や資源など別の契約上の性質が変わる | その性質の検査へ渡し、内部実装を固定する機能テストで代替しない |
| runner または実行環境の失敗 | 基線の失敗、構文や型として成立しない変異以外の compile の失敗、テストの発見や選択、runner、判定前の timeout により分析が成立しない | 分析の不成立として記録し、原因への対処後に必要な範囲を再実行する。製品の欠陥または検出済みとして数えない |

複数の原因が重なる場合は、それぞれの根拠と対処を残す。
等価または契約内の観測差と判断した根拠は、契約の入力領域、変異の正確な識別子と実差分、判断に使った source と依存 lock の同一性に結び付ける。
根拠が未確認か入力の同一性が一致しない変異は、未分類として残す。
道具の結果と終了 status を保持し、契約に照らした分類を別に記録する。
検出力を改善した場合は、該当する性質の違反を実際に検出することを確かめ、同じ mutant を使う場合は識別子と結果を対応付ける。
製品の修正は、該当する回帰検査と修正の影響範囲で確認し、無関係な mutation の再完了を条件にしない。
通常の品質検査は厳格な型と lint を維持し、mutation の環境では変異に伴う未使用などの診断が実行可能な変異を不必要に止めないようにする。
compiler が構文や型として成立しないと判定した変異は、実行可能な mutant と分けて報告し、検出にも未検出にも算入しない。
lint が実行可能な変異の実行を妨げた場合は分析の未完了として報告し、構文や型として成立しない変異やテストによる検出として扱わない。
変異の生成、被覆テストの選択、実行と判定の各状態を記録し、lint の停止や未実行を検出済みとしない。
被覆の確認が成立した結果として対象の mutant を覆うテストが無い場合は、未被覆による未検出として数える。
被覆によって選んだテストがあるのに runner が実行しなかった場合は、分析の不成立として別に報告し、検出にも未検出にも算入しない。
timeout 自体が契約の違反を観測する判定なら、その期限、実行の成立、失敗した保証を示す。
mutant の生成が 0 件なら、入力差分の取得、選択した対象と演算子、変異できる箇所の有無を示し、0 件だけでテストの有効性を示さない。
変更部分の生成が 0 件であることから、影響部分の分析結果を推定しない。
分析の実行、未完了の扱い、結果を修正へ返す経路は [process/verification](../../process/verification.md) に従う。
未実行の箇所は、カバレッジで見つける。
カバレッジは、仕様から導いたテストの取りこぼしを確かめる手段であり、数値を目標にしない。
数値が高くてもアサーションの強さは示されず、対象の性質への検出力は mutation や故障注入、既存の回帰証拠で確かめる。
低いカバレッジは、確実に検証の不足を意味する。
各 project は、言語 ecosystem が定めるカバレッジ指標の下限を記録し、repository の検証入口で判定する。
カバーしない箇所は、見落としでなく判断の結果として残す。
snapshot を、主たる検証にしない。
AI が生成したテストも、守る性質、独立した期待値と、その性質の違反を検出した証拠に照合し、mutation 全件の完了を受入の代わりにしない。
検証の合否の判定は [README](../../README.md) に従う。
テストの緩和は、人間が承認する。
型と lint は、予防として用いる。

## 探索

自動の検証は、割り当てた性質と書かれた例だけを判定し、書かれなかった欠陥を見つけない([principles/verification](../../principles/verification/enforce-existence.md) の「検査が見るのは書かれたものだけである」に従う)。
仕様の漏れ、想定しなかった入力、機能どうしの組み合わせ、使い勝手の問題は、探索的テストで探す。
探索的テストは、対象と探す情報を一文で述べた charter を定め、操作の結果から次に試すことを決めながら進める。
charter の観点は、自動の検証が覆っていない機能、操作、データの組み合わせから選ぶ。
探索の記録は、charter、触れた範囲、見つけた事象を持つ作業中の文書とし、読み手を探索した作業単位の実施者とする。
見つけた事象は、欠陥、仕様の漏れ、意図した振る舞いに分ける。
見つけた欠陥は、この file の「見つけた欠陥」の節に従って自動の検証へ移す。
記録の読み手は、見つけた欠陥の自動の検証がすべて緑になり、仕様の漏れをすべて戻し終えた時点でいなくなる([principles/documentation](../../principles/documentation/separate-document-types.md) の「文書の種別を分け、読み手を定める」に従う)。
探索の結果を、検証入口の合否に使わない。
探索を行う時点、仕様の漏れを戻す先、記録を取り除く手順は [process/implementation](../../process/implementation.md) が定める。

## 見つけた欠陥

見つけた欠陥は、見つけた経路を問わず、直す前にその欠陥で失敗する自動の検証を足して赤を確かめる。
足す検証は、見つけた一件の入力と手順の再現で閉じず、その欠陥が破った性質を特定して判定する。
破った性質の判定は、この file の「規範から検証への対応」の節に従って一つを選ぶ。
実行テストへ割り当てた性質は、見つけた入力だけを例として固定せず、この file と、冒頭の表が対象別に分けた file がその対象に定める技法で、その性質が成り立つべき入力の集合を検証する。
それらの file がその対象に技法を定めていない場合は、その性質が成り立つべき入力を生成して検証する。

## 実行範囲

検証の実行の順序と、変更からの範囲の広げ方は、[process/verification](../../process/verification.md) が定める。
性能の目標は [concerns/performance](../../concerns/performance/README.md)、耐障害性は [concerns/resilience](../../concerns/resilience/README.md) と [concerns/lifecycle](../../concerns/lifecycle/README.md)、security と privacy は [concerns/security](../../concerns/security/README.md) と [concerns/privacy](../../concerns/privacy/README.md) に従う。
利用者面の体験は [concerns/experience](../../concerns/experience/README.md)、可達性と識別性は [concerns/accessibility](../../concerns/accessibility/README.md) に従う。
言語ごとの具体の機構と道具の採用は [languages](../../languages/) の各 ecosystem が定める。
