# tests の方法: 契約

この file は、[methods](./methods.md) が対象別に分けた技法のうち、契約の意味と生成、信頼できない入力の契約駆動の fuzz と公開 API の契約への適合、protocol と HTTP binding の適合の検証を定める。
検査の選択、性質と入力領域、規範から検証への割当は [methods](./methods.md) に従う。

## 契約の意味と生成

契約の意味は [contracts/canonical](../contracts/canonical.md)、生成経路と能力は [contracts/generated](../contracts/generated.md)、application との接続は [contracts/adapters](../contracts/adapters.md) に照合する。
生成器の検査は、compiler の意味情報と契約 profile を入力にする生成入口から各言語の公開 consumer までを対象にし、交換用 schema の投影や生成 source の語句の一致だけで意味の保持を判定しない。
入力集合と oracle は生成結果から逆算せず、契約が受理する値、拒否する値、保持する情報と操作結果の対応から独立に定める。
契約から導く PBT 入力生成は、有効値と規則を一つだけ破る値を増やす手段として使えるが、業務結果や状態遷移の oracle の代わりにしない。
この拡張のために、既存の検証技法全体の置換を要求しない。

### 生成入口と静的な保証

対応する定義の受理と、未対応の意味、不整合、必要な binding の欠落、結果を一意に識別できない曖昧さの拒否を、生成入口の終了結果で観測する。
未対応の入力には、compiler が認識するが生成器が解釈できない注釈や encoding を含め、未知の構文の拒否だけで代替しない。
拒否では、元の宣言位置、該当する操作・型・field、対象出力と保存できない意味を診断へ照合し、必須の出力が欠けた部分生成物を成功した更新として公開しないことを確かめる。
欠けた binding は対応を要する元の宣言を、曖昧な binding は競合する各宣言を診断が指すことを確かめる。
pattern は profile 外の構文を不正な既定値の評価より前に拒否し、任意の既定値を与えても危険な engine 評価を始めないことを観測する。
登録外の encoding と対象型との不適合を拒否し、literal とドキュメントコメントへ出力する引用符・改行・制御文字・区切り文字は、生成物の compile と復元値の一致で検査する。
HTTP binding の route と header の不正な構文、区切り文字の注入を生成入口で拒否し、実行時の値の encode も実際の要求で観測する。
制約や結果を変更した定義は、変更後の生成物を compile して実行し、新しい受理範囲と操作結果へ追随することを確かめる。
同じ定義、profile、生成器、依存の版と設定を異なる一時 path で生成し、規定した成果物が一致することと、記録された生成物との drift を別々に検査する。
生成能力の不足はその所有者の検証入口で失敗とし、未対応を拒否できること、drift がないこと、代表契約の一部が通ることを、必要な生成先と binding の完成の証拠にしない。

distinct の役割の取り違え、必須入力の欠落、variant と payload の不一致を拒否する consumer と、alias を同じ型として受理する consumer を、各言語の型検査へ渡す。
通常の field 制約だけを持つ値は基礎型で使える consumer を型検査へ渡し、値域の強制と精度・表現の保持は構築と codec の観測へ割り当てる。
生成した型と codec の依存単位は [contracts/generated](../contracts/generated.md) の「生成物」に照合し、その実行時の依存閉包に通信 client・stub、HTTP client と通信 runtime が含まれないことを構造検査で確かめる。
core は composition を含め generated を参照せず、手書きの契約 adapter が generated の Interface と独立した application の公開 Interface だけを接続することを、[skeleton](../skeleton.md) と各 layout の依存に照合する。

### 構築と codec

local な構築と wire の decode は、受理値または位置と規則の種別を持つ構造化した違反を返すことを検証する。
両入口で表せる同じ値には同じ制約を適用し、一方だけが不正値を受理しないことを確かめる。
言語が許す default、明示した undefined、型 assertion 等の検証迂回候補は、該当言語の規律に照合して構築・encode・操作入口の検査へ含める。
構築後に入力側の可変な object や配列を変更しても受理済みの値が壊れないことを、公開値と再 encode の結果で観測する。
全 variant の判別子と payload を encode と decode で往復し、往復の一致に加えて、受理した値と外部表現を独立した期待値へ照合する。
未知項目を検知する生成経路は、全 variant、入れ子の object と配列内の object に未知キーを加え、その受容、捕捉と境界の報告を各言語の規律に照合する。
同じ入力集合について、既知の必須項目の欠落、値の制約違反、判別子と payload の不一致が拒否されることも検証し、未知項目の受容で既知項目の検証を失わないことを確かめる。
既知項目の違反と未知項目を同じ入力へ入れ、拒否時にも両方の診断が残り、部分値と未知項目の値が公開・転送されないことを確かめる。
JSON は [contracts/layout](../contracts/layout.md) の「JSON の相互運用 profile」から、同値・異値・escape 等価の重複名、未知 subtree の重複、text と byte の先頭 BOM、不正 UTF-8 と孤立 surrogate を拒否する入力を作る。
文字列内と項目名内の U+FEFF、有効な非文字と補助平面の文字、正確な数値の意味を保つ入力も独立した期待値へ照合し、拒否例だけで profile を検証したとしない。
項目の必須・任意と null 許容に応じ、未指定、null、有効な値、不正な値の受容と拒否を別々に検証する。
任意入力の既定値は、提供側の受理処理で未指定にだけ一か所で適用され、client が未指定を送れることと、null や不正値が既定値へ置き換わらないことを確かめる。
値の制約のうち形式、数値の値域と精度、日時の精度と offset、文字列長の単位は、契約が受理する範囲の端とその外の値を入力に加え、構築・decode した値を契約から定めた独立した期待値へ照合する。
入力は、形式に違反する値、整数の値域の端と ±(2^53-1) を越える整数、binary64 で正確に表せない十進数、生成先の既定の日時型が持てる精度より細かい小数秒と契約が許す offset を持つ日時、BMP の外の文字を含む長さの端の文字列を、契約が定める範囲に応じて含める。
同値性と、scale・offset・字句表現等の保持を別々に照合し、生成先の既定型や試行実装が扱える値域へ期待値を狭めない。
再帰的な契約の有限値は、library の既定の深さを越える入力で構築・parse・既定値適用・読取り・書出し・解放・公開 trait の各経路を観測する。
実行例だけで任意の有限深さを証明したとは扱わず、明示的な走査状態、storage と解放の所有を source へ照合して、call stack と隠れた深さ上限への依存がないことを確かめる。
循環する local graph の拒否と、同じ不変な子を共有する DAG の受理を分け、受理した子の identity と出力の全出現位置を観測する。
host の byte・出力予算が純粋な型・codec の依存や値の制約へ侵入しないことを構造検査し、出力拒否後も確定済みの業務操作が取り消された結果にならないことを両端で観測する。
総数の選択を提供する集合操作は、集合と評価の文脈を固定し、選択だけでは頁の要素や順序が変わらないことと、選択ごとの結果の形を検証する。
相対日付の条件は、宣言した基準時点と暦の文脈を変え、日付の境界の結果を契約から定めた期待値へ照合する。
捕捉した未知項目の位置とキーの報告、捕捉した値の domain や応答への非流入など、各言語が定める捕捉結果の扱いも検証する。
同じ契約から複数の言語で生成物を持つ場合は、契約から一度だけ入力集合を定め、各入力の期待値を独立して定める。
期待値は、受理か拒否か、拒否する入力では破った規則、受理する入力では構築・decode した値と保持する情報とする。
拒否の区分は、拒否した項目の位置と、必須項目の欠落・値の制約違反・判別子と payload の不一致のような規則の種別で表す。
拒否する入力は、他の制約を満たしたまま破る規則を一つに絞って作る。
指定した規則だけを破る入力が存在しないと導けた場合、生成機構の未対応、探索で見つからなかった場合を区別し、後二者を入力領域の検証済みとして扱わない。
各言語の拒否を、拒否した項目の位置と破った規則の種別へ写して期待値と照合し、別の規則による拒否を合格にしない。
言語ごとの例外の型や文言は期待値にしない。
入力集合と期待値は、全ての対象言語の生成物へ同じ形で適用する。
構築・decode した値の期待値は言語に依らない表現で定め、各言語の値をその表現へ写して照合する。
複数の言語が同じ誤りを持てば出力は一致するため、言語間の出力の一致だけを合格の根拠にしない。

### 両端の接続と結果

公開すると定めた operation と通信方式の組ごとに、生成した consumer の呼び出しから、実際の binding、提供側の decode・dispatch、handler と応答の encode を通して操作と結果の対応を観測する。
実際の提供側では、手書き adapter から独立した application の公開入口への接続と入出力の写像も検証し、登録一覧の一致や frame の復元だけで実行したことにしない。
全ての宣言結果を起こし、同じ payload を持つ異なる結果、body 不在、null、空 object、空 binary を binding が区別し、宣言した識別情報で結果を選ぶことを確かめる。
構築・decode の違反情報の分類と操作の終了は、[concerns/effect](../../concerns/effect/README.md) と各言語の実現に照合し、通常の入力拒否を例外の発生だけで検証したことにしない。
HTTP の generated の client の応答の分類は、[contracts/generated](../contracts/generated.md) の「応答の分類」に照合し、実際の HTTP 応答で検証する。
宣言した全ての status の応答を、body を持たない成功の status も含めて起こし、生成した client が宣言した成功を成功へ、宣言した失敗を想定内の失敗へ分類することを確かめる。
宣言していない status、宣言した成功と失敗のそれぞれで契約の型に合わない body、契約に合わない media type、JSON・binary の本文途中での接続の切断、接続の拒否、要求の組立の失敗、呼び出しごとの時間上限の超過、呼び出し側の取り消し、上流の期限の伝播として受け取った token・signal の取り消し、その client が持つ場合の下位の層が自ら設けた timeout と HTTP client 自身の内部の取り消しを起こし、返る分類を別々に観測する。
非 streaming の呼び出しは、本文の読取・decode・検証を終えてから結果を返し、返却後の accessor の参照で初めて body の不正が判明する経路を持たないことを確かめる。
502・503・504 で body が契約の型に一致しない応答が、宣言の有無に関わらず通信の失敗に、一致する応答が宣言した失敗に、それ以外の宣言していない status が成功の範囲を含めて欠陥に分類されることを確かめる。
502・503・504 以外の宣言した status で body だけを契約に合わない形にした応答が、成功の status でも失敗の status でも欠陥に分類され、宣言した成功にも宣言した失敗にも分類されないことを確かめる。
時間上限の超過が取り消しにならず、呼び出し側の取り消しと上流の期限の伝播による取り消しが、通信の失敗にも時間上限の超過にもならないことを確かめる。
取り消しと自身の上限の超過がともに成り立つ場合に取り消しになることと、親でも自身の上限でもない中断が通信の失敗になることも確かめる。
応答を受け取り終えた後に取り消しや期限の超過を起こしても、その応答の分類が書き換わらないことも確かめる。
取り消しか時間上限の超過かの別を決める判定が、受け取った token・signal と自身の上限の状態だけに依り、error の値(判定関数、例外の型、reason)に依らないことを、構造検査で確かめる。

### 証跡の所有と再利用

生成器共通の能力は、生成器を所有する検証入口で対象 profile・言語・通信方式に対応付けて検証する。
利用する製品は、その版と設定に対する有効な証跡を参照し、現在の契約の生成・drift、adapter の写像、実際の binding と業務の受入を検証する。
生成器側の全検査を各製品へ複製せず、生成器・profile・設定・契約・依存の変更で影響する保証は [methods](./methods.md) の「変更と影響範囲」に従って再選択する。
代表入力で観測した範囲、未実装の能力、未実行の条件を必要な受入条件へ対応付け、試行の成功した部分を必要な能力全体の充足へ読み替えない。

## 契約駆動の fuzz と適合

信頼できない入力は、契約を駆動にした fuzz で検証する。
契約駆動の fuzz は、生成した OpenAPI を駆動元にし、道具の採用は [tools/build](../../tools/build/README.md) が定める。
公開 API の契約への適合も、同じ機構で検証する。
protocol 経路の適合は、生成物と実装の drift の検査と conformance で検証する。
ファイルを運ぶ HTTP binding は [contracts/http](../contracts/http.md) の「ファイルの表現」に照合し、実際の送受信経路で Content-Type、復元した本文の byte 列、multipart の part と属性の対応を独立した期待値へ照合する。
ファイルの操作が宣言する失敗も、契約どおりの status と problem+json で返ることを検証する。
