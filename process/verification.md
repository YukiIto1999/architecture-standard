# 検証の順序

検証は、製品の受入を確認する経路と、検査の検出力を改善する分析の経路を分けて進める。
技法、入力領域、影響範囲、mutation の役割と結果の分類は [structure/tests/methods](../structure/tests/methods.md)、配置と実行資源は [structure/tests/layout](../structure/tests/layout.md) に従う。
製品の受入条件を維持し、長時間の検証の完了待ちが開発、push、本流への取り込み、release を妨げない実行計画を作る。

| 段 | 実行する時点 | 入口の task 名 | 実行と結果の利用 |
|---|---|---|---|
| T0 | 編集中の局所フィードバック | なし | 変更に関係する型・analyzer・lint・formatter・構造と、選んだ公開振る舞いの検査 |
| T1 | 作業単位を終える前と commit の前 | `verify` | 影響範囲の静的検査、root の arch、Small test、契約の迅速な確認 |
| T2 | push の前 | `verify-push` | 変更に必要な実結合と利用者面の受入の迅速な確認。有効な証跡を照合し、不足する検査を実行 |
| T3 | project が定める継続的な品質評価の契機 | `verify-full` | 選択した mutation、全量回帰、長期負荷などの独立した評価。結果を改善へ返し、実行完了を製品変更の共通条件にしない |

## 順序

1. 変更単位と受入条件を定め、製品の保証ごとに検査、入力、観測する境界、確認する時点を対応付ける。
   検出力を調べる分析は別の目的として定め、製品受入の完了条件へ混ぜない。
2. 比較元、source、依存、テスト、入力と設定を確定し、[methods](../structure/tests/methods.md) の「変更と影響範囲」から対象を選ぶ。
   契約、migration、認証・認可、供給網、検証入口の変更は保証を共有する境界へ追い、無関係な全量の反復と区別する。
3. 検査ごとの既存証跡を照合し、必要な保証が有効な証跡で覆われない範囲だけを実行計画へ入れる。
4. 一走行の起動・build、cache、検査本体、資源待ち、結果確定と、変更全体の待ち時間を [concerns/performance](../concerns/performance/measure-before-compare.md) の「計測を定めてから比べる」に従って測る。
   累積実行時間は実行区間の和集合で記録し、中断や再試行を含め、並行区間を二重計上しない。
5. フィードバック時間の目標と一走行の資源保護の上限を、範囲と環境の実測から現在の検証設定と [決定の記録](../principles/documentation/decision-records.md) へ残す。
   初回の計測は有限の上限で行い、入口と外側の runner は同じ上限を参照する。
   累積時間は重複、過剰な範囲、固定費、競合を見直す材料とし、原因に対応する修正や回復後の実行を累積消費だけで止めない。
6. T0 は選んだ振る舞いと変更の局所検査で回し、編集のたびに全量入口を起動しない。
   判断に実 DB や画面の観測が必要ならその段階で使い、静的検査だけで代替しない。
7. T1 は `verify` から必要な保証を確認して、作業単位の確定へ進む。
   root の arch は Medium の資源を使う場合もここで確認する。
8. T2 は pre-push hook から `verify-push` を起動し、送信する source に対する受入の証跡と不足する検査の結果を確認する。
   本流が更新された場合も、実際に取り込む内容への影響を判定し、該当する証跡と検査を更新する。
9. CI は同じ root の task を使い、commit の規約、secret と必要な製品検証を確認する。
   検査の実行場所でなく source、入力、環境、実行者と結果の出所を照合し、有効な証跡であれば作業機と CI で同じ検査を重ねない。
10. T3 は製品検証の入口から分離し、評価対象を固定した環境で非同期に実行する。
    project は実行の契機、資源割当、結果を扱う担当とレビューまたは改善作業への取込先を現在の設定に定める。
    mutation は [methods](../structure/tests/methods.md) の「変更と影響範囲」から選択し、全量分析も必要な問いがある場合に選ぶ。
11. 分析結果は対象 source と現在の変更への適用を照合し、[methods](../structure/tests/methods.md) の「テストの有効性」に従って分類する。
    判明した製品の欠陥や具体的な受入検査の不足は通常の修正へ返し、該当する回帰検査と影響範囲で確認する。
    修正の完了を、無関係な分析の再完了に依存させない。
12. 失敗後は失敗検査と修正の影響範囲を再選択し、影響しない有効な証跡を再利用する。
    保存進捗からの再開と、未完了範囲の再試行を分け、確定した結果、残る範囲、失効と再利用の理由を確認して次の走行を選ぶ。

## 確認点

製品の受入と検出力の分析が別の目的、実行結果と状態として記録されている。
mutation の実行中、未実施、未分類、未検出や score だけで、commit、push、本流への取り込み、release を止めない。
分析の生の終了 status は保存し、製品検証の合否へ直結させたり、未完了を成功へ書き換えたりしない。
分析で具体的な欠陥や必要な検査の不足が判明した場合は、分析結果を放置せず、その保証の修正へ返す。
製品の受入検査が不成立なら、その受入条件を満たしたとは扱わない。
技法や size だけで承認時点を決めず、必要な実観測を T3 へ先送りしない。
長い検査の待機点を後段へ移すこと、task を分けて最後に全量を待つこと、上限を延長することだけで検証設計の問題を解決したとしない。
製品検証が長時間の待機を要する構成では、保証の割当、対象選択、証拠の再利用、起動と build、資源競合を見直して短い経路を成立させる。
時間短縮だけを理由に、必要な入力領域を削ったり、実依存の観測を fake へ置き換えたりしない。
非同期分析は資源を独占して製品検証を妨げず、終了待ちを hook や CI の必須チェックへ再導入しない。
利用者面の scenario と実際の結果、未確認条件は [methods](../structure/tests/methods.md) の「利用者面の受入」に従う。
変更単位の受入証拠を全体要件へ戻し、その単位の成立と依頼全体の完了を区別する。
証跡の再利用は、source の依存閉包、テスト、入力、command、設定、実行環境、検証器と出所の同一性を照合する。
検査名や変更 file の一致だけでは再利用せず、無関係な source の変更だけでも失効させない。
有効な同一検査の結果は再実行せず、未知の同一性、新たな失敗や反証がある範囲を確認する。
T0 で絞った PBT の反復や入力はその範囲の証拠であり、受入に必要な入力領域の検査を代替しない。
一走行の上限を超えた実行は取り消し、未実行・中断を合格にしない。
走行開始時の上限は途中で延長せず、範囲や環境の変更で見直す場合も過去の実行時間を記録に残す。
新たな証拠、再開可能な進捗、原因に対応する変更や回復根拠がない自動反復を止める。
ログや試行回数の増加、原因と無関係な入力・設定変更を再試行の根拠にしない。
入口を package.json の scripts に定める場合は、T2 と T3 の task 名を `verify:push` と `verify:full` にする。

## 範囲外

検証の技法、入力領域と検査対象の選択は扱わない([structure/tests/methods](../structure/tests/methods.md) が正本である)。
