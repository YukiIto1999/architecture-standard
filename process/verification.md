# 検証の順序

検証は、承認する変更に必要な保証と完了時点を先に定め、変更の影響範囲と有効な既存証跡から実行計画を作る。
検証の技法、入力領域、影響範囲と mutation の対象の選択は [structure/tests/methods](../structure/tests/methods.md)、test の配置と実行資源は [structure/tests/layout](../structure/tests/layout.md) に従う。
時間予算は実行計画の制限であり、保証や承認時点を変更する根拠にしない。

| 段 | 完了する時点 | 予算の上限 | 入口の task 名 | 実行する検査 |
|---|---|---|---|---|
| T0 | 編集時の局所フィードバック | 10 秒 | なし | 変更した file の型・analyzer・lint・formatter・構造の静的検査 |
| T1 | agent が作業を止める前と commit の前 | 2 分 | `verify` | 影響範囲の静的検査、Small test、契約の検証 |
| T2 | push の前の作業機 | 15 分 | `verify-push` | 影響範囲の実 datastore を使う test、変更した箇所と影響する箇所の mutation、影響する scenario |
| T3 | project が定める全量確認の契機 | なし | `verify-full` | 全量の mutation、Large test と e2e、SLO 計測 |

## 順序

1. 承認する変更単位と、commit または push までに必要な保証を定め、保証ごとに検査、対象、入力、完了する段を対応付ける。
2. 比較元、検査する source の内容、依存と設定、テストの入力を確定し、差分と影響範囲を [methods](../structure/tests/methods.md) の「変更と影響範囲」で導き、mutation の生成対象と被覆テストの選択を分けて計画する。
3. 各検査の有効な既存証跡を照合し、再利用できない検査だけを実行計画へ入れる。
4. T0 は変更した file の局所フィードバックとして実行し、編集のたびに全量入口を起動しない。
5. T1 は `verify` で実行し、必要な検査の完了を確認してから commit または作業終了へ進む。
6. T2 は git の pre-push hook から起動し、push する変更と同じ source に対し、変更した箇所と未変更の影響する箇所の mutation を含む必要な検査の完了を確認してから push を許可する。
7. 各段は、静的検査から資源を要する検査へ進め、検査が失敗または未完了なら後続の承認を止める。
8. 契約、migration、認証・認可、供給網、検証入口の変更は、それぞれの保証を共有する境界へ影響を広げる。全量入口の実行と同一視せず、選んだ境界と検査ごとの範囲を計画に示す。
9. T3 は変更ごとの入口と分離し、project が現在の検証設定と [決定の記録](../principles/documentation/decision-records.md) に定めた契機で実行する。
10. T3 の新たな失敗と未検出 mutant は、対象の保証と影響範囲を特定して修正へ渡し、変更の必須保証が成立しないと分かった結果を backlog に置くだけで承認しない。
11. CI は commit の規約、secret の漏洩、T1 を検査する。作業機で必要な T2 が完了していないことを、CI の成功で代替しない。
12. 失敗後は、失敗した検査と修正が影響する検査を再選択し、影響しない検査の成功証跡は同一性が成立する間再利用する。

## 確認点

実行計画から、比較元、検査する source、変更入力、影響する consumer、各検査の対象と範囲を読める。
mutation は、[methods](../structure/tests/methods.md) の「変更と影響範囲」に従って変更部分と影響部分の和集合を選び、production の diff が空の場合も影響部分の選択と判定を確認する。
実際に使う diff の選択機能、生成対象の選択機能、被覆テストの選択と、各範囲を完了した証跡を区別する。
非影響を確定できず範囲を広げた場合は、解決できなかった依存と拡大先を示す。
局所変更で起動した全体向け command は、局所検査と表示せず、実際の範囲を示す。
index、worktree、未追跡の内容を検出したことと、その内容を実際に検査したことを分け、別の source の成功を承認の証跡にしない。
同じ検査の証跡を再利用する場合は、source の依存閉包、テスト、入力、command、設定、実行環境と検証器の同一性を確認する。
失敗した検査と同じ名前であることや、変更した file が同じであることだけで、証跡を再利用しない。
T0 の結果があっても、T1 で必要な保証の完了は別に確認する。
有効な同一検査の成功を得ている場合は実行を重ねない。
局所フィードバックで PBT の反復数や入力を絞った結果は、その範囲の証跡として示し、承認に必要な入力領域の検査を代替しない。
入口の予算を超えた段は失敗として止め、未実行または中断した検査を合格にしない。
予算超過では、重複実行、影響範囲の過剰な拡大、起動と build の固定費を調べ、選択、再利用、分割、並列化を見直す。
検証器を置き換える場合は [methods](../structure/tests/methods.md) の同じ性質の判定に従い、必要な保証と承認前の完了を維持する。
必須検査を T3 へ移すこと、入力範囲を減らすこと、実依存を fake に替えることを、時間短縮だけで正当化しない。
段は必要な検査の実行順序と資源の配分に使い、未変更の影響範囲を承認後の段へ残す理由にしない。
T3 の周期と全量実行の結果の扱いは、現在の設定と読者向けの説明から分かるようにする。
入口を package.json の scripts に定める場合は、T2 と T3 の task 名を `verify:push` と `verify:full` にし、pre-push hook は T2 の入口を起動する。
検証の合否は、root の [README](../README.md) の適用の4則に従い、実際に必要な検査を完了した証跡で判定する。

## 範囲外

検証の技法、入力領域と検査対象の選択は扱わない([structure/tests/methods](../structure/tests/methods.md) が正本である)。
