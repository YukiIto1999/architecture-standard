## 境界で一度だけ parse する

### 要求
外部から入る値の検証は、[modeling](../../principles/modeling/parse-at-boundary.md) の「境界で検証して型に通す」に従う。
どの経路の入力も一つの変換器の集合を通して検証済みの型へ変換し、内側では再検証しない。
一つの検証済みの型に対して外部の表現の形式が複数あるときは、その形式が並走する区間を最短にする。

### 根拠
外部入力は HTTP・CLI・メッセージ・外部 API など複数の経路から入り、経路ごとに別々の検証基準を持つと、通った値の信頼度が経路によって揺れる。
経路を横断して一つの変換器の集合に検証を集約すれば、全系を貫く鎖が一つに保たれる。
一つの検証済みの型に対して外部の表現の形式が複数並走すると、どの形式を扱っているかの判別が要る。
並走する区間が長いほどその判別が内側へ漏れ、内側が型の保証だけで済まなくなる。
境界で検証相と実行相を分ける理由は [modeling](../../principles/modeling/parse-at-boundary.md) に従う。
自システムが検証して保存したデータの読出しも同じ変換器を通すが、その不正は外部入力の不正でなく欠陥である。
不正と欠陥の判別は [effect](../effect/README.md) に従う。
形式の検証は境界で行い、資源の照会を要する検証は方針の側で行う。
検証の証明責任は、必要な範囲で最も上流の境界に置く。
利用者の入力補助のための検証は契約の検証と目的が異なり、前者があっても後者を省かない。

### 完了条件
HTTP・CLI・メッセージ・外部 API のどの経路も、同じ変換器の集合を通って検証済みの型になっている。
内側の処理が未検証の生の値を受け取らないことの判定は、[modeling](../../principles/modeling/README.md) の完了条件に従い、外部の表現を写した DTO を未検証の生の値に含める。
証明責任が、必要な範囲で最も上流の境界に置かれている。
資源の照会を要する検証が、境界の変換器でなく方針の側で行われている。
一つの検証済みの型に対して複数の形式が並走する区間が、境界のモジュールに閉じている。

### 禁止事項
境界の検証を迂回して、外部の値を検証済みの型として構築すること。
入力補助の検証があることを理由に、契約の境界の検証を省くこと。
一つの検証済みの型に対する複数の形式の判別を、境界のモジュールより内側へ持ち込むこと。

### 行動
外部との接点を境界として特定し、そこに変換器を一つ置く。
未検証の型と検証済みの型を分け、検証済みの型は変換器を通してしか構築できないようにする。
経路が増えたら、既存の変換器の集合へ、その経路を検証済みの型に変換する処理を加える。

### 例

境界の変換器を通った型だけを内側へ渡す。内側では型が検証済みであることを保証するため、再検証しない。

```
parseUser(input: unknown): ValidUser | Error
sendWelcome(user: ValidUser)
```
