## 並行度を制限し、背圧を扱う

### 要求
並行して走る処理の数を有界に保ち、背圧は消費側が処理できる量を需要として表し生産側がそれを超えて送らない形で扱う。
memory と durable の待ち行列の滞留上限、満杯時の拒否、期限切れの仕事の扱いは [resilience](../resilience/README.md) に従う。
再配送が必要な入力の durable receipt、upstream delivery ack、処理完了の確定点は [messaging](../messaging/README.md) に従う。

### 根拠
並行度を無制限にすると、資源が枯渇し、外部の依存先を圧迫する。
生産が消費を超え続けると、待ち行列が無限に伸び、記憶を食い尽くす。
有界の並行と背圧があれば、負荷が上限に収まり、過負荷で全体が倒れない。
消費側が需要を表し生産がそれを超えないようにすれば、待ち行列が有界に収まる。
協調スケジューリングの runtime では、背圧をブロッキングの待機で表すと、非同期の利点を消しデッドロックを招くので、需要の signal で表す。
需要の伝播だけを並行の責務にすれば、保存容量と回復の規律、配送の確定点を別の concern で重複して定義せずに済む。

### 完了条件
並行して走る処理の数に、上限がある。
消費側が需要を表し、生産側がその需要を超えて送っていない。
背圧が、ブロッキングの待機でなく需要の signal で表されている。
待ち行列の容量と回復が resilience、配送の確定点が messaging の完了条件で検証されている。

### 禁止事項
並行度に上限を設けず、無制限に処理を起動すること。
生産側が、消費側の需要を無視して送ること。
制御できない源で、境界を守らず際限なくバッファすること。
待ち行列の保存と回復、または配送の receipt と ack の規律を concurrency で再定義すること。

### 行動
並行して走らせる処理の数に上限を設ける。
消費側が処理できる分だけ需要を出し、生産はそれを超えて送らない。
待ち行列が満ちたら、需要を絞って生産を抑えるか、受けきれない分を拒む。
待ち行列の滞留と期限切れは resilience、durable receipt と ack は messaging の検査へ割り当てる。

### 例

入力ごとに無制限に処理を起動すると、依存先を圧迫する。

```
for (x of inputs) spawn(handle(x))
```

並行度に上限を設ける。

```
withConcurrencyLimit(16, inputs, handle)
```
