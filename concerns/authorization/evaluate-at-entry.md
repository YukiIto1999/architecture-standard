## 入口で評価し、通った要求だけ進める

### 要求
認可は要求の入口で操作の単位を評価し、評価を通った要求だけが業務の処理へ進む。
資格情報に操作や対象の許可範囲がある要求は、[credential-to-actor](../authentication/credential-to-actor.md) の「資格情報を検証して actor を構築する」に従って検証された許可範囲も入口で評価し、actor の業務権限と資格情報の許可範囲の両方が許す操作だけを通す。
個々の対象への操作は、その対象を取り出す境界で対象の単位を改めて評価する。
資格情報が対象も制限する場合は、その制約も対象の評価へ引き継ぎ、actor が所有する対象であることだけで許可しない。
同じ主体へ到達する別の資格情報や session の経路を洗い出し、一つの資格情報の scope で別経路の権限まで制限できたと扱わない。

### 根拠
認可を処理の途中に散らすと、評価の漏れや順序の誤りが生まれる。
入口で一度評価し、通った要求だけを内側へ通せば、内側は操作の認可を前提にできる。
入口の評価は操作の単位までなので、到達してよい操作の中で他人の対象に触れる越権は防げない。
対象を取り出す境界で対象の単位も評価すれば、識別子を差し替えて他人の対象を操作する越権を止められる。
actor への写像は主体を確定する処理なので、資格情報の許可範囲を捨てると、限定された操作の資格情報から主体の全権限を行使できてしまう。
資格情報の制約と actor に対する業務上の認可を独立に評価すれば、scope が操作を許しても、他人の対象へのアクセスは許可されない。
別の session が広い権限を持つ場合、その経路も利用できる要素の権限は、限定された資格情報の scope だけでは説明できない。

### 完了条件
認可が、要求の入口で操作の単位として評価されている。
個々の対象への操作が、その対象を取り出す境界で対象の単位でも評価されている。
限定された資格情報が広い権限を持つ actor へ写像されても、許可範囲外の操作と対象が拒否されている。
資格情報の許可範囲の評価が境界内で完結し、token、claim、認証方式の型を core へ渡していない。
同じ主体へ到達する各資格情報と session の受理経路が明示され、scope 外の操作へ別経路で迂回できないという判断は、その経路も制限した証拠に基づいている。
評価を通った要求だけが、業務の処理へ進む。
認可の評価が、入口と対象を取り出す境界に限られ、業務の処理の途中に散っていない。

### 禁止事項
認可の評価を、業務の処理の途中へ散らすこと。
対象の単位の認可を省き、識別子の差し替えで他人の対象を操作させること。
actor の業務権限が広いことを理由に、資格情報の scope や対象の制約を無視すること。
資格情報の scope が操作を許すことを理由に、actor と対象に対する業務上の認可を省くこと。
一つの資格情報の scope を、独立して受理する別の資格情報や session の権限へ適用された制限とみなすこと。

### 行動
認可の評価点を入口に置き、通過した要求だけを内側へ渡す。
認証境界から検証済み資格情報の許可範囲を受け取り、操作への制約を入口で評価し、対象への制約を対象の評価点へ引き継ぐ。
同じ actor に写像される広い session と限定された資格情報をそれぞれ試し、経路ごとの許否と、別経路からの迂回の有無を確認する。
対象を取り出す境界を洗い出し、対象の単位の評価が抜けている取り出しを是正する。

### 例

入口で操作だけを認可すると、識別子の差し替えによって他人の対象へ到達できる。

```
function handle(request) { authorize(actor, "orders:read"); return getOrder(request.id); }
```

入口では操作を認可し、対象を取り出す境界ではその対象へのアクセスを認可する。

```
function handle(request) { authorize(actor, "orders:read"); const order = getOrder(request.id); authorize(actor, order); return order; }
```
