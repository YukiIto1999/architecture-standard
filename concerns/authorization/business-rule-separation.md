## 業務規則と認可を分ける

### 要求
業務事実の記録と状態遷移が成り立つ条件は、規則が主体の識別子を参照しても、業務の核の不変条件に置く。
誰にその操作を試みさせるかのアクセス制御は、認可の policy に置く。
規則が変わる理由が業務の事実と遷移の定義の変更なら不変条件、誰に操作を許すかの方針の変更なら認可と見分ける。
主体に依存するというだけの理由で、業務の不変条件を認可へ移さない。
同じ規則を、両方に持たない。
認可の規則は、テストで検証する。

### 根拠
業務規則とアクセス制御は、変わる理由が違う。
両方に同じ規則を持つと、片方だけ変えて食い違う。
業務の不変条件は、記録される事実と遷移の正しさを定めるので、誰が操作しても核が守る。
認可の policy は誰に許すかの方針として変えられるので、不変条件をそこへ置くと、方針の緩和や管理操作への許可で事実と遷移が不正に成立する。
規則が主体の識別子を参照することと、規則がアクセス制御であることは別であり、前者だけで認可へ置くと、事実の正しさが認可の設定に依存する。
業務の事実と遷移の不変条件は核が守り、誰に何を許すかは認可が判定する、と分ければ、各々を独立に変えられる。

### 完了条件
業務事実の記録と状態遷移が成り立つ条件が、業務の核の不変条件として置かれている。
誰にその操作を試みさせるかが、認可の policy に置かれている。
主体の識別子を参照する不変条件が、認可の policy へ移されておらず、必要な識別子が検証済みの業務入力として核へ渡されている。
同じ規則が、両方に重複していない。
認可の規則が、テストで検証されている。

### 禁止事項
同じ規則を、業務の核と認可の policy の両方に持つこと。
主体に依存することだけを理由に、業務の事実と遷移の不変条件を認可へ置くこと。
アクセス制御の方針を、業務の核の不変条件として置くこと。

### 行動
規則ごとに、記録される事実と遷移の成立を定めるか、誰に操作を許すかを定めるかを見分ける。
前者は主体の識別子を参照しても業務の核へ、後者は認可の policy へ置く。

### 例

役割の判定を業務の核へ入れると、認可と業務規則が混ざる。

```
function cancel(order, user) { if (user.role !== "admin") throw; if (order.shipped) throw; }
```

認可は保護入口に置き、核では「出荷済みの注文は取り消せない」という業務の不変条件だけを判断する。

```
function cancel(order: Order): Result<Order, E> { ... }
```

申請者と承認者が別であることを認可の policy だけに置くと、方針を緩めた操作や管理操作で、申請者が自分の申請を承認した事実が記録される。

```
policy approveRequest: deny if subject.id == request.requesterId
function approve(request: Request, approverId: ApproverId): Approval { ... }
```

この規則は承認の事実の成立条件なので、業務の核が承認者の識別子を受け取って判断する。

```
function approve(request: Request, approverId: ApproverId): Result<Approval, E> {
    if (request.requesterId == approverId) return Err(SelfApproval)
    ...
}
```
