## 資格情報を検証して認証主体を確定する

### 要求
資格情報を受け取るすべての信頼境界は、単一の認証境界を持つ。
認証境界は資格情報を未検証の入力として受け取り、その契約が定める発行元、対象、完全性、期限と失効条件を含む有効性を検証してから認証主体を確定する。
資格情報の種類ごとに、発行元、対象、完全性、有効性をどの証拠と検証で保証するか、拒否条件と認証主体・許可範囲への対応を定める。
認証主体は、検証済みの資格情報が表す主体と、その資格情報の許可範囲を、認証と認可の内側で保持する。
資格情報、principal、token、claim、認証方式の型、認証主体は、core の公開 API と業務の処理へ渡さない。
業務が主体を必要とする操作だけは、認証主体からその操作が定める業務の識別子へ対応づけ、検証済みの業務入力として渡す。
主体を必要としない操作には、主体に関する入力を渡さない。
操作の主体を表す業務入力は、認証主体との対応、または認可された代理・委任の関係を検証して与え、要求側が指定した値だけでは受け入れない。
要求が対象として指す他の主体の識別子は、要求の入力として受け取り、その操作を許すかは [evaluate-at-entry](../authorization/evaluate-at-entry.md) の「入口で評価し、通った要求だけ進める」に従って評価する。
認証主体、principal、claim、role は、業務のモデリングで使う役割や変更要求者と同一視せず、役割名を認証の型として全域で共通化しない。
資格情報を検証できない要求は、認証主体を確定せず core の手前で拒否する。

### 根拠
資格情報の検証を信頼境界ごとの単一の認証境界に閉じれば、検証の抜けと経路ごとの食い違いを同じ境界で防げる。
認証主体と許可範囲を認証と認可の内側に保てば、core は資格情報の形式と認証方式を知らず、限定された資格情報を広い権限へ昇格させることも防げる。
業務が必要とするのは操作ごとの業務の識別子であり、認証主体そのものではない。
必要な操作だけへ対応づければ、認証方式の型が業務型へ侵入せず、認証の契約の変更が全ての操作の署名へ波及しない。
全ての操作へ共通の主体の型を渡すと、主体を使わない操作も認証の変更に巻き込まれ、操作ごとに異なる変更要求者の区別も失われる。
認証の主体は資格情報の発行元の契約で変わり、業務の役割と変更要求者は業務の要件で変わるので、同一視すると一方の変更が他方へ波及する。
操作の主体と実行する認証主体の対応や代理・委任を検証すれば、両者を同一の識別子へ潰さず、要求側による成りすましも防げる。
検証に失敗した要求で認証主体を確定しなければ、未確認の主体が保護対象の処理へ到達しない。
資格情報を取得できた事実と、その資格情報が主体、対象、有効範囲の契約を満たすことは異なる。

### 完了条件
資格情報を受け取るすべての信頼境界に、認証境界が一つずつある。
認証境界が、資格情報の発行元、対象、完全性、期限と失効条件を含む有効性を検証してから認証主体を確定している。
資格情報、principal、token、claim、認証方式の型、認証主体が、core の公開 API と業務の処理に現れていない。
資格情報の検証済みの許可範囲が認証主体とともに境界内の認可評価へ渡され、業務入力への対応づけによって失われていない。
主体を必要とする操作の業務入力だけが認証主体から対応づけられ、主体を必要としない操作は主体に関する入力を受け取っていない。
操作の主体を表す業務入力が、検証された認証主体との対応か、認可された代理・委任の関係から与えられている。
認証の principal と role が、業務のモデリングの役割や変更要求者を表す型として使われておらず、役割名が認証の型として全域で共通化されていない。
資格情報を検証できない要求が、認証主体を確定せず core の手前で拒否されている。
採用した資格情報の種類ごとに、各性質の検証根拠、拒否の検査、認証主体と許可範囲への対応を辿れる。

### 禁止事項
資格情報の検証と認証主体の確定を、同じ信頼境界の複数箇所へ分散させること。
未検証の資格情報または属性から、認証主体を確定すること。
引数や環境変数の未検証の属性、または設定や secret を読めたことだけを、検証済みの主体や許可範囲の根拠にすること。
資格情報、principal、token、claim、認証方式の型、認証主体を、core の公開 API または業務の処理へ渡すこと。
認証主体の確定を、汎用の業務の主体の型の構築と同一視し、全ての操作へ引数として渡すこと。
認証主体を確定したことだけを理由に、資格情報の許可範囲を捨てること。
要求側が指定した主体の値だけを、操作の主体を表す業務入力として受け入れること。
認証の principal や role を、業務のモデリングの役割や変更要求者として扱うこと。

### 行動
信頼境界ごとに資格情報の入口を洗い出し、検証と認証主体の確定を単一の認証境界へ集める。
資格情報の契約に従って発行元、対象、完全性、期限と失効条件を含む有効性を検証し、検証済みの値から認証主体を確定する。
資格情報の取得源と各性質の検証根拠を決定の記録へ対応付け、検証できない条件と許可範囲を越える条件を拒否の検査へ渡す。
認証主体と資格情報の許可範囲は境界内に保持し、認可評価へ引き渡す。
操作ごとに主体を必要とするかを確かめ、必要な操作だけ業務の識別子へ対応づけて検証済みの業務入力とする。
core の公開 API から資格情報、principal、token、claim、認証方式の型、認証主体を除き、業務入力だけを渡す。
検証に失敗した要求は、認証主体を確定する前に拒否する。

### 例

資格情報を core へ渡すと、業務処理が主体の確定まで担う。

```
core.handle(request.credential, request.input)
```

認証境界で検証と認証主体の確定を終え、入口の認可を通った後に core へ渡すのは、主体を必要とする操作の業務の識別子と検証済み入力だけにする。
主体を必要としない操作は、主体に関する入力を受け取らない。

```
subject = authenticationBoundary.verify(request.credential)
protectedEntry.enforce(subject, request.operation)
core.placeOrder(CustomerId.of(subject), parse(request.input))
core.listCatalog(parse(request.input))
```
