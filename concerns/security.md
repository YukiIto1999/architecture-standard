# security

## 概要
security は、安全の姿勢を全系で統べる規律である。
principles の [separation](../principles/separation.md) が定める境界とコンテキストの自己完結を、全系の安全の姿勢として具象化する。

## 境界の外を既定で信頼しない

### 要求
境界の外から来るものを既定で信頼せず、信頼は境界での検証と認可を経た後にだけ与える。
検証は、形式の妥当性と業務的な妥当性の両面で行う。

### 根拠
外から来る値は、改竄や誤りを含みうる。
既定で信頼すると、不正な入力がそのまま内部を流れる。
境界で検証し認可を経たものだけを信頼すれば、内部は信頼できる値だけを扱う。

### 完了条件
境界の外から来る値が、検証と認可を経るまで信頼されていない。
信頼が、境界での検証と認可の後にだけ与えられている。
検証が、形式と業務的な妥当性の両面で行われている。

### 禁止事項
境界の外から来る値を、検証と認可を経ずに信頼すること。
境界の検証だけを、注入への唯一の防御にすること。

### 行動
外部入力を境界で検証して型へ通し、認可を経たものだけを内側へ渡す。
許す値を列挙して通し、危険な値の除外はそれを補う形にとどめる。
パラメータ化やエスケープのような出口側の防御も、境界の内の出力の直前で行う。
検証は [types](./types.md)、認可は [authorization](./authorization.md) に従う。

### 例
```
// 外部入力をそのまま信頼して使う
database.query(request.body.filter)
// 境界で検証して型へ通し、認可を経たものだけを内側へ
const query = parseQuery(request.body); authorize(actor, query); search(query)
```

## 最小権限を与える

### 要求
各要素には必要な最小の権限だけを与え、権限の既定値を許可しないに置く。
既定の拒否は、framework の既定に頼らず明示する。
与えた権限は、定めた周期で見直して記録し、不要になった権限を回収する。

### 根拠
過剰な権限は、侵害されたときの被害を広げる。
必要な分だけに絞れば、被害が局所に収まる。
既定を拒否に置けば、許可は明示的に与えた分だけになる。

### 完了条件
各要素が、必要な最小の権限だけを持つ。
権限の既定値が、許可しないに置かれている。
既定の拒否が、framework の既定に依存せず明示されている。
与えた権限の見直しの周期が定められ、前回の見直しの記録があり、不要になった権限が回収されている。

### 禁止事項
必要を超える権限を、既定で与えること。

### 行動
要素ごとに必要な権限を洗い出し、それだけを与える。
権限の既定を拒否に置き、許可は明示的に与える。
権限の膨張を定期的に見直し、不要になった権限を回収する。

### 例
```
// 広い権限を既定で与える
grant(service, ALL)
// 必要な操作だけを与え、既定は拒否
grant(service, [readOrders])   // 他は既定で拒否
```

## 多層で防御する

### 要求
安全は単一の対策に頼らず、複数の層で重ねて守る。
層は異なる種類の防御で重ね、同じ対策の重複や数の増やしすぎにしない。

### 根拠
単一の対策は、破られると無防備になる。
複数の層で重ねれば、一つが破られても別の層が被害を抑える。
同じ種類の対策を重ねても、同じ穴で同時に破られる。
重ねるほど機構が複雑になり、新たな穴を生む。

### 完了条件
project が重要と定めた資産が、複数の層で重ねて守られている。
一つの層が破られても、別の層で被害が抑えられる。

### 禁止事項
安全を単一の対策へ集約し、迂回で無防備になる形にすること。

### 行動
重要な資産を、境界の検証・認可・最小権限・暗号など複数の層で守る。
どれか一つに依存していないかを確かめる。

### 例
```
// 入口の検証だけに頼る。抜けると無防備
validateAtGateway()
// 入口の検証に加え、認可・最小権限・データ層の制約でも重ねて守る
validateAtGateway(); authorize(); leastPrivilege(); dbConstraints()
```

## 攻撃面を最小にする

### 要求
外部へ開く面を必要なものだけに絞り、使わない経路・機能・権限を開いたまま残さない。

### 根拠
開いた面は、すべて攻撃の入口になりうる。
使わない面を閉じれば、攻撃の入口が減る。
閉じるのは使わない面であって、要求された機能ではない。
要求された機能は作り切る。

### 完了条件
外部へ開く面が、必要なものだけに絞られている。
使わない経路・機能・権限が、開いたまま残っていない。

### 禁止事項
使わない経路・機能・権限を、開いたまま残すこと。

### 行動
公開する経路・機能・権限を棚卸しし、使わないものを閉じる。
新たに開く面ごとに、必要性を確かめる。

### 例
```
// 使わない管理用の経路を開いたまま残す
expose(["/api", "/admin", "/debug"])
// 必要な面だけを開く
expose(["/api"])   // /admin /debug は閉じる
```

## 標準の暗号に任せる

### 要求
暗号と鍵の扱いは検証された標準のアルゴリズムと実装に任せ、自前で実装しない。
プロセスをまたぐ伝送は、暗号化された経路を前提にする。
secret の伝送も、この暗号化された経路の要求に含まれる。

### 根拠
暗号の自前実装は、わずかな誤りで安全を失う。
検証された標準の実装は、広く検査され攻撃に耐えている。
プロセス間の伝送を暗号化すれば、経路上の盗聴と改竄を防ぐ。

### 完了条件
暗号と鍵の扱いが、検証された標準のアルゴリズムと実装で行われている。
プロセスをまたぐ伝送が、暗号化された経路で行われている。

### 禁止事項
暗号のアルゴリズムやプロトコルを、自前で実装すること。
標準のライブラリに任せきりにして、方式・鍵長・乱数源・伝送の版を確かめないこと。

### 行動
暗号は標準のライブラリに任せ、鍵の管理は専用の仕組みへ委ねる。
鍵をデータと分けて保管し、鍵の更新の手順を必要になる前に用意する。
プロセスをまたぐ伝送を、暗号化された経路にする。

### 例
```
// 自前の暗号やハッシュを書く
const hash = myXor(password, key)
// 検証された標準の実装に任せる
const hash = argon2id(password)
```

## 供給網を保証する

### 要求
release する成果物は、署名・SBOM・SLSA provenance を備える。
版は semver で付け、一意かつ不変とする。
署名のない成果物を、release しない。
依存する部品の既知の脆弱性を SBOM から検査し、見つかったら release を止める。
生成と検査の機構の採用は、[tools](../tools/README.md) が定める。

### 根拠
成果物の出所と組成を証明できないと、改竄や混入を配布の後から検出できない。
署名と provenance は、成果物が定めた過程から生まれたことを証明する。
SBOM は、成果物を構成する部品を明かし、既知の脆弱性との照合を可能にする。
同じ版の中身が変わると、検証した成果物と配布された成果物の対応が崩れる。
一意で不変な版は、検証と配布の対応を固定する。

### 完了条件
release された成果物が、署名・SBOM・SLSA provenance を備えている。
版が semver で付けられ、一意で不変である。
依存する部品の既知の脆弱性が、SBOM から検査されている。
脆弱性が見つかった release が、止まっている。

### 禁止事項
署名のない成果物を、release すること。
release した版を、付け直すこと。
既知の脆弱性の検査を経ずに、release すること。

### 行動
release の経路に、SBOM の生成・provenance の生成・署名を組み込む。
依存する部品の既知の脆弱性を SBOM から検査し、見つかったら release を止め、部品を直してから改めて release する。
