# observability

## 概要
observability は、外部の出力から内部の状態を推し量れる状態を全系で統べる規律である。
principles の [separation](../principles/separation.md) が定める副作用の境界隔離を全系の観測として具象化し、未知の原因を運用しながら絞り込めるようにする。

## 文脈を一つにまとめて伝える

### 要求
trace・cancel・principal は一つの request context にまとめて伝え、処理は必要な文脈をその context から受け取る。
相関の識別子を文脈に載せ、境界を越えて伝播させる。
context は不変に保ち、値の追加は新しい context を生む。
境界を越えて伝播する文脈に、秘密や個人情報を載せない。

### 根拠
trace・cancel・principal を別々の経路で引き回すと、引数が増え、伝え漏れが起きる。
一つの context にまとめれば、境界を越える文脈が一貫して伝わる。
相関の識別子を載せれば、分散した処理を一つの流れとして追える。
context を不変にすれば、並行する処理が同じ context を共有しても壊れない。
伝播する文脈は境界を越えて外まで流れるので、秘密や個人情報を載せると漏れる。

### 完了条件
trace・cancel・principal が、一つの request context で伝わっている。
処理が、必要な文脈をその context から受け取っている。
相関の識別子が、境界を越えて伝播している。
request context が不変で、値の追加が新しい context を生んでいる。
境界を越えて伝播する文脈に、秘密や個人情報が載っていない。

### 禁止事項
trace・cancel・principal を、別々の経路で個別に引き回すこと。
相関の識別子を、境界で途切れさせること。
request context を、破壊的に書き換えること。
境界を越えて伝播する文脈に、秘密や個人情報を載せること。

### 行動
文脈を一つの request context にまとめ、境界を越えて伝播させる。
相関の識別子を文脈に載せ、下流と外部呼び出しへ引き継ぐ。

### 例
```
// trace・cancel・principal を別々に引き回す。引数が増え、伝え漏れる
f(trace, cancel, principal, arg)
// 一つの context にまとめて伝える
f(context, arg)   // context に trace・cancel・principal・相関 id を載せる
```

## 事実をイベントとして表し、構造化して出す

### 要求
観測の対象となる事実はイベントとして表し、観測はそれらの事実から組み立てる。
観測の出力は、field の名前と型と意味が一貫した構造を持つ形式で表す。

### 根拠
観測を、ログ・計測・トレースの信号として事実から組み立てれば、後から問いを立て直せる。
構造を持つ出力は、機械で集計・検索・異常検知できる。
文字列の継ぎはぎは、機械で解釈できず、観測の価値を下げる。
同じ事象が出力ごとに field の名前や型のばらつく形だと、構造を持っても機械で揃えられない。

### 完了条件
観測の対象となる事実が、イベントとして表されている。
観測の出力が、field の名前と型と意味の一貫した構造を持つ。
ログ・計測・トレースが、相関の識別子でつながっている。

### 禁止事項
観測の出力を、構造を持たない文字列の継ぎはぎで表すこと。

### 行動
観測する事実をイベントとして定義し、構造化された形式で出す。
相関の識別子で、ログ・計測・トレースをつなぐ。

### 例
```
// 構造のない文字列。機械で集計も検索もできない
log("user " + id + " did " + action + " at " + time)
// 構造化した形式。field の名前と型は出力ごとに一貫し、相関 id でつながる
log({ event: "order_placed", orderId, actorId, traceId, at })
```

## 文脈を豊かに載せ、事後に問いを立て直せるようにする

### 要求
観測する事実に、利用者・対象・版・経路などの高い次元の文脈を載せ、事前に決めた集計の軸に縛られず、事後に任意の切り口で絞り込めるようにする。

### 根拠
事前に決めた指標だけを集めると、想定した範囲の問いにしか答えられず、原因の分からない障害を運用しながら絞り込めない。
事実に高い次元の文脈を載せておけば、後から問いを立て直し、未知の原因へ任意の切り口で迫れる。
集計の段階で文脈を捨てると、その軸でしか見られなくなる。

### 完了条件
観測する事実に、利用者・対象・版・経路などの高い次元の文脈が載っている。
事前に決めた集計の軸に縛られず、事後に任意の切り口で絞り込める。

### 禁止事項
観測を、事前に決めた指標の集計だけに閉じ、未知の原因を事後に絞り込めなくすること。
高い次元の文脈を、集計の段階で捨てること。

### 行動
観測する事実に、後から問うであろう切り口の文脈を載せる。
事前の集計は補助に留め、生の事実から事後に絞り込める形を一次にする。
量が問題になるなら、相関を壊さない形で標本化する。

## 個人情報は最小化して載せ、期限で消す

### 要求
観測の対象となる事実に個人情報を載せるときは、目的に必要な項目だけに絞る。
本人を特定できる項目は、必要がなければ載せず、必要なら仮名化するか識別子に置き換える。
個人情報を含む観測の記録には保持の期限を定め、期限を過ぎた記録を消す。

### 根拠
文脈を豊かに載せる規律は、個人情報を無制限に運んでよい理由にはならない。
載せる項目を目的に必要な範囲へ絞れば、記録が漏れたときに及ぶ範囲を狭められる。
本人を特定できる形をそのまま残すと、観測の記録そのものが個人情報の保管先になり、消去の義務を負う対象が観測系にまで広がる。
仮名化や識別子への置き換えは、事後の相関を保ちながら本人の特定を難しくする。
保持の期限がない記録は、消去の義務を果たす手段を欠いたまま個人情報を溜め続ける。

### 完了条件
観測の対象となる事実に含まれる個人情報が、目的に必要な項目だけに絞られている。
本人を特定できる項目が、仮名化されているか識別子に置き換えられているか、必要がなければ載っていない。
個人情報を含む観測の記録に、保持の期限が定められている。
期限を過ぎた記録が、消えている。

### 禁止事項
目的に必要でない個人情報を、観測の対象となる事実に載せること。
個人情報を含む観測の記録を、期限を定めずに保持し続けること。

### 行動
観測へ載せる項目を洗い出し、目的に必要な範囲を確認する。
本人を特定できる項目は、仮名化するか識別子に置き換える。
個人情報を含む観測の記録に保持の期限を設定し、期限で消す仕組みを用意する。
消去の義務を負う個人データそのものの消去は [structure/core/infrastructure](../structure/core/infrastructure.md) の消去の規律に従う。

### 例
```
// 個人情報をそのまま載せる。漏れれば本人を特定できる範囲が広い
log({ event: "order_placed", customerName, customerEmail, amount })
// 目的に必要な範囲へ絞り、本人を特定できる項目は識別子で扱う
log({ event: "order_placed", customerId, amount })
```

## 仕込みを境界の殻で行う

### 要求
観測の仕込みは業務の核の外側、境界の殻で行い、業務の核に観測のための処理を混ぜない。
telemetry の出力は、OpenTelemetry に統一する。
collector は、別プロセスに置く。
利用者の環境で動く surface も観測の対象であり、そこでの収集も境界の殻で行う。

### 根拠
観測の処理を業務の核に埋めると、判断のテストに観測の足場が要り、核が観測に結合する。
仕込みを境界の殻で行えば、核は純粋な判断に保てる。
利用者の環境で動く surface は、動く場所が利用者の端末であっても、業務の判断を持たず境界の殻に観測を閉じるという構造は他の surface と変わらない。
利用者の環境から届く観測は、境界の外から来る値であり、[security](./security.md) の既定で信頼しない規律に従って扱う。

### 完了条件
観測の仕込みが、業務の核の外側、境界の殻で行われている。
業務の核に、ログや計測の処理が混ざらず、核は判断と事実を値として返している。
業務の核の単体テストに、ログや計測の足場が要らない。
利用者の環境で動く surface の観測が、境界の殻で行われている。
利用者の環境から届く観測が、境界の外から来る値として、検証を経ずに信頼されていない。

### 禁止事項
業務の核に、ログや計測の処理を埋め込むこと。

### 行動
観測の仕込みを境界の殻へ移し、核は決定を値として返すだけにする。
利用者の環境で動く surface では、境界の殻の実装として収集を行う。
収集に個人情報が載る場合は、前項の個人情報の規律に従う。

### 例
```
// 業務の核にログが混ざる。判断のテストに観測の足場が要る
function decide(x) { logger.info("deciding"); return x.ok ? a : b; }
// 核は純粋。観測は殻で
function decide(x) { return x.ok ? a : b; }     // 殻: log(...); decide(x); record(...)
```

## 観測は振る舞いを変えない

### 要求
観測は業務の振る舞いを変えず、観測の有無で業務の結果や順序が変わらないようにする。
観測の経路が無効でも業務は同じ結果と順序で動き、観測の呼び出しが業務を失敗させたり止めたりしない。

### 根拠
観測が業務の結果や順序を変えると、観測を入れたり外したりで挙動が揺れる。
観測を業務から独立に保てば、観測は安全に足し引きできる。
観測の経路を無効にしても業務が同じに動けば、観測の有無が結果に影響しない。
観測の出力を業務と切り離して非同期に流せば、出力先の不調が業務を止めない。

### 完了条件
観測の有無で、業務の結果や順序が変わらない。
観測の経路が無効でも、業務が同じ結果と順序で動く。
観測の呼び出しが、業務を失敗させたり止めたりしない。

### 禁止事項
観測のために、業務の結果や順序を変えること。
観測の出力の成否で、業務を失敗させたり止めたりすること。

### 行動
観測を業務の判断から切り離し、結果に影響しない位置で行う。

### 例
```
// 観測が副作用を持ち、業務の順序に影響する
const count = counter.incrementAndGet(); if (count > limit) reject()   // 観測が判断を変える
// 観測は記録するだけ。判断は業務の値で行う
record(metric); if (decision.rejected) reject()
```
