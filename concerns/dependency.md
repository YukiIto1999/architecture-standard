# dependency

## 概要
dependency は、依存の向きと合成を全系で統べる規律である。
principles の [separation](../principles/separation.md) が定める依存の単方向性とコンテキストの自己完結を、全系の依存の扱いとして具象化する。
依存はゼロにするのでなく、安定で抽象なものへ向ける。
効果が要求する依存の型での表現は [effect](./effect.md) が定め、dependency はその配線を統べる。

## 依存を内側へ一方向に向ける

### 要求
ソースコードの依存は、外側の詳細から内側の方針へ、一方向に向ける。
内側の方針は、外側の詳細の名前を参照しない。

### 根拠
実行時の呼び出しは方針から詳細へ向かうが、コンパイル時のソース依存は逆に内へ向ける。
内側が外側を知らなければ、詳細の変更が中心の方針へ波及しない。
外側で生成されたデータ形式を内側で使うと、内側がその詳細に縛られる。
方針が外側の詳細へ依存しない理由は、[separation](../principles/separation.md) に従う。

### 完了条件
内側の方針のソースコードに、外側の詳細への import や参照が現れていない。
外側で生成された DTO や DB の行を、内側がそのまま使っていない。
依存方向が一方向で、循環がない。

### 禁止事項
内側の方針から、外側の詳細の名前を参照すること。
framework や DB が生成したデータ形式を、内側で使うこと。

### 行動
import・参照・型共有の向きを確認し、内向きでない依存を見つける。
外側の名前が内側に現れていれば、抽象を挟んで向きを戻す。

### 例
```
// 中心が具体の詳細を参照する
PricingPolicy ── import ──> PostgresClient
// 依存は内へ。中心は抽象だけを知る
PricingPolicy ── uses ──> RateRepository           // 内側が定義し所有
PostgresRateRepository ── implements ──> RateRepository  // 外側が実装
```

## 抽象を方針側が所有する

### 要求
方針が必要とする抽象は、方針のパッケージ側に置き、詳細がそれを実装する。
抽象は、方針が必要とする操作だけに絞る。

### 根拠
使う側が抽象を所有し、実装する側がそれに依存すると、依存が逆転して内へ向く。
方針が必要としない操作まで持つ太い汎用の抽象は、方針に不要な知識を負わせる。
業務規則ごとに必要な分だけの抽象を切れば、変更の波及が小さくなる。
抽象の所有を方針側に置く理由は、[separation](../principles/separation.md) に従う。

### 完了条件
境界をまたぐ抽象の置き場所が、それを使う方針の側になっている。
抽象が、方針の必要とする操作だけを宣言している。
詳細の実装が、方針の抽象に依存している。

### 禁止事項
抽象の所有を、詳細の側へ譲ること。
全機能を露出する太い汎用の抽象を、内側に置くこと。

### 行動
方針が必要とする操作を洗い出し、その分だけの抽象を方針側に定義する。
詳細にその抽象を実装させ、方針が詳細の名前を知らない状態を保つ。

### 例
```
// 方針が必要な分だけの抽象を所有する
interface RateRepository { find(id: SkuId): Rate }   // domain が定義する
// 全 CRUD を露出する汎用 Repository<T> を内側に置かない
```

## port を目的で宣言する

### 要求
外界とのやり取りは、技術ではなく目的で設計した port で行う。
アプリを駆動する側と、アプリが駆動する側を区別する。

### 根拠
port を目的で設計すれば、同じ目的の技術別の実装を差し替えられる。
port を技術で割ると、技術の組み合わせごとに版が増えて爆発する。
駆動する側と駆動される側を分けると、テストでアプリを隔離して動かせる。

### 完了条件
port が、技術でなく目的で定義されている。
アプリを駆動する port と、アプリが駆動する port が区別されている。
実行時の機器や DB なしに、アプリを隔離してテストできる。

### 禁止事項
port を、技術ごとに割ること。
ユースケースに、port の向こうの技術詳細を書き込むこと。

### 行動
外界との接点ごとに、目的を表す port を定義する。
駆動する側はテストのドライバで、駆動される側はインメモリの代役で差し替える。

### 例
```
// 目的で設計したport(技術非依存)。技術別アダプタが差し替わる
interface NotificationPort { notify(to: Recipient, message: Message): Result<Sent, NotifyError> }
```

## 配線を組立点に集める

### 要求
オブジェクトの組み立ては、エントリ点に近い一つの組立点に集める。
組立点は業務判断を持たず、配線と写像だけを担う。

### 根拠
組み立てを一点に集めると、どの詳細が使われるかを一箇所で読める。
組立点はアプリだけが持ち、ライブラリは持たない。
さもないと利用者の差し替えの自由を奪う。
配線を早い段階で固定するほど選択肢が狭まるので、組み立てはエントリ点に寄せる。

### 完了条件
オブジェクトの組み立てが、エントリ点に近い一つの組立点に集まっている。
組立点が、配線と写像だけを行い、業務判断を持たない。
ライブラリが、組立点を持たない。

### 禁止事項
組み立てを、アプリの各所に散らすこと。
組立点に、業務判断を置くこと。
ライブラリやフレームワークが、利用者のために組立点を持つこと。

### 行動
オブジェクトグラフの構築を、エントリ点に近い一点へ集める。
DI コンテナを使う場合も、その参照を組立点に限る。

### 例
```
// エントリ点の組立点だけが具体型を知る
main() {
  const repository = new PostgresRateRepository(connection);
  const policy = new PricingPolicy(repository);    // 方針は port を受け取る
  serve(new HttpController(policy));
}
```

## 依存は構成子で受け取る

### 要求
依存は構成子の引数で受け取る。
効果の記述が要求を型に宣言する計算は、環境の提供を組立点で行う。
構成子注入は、効果を持たない構成要素の配線に用いる。
動的に選ぶ依存は、注入したファクトリで生成する。

### 根拠
構成子で必須の依存を受け取れば、依存が欠けた状態を作れない。
依存をその場で探す解決は、依存をシグネチャから隠し、コンパイル時の誤りを実行時の誤りに変える。
構成子で受ければ、依存はシグネチャに現れ、欠けた配線がコンパイル時に分かる。
効果の記述は要求する依存を型そのものに宣言するので、構成子注入と同じ役割を型のシグネチャで果たし、両者は競合せず対象で住み分ける。
動的な生成は、目的の型だけを要求できる注入したファクトリで行う。

### 完了条件
必須の依存が、構成子の引数または効果の型の要求として宣言され、組立点で配線されている。
依存が、シグネチャに現れている。
動的な生成が、注入したファクトリで行われている。

### 禁止事項
依存を、その場で探す解決(service locator)で取得すること。
依存を、暗黙のグローバルや ambient な機構で解決すること。
任意の型を要求できる仕組みで、動的生成を行うこと。

### 行動
依存を構成子の引数に移し、シグネチャに現す。
その場で探す解決やグローバルを、構成子注入と組立点での配線に置き換える。
動的生成は、目的の型に絞った注入ファクトリにする。

### 例
```
// 依存をシグネチャに現す
class PricingPolicy { constructor(private rates: RateRepository) {} }
// その場で探す解決やグローバルで依存を取らない
```

## 循環を作らず、安定へ依存し、詳細を先送りする

### 要求
コンポーネント間の依存に循環を作らない。
変わりにくく抽象なコンポーネントへ依存し、framework や DB の選択は組立点まで先送りする。

### 根拠
依存グラフに循環があると、独立して変更・デプロイ・テストできなくなる。
依存先ほど安定で抽象なら、変わりやすい側の変更が安定な側へ波及しにくい。
DB は入出力の機器にすぎず、業務規則はそれに依存しない。
詳細の選択を先送りすれば、軽く速いテスト環境を作れ、後で情報を得てから選べる。
ただし依存を最小化しすぎる過剰な抽象や分割もまた、不要な複雑さを生む。

### 完了条件
コンポーネントの依存グラフに循環がない。
依存が、より安定で抽象なコンポーネントへ向いている。
framework・DB の具体が、組立点で注入されるまで内側で未確定である。

### 禁止事項
コンポーネント間に、循環参照を作ること。
変わりやすい具体へ、安定な方針を依存させること。
framework を先に被せて、内側をその制約に縛ること。

### 行動
依存グラフを確認し、循環があれば抽象を挟むか共通部分を別コンポーネントへ抽出して断つ。
安定度と抽象度がずれるコンポーネントを見つけ、安定なものほど抽象である状態へ寄せる。
framework・DB の選択は組立点まで遅らせ、内側は port だけを知る。
