# concurrency

## 概要
concurrency は、非同期と並行の実行を全系で統べる規律である。
principles の [construction](../principles/construction.md) が定める不変な値の扱いと、[separation](../principles/separation.md) が定める副作用の境界隔離を、全系の並行の扱いとして具象化する。
ここで扱うのは、複数を束ねて捌く構造の並行であり、同時に動かして速くする実行の並列ではない。
性能目的の並列化は、[performance](./performance.md) が計測の後の最適化の一手段として定める。
業務の核は同期の純粋関数に保ち、並行と非同期は境界で扱う。

## 構造化並行で寿命をスコープに束ねる

### 要求
並行する処理は、生存期間を持つスコープの下に置き、親はスコープを抜ける前に子の完了を待つ。
子の一つが失敗したら、残りの兄弟を取り消し、それらの完了を待ってから失敗を伝える。
スコープを抜けた処理を、背後で走らせ続けない。

### 根拠
寿命を持たない並行処理は、どこで終わるか追えず、エラーも取り消しも伝わらない孤児になる。
子の寿命を親のスコープに束ねれば、子の失敗が親へ伝わり、親の終了で子も確実に終わる。
スコープを抜けたら全ての子が完了している、という不変条件が、並行の見通しを保つ。

### 完了条件
並行して開始した処理が、生存期間を持つスコープの下にある。
親が、スコープを抜ける前に全ての子の完了または取り消しを待つ。
スコープを抜けた後に走り続ける処理がない。
子の失敗が、親のスコープへ伝播する。
子の一つが失敗したとき、親が残りの兄弟を取り消し、それらの完了を待ってから失敗を伝える。

### 禁止事項
生存期間のスコープを抜けた処理を、追跡せずに走らせること。
子の完了を待たずに、親のスコープを抜けること。
子の失敗を、親へ伝えずに握り潰すこと。

### 行動
並行処理を、生存期間を持つスコープの下で開始する。
スコープの境界で、全ての子の完了・失敗・取り消しを合流させる。
親より長生きさせる必要がある処理も、どこかのスコープに束ね、そのスコープを引数で明示して渡す。

### 例

タスクを投げっぱなしにすると寿命を追えず、失敗も取り消しも伝わらない。

```
spawn(doWork())
```

タスクをスコープへ束ねると、スコープを抜けるまでにすべての子が終わり、失敗は親へ伝わる。

```
scope { s ->
  s.start(doWork())
  s.start(doOther())
}
```

## 取り消しを協調的に伝える

### 要求
取り消しは、強制中断でなく協調的に伝える。
取り消しを受けた処理は新しい外部効果を始めず、開始済みの効果の完了か補償を境界で決める。
時間の上限は各層に相対の値を配らず、絶対の期限として文脈に載せて伝え、下流へ取り消しとして伝播する。
後始末や補償の処理は、取り消しされない領域で行う。

### 根拠
強制中断は、途中の状態を不整合にし、確保した資源を解放させない。
協調的な取り消しなら、処理は安全な地点で中断し、資源を解放できる。
取り消しやタイムアウトを下流へ伝えなければ、上流が諦めた後も下流が走り続ける。
各層に相対の時間上限を配ると、境界をまたぐたびに再計算が要り合成できない。
絶対の期限を文脈に載せれば、境界をまたいでも一つの期限で測れる。
後始末を取り消しできる領域で行うと、後始末自体が中断され、資源を漏らす。

### 完了条件
取り消しが協調的に伝わり、処理が安全な地点で中断する。
取り消しを受けた処理が、新しい外部効果を始めない。
タイムアウトが、下流へ取り消しとして伝播する。
時間の上限が、絶対の期限として文脈で伝わっている。
後始末や補償が、取り消しされない領域で行われている。
確保した資源が、取り消し時に解放される。

### 禁止事項
処理を、強制的に中断すること。
取り消しを無視して、新しい外部効果を始めること。
上流の取り消しやタイムアウトを、下流へ伝えないこと。

### 行動
取り消しの合図を引数や文脈で下流へ渡し、処理がそれを確認する地点を設ける。
時間の上限は絶対の期限で文脈に載せ、各層へ相対値を配らない。
タイムアウトを取り消しへ変換し、下流へ伝播させる。
後始末は取り消しされない領域で行い、確保した資源は取り消し時に解放されるよう束ねる。

### 例

取り消しを受け取らず、相対的な時間上限を各層へ配ると、処理を合成できず、呼び出し側が諦めた後も実行が続く。

```
fetch(url); read(socket, timeout=10); parse(timeout=10)
```

絶対時刻の期限と signal を文脈で渡せば、期限切れや取り消しを受けた後は新しい I/O を始めず、協調的に中断できる。

```
fetch(url, context)
```

## 共有可変状態を避ける

### 要求
複数の実行から、同じ可変状態を直接共有しない。
状態は不変な値として受け渡すか、所有を単一の通信境界へ閉じる。

### 根拠
複数の実行が同じ可変状態を変更すると、競合で順序に依存する不具合が生まれる。
不変な値は共有しても壊れず、受け渡しで安全に並行できる。
可変状態の所有を単一の境界に閉じ、メッセージで受け渡せば、競合が起きない。

### 完了条件
並行する実行の間で受け渡す値が、不変である。
可変状態の所有が、単一の実行または通信境界に閉じている。
共有された可変状態を、複数の実行が直接変更していない。

### 禁止事項
同じ可変状態を、複数の実行から直接変更すること。
可変な値を、複数の実行で直接共有すること。

### 行動
並行の境界を越える値を不変にする。
可変な状態は、所有する単一の実行へ閉じ、他からはメッセージで依頼する。

### 例

複数の実行が共有カウンタを直接書き換えると競合する。

```
shared.count += 1
```

状態を所有する実行へメッセージで依頼するか、不変値を集計する。

```
owner.send(Increment)
```

## 並行度を制限し、背圧を扱う

### 要求
並行して走る処理の数を有界に保ち、背圧は消費側が処理できる量を需要として表し生産側がそれを超えて送らない形で扱う。
memory と durable の待ち行列の滞留上限、満杯時の拒否、期限切れの仕事の扱いは [resilience](./resilience.md) に従う。
再配送が必要な入力の durable receipt、upstream delivery ack、処理完了の確定点は [messaging](./messaging.md) に従う。

### 根拠
並行度を無制限にすると、資源が枯渇し、外部の依存先を圧迫する。
生産が消費を超え続けると、待ち行列が無限に伸び、記憶を食い尽くす。
有界の並行と背圧があれば、負荷が上限に収まり、過負荷で全体が倒れない。
消費側が需要を表し生産がそれを超えないようにすれば、待ち行列が有界に収まる。
協調スケジューリングの runtime では、背圧をブロッキングの待機で表すと、非同期の利点を消しデッドロックを招くので、需要の signal で表す。
需要の伝播だけを並行の責務にすれば、保存容量と回復の規律、配送の確定点を別の concern で重複して定義せずに済む。

### 完了条件
並行して走る処理の数に、上限がある。
消費側が需要を表し、生産側がその需要を超えて送っていない。
背圧が、ブロッキングの待機でなく需要の signal で表されている。
待ち行列の容量と回復が resilience、配送の確定点が messaging の完了条件で検証されている。

### 禁止事項
並行度に上限を設けず、無制限に処理を起動すること。
生産側が、消費側の需要を無視して送ること。
制御できない源で、境界を守らず際限なくバッファすること。
待ち行列の保存と回復、または配送の receipt と ack の規律を concurrency で再定義すること。

### 行動
並行して走らせる処理の数に上限を設ける。
消費側が処理できる分だけ需要を出し、生産はそれを超えて送らない。
待ち行列が満ちたら、需要を絞って生産を抑えるか、受けきれない分を拒む。
待ち行列の滞留と期限切れは resilience、durable receipt と ack は messaging の検査へ割り当てる。

### 例

入力ごとに無制限に処理を起動すると、依存先を圧迫する。

```
for (x of inputs) spawn(handle(x))
```

並行度に上限を設ける。

```
withConcurrencyLimit(16, inputs, handle)
```

## 並行の駆動を言語の機構に委ねる

### 要求
非同期の駆動と並行のスケジューリングは、言語の async の機構へ委ねる。
取り消しの伝播と構造化並行を、自前のスケジューラとして作らない。

### 根拠
取り消しの自動伝播と構造化並行は型では閉じず、スケジューラと協調する取り消しの runtime を要する。
これを自前で作ると、host の async に委ねる利点を捨て、重いスケジューラの再発明になる。
処理に言語の取り消しの合図を通すだけで、伝播は言語の機構が担う。

### 完了条件
非同期の駆動と並行のスケジューリングが、言語の async の機構で行われている。
取り消しの伝播や構造化並行のための、自前のスケジューラがない。

### 禁止事項
取り消しの伝播や構造化並行を、自前のスケジューラとして作ること。
言語の async 機構の外に実行モデルを持つ枠組みで、並行を組むこと。

### 行動
並行の駆動が言語の async の機構の外にないかを確かめる。
外にあれば、言語の機構へ移す。

## 非同期と並行を業務の核から隔離する

### 要求
純粋核と効果の殻の分離は [separation](../principles/separation.md) の「副作用を境界に集める」に従い、非同期と並行の制御は核に持ち込まず境界で扱う。

### 根拠
非同期や並行の制御が業務判断に混ざると、判断のテストに並行の足場が要る。
業務の核を同期の純粋関数に保てば、判断を単体で再現しテストできる。
非同期は並行と別の関心であり、ブロッキングは境界へ追い出す。

### 完了条件
業務の計算・判断が、非同期と並行の制御を持たない同期の関数として書かれている。
非同期と並行の制御が、境界に置かれている。
ブロッキングする処理が、境界へ隔離されている。

### 禁止事項
業務の核に、非同期や並行の制御を持ち込むこと。
業務の判断の途中で、ブロッキングする処理を呼ぶこと。

### 行動
業務の判断を同期の純粋関数へ切り出し、並行と非同期は呼び出し側の境界に置く。
ブロッキングする処理を、専用の境界へ追い出す。

### 例

業務の判断へ非同期処理を入れると、判断と外部効果を分離できない。

```
async function decide(x) { const r = await fetch(...); return r.ok ? a : b; }
```

非同期処理を境界へ置き、判断を同期の純粋関数にすれば、外部効果の足場なしで判断を検証できる。

```
function decide(x, fetched) { return fetched.ok ? a : b; }
```
