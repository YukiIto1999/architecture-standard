# experience

## 概要
experience は、利用者に向けた画面の体験を統べる規律である。
適用範囲は、利用者が判断し操作する面である。
GUI の viewer を主に、extension の UI や console の対話にも及ぶ。
視覚的な重み、target size、mouse 操作、route の規律は、visual UI だけに適用する。
console には、判断、feedback、keyboard 操作、進行表示の規律を適用する。
principles の [legibility](../principles/legibility.md) が定める明快さと [separation](../principles/separation.md) が定める責務の境界を、利用者に向けた面へ具象化する。
設計の目的は、利用者の判断と操作を、楽に安全に迷いなくすることである。
コードの設計が変更を楽にするのと、同じ型である。

## 判断の易しさを最適化する

### 要求
各利用者面は、利用者に求める判断を一つに絞り、その判断を自明にする。
次の判断に要る情報と操作を、その場に置く。
選択肢を絞り、クリック数の目安で設計しない。

### 根拠
判断にかかる時間は、選択肢が増えるほど長くなる。
求める判断を一つに絞り自明にすると、利用者は迷わず進める。
クリック数を減らしても、各クリックの判断が曖昧なら速くならない。
判断に要る情報を別の利用者面へ探しに行かせると、文脈が切れて誤る。

### 完了条件
各利用者面が、利用者に求める主たる判断を一つ持っている。
その判断に要る情報と操作が、同じ文脈にある。
主操作に、説明文やツールチップなしで到達できる。

### 禁止事項
一つの利用者面に、独立した複数の判断を詰め込むこと。
クリック数の少なさのために、各段の判断を曖昧にすること。
冗長な説明文で、自明でない操作を補うこと。

### 行動
利用者面ごとに、独立した複数の判断が混じっていないか確認する。
混じっていれば、判断ごとに利用者面を分ける。
判断に要る情報と操作を同じ文脈へ集め、説明文で補う操作を自明な形へ直す。

## 主操作と既定値を先に示し、頻用操作に近道を備える

### 要求
利用者面の主操作は一つにする。
visual UI の主操作は、見つけやすい位置に、押しやすい target size で置く。
visual UI の pointer target は、WCAG 2.2 の Success Criterion 2.5.8 に従い、24×24 CSS px 以上にする。
24×24 CSS px 未満の target は、Success Criterion 2.5.8 が定める例外に該当する場合だけ許し、該当する例外と理由を記録する。
予測できる既定値を選択済みで提示し、変えたい利用者だけが触る形にする。
予測できる妥当な既定値が無いなら、選択済みにせず空で出す。
既定値を選ぶ基準は、project が定める。
頻繁に使う操作には、熟達した利用者のための近道を添える。

### 根拠
主操作が一つなら、利用者は次の一手に迷いにくい。
visual UI の主操作が見つけやすく十分な target size を持てば、操作対象を探して正確に押す負担が減る。
24×24 CSS px という閾値を固定すれば、押しやすさを印象でなく bounding box で判定できる。
妥当な既定値を先に出すと、多くの利用者は確認だけで進める。
妥当でない値を選択済みにすると、確認だけで進む利用者が誤った値のまま確定する。
頻用操作の近道は、初学者には隠れ、熟達者の速度だけを上げる。

### 完了条件
各利用者面の主操作が、一つに絞られている。
visual UI の主操作が、他の操作より強い視覚的重みと十分な target size を持つ位置に置かれている。
visual UI の pointer target が24×24 CSS px以上であるか、Success Criterion 2.5.8 の例外と理由を持っている。
各 pointer target の表示後の CSS px の bounding box と例外記録が、照合できる証拠として残っている。
予測できる既定値が選択済みで示され、予測できない項目が空で示されている。
頻繁に使う操作に、近道がある。

### 禁止事項
同格の操作を利用者面に複数並べ、主操作を埋もれさせること。
妥当でない既定値を、選択済みにすること。
Success Criterion 2.5.8 の例外記録がない pointer target を、24×24 CSS px 未満にすること。

### 行動
利用者面の操作を見渡し、主操作が複数並んでいないか確認する。
主操作を一つに定める。
visual UI では、主操作を見つけやすい位置に十分な target size で置く。
各 pointer target の表示後の bounding box を CSS px で測り、幅と高さを24 CSS px以上にする。
24×24 CSS px 未満の target は、Success Criterion 2.5.8 の例外と理由が記録されている場合だけ検査から除外する。
妥当な既定値を選択済みで出し、無ければ空で出す。
頻用操作に近道を添える。

### 例

```
対象: 保存の主操作
表示後の bounding box: 幅32 CSS px、高さ24 CSS px
Success Criterion 2.5.8 の例外: 無し
判定: 24×24 CSS px 以上
```

## 状態と結果を即時に返す

### 要求
システムの現状を、利用者へ常に知らせる。
操作には即時の反応を返す。
操作の入力から状態または feedback が表示されるまでを100ms以内にする。
1秒を超える operation は、操作の入力から1秒以内に progress の表示を始め、完了まで進行を知らせ続ける。

### 根拠
現状が見えないと、利用者は何が起きているか分からず誤る。
操作直後に反応がないと、利用者は効いたか分からず繰り返す。
時間のかかる処理は、進行を知らせないと止まったと誤解される。
反応しない操作は、検証できず利用者の信頼を損なう。
100msと1秒の閾値を固定すれば、即時と時間のかかる処理を入力時刻と表示時刻の差で判定できる。

### 完了条件
処理中と成功と失敗の現状が、利用者面に現れている。
すべての操作が、入力から100ms以内に状態または feedback を表示している。
1秒を超える operation が、入力から1秒以内に progress の表示を始めている。
1秒を超える operation が、完了まで progress を表示している。
入力時刻、状態または feedback の表示時刻、progress の表示時刻、完了時刻が、経過時間を照合できる証拠として残っている。

### 禁止事項
現状を知らせずに、利用者を待たせること。
反応しない操作を、利用者面に置くこと。
操作の入力から100msを超えて、状態または feedback を表示しないこと。
1秒を超える operation で、入力から1秒以内に progress の表示を始めないこと。

### 行動
利用者面の操作を辿り、反応のない操作と現状の見えない処理がないか確認する。
状態を利用者面に常に示し、操作直後に反応を返す。
操作の入力から状態または feedback の表示までを測り、100ms以内であることを検査する。
1秒を超える operation は、入力から progress の表示までを測り、1秒以内に表示を始めて完了まで続けることを検査する。

### 例

```
操作: 保存
入力: 0ms
feedback の表示: 80ms
progress の表示開始: 900ms
完了: 1500ms
progress の表示: 開始から完了まで継続
```

## 誤りを防ぎ、起きたら回復を助け、取り返せるようにする

### 要求
不正な値を入力させない形にする。
列挙できる値は選択で、数と日付と真偽は専用の入力で受け、自由入力は値が定型を持たない場合に限る。
誤りが起きたら、平易な言葉で何が問題かを示し、直し方を添える。
誤った操作は、取り消しと脱出で取り返せるようにする。

### 根拠
良いエラー文よりも、誤りが起きない構造の方が確実である。
入力を型と選択で縛ると、不正な場合がそもそも生じない。
それでも利用者は誤るので、起きた誤りには問題と直し方を示し、番号だけのエラーを出さない。
取り消しと脱出がないと、利用者は作業を失う。

### 完了条件
列挙できる値が、選択で受けられている。
数と日付と真偽が、専用の入力で受けられている。
自由入力が、定型を持たない値に限られている。
エラーの表示が、平易な言葉で問題と直し方を示している。
誤った操作に、取り消しか脱出の経路がある。

### 禁止事項
列挙できる値を、自由入力で受けること。
不正な値を入力できる形にすること。
番号や内部の語だけで、エラーを示すこと。
取り返せない操作を、確認なく実行させること。

### 行動
入力ごとに、選択と数と日付と真偽と自由の別を確かめ、不正値を作れない入力にする。
エラーの表示を点検し、問題と直し方を平易な言葉で示す。
主要な操作に、取り消しと脱出を備える。

### 例

出力形式を自由入力で受けると、利用者が不正な値を入力できる。

```
outputFormat: 自由入力
```

列挙できる値を選択肢で受ければ、不正な値を作れない。

```
outputFormat: 選択(CSV / JSON)
```

## 利用者の語彙と現実に合わせ、操作できることを見える形で示す

### 要求
画面は、利用者の言葉と概念と順序で語る。
内部の用語と実装の都合を、画面に出さない。
操作とその効果の対応を、自然な形にする。
操作できる要素は、操作できると見て分かる形にする。

### 根拠
利用者は、自分の言葉で書かれた画面を理解できる。
内部のジャーゴンを出すと、利用者は意味を推測させられる。
同じ概念に複数の語を当てると、別物と誤解される。
操作と効果の対応が自然なら、利用者は結果を予測できる。
操作できる手掛かりが見えないと、利用者は何が操作できるか分からない。

### 完了条件
画面の語が、利用者の語彙に一致している。
内部の用語と実装の都合が、画面に現れていない。
操作の名前と並びが、実世界の慣習と同じ順序と向きである。
操作できる要素が、操作できると見て分かる形になっている。

### 禁止事項
内部の用語と実装の都合を、画面に出すこと。
同じ概念に、画面ごとに別の語を当てること。
操作できる要素を、操作できると分からない形にすること。

### 行動
画面の語を業務の語彙と照らし、内部の用語を写し替える。
操作と効果の対応を、実世界の慣習に合わせる。
操作できる要素に、操作できると分かる手掛かりを与える。

## 情報を局面と依存でまとめ、余白と階層で導く

### 要求
情報は、利用の局面と前後の依存でまとめ、無関係なものを同列に混ぜない。
visual UI の視覚の区切りを、責務の境界に一致させる。
visual UI の構造は、罫線の多用でなく余白と字の強弱で示す。
無関係なものと稀にしか使わないものを、利用者面に出さない。

### 根拠
局面と依存でまとめると、利用者は今の局面に要るものだけを見られる。
visual UI で依存の向きをレイアウトで示すと、何が先で何が後かが分かる。
余分な情報は、関連する情報と競合して相対的な見やすさを下げる。
visual UI の装飾が主題を覆うと、データより様式が前に出る。

### 完了条件
情報が、利用の局面と依存でまとまっている。
visual UI の視覚の区切りが、責務の境界と一致している。
visual UI の構造が、罫線の多用でなく余白と字の強弱で示されている。
無関係なものと稀用のものが、利用者面に出ていない。

### 禁止事項
依存の異なる情報を、同列のフラットな並びに混ぜること。
visual UI の装飾で、データを覆うこと。
稀にしか使わない情報を、常時利用者面に出すこと。

### 行動
利用者面の情報を、利用の局面と依存で見分け、混在を解く。
visual UI では、依存の向きをレイアウトで表し、余白と強弱で階層を示す。
visual UI の装飾と、稀用の情報を削る。

## 同じ目的に同じ画面のパターンを使う

### 要求
同じ目的の操作と表示には、同じパターンを当てる。
同じ目的の部品は、一つにして使い回す。
広く使われている慣習に従う。

### 根拠
同じ目的に同じ形を当てると、利用者は一度学べば全画面で通じる。
目的ごとに別の形を当てると、利用者は画面ごとに学び直す。
利用者は他の製品で多くの時間を過ごすので、慣習に従うと学習が要らない。

### 完了条件
同じ目的の操作と表示が、同じパターンで実現されている。
同じ目的の部品が、一つに集約されている。
同種の操作が、広く使われている形と同じになっている。

### 禁止事項
同じ目的に、画面ごとに別のパターンを当てること。
同じ目的の部品を、画面ごとに作り直すこと。

### 行動
画面を横断し、同じ目的に別のパターンや別の部品が当たっていないか確認する。
同じ目的の操作と表示を、一つのパターンと部品に統一する。
広く使われている慣習に合わせる。

## キーボードで操作でき、色だけに頼らない

### 要求
visual UI と console のすべての操作を、keyboard で行えるようにする。
visual UI は、WCAG 2.2 Level AA を満たす。
visual UI のフォーカスを、通常の keyboard 操作で脱出できない場所に閉じ込めない。
modal dialog を開いている間は Tab 順序を dialog 内に保ち、Escape と明示された閉じる操作の双方で dialog を閉じられるようにし、起点か次の操作先へフォーカスを戻す。
visual UI の状態は、色とラベルの両方で示す。
visual UI の通常の text と images of text は、Success Criterion 1.4.3 に従い、背景との contrast ratio を4.5:1以上にする。
visual UI の large text と large images of text は、Success Criterion 1.4.3 に従い、背景との contrast ratio を3:1以上にする。
Roman の large text は、18pt(24 CSS px)以上、または14pt(約18.67 CSS px)以上かつ bold の text に限る。
Roman の bold は、使用した font face と user agent の font metadata から判定する。
CJK の large text は、font metrics から WCAG 2.2 が定める large print と同等の大きさであることを checker が実証できる text に限る。
CJK の large print 相当を実証できない text には、通常の text と同じ4.5:1以上を適用する。
Success Criterion 1.4.3 の対比要件から除外するのは、inactive な UI component の text または image of text、純粋な装飾、表示されない text または image of text、重要な他の視覚内容を含む画像の一部である text または image of text、logotype または brand name に限る。
visual UI の component と state の識別に必要な visual information と、内容の理解に必要な graphic は、Success Criterion 1.4.11 に従い、隣接色との contrast ratio を3:1以上にする。
component と state の visual information から除外するのは、inactive な UI component と、user agent が外観を決めて author が変更していない UI component に限る。
内容の理解に必要な graphical object から除外するのは、その particular presentation が情報に不可欠な場合に限る。

### 根拠
visual UI では、mouse を使えない利用者も keyboard で全操作に届く必要がある。
脱出手段のない keyboard trap は、keyboard の利用者が先へ進むことを妨げる。
modal dialog は背後を操作不能にするため、開いている間はフォーカスを内側に保ち、閉じる操作と閉鎖後の復帰先を備える。
visual UI で色だけを使って状態を示すと、色を見分けにくい利用者に伝わらない。
visual UI で対比が足りないと、文字が読めない。
contrast ratio と success criterion を固定すれば、対比を印象でなく computed style から判定できる。

### 完了条件
visual UI で mouse から届く操作が、すべて keyboard でも届く。
console のすべての操作が、keyboard から届く。
visual UI に、通常の keyboard 操作で脱出できない focus trap がない。
modal dialog の Tab 順序が dialog 内に保たれ、Escape と明示された閉じる操作で閉じられ、閉鎖後のフォーカスが起点か次の操作先へ戻っている。
visual UI の状態が、色とラベルの両方で示されている。
visual UI が、WCAG 2.2 Level AA を満たしている。
通常の text と images of text の contrast ratio が4.5:1以上である。
large text と large images of text の contrast ratio が3:1以上である。
Roman の large text が、18pt(24 CSS px)以上、または14pt(約18.67 CSS px)以上かつ font face と user agent の metadata で bold と判定されている。
CJK の large text が、font metrics により WCAG 2.2 の large print と同等であることを実証されている。
CJK の large print 相当を実証できない text に、4.5:1以上が適用されている。
component と state の識別に必要な visual information と、内容の理解に必要な graphic の contrast ratio が3:1以上である。
Success Criterion 1.4.3 と1.4.11の除外が、各 criterion の例外種別と対象を記録した場合だけ適用されている。
Success Criterion 1.4.11 の UI component の例外と graphical object の例外が、それぞれの対象だけに適用されている。
表示結果の style、font face、user agent の font metadata、font metrics、隣接色、例外記録が、各 contrast ratio を照合できる証拠として残っている。

### 禁止事項
visual UI に、mouse でしか行えない操作を置くこと。
visual UI の状態を、色だけで示すこと。
visual UI のフォーカスを、通常の keyboard 操作で脱出できない場所に閉じ込めること。
modal dialog から Escape と明示された閉じる操作を外すこと。
modal dialog を閉じた後のフォーカスの復帰先を定めないこと。
通常の text または image of text を、contrast ratio が4.5:1未満の状態で表示すること。
基準未満の text を、Success Criterion 1.4.3 の例外に該当しないまま対比検査から除外すること。
Roman の large text の大きさと font face の bold metadata を確認せず、3:1の閾値を適用すること。
CJK の large print 相当を font metrics で実証せず、3:1の閾値を適用すること。
component と state の識別に必要な visual information または内容の理解に必要な graphic を、Success Criterion 1.4.11 の例外に該当しないまま3:1未満で表示すること。
inactive または user agent appearance の例外を、graphical object へ適用すること。
essential presentation の例外を、UI component または state へ適用すること。

### 行動
visual UI と console を keyboard だけで辿り、届かない操作を見つける。
visual UI では、脱出手段のない focus trap を見つける。
modal dialog では、Tab と Shift+Tab が dialog 内を循環し、Escape と閉じる操作で閉鎖でき、フォーカスが起点か次の操作先へ戻ることを確かめる。
すべての操作に keyboard の経路を与える。
visual UI では、フォーカスの順路を保ち、状態を色とラベルの両方で示し、対比を確保する。
表示後の Roman text の style、font face、user agent の font metadata を取得し、18pt以上、または14pt以上かつ bold のどちらかへ分類する。
CJK text は font metrics から WCAG 2.2 の large print と同等であることを checker で実証し、実証できない場合は通常の text として扱う。
表示後の text、component と state の識別に必要な visual information、内容の理解に必要な graphic の隣接色を取得し、Success Criterion 1.4.3と1.4.11のcontrast ratioを検査する。
対比検査から除外する対象は、該当する criterion の例外種別と理由を記録して照合する。
Success Criterion 1.4.11 は、UI component と state の例外を UI component だけに、essential presentation の例外を graphical object だけに照合する。

### 例

```
対象: 通常の text
隣接色との contrast ratio: 4.7:1
適用する閾値: 4.5:1
例外: 無し
判定: 適合

対象: 保存操作の識別に必要な境界線
隣接色との contrast ratio: 3.2:1
適用する閾値: 3:1
例外: 無し
判定: 適合
```

## 情報構造を作業の流れに沿わせ、現在地を示す

### 要求
利用者面の構成と並びを、利用者の作業の流れに沿わせる。
visual UI の一覧と詳細は、多数を検索して開くなら route を分け、短い設定を頻繁に行き来するなら並置で組む。
利用者が今どこにいるかを、常に示す。

### 根拠
作業の流れに沿った構成は、利用者が次にどこへ行くかを予測できる。
visual UI で多数を検索して開く場合は、一つずつ route で開くと戻る操作と共有がしやすい。
visual UI で短い設定を頻繁に行き来する場合は、一覧と詳細を並置すると移動が要らない。
現在地が見えないと、利用者は全体の中で自分の位置を見失う。

### 完了条件
利用者面の構成と並びが、作業の流れに沿っている。
visual UI の一覧と詳細が、用途に応じて route の分割か並置のどちらかで組まれている。
現在地が、常に利用者面に示されている。

### 禁止事項
作業の流れに反する順序で、利用者面を並べること。
現在地を、利用者から隠すこと。

### 行動
利用者面の並びを作業の流れと照らし、合わない順序を直す。
visual UI では一覧と詳細の用途を見分け、route の分割か並置を選ぶ。
現在地を常に示す。

## 誇張せず、効かないものを見せない

### 要求
利用者面は、製品の能力を実際以上に見せない。
前提が未充足で、現在の作業の流れで充足可能な操作は、満たすべき前提と理由を示して無効化する。
前提を満たしている操作は、有効にする。
現文脈で効かない操作と選べない選択肢は、非表示にする。
利用者を欺く誘導をしない。

### 根拠
能力を実際以上に見せると、利用者は果たされない期待で誤る。
前提が未充足でも現在の作業の流れで充足可能なら、理由付きで無効化することで、利用者は操作の存在と有効にする手順を理解できる。
前提を満たした操作を有効にすれば、利用者はその場で実行できる。
現文脈で効かない操作と選べない選択肢は、表示しても利用者の判断を増やすだけで意味を持たない。
利用者を欺く誘導は、短期の数字と引き換えに信頼を失う。

### 完了条件
利用者面の表示が、製品の実際の能力に一致している。
前提が未充足で、現在の作業の流れで充足可能な操作が、満たすべき前提と理由を示して無効化されている。
前提を満たしている操作が、有効になっている。
現文脈で効かない操作と選べない選択肢が、利用者面に出ていない。
利用者を欺く誘導が、利用者面にない。

### 禁止事項
製品の能力を、実際以上に見せること。
前提が未充足で現在の作業の流れで充足可能な操作を、理由を示さず無効化すること。
前提を満たしている操作を、無効化すること。
現文脈で効かない操作と選択肢を、見せること。
利用者を欺く誘導を、置くこと。

### 行動
操作の前提が現在の作業の流れで満たせるかを確かめる。
前提を満たしていれば、操作を有効にする。
前提は未充足でも現在の作業の流れで充足可能なら、満たすべき前提と理由を示して無効化する。
現文脈で効かない場合は、操作を非表示にする。
表示を製品の実際の能力に合わせ、欺く誘導を取り除く。

### 例
```
if (prerequisite.isSatisfied) showEnabled(operation)
else if (currentFlow.canSatisfy(prerequisite)) showDisabled(operation, reason)
else hide(operation)
```
