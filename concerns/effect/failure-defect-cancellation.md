## 失敗と欠陥と取り消しを分ける

### 要求
効果の終了を、成功・想定内の失敗・欠陥・取り消しに分ける。
想定内の失敗は失敗の型で表し、欠陥と取り消しを失敗の型に混ぜない。
一つの実行の終了は四つのうち一つに定め、終了を確定した後に観測した取り消しや期限の超過で、確定した終了を書き換えない。
取り消しは、結果を待つ側がその結果を要らなくなったことで起きる終了であり、全ての層で取り消しとして終える。
時間の上限を設けた側は、自身の上限の超過を想定内の失敗として受け取り、上限の内側の処理は、その超過を取り消しとして受けて取り消しで終える。
上限を設けた側が終了を判定する時点で、結果を待つ側からの取り消しと自身の上限の超過がともに成り立つ場合は、取り消しとする。
処理が中断で終えたかどうかは、中断を伝える機構が終了に与える表現で識別し、中断の原因が取り消しか上限の超過かは、判定の時点の状態で決める。
上限を設けた側は、超過の判定を、自身が設けた上限の状態で行い、それ以外の理由で中断したことから上限の超過を推測しない。
欠陥で終えた実行は、取り消しや上限の超過が同時に成り立っても欠陥とする。
並行に走らせた子の終了を一つにまとめるときは、欠陥で終えた子があれば欠陥、なければ判定の時点で結果を待つ側の取り消しが成り立ち中断で終えた子があれば取り消し、なければ組が自ら中断させた子を除く子の結果から定め、全ての子が結果を返して終えた後に観測した取り消しや上限の超過で書き換えない。
外部へ公開するエラーは、境界で標準の形へ写す。

### 根拠
終了を四つに分けると、想定内の失敗と回復できない欠陥と取り消しを、一つの結果型に潰さず区別できる。
欠陥は回復できないプログラムの誤りなので、失敗の型に混ぜず、別の終了として速やかに失敗させる。
取り消しは失敗でも成功でもないので、別の終了として扱う。
欠陥や取り消しを失敗の型に潰すと、情報が落ち、回復できない誤りを回復できる失敗と取り違える。
確定した終了を後から観測した取り消しや期限で書き換えると、成功した書き込みや起きた外部効果が失敗として報告され、呼び出し側が重複した再実行を始める。
時間の上限の超過は、上限を設けた側にとって応答や再試行を決める必要のある結果であり、結果を要らなくなった取り消しとは扱いが異なる。
上限の内側の処理には、上限を設けた側が結果を待たなくなったことだけが伝わるので、内側では取り消しとして終える。
結果を待つ側が取り消した後には、上限の超過を受け取って応答や再試行を決める側がいないので、取り消しを優先する。
中断の理由を自身の上限の状態でなく推測で決めると、他の機構による中断が上限の超過として報告され、応答と再試行の判断を誤らせる。
終了の表現は、中断で終えたか、結果を返したか、誤りで終えたかを示すが、中断の原因は終了の値の間で受け渡されるうちに失われうるので、原因は状態で決める。
欠陥は直すべき誤りの証拠であり、同時に起きた取り消しや上限の超過で隠すと、誤りが観測されないまま残る。
結果を待つ側の取り消しで中断した子がある組は結果が全体として欠け、その結果を待つ側もいないが、組が最初の失敗で兄弟を中断させただけならその失敗が組の結果であり、全ての子が結果を返した組は確定した終了なので、後から観測した取り消しで書き換えない。
対象の不在は、理由が要らなければオプション型で表し、理由が要ればドメインの失敗として表す。
外部へ公開するエラーは、境界で標準の形へ写し、内部の詳細を漏らさない。

### 完了条件
効果の終了が、成功・想定内の失敗・欠陥・取り消しに分かれている。
想定内の失敗が、網羅された失敗の型で表されている。
欠陥と取り消しが、失敗の型に混ざっていない。
一つの実行の終了が四つのうち一つに定まり、確定した後に観測した取り消しや期限の超過で書き換えられていない。
時間の上限を設けた側が自身の上限の超過を想定内の失敗として受け取り、上限の内側の処理が取り消しで終えている。
結果を待つ側の取り消しと自身の上限の超過がともに成り立つ場合に、取り消しとして終えている。
上限の超過が、上限を設けた側が所有する上限の状態から判定されている。
中断で終えたことが中断の機構の表現で識別され、その原因が判定の時点の状態で決められている。
取り消しや上限の超過と同時に成り立つ欠陥が、欠陥として終えている。
並行の子の終了が、欠陥、判定の時点の結果を待つ側の取り消しと中断で終えた子、組が自ら中断させた子を除く子の結果の順でまとめられ、全ての子が結果を返して終えた後に書き換えられていない。
結果を要らなくなった側からの取り消しが、全ての層で取り消しとして終えている。
外部へ公開するエラーが、境界で標準の形へ写され、内部の詳細を含まない。

### 禁止事項
欠陥や取り消しを、想定内の失敗の型に混ぜること。
想定内の失敗を、欠陥として送出すること。
外部へ公開するエラーに、スタックトレースや内部の詳細を含めること。
確定した成功や想定内の失敗を、後から観測した取り消しや期限の超過で別の終了へ書き換えること。
時間の上限を設けた側で、自身の上限の超過を取り消しとして扱うこと。
自身の上限の状態を確かめず、中断したことから上限の超過を推測すること。
欠陥を、同時に成り立つ取り消しや上限の超過に置き換えること。
全ての子が結果を返して終えた並行の組を、後から観測した取り消しや上限の超過で書き換えること。

### 行動
終了を、成功・想定内の失敗・欠陥・取り消しに仕分ける。
想定内の失敗を網羅した型にし、欠陥と取り消しを別の終了に分ける。
境界で、内部のエラーを標準の形へ写し、内部の詳細を落とす。
終了を確定した時点で終了の種類を固定し、その後に観測した取り消しや期限の超過は診断として記録する。
時間の上限を設けた箇所で自身の上限による終了を想定内の失敗へ写し、上限の内側には取り消しとして伝える。
中断で終えたかを中断の機構の表現で見分け、中断の原因を判定の時点の取り消しと上限の状態で決め、欠陥は欠陥のまま通す。
並行の子の終了を、欠陥、判定の時点の結果を待つ側の取り消しと中断で終えた子、組が自ら中断させた子を除く子の結果の順でまとめる。

### 例

終了は、成功、型で網羅した想定内の失敗、回復不能な欠陥、取り消しに分ける。
欠陥と取り消しを想定内の失敗へ混ぜない。

```
成功 | 想定内の失敗(網羅した直和) | 欠陥(回復不能) | 取り消し
```

外部へ公開する形式への変換は境界で行い、内部の詳細を含めない。
形式は contracts の binding が定める。

```
toProblemDetails(failure)
```

要求に期限を設けた境界は、期限の超過を想定内の失敗として受け取って応答を決め、期限の内側の処理は取り消しで終える。

```
boundary(request) = withDeadline(deadline, handle(request))   // 期限の超過は boundary の想定内の失敗
handle(request)   = fetch(url, context)                      // 期限の超過は handle と fetch の取り消し
```
