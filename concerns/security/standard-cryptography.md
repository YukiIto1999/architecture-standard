## 標準の暗号に任せる

### 要求
暗号と鍵の扱いは検証された標準のアルゴリズムと実装に任せ、自前で実装しない。
伝送に暗号化経路を要するかは、プロセスをまたぐかどうかでなく、値が越える信頼境界と、経路上で値を読み書きできる主体の範囲で判定する。
ネットワークを通る伝送と、信頼境界を越える伝送は、意図した最終受信者を認証し、盗聴と改竄を防ぐ標準の暗号化経路で行う。
最終受信者の手前で復号する中継点を含む経路は、最終受信者までの暗号化経路とみなさず、中継点が最終受信者と同じ信頼境界の内側にあり、復号後の各区間もこの判定を満たす場合に限り許容する。
ネットワークを通らず、同じ信頼境界の内側にあるローカルの IPC とファイルの引き渡しは、OS のアクセス制御、descriptor、ファイルシステムによる保護を、実際の peer、受信の権限、アクセスできる主体、媒体の寿命から示せる場合に限り、暗号化経路を必須としない。
同じ host、同じ OS 利用者、プロセスの親子関係、実行側と検査側のような役割の名称は、同じ信頼境界の内側であることの根拠にしない。
保護の条件を示せない伝送と、host が実際に与える保護を確認できない伝送は、保護されているとみなさない。
secret の伝送も、この判定に従う。
この判定は伝送だけを対象にし、受け取りの後もファイルとして残る値の機密性、完全性、アクセス、保持、backup は対象にしない。
secret の保管と保持は [secrets](../secrets/README.md) に、個人情報の保持と backup は [privacy](../privacy/README.md) に従う。

### 根拠
暗号の自前実装は、わずかな誤りで安全を失う。
検証された標準の実装は、広く検査され攻撃に耐えている。
経路上の盗聴と改竄の危険は、伝送がプロセスをまたぐかどうかでなく、経路を読み書きできる主体の範囲と、その主体が受信の権限を持つかで決まる。
ネットワークの途中や異なる信頼境界の間には、送り手と受け手の管理の外にある主体が経路へ関わりうる。
暗号化経路は、意図した最終受信者を認証して初めて、意図しない相手への漏洩と改竄を防ぐ。
中継点で復号すると、復号後の区間は暗号化経路の保護の外に出て、最終受信者までの保護が途切れる。
OS のアクセス制御は、経路や媒体に触れられる主体を絞る手段であり、暗号化でも通信相手の認証でもない。
鍵を使わない hash は誰でも再計算できるので、機密性も送り手の真正性も示さない。
同じ host、OS 利用者、親子関係、役割の名称は、実際に経路へ触れられる主体の範囲も、受信の権限も定めない。
引き渡しの媒体は受け手が受け取るまで値を保持し、その間に触れられる主体が値を読み書きできる。
host が実際に与える保護は、その環境の設定と実装に依存し、この規律の本文だけでは分からない。
確認できない保護を保護済みとみなすと、未確認の前提が安全の根拠へ変わる。
伝送中の露出と、受け取りの後もファイルとして残る値の露出は、読める主体と期間が異なるので、別の規律で判定する。

### 完了条件
暗号と鍵の扱いが、検証された標準のアルゴリズムと実装で行われている。
ネットワークを通る伝送と、信頼境界を越える伝送が、意図した最終受信者を認証する標準の暗号化経路で行われている。
最終受信者の手前で復号する中継点がある場合は、その中継点が最終受信者と同じ信頼境界の内側にあり、復号後の各区間も同じ判定を満たしている。
暗号化経路を使わないローカルの伝送ごとに、ネットワークを通らず同じ信頼境界の内側にあることと、peer、受信の権限、アクセスできる主体、媒体の寿命が、実際の構成から確認できる。
保護の条件を示せない伝送と、host が実際に与える保護を確認できない伝送が、保護されているものとして扱われていない。

### 禁止事項
暗号のアルゴリズムやプロトコルを、自前で実装すること。
標準のライブラリに任せきりにして、方式・鍵長・乱数源・伝送の版を確かめないこと。
ネットワークを通る伝送または信頼境界を越える伝送を、暗号化されていない経路や、受信者を認証しない経路で行うこと。
同じ host、同じ OS 利用者、プロセスの親子関係、役割の名称だけを根拠に、同じ信頼境界の内側として扱うこと。
OS のアクセス制御や鍵を使わない hash を、暗号化または peer の認証と同じものとして扱うこと。
最終受信者の手前で復号する経路を、最終受信者までの暗号化として扱うこと。
保護の条件を示せない、または確認できない伝送を、保護されているとみなすこと。
伝送の判定の通過を、受け取りの後にファイルとして残る値の保管・保持・backup の保護の根拠にすること。

### 行動
暗号は標準のライブラリに任せ、鍵の管理は専用の仕組みへ委ねる。
鍵をデータと分けて保管し、鍵の更新の手順を必要になる前に用意する。
伝送ごとに、送り手、受け手、通る媒体、中継点を洗い出し、越える信頼境界と値を読み書きできる主体を確かめる。
ネットワークを通る伝送と、信頼境界を越える伝送を、意図した最終受信者を認証する標準の暗号化経路にし、復号する中継点があればその先の区間まで同じ判定を行う。
ネットワークを通らないローカルの伝送で暗号化経路を使わないなら、peer、受信の権限、アクセスできる主体、媒体の寿命を実際の構成から確かめる。
保護を示せない伝送は未確認として扱い、受信者を認証した暗号化経路を確立できるまで値を送らない。
最終受信者と peer が値を受け取る権限は、[authorization](../authorization/README.md) に従って確かめる。

### 例

独自の暗号処理やハッシュ処理を実装しない。

```
const hash = myXor(password, key)
```

検証された標準の実装に委ねる。

```
const hash = argon2id(password)
```
