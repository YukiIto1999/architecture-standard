## 外部依存の呼び出しを制御する層に置く

### 要求
一回の実行内の外部依存への呼び出しは port を包む層で制御し、時間の上限・再試行・遮断をその層に置く。
この呼び出しの障害制御を、業務の判断へ持ち込まない。
port 層の時間上限は、文脈で伝わる絶対期限と合成し、短い方を採る。
期限の意味は [concurrency](../concurrency/README.md)、carrier の伝播は [context-propagation](../context-propagation/README.md) に従う。
一回の実行内の同じ呼び出しの再試行は、port を包む層のうち一箇所だけが担い、上流の層で重ねない。
停止を越える処理の再実行と、その状態の置き場、全体の試行上限は [workflow](../workflow/resumable-progress.md) の「進行の状態を持ち、停止から再開する」が定め、この規律は実行中の呼び出しの制御だけを扱う。
進行の再実行と併用する場合は、各実行の呼び出しの試行を、その全体の試行上限へ数え入れる。

### 根拠
呼び出しの時間上限・再試行・遮断を業務の判断に埋めると、業務規則と障害制御が混ざる。
呼び出しの制御を port を包む層に集めれば、業務の判断から独立に調整できる。
時間の上限のない呼び出しは、依存の停止で自分も止まる。
port 層だけの上限を文脈の期限と独立に持つと、上流が諦めた後も port 層が待ち続ける。
短い方を採れば、上流の期限を越えて待たない。
呼び出しは複数の層を通ることがあり、層ごとに同じ呼び出しを再試行すると、試行の回数が層の数だけ掛け算で膨らむ。
下流が既に諦めた呼び出しを上流がなお再試行すると、下流が最も弱っている時に負荷が積み増される。
再試行を一箇所に決めれば、その呼び出しの総試行回数を見積もれる。
進行の状態から再実行する判断は、実行中の一つの呼び出しを繰り返す制御とは変更理由が異なり、どちらも再試行と呼ぶだけでは所有を決められない。

### 完了条件
外部依存への呼び出しが、port を包む層で制御されている。
呼び出しに、時間の上限がある。
実行中の呼び出しの再試行・遮断・時間上限が、業務の判断に埋まっていない。
port 層の時間上限が、文脈で伝わる絶対期限と合成され、短い方が採られている。
一回の実行内の同じ呼び出しの再試行が、port を包む一箇所に限られ、上流で重ねられていない。
停止を越える再実行と実行中の呼び出しの再試行が分かれ、併用する場合に各実行の呼び出しの試行が全体の試行上限へ数えられている。

### 禁止事項
実行中の呼び出しの障害制御を、業務の判断へ埋め込むこと。
時間の上限のない外部呼び出しを行うこと。
同じ呼び出しを、複数の層で重ねて再試行すること。
一回の実行が終わる前に同じ呼び出しを上流から繰り返す制御を、停止を越える再実行と呼び替えて重ねること。

### 行動
一回の実行内の呼び出しを制御する層を一つ決め、それ以外の層は再試行せず結果を伝える。
停止を越える処理では、実行中の呼び出しの制御を進行の再実行と分け、併用する場合は各実行の呼び出しの試行を全体の試行上限へ数え入れる。

### 例

業務処理に時間上限と再試行を埋め込むと、判断と障害制御が混ざる。

```
function place(order) { for (i in 0..3) try { return api.call(order) } catch {} }
```

時間上限、再試行、遮断は port を包む層で制御し、業務には結果だけを返す。

```
class ResilientRateClient implements RateClient { ... }
```
