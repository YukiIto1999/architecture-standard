# types

## 概要
types は、型で全系の不変条件を守る規律である。
principles の [modeling](../principles/modeling.md) が定める、不正な状態の排除・境界での parse を、全系の型の扱いとして具象化する。
全系を貫く鎖は一つである。
境界で一度だけ外部の表現を型へ変換し、通った値だけが内側へ入り、内側は再検証せず型が保証する。

## 不正な状態を型で構築できなくする

### 要求
全系の状態を表す型に、[modeling](../principles/modeling.md) の「不正な状態を表現できなくする」を適用する。
状態の追加や変更の漏れが、型検査に現れる形に保つ。

### 根拠
表現できる状態が業務上ありうる状態より多いと、全系のどこかで不正な状態が生まれる。
各処理が同じ前提検査を書かされるのは、型が緩い兆候である。
状態を型で絞れば前提検査は不要になり、状態の追加は網羅の漏れとして型検査に現れる。

### 完了条件
全系の状態を表す型に業務上ありえない値の組み合わせが構築できないことの判定は、[modeling](../principles/modeling.md) の完了条件に従う。
場合分けの網羅が [construction](../principles/construction.md) の定めで判定されている。

### 禁止事項
網羅の判定を型検査の外へ逃がすことは、[construction](../principles/construction.md) の禁止事項に従う。

### 行動
状態を表す型ごとに、表現可能な状態数と業務上 valid な状態数を比べる。
余剰があれば判別子つきの直和へ組み替え、状態固有のデータを各ケースへ移す。
分岐は網羅で書き、既定の枝で未知の状態を受けない。

### 例

二つの任意項目で状態を表すと四つの組み合わせを構築できるが、正しい状態は二つしかない。各処理で前提条件の検査が必要になる。

```
type Target = { email?: Address; toAll?: boolean }
```

直和型なら正しい状態だけを構築でき、受け手が扱うのも二つのケースだけになる。

```
type Target = { kind: "all" } | { kind: "specific"; email: Address }
```

## 境界で一度だけ parse する

### 要求
外部から入る値の検証は、[modeling](../principles/modeling.md) の「境界で検証して型に通す」に従う。
どの経路の入力も一つの変換器の集合を通して検証済みの型へ変換し、内側では再検証しない。
一つの検証済みの型に対して外部の表現の形式が複数あるときは、その形式が並走する区間を最短にする。

### 根拠
外部入力は HTTP・CLI・メッセージ・外部 API など複数の経路から入り、経路ごとに別々の検証基準を持つと、通った値の信頼度が経路によって揺れる。
経路を横断して一つの変換器の集合に検証を集約すれば、全系を貫く鎖が一つに保たれる。
一つの検証済みの型に対して外部の表現の形式が複数並走すると、どの形式を扱っているかの判別が要る。
並走する区間が長いほどその判別が内側へ漏れ、内側が型の保証だけで済まなくなる。
境界で検証相と実行相を分ける理由は [modeling](../principles/modeling.md) に従う。
自システムが検証して保存したデータの読出しも同じ変換器を通すが、その不正は外部入力の不正でなく欠陥である。
不正と欠陥の判別は [effect](./effect.md) に従う。
形式の検証は境界で行い、資源の照会を要する検証は方針の側で行う。
検証の証明責任は、必要な範囲で最も上流の境界に置く。
利用者の入力補助のための検証は契約の検証と目的が異なり、前者があっても後者を省かない。

### 完了条件
HTTP・CLI・メッセージ・外部 API のどの経路も、同じ変換器の集合を通って検証済みの型になっている。
内側の処理が未検証の生の値を受け取らないことの判定は、[modeling](../principles/modeling.md) の完了条件に従い、外部の表現を写した DTO を未検証の生の値に含める。
証明責任が、必要な範囲で最も上流の境界に置かれている。
資源の照会を要する検証が、境界の変換器でなく方針の側で行われている。
一つの検証済みの型に対して複数の形式が並走する区間が、境界のモジュールに閉じている。

### 禁止事項
境界の検証を迂回して、外部の値を検証済みの型として構築すること。
入力補助の検証があることを理由に、契約の境界の検証を省くこと。
一つの検証済みの型に対する複数の形式の判別を、境界のモジュールより内側へ持ち込むこと。

### 行動
外部との接点を境界として特定し、そこに変換器を一つ置く。
未検証の型と検証済みの型を分け、検証済みの型は変換器を通してしか構築できないようにする。
経路が増えたら、既存の変換器の集合へ、その経路を検証済みの型に変換する処理を加える。

### 例

境界の変換器を通った型だけを内側へ渡す。内側では型が検証済みであることを保証するため、再検証しない。

```
parseUser(input: unknown): ValidUser | Error
sendWelcome(user: ValidUser)
```

## 型の情報を失う箇所を監査する

### 要求
外部入力は、操作の前に絞り込みを強制する型で受ける。
型の情報を失う操作は、外界へ報告する最外の境界だけに閉じ、存在箇所を漏れなく監査できるようにする。

### 根拠
内側で型検査を切ると、その点から先へ型が情報を伝播できなくなる。
外界への報告で型の情報を保てない場合も、最外の境界に閉じれば、内側の型安全を保ったまま例外的な箇所を監査できる。
外部入力を、操作前に絞り込みを強制する型で受ければ、検証を省けない。

### 完了条件
外部入力が、無条件には操作できない型で受けられ、絞り込みを経て使われている。
型の情報を失う操作が、外界へ報告する最外の境界だけに存在する。
型の情報を失う箇所が、漏れなく列挙され、監査できる。

### 禁止事項
外界へ報告する最外の境界より内側で、型の情報を失うこと。
外部入力を、絞り込みなしで操作できる型として受けること。

### 行動
外部入力を、操作前に絞り込みを強制する型で受ける。
型の情報を失う箇所を洗い出し、外界へ報告する最外の境界へ移す。
残した箇所を列挙し、内側に漏れがないことを監査する。

### 例
```
内部の失敗: 内側では具体的な型の情報を保つ
外界への報告: 最外の境界だけで外界の報告形式へ変換し、その箇所を監査対象として記録する
```
