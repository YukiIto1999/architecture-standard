## 抽象を方針側が所有する

### 要求
方針が必要とする抽象は、方針のパッケージ側に置き、詳細がそれを実装する。
抽象は、方針が必要とする操作だけに絞る。
関数の引数の型も、受け手が必要とする性質だけに絞る。

### 根拠
方針が必要としない操作まで持つ太い汎用の抽象は、方針に不要な知識を負わせる。
業務規則ごとに必要な分だけの抽象を切れば、変更の波及が小さくなる。
抽象の所有を方針側に置く理由は、[separation](../../principles/separation/stable-abstract-dependencies.md) に従う。
絞った抽象は、意味のあるまとまりとして名付けられなければならず、名付けられない切り方は分割の誤りである。
絞り込みは、内部の関心が呼び出し側へ漏れない範囲に留める。

### 完了条件
抽象が、方針の必要とする操作だけを宣言している。
詳細の実装が、方針の抽象に依存している。
関数の引数の型が、受け手が必要とする性質だけに絞られている。

### 禁止事項
抽象の所有を、詳細の側へ譲ること。
全機能を露出する太い汎用の抽象を、内側に置くこと。
受け手が必要としない性質まで持つ広い引数の型を渡すこと。

### 行動
方針が必要とする操作を洗い出し、その分だけの抽象を方針側に定義する。
詳細にその抽象を実装させ、方針が詳細の名前を知らない状態を保つ。

### 例

方針側は、その方針に必要な操作だけを持つ抽象を所有する。

```
interface RateRepository { find(id: SkuId): Rate }
```

全 CRUD を公開する汎用の `Repository<T>` は内側へ置かない。
