## 整合性を一つの書き込みパスに閉じる

### 要求
同時に守らなければ不正となる整合性は、一つの書き込みパスに閉じる。
その範囲を一つの集約に一致させ、複数の集約にまたがる整合性はイベントによる結果整合性で保つ。
集約は不変条件が及ぶ範囲で決め、複数の関係の行を含んでよく、書き込みパスの一回の確定は、一つの集約か、両方の集約に属する期間を書く確定ではその期間が属する集約だけを変える。
二つの集約の期間の内側にある期間は、その期間の集合に件数の不変条件を持つ側の集約が所有する。
一意制約のようにデータ層の宣言が守る件数の条件は、書き込み経路が検証しないので、所有と鍵を決める件数の不変条件に数えない。
両側の集約がその期間の集合に件数の不変条件を持つ場合は、その期間を両方の集約に属するものとし、その期間を始める書き込みと閉じる書き込み(予定した終わりを定める業務事実とその取り消しの追記を含む)は、両方の集約の鍵を排他で取って一つの確定で行い、その確定ではその期間の行と、同じ操作が変えるそれらの集約の行だけを書き、外側の期間は内側の期間を閉じてから閉じる。
一つの操作が外側の期間を閉じるのに伴って両方の集約に属する内側の期間を多数閉じる場合(開催回の中止がその回の予約を全て閉じるなど)は、閉じる期間が属する全ての集約の鍵を全順序で排他に取り、内側の期間と外側の期間を一つの確定で閉じる。
どちらの集約も件数の不変条件を持たない場合は、所有する集約を一つに決め、決定の記録に残す。
同じ集約へ書き込む経路は、利用者の操作、管理操作、バッチ、イベントの消費、移行のいずれであっても、その集約の書き込みパスを通す。
集約の判定の対象についての競合制御は、集約ごとに一つを選び、その集約へ書き込む全ての経路が同じ制御を通す。
関係をまたぐ排他や複数の行にまたがる条件を持つ集約は、集約の鍵を排他で取って直列化し、鍵の後に今の状態を検証して、検証から確定までの間に他の書き込みを入れない。
集約の鍵は、書き込み経路に事実の行への更新権限を与えずに取れる形で取る。
集約の鍵で競合制御する集約では、集約の判定の対象、つまり期間の開閉と件数の不変条件にかかわる行と書き込みの検証が条件として読む行を、挿入または削除する書き込みと、検証が読む列を更新する書き込みは、その集約の鍵を排他で取る。
判定の対象でない行だけを書く書き込みと、検証が読まない列だけを更新する書き込みは、その書き込みの条件を確かめるための共有の鍵で足り、条件がなければ鍵を取らない。
共有の鍵か鍵なしで更新する可変属性の行は、同じ行への同時の更新をその行の版で検出する。
別の集約の判定の対象を条件にする書き込みは、その集約の鍵を共有で取る。
ただし、自分の集約の鍵を排他で取り、その条件を満たさなくする全ての書き込みが自分の集約の鍵を共有か排他で取ると列挙できる場合は、相手の集約の鍵を省いてよい。
新しく採番した識別子で集約を始める書き込みは、確定するまで他の検証から見えないので、その集約の鍵を取らない。
鍵の値を決めるために、書き換えないキーの行と、削除や一括処理の候補の一覧を鍵より前に読んでよいが、検証は鍵の後に同じ条件で行い、鍵の後の候補に鍵を取っていない対象があれば、確定せずに鍵を取り直す。
一つの書き込みが複数の鍵を取る場合は、全ての書き込み経路で同じ一つの全順序に従って取り、多数の鍵は全順序に並べて一つの問い合わせで取る。
集約の鍵で競合制御する集約の検証は、鍵を待った後に直前の確定を読める読取条件で行い、鍵を取る前の snapshot による検証結果を使わない。
期間が開いているかに依存する認可は、[authorization](../authorization/evaluate-at-entry.md) の「入口で評価し、通った要求だけ進める」が定める対象を取り出す境界の評価として、鍵の後に、書き込みと同じ確定の中で行う。
一つの行の更新または業務事実の関係への追記だけで判定の対象の条件が閉じる集約は、可変属性の更新の条件に版を付けるか、業務事実の追記を識別子と版の一意制約で拒むかで、衝突を検出してよい。
同じ集約への同時の更新は、直列化するか版の衝突として検出し、後の書き込みが前の更新を失わせない。

### 根拠
集約とトランザクション境界の一致の理由は [data](../../principles/data/aggregate-integrity.md) に従う。
集約が複数の関係を含んでも、確定が一つの集約に閉じていれば、トランザクションが集約をまたぐ結合は増えない。
件数の不変条件は、要素の集合を持つ一つの集約の鍵の下でしか検証できないので、その集合に属する内側の期間をその集約が所有する。
所有しない側の外側の期間の終わりで内側を暗黙に閉じると、所有する側の件数の不変条件を検証しないまま要素が減る。
両側が件数の不変条件を持つ期間は、どちらに所有させても他方の不変条件を同じ確定で検証できないので、両方の集約に属させ、両方の鍵の下で書く。
両方の鍵を持つ確定で同じ操作が変える二つの集約の行も書けば、その操作の残りを結果整合で運ぶ必要がない。
外側の期間の終わりに伴う多数の内側の期間の終わりを期間ごとの確定に分けると、途中で止まった操作が、外側の終わりを理由に閉じた内側の期間と、開いたままの外側の期間を残す。
同じ集約を同時に更新すると、後の書き込みが前の更新を失わせる。
競合制御を集約ごとに一つ定めて経路の種類を問わず通せば、どの経路から書いても同じ条件で直列化されるか衝突として検出される。
一部の経路だけが従うと、その経路と他の経路が互いの確定前の状態を見て、それぞれが正しい検証を通りながら不変条件を破る。
複数の行にまたがる条件は、各行の版だけでは守れないので、全ての経路が共通に取る集約の鍵が要る。
同じ利用者に開いた停止を二つ作らないことのように、外部キーでは拒めない条件も、集約の鍵を排他で取ってから検証して守る。
行の排他のために事実の行への更新権限を与えると、その権限で事実の行を書き換えられるので、鍵は書き込み権限と切り離して取る。
判定の対象を変える書き込みを全て排他にすれば、書き込みごとに条件を崩しうるかを分析せずに済み、規則が書き込みごとの判断に依存しない。
条件を満たさなくする書き込みが全て自分の集約の鍵を取るなら、自分の鍵を排他で取るだけでそれらと直列になり、相手の鍵を取る必要がない。
採番したばかりの識別子の集約は確定するまで他から見えないので、競合する書き込みがない。
共有の鍵では同じ行への同時の更新が直列にならないので、可変属性の行は版で後の更新が前の更新を失わせないようにする。
鍵を一つの全順序で取れば、鍵どうしの待ちが循環せず、デッドロックが起きない。
認可を入口だけで判定すると、判定から書き込みまでの間に期間が閉じうる。
版を確かめて確定すれば、間に変わった更新を検出して失わない。
版の衝突として検出できることは、同時に競合が起きた事実を書き込みパスの外へ露わにする。

### 完了条件
同時に守る整合性が、一つの書き込みパスの内で検証されている。
二つの集約の期間の内側にある期間ごとに、所有する集約、または両方の集約に属することと、閉じ方が決定の記録から追える。
同じ集約へ書き込む全ての経路が、その集約の書き込みパスを通り、関係を直接書き換える経路が残っていない。
集約に定めた競合制御が、全ての経路で同じ方式として実装されている。
集約の鍵で競合制御する集約で、判定の対象を変える全ての書き込みが、その集約の鍵を排他で取っている。
書き込み経路が、鍵を取るために事実の行への更新権限を持っていない。
複数の鍵を取る書き込みが、全ての経路で同じ全順序に従っている。
競合する二つの書き込みを同時に実行しても、片方が待たされて検証をやり直すか衝突として失敗し、両方が確定して不変条件を破る組が起きない。
関係をまたぐ排他の検証と、期間に依存する認可が、鍵の後に、直前の確定を読み取れる条件で、変更と同じ確定の中で行われている。
同じ集約への同時の更新が、直列化されるか版の衝突として検出され、片方の更新を失わない。
共有の鍵か鍵なしで更新する可変属性の行が、版で同時の更新を検出している。
版で衝突を検出する集約では、検出が可変属性の更新の条件または業務事実の関係への同じ版の重複の追記を拒む一意制約で行われている。

### 禁止事項
同時に守る整合性の判断を、複数の書き込みパスへ分けること。
一つの書き込みパスの確定で、書く期間が属する集約のほかに、複数の集約を同時に変更すること。
管理操作、バッチ、移行が、集約の書き込みパスを迂回して関係を直接書き換えること。
件数の不変条件を持つ集約が所有する期間を、別の集約の期間の終わりで暗黙に閉じること。
鍵を取るためだけに、事実の行への更新権限を書き込み経路に与えること。
集約の鍵で競合制御する集約の判定の対象を変える書き込みを、その集約の鍵を排他で取らずに確定すること。
複数の鍵を、経路ごとに異なる順序で取ること。
鍵も版の一致も確定の条件にせずに読んだ状態で検証し、その結果を根拠に変更を確定すること。
期間に依存する認可を、鍵の前や確定の外だけで判定すること。

### 行動
同時に守る不変条件を洗い出し、それが及ぶ範囲を一つの集約と一つの書き込みパスに収める。
二つの集約の期間の内側にある期間ごとに、件数の不変条件を持つ側を確かめ、所有する集約か両方の集約に属することと、閉じ方を決定の記録に残す。
集約ごとに、集約の鍵と版の検査のどちらで競合制御するかを選び、鍵の値と取る順序を定める。
その集約へ書き込む全ての経路を書き出し、書き込みパスを通らない経路を見つけたら、書き込みパスの呼び出しへ置き換える。
集約の鍵で競合制御する集約では、書き込みごとに、判定の対象を変えるかを確かめ、変えるものは排他、条件を読むだけのものは共有で鍵を取る。
関係をまたぐ排他と期間に依存する認可は、鍵を取った後に検証してから変更する。
排他で直列化しない集約の同時の更新は、可変属性の更新を版で条件付けるか、業務事実の追記を識別子と版の一意制約で拒み、衝突として検出する。

### 例

一度の書き込みで複数の集約を変更すると、競合と結合が増える。

```
transaction { order.place(); inventory.reserve(); }
```

一つの集約だけを変更し、`OrderPlaced` を outbox へ記録する。
在庫は別集約のトランザクションでイベントを受け、結果整合的に引き当てる。

```
transaction { order.place() }
```

組織に管理者を一人以上置く条件を、鍵を取らずに条件付きの削除だけで守ると、二人の管理者のロールを同時に外す二つの経路が互いの確定前の状態を見て、どちらも成功する。

```text
transaction:
  remove membershipRole(membershipId, adminRole)
    where exists other current membership in organizationId with adminRole
```

所属とロールの付与は組織の集約に属するので、ロールを外す全ての経路が組織の集約の鍵を排他で取り、直前の確定を読める読取条件で、外した後も管理者が残ることを確かめる。
後の経路は先の経路の確定を待ってから検証するので、最後の管理者のロールを外す書き込みは確定しない。
鍵は事実の行への更新権限を要しない形で取り、管理操作とバッチを含む全ての経路がこの手順を通る。

```text
transaction (read committed):
  exclusive organizationAggregate(organizationId)
  require membershipId is a current membership of organizationId
  remove membershipRole(membershipId, adminRole)
  require exists current membership in organizationId with adminRole
```
