## 整合性を一つの書き込みパスに閉じる

### 要求
同時に守らなければ不正となる整合性は、一つの書き込みパスに閉じる。
その範囲を一つの集約に一致させ、複数の集約にまたがる整合性はイベントによる結果整合性で保つ。
集約は複数の関係の行を含んでよく、書き込みパスの一回の確定は一つの集約だけを変える。
同じ集約へ書き込む経路は、利用者の操作、管理操作、バッチ、イベントの消費、移行のいずれであっても、その集約の書き込みパスを通す。
競合制御は、集約ごとに一つを選び、その集約へ書き込む全ての経路が同じ制御を通す。
関係をまたぐ排他や複数の行にまたがる条件を持つ集約は、親の行を排他して直列化し、排他の後に現在の状態を検証して、検証から確定までの間に他の書き込みを入れない。
その検証は、ロックを待った後に直前の確定を読める読取条件で行い、排他前の snapshot による検証結果を使わない。
一つの行の更新または業務事実の列への追記だけで条件が閉じる集約は、現在関係の更新の条件に版を付けるか、業務事実の追記を識別子と版の一意制約で拒むかで、衝突を検出してよい。
同じ集約への同時の更新は、直列化するか版の衝突として検出し、後の書き込みが前の更新を失わせない。

### 根拠
集約とトランザクション境界の一致の理由は [data](../../principles/data/aggregate-integrity.md) に従う。
集約が複数の関係を含んでも、確定が一つの集約に閉じていれば、トランザクションが集約をまたぐ結合は増えない。
同じ集約を同時に更新すると、後の書き込みが前の更新を失わせる。
競合制御を集約ごとに一つ定めて経路の種類を問わず通せば、どの経路から書いても同じ条件で直列化されるか衝突として検出される。
一部の経路だけが従うと、その経路と他の経路が互いの確定前の状態を見て、それぞれが正しい検証を通りながら不変条件を破る。
複数の行にまたがる条件は、各行の版だけでは守れないので、全ての経路が共通に排他する親の行が要る。
現在関係の行と退会の業務事実のように、外部キーでは両立を拒めない二つの関係の排他も、共通の親の行を排他してから検証して守る。
版を確かめて確定すれば、間に変わった更新を検出して失わない。
版の衝突として検出できることは、同時に競合が起きた事実を書き込みパスの外へ露わにする。

### 完了条件
同時に守る整合性が、一つの書き込みパスの内で検証されている。
同じ集約へ書き込む全ての経路が、その集約の書き込みパスを通り、関係を直接書き換える経路が残っていない。
集約に定めた競合制御が、全ての経路で同じ方式として実装されている。
競合する二つの書き込みを同時に実行しても、片方が待たされて検証をやり直すか衝突として失敗し、両方が確定して不変条件を破る組が起きない。
関係をまたぐ排他の検証が、親の行の排他の後に、直前の確定を読み取れる条件で、変更と同じ確定の中で行われている。
同じ集約への同時の更新が、直列化されるか版の衝突として検出され、片方の更新を失わない。
版で衝突を検出する集約では、検出が現在関係の更新の条件または業務事実の関係への同じ版の重複の追記を拒む一意制約で行われている。

### 禁止事項
同時に守る整合性の判断を、複数の書き込みパスへ分けること。
一つの書き込みパスの確定で、複数の集約を同時に変更すること。
管理操作、バッチ、移行が、集約の書き込みパスを迂回して関係を直接書き換えること。
排他を取らずに読んだ状態で検証し、その結果を根拠に変更を確定すること。

### 行動
同時に守る不変条件を洗い出し、一つの集約と一つの書き込みパスに収める。
集約ごとに、親の行の排他と版の検査のどちらで競合制御するかを選び、親の行を特定する。
その集約へ書き込む全ての経路を書き出し、書き込みパスを通らない経路を見つけたら、書き込みパスの呼び出しへ置き換える。
関係をまたぐ排他は、親の行を排他した後に検証してから変更する。
排他で直列化しない集約の同時の更新は、現在関係の更新を版で条件付けるか、業務事実の追記を識別子と版の一意制約で拒み、衝突として検出する。

### 例

一度の書き込みで複数の集約を変更すると、競合と結合が増える。

```
transaction { order.place(); inventory.reserve(); }
```

一つの集約だけを変更し、`OrderPlaced` を outbox へ記録する。在庫は別集約のトランザクションでイベントを受け、結果整合的に引き当てる。

```
transaction { order.place() }
```

組織に管理者を一人以上置く条件を、条件付きの更新だけで守ると、二人の管理者を同時に降格する二つの経路が互いの確定前の状態を見て、どちらも成功する。

```sql
BEGIN;
  UPDATE memberships SET role = 'member'
   WHERE user_id = :user_id AND organization_id = :organization_id
     AND EXISTS (
       SELECT 1 FROM memberships other
        WHERE other.organization_id = :organization_id
          AND other.role = 'admin'
          AND other.user_id <> :user_id
     );
COMMIT;
```

この例は PostgreSQL の READ COMMITTED を明示し、組織の行の排他を取得した後に別の文で条件を検証する。
全経路がこの手順を通れば、後の経路の検証は先の確定を読み、最後の管理者を降格する更新は0件になる。
更新が0件なら確定せず、衝突として失敗させる。
管理操作とバッチを含む全ての経路が、この手順を通る。

```sql
BEGIN ISOLATION LEVEL READ COMMITTED;
  SELECT id FROM organizations WHERE id = :organization_id FOR UPDATE;
  UPDATE memberships SET role = 'member'
   WHERE user_id = :user_id AND organization_id = :organization_id
     AND EXISTS (
       SELECT 1 FROM memberships other
        WHERE other.organization_id = :organization_id
          AND other.role = 'admin'
          AND other.user_id <> :user_id
     );
COMMIT;
```
