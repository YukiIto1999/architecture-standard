# effect

## 概要
effect は、副作用の統合を全系で統べる親規律であり、効果システムを定める。
効果システムは、生成と合成、要求する依存、想定内の失敗と欠陥と取り消し、資源、境界での解釈を、効果の代数として備える。
副作用は、遅延した効果の記述として組み、純粋核を包まない。
要求する依存と想定内の失敗を型に現し、実行は runtime の境界に限る。
効果が要求する依存の配線は、[dependency](./dependency.md) に従う。
principles の [construction](../principles/construction.md) が定める不変と変換パイプラインと、[separation](../principles/separation.md) が定める副作用の境界隔離を、全系の効果の扱いとして具象化する。
非同期と取り消しは [concurrency](./concurrency.md) へ委譲する。
失敗の直和の網羅と構築の規律は、[types](./types.md) の「不正な状態を型で構築できなくする」に従う。

## 純粋核と効果の殻に分ける

### 要求
純粋核と効果の殻の分離は、[separation](../principles/separation.md) の「副作用を境界に集める」に従う。
純粋核は効果の記述で包まず、純粋な値と関数のままにする。
処理は、読む・判断する・書く、の順に並べ、書き始めたら入力の読みへ戻らない。

### 根拠
核と殻を分ける理由と、殻だけが核を呼べる非対称は、[separation](../principles/separation.md) に従う。
この非対称が、核と殻の配置を一意に決める。
純粋な核を効果の記述で包むと、不要な殻の語彙が核に侵入し、再現性と単純さを損なう。
読む・判断する・書くの順を崩し、書いた後にまた読むと、状態への依存が増えて複雑になる。

### 完了条件
シグネチャに入出力の型が現れない処理が、すべて純粋な核に置かれている。
純粋な核が、効果の記述で包まれていない。
殻が薄く、業務判断を持たない。
処理が、読む・判断する・書くの順に並んでいる。

### 禁止事項
純粋な核を、効果の記述で包むこと。
判断と効果の記述を、同じ関数に混ぜること。
書き込みを始めた後に、入力の読み出しへ戻ること。

### 行動
関数ごとに、入出力の型が要るかを見る。
要らなければ核へ、要れば殻の読みか書きへ分類する。
判断を純粋な関数へ切り出し、決定を値で返させ、入出力は殻へ移す。

### 例

読み取りと書き込みを殻へ置き、核は受け取った値から判断だけを返す。

```
existing = read(input)
decision = decide(existing, input)
write(decision)
```

## 効果を遅延した記述にして端で実行する

### 要求
副作用を伴う計算は、生成では実行されない遅延した記述として組み、実行を runtime の境界に限る。

### 根拠
記述は値なので、合成し、再試行し、差し替えても、その時点では副作用が起きない。
実行を境界に集めると、どこで副作用が起きるかが一箇所で読め、内側は副作用の起動を持たない。
生成と同時に実行する形は、合成も再試行も差し替えもできず、副作用がコード全体に散る。

### 完了条件
副作用を伴う計算が、生成では実行されない遅延した記述になっている。
記述の実行が、runtime の境界に限られている。
内側の層が、記述を実行していない。

### 禁止事項
生成と同時に副作用を起動する計算を、内側の層に置くこと。
記述の実行を、境界の外へ散らすこと。

### 行動
内側の層で生成と同時に副作用を起動している箇所を、洗い出す。
副作用を伴う計算を、遅延した記述として返し、合成する。
記述の実行を、入口の組立点に集める。

### 例

値を生成した時点で処理を実行すると、処理の合成も差し替えもできない。

```
const user = fetchUser(id)
```

処理を遅延した記述として構築し、境界の `run` でだけ実行する。

```
const program = fetchUser(id)
run(program)
```

## 要求と想定内失敗を型に現す

### 要求
効果の記述は、要求する依存と、想定内の失敗と、成功の値を型に現す。
要求する依存は、計算ごとに必要な分だけを型に宣言する。

### 根拠
要求する依存が型に出ると、計算が何を必要とするかをシグネチャだけで読め、不足が型検査に出る。
想定内の失敗が型に出ると、呼び出し側は全ての失敗を型で受け、漏れが型検査に出る。
依存を型に宣言すると、テストで別の実装を渡して差し替えられる。
依存を全部入りの単一の環境にすると、全ての計算が全てを要求するように見え、必要な分だけの宣言が崩れる。
依存をその場で名前で取り出すと、型付きの service locator になり、要求が型に出ない。
要求の宣言は効果の型で行い、その実装の配線は [dependency](./dependency.md) に従う。

### 完了条件
効果の記述の型に、要求する依存と想定内の失敗と成功の値が現れている。
各計算が、必要な依存だけを型に宣言している。
テストで、要求する依存を別の実装に差し替えられる。

### 禁止事項
要求する依存を、型に出さず暗黙のグローバルや単一の環境から取ること。
想定内の失敗を、型に出さずに送出すること。
依存を名前で取り出す、型付きの service locator を作ること。

### 行動
計算ごとに、必要な依存を型へ宣言し、想定内の失敗を結果の型に出す。
本番とテストで、要求する依存の実装を差し替える。

### 例

依存と失敗を型に出さないと、処理が何を要求するのかシグネチャから読めない。

```
register(command): UserId
```

要求する依存、失敗、成功値を型へ現す。

```
register(command): Effect<requires {Clock, Users}, RegisterFailure, UserId>
```

## 失敗と欠陥と取り消しを分ける

### 要求
効果の終了を、成功・想定内の失敗・欠陥・取り消しに分ける。
想定内の失敗は失敗の型で表し、欠陥と取り消しを失敗の型に混ぜない。
外部へ公開するエラーは、境界で標準の形へ写す。

### 根拠
終了を四つに分けると、想定内の失敗と回復できない欠陥と取り消しを、一つの結果型に潰さず区別できる。
欠陥は回復できないプログラムの誤りなので、失敗の型に混ぜず、別の終了として速やかに失敗させる。
取り消しは失敗でも成功でもないので、別の終了として扱う。
欠陥や取り消しを失敗の型に潰すと、情報が落ち、回復できない誤りを回復できる失敗と取り違える。
対象の不在は、理由が要らなければオプション型で表し、理由が要ればドメインの失敗として表す。
外部へ公開するエラーは、境界で標準の形へ写し、内部の詳細を漏らさない。

### 完了条件
効果の終了が、成功・想定内の失敗・欠陥・取り消しに分かれている。
想定内の失敗が、網羅された失敗の型で表されている。
欠陥と取り消しが、失敗の型に混ざっていない。
外部へ公開するエラーが、境界で標準の形へ写され、内部の詳細を含まない。

### 禁止事項
欠陥や取り消しを、想定内の失敗の型に混ぜること。
想定内の失敗を、欠陥として送出すること。
外部へ公開するエラーに、スタックトレースや内部の詳細を含めること。

### 行動
終了を、成功・想定内の失敗・欠陥・取り消しに仕分ける。
想定内の失敗を網羅した型にし、欠陥と取り消しを別の終了に分ける。
境界で、内部のエラーを標準の形へ写し、内部の詳細を落とす。

### 例

終了は、成功、型で網羅した想定内の失敗、回復不能な欠陥、取り消しに分ける。欠陥と取り消しを想定内の失敗へ混ぜない。

```
成功 | 想定内の失敗(網羅した直和) | 欠陥(回復不能) | 取り消し
```

外部へ公開する形式への変換は境界で行い、内部の詳細を含めない。形式は contracts の binding が定める。

```
toProblemDetails(failure)
```

## 失敗と欠陥を値の出所で判別する

### 要求
失敗と欠陥は、値の出所で判別する。
境界を越えて入る外部入力の不正は、想定内の失敗とする。
検証済みで保存した内部データの破損と、自ら直列化し自ら復元する処理の不一致は、欠陥とする。

### 根拠
[types](./types.md) の規律により、境界を一度通った値は内側で再検証されず、型がその正しさを保証する。
内側の奥で値の破損が見つかるのは、その保証が破れた場合であり、外部から新たな不正が混ざったのではない。
外部入力の不正は、まだ境界の変換を経ていない値に生じるため、想定内の失敗として型で受け止められる。
自ら直列化し自ら復元する処理の不一致も、外部からの入力を経由しないため、実装の誤りであり欠陥である。
値の出所で判別すれば、壊れた値の形が同じでも、境界の外か内かで終了の種類が一意に決まり、判断のたびに裁量で揺れない。

### 完了条件
効果の終了が、値の出所を基準に想定内の失敗と欠陥へ振り分けられている。
境界を越える前に生じた値の不正が、想定内の失敗として扱われている。
境界を越えた後に見つかった値の破損が、欠陥として扱われている。
同種の出所のエラーが、全コンテキストで同じ終了へ写像されている。

### 禁止事項
値の出所を確かめず、エラーの見た目や型の一致だけで失敗と欠陥を選ぶこと。
同じ出所のエラーを、コンテキストによって異なる終了へ振り分けること。
境界を越えた後に見つかった値の破損を、想定内の失敗として扱うこと。

### 行動
エラーを終了へ仕分ける前に、その値が境界を通る前に生じたか、通った後に生じたかを確かめる。
境界を通る前に生じた値の不正は、想定内の失敗の型へ運ぶ。
境界を通った後に見つかった値の破損や、自ら直列化し自ら復元する処理の不一致は、欠陥として速やかに終了させる。

### 例

境界の外から届いた不正な入力は、想定内の失敗として扱う。

```
parseOrder(input: unknown): Result<Order, ValidationFailure>
```

境界の内側で検証済みの値を読み出せない場合は、型の保証が破れた欠陥として終了する。

```
loadOrder(id: OrderId): Order
```

## 取り消しと資源を言語の機構に委ねる

### 要求
取り消しは計算全体へ伝播させ、その協調の仕方は [concurrency](./concurrency.md) に従う。
資源は、取得と使用と解放を一つの効果に閉じ、失敗と取り消しの下でも解放する。
並行の駆動とスケジューリングは、[concurrency](./concurrency.md) の「並行の駆動を言語の機構に委ねる」に従う。

### 根拠
取り消しを計算全体へ伝播させると、諦めた計算が走り続けず、資源が放置されない。
効果の記述は遅延した薄い値で、境界の runtime が言語の async と取り消しで駆動する。
記述に言語の取り消しの合図を通すだけで足りる。
資源の解放を効果に閉じると、失敗や取り消しでも解放が漏れない。

### 完了条件
取り消しの合図が、記述の全体へ伝播している。
資源の取得と使用と解放が一つの効果に閉じ、失敗と取り消しでも解放されている。
伝播の細部の判定は、[concurrency](./concurrency.md) の完了条件に従う。

### 禁止事項
資源の解放を、失敗や取り消しの経路で漏らすこと。

### 行動
取り消しを計算全体へ通し、言語の取り消し機構へ委ねる。
資源を、取得と使用と解放を閉じた一つの効果として扱う。

### 例

取得、使用、解放を一つの効果に閉じ、失敗や取り消しでも解放する。取り消しは計算全体へ伝え、処理は言語の機構に委ねる。

```
withResource(acquire, use, release)
```

## 合成して部分代替できるようにする

### 要求
失敗しうる処理は、合成できる段の連なりとして組む。
純粋な判断は Result の段で、効果は記述の段で連ねる。
途中の失敗・欠陥・取り消しは後段を短絡して伝播させ、握り潰さない。
各段を差し替え・追加・除去できる形にする。

### 根拠
各段が Result または効果の記述で、成功と失敗の二線で連なるので、合成でき、差し替え・追加・除去ができる。
失敗・欠陥・取り消しが後段を短絡して伝播すると、誤った状態のまま処理が進まない。
途中の失敗を握り潰すと、誤った状態のまま処理が続く。

### 完了条件
処理が、Result または効果の記述の段の連なりとして組まれている。
途中の失敗・欠陥・取り消しが、後段へ伝播し、握り潰されていない。
各段が独立した記述で、差し替え・追加・除去ができる。

### 禁止事項
途中の失敗・欠陥・取り消しを、握り潰して処理を続けること。
成功と失敗の分岐を、一つの関数に手続き的に散らすこと。

### 行動
処理を、効果の記述の段に分け、連ねて合成する。
途中の失敗・欠陥・取り消しは後段へ短絡させ、起点の読みと終点の書きを殻に置く。

### 例

各段を純粋な `Result` の連なりとして構成する。失敗は後段を短絡して伝播し、読み取りと書き込みの効果は殻へ置く。

```
validate(input) |> flatMap(decide) |> map(toEvents)
```
