# authorization

## 概要
authorization は、アクセス制御の流れを全系で統べる規律である。
principles の [separation](../principles/separation.md) が定める変更理由での分割・関心の隠蔽・副作用の隔離を、全系のアクセス制御として具象化する。
authorization は認証境界による構築済みの actor の権限評価を扱い、資格情報の検証と actor の構築は [authentication](./authentication.md) が扱う。

## 業務規則と認可を分ける

### 要求
誰であるかに依らない業務規則は業務の核の不変条件に置き、誰に何を許すかのアクセス制御は認可の判定に置く。
同じ規則を、両方に持たない。
認可の規則は、テストで検証する。

### 根拠
業務規則とアクセス制御は、変わる理由が違う。
両方に同じ規則を持つと、片方だけ変えて食い違う。
誰に依らない不変条件は核が守り、誰に何を許すかは認可が判定する、と分ければ、各々を独立に変えられる。

### 完了条件
誰に依らない業務規則が、業務の核の不変条件として置かれている。
誰に何を許すかが、認可の判定に置かれている。
同じ規則が、両方に重複していない。
認可の規則が、テストで検証されている。

### 禁止事項
同じ規則を、業務の核と認可の判定の両方に持つこと。

### 行動
規則ごとに、誰に依らないか、誰に何を許すかを見分ける。
前者は業務の核へ、後者は認可の判定へ置く。

### 例

役割の判定を業務の核へ入れると、認可と業務規則が混ざる。

```
function cancel(order, user) { if (user.role !== "admin") throw; if (order.shipped) throw; }
```

認可は入口に置き、核では「出荷済みの注文は取り消せない」という業務の不変条件だけを判断する。

```
function cancel(order: Order): Result<Order, E> { ... }
```

## 入口で評価し、通った要求だけ進める

### 要求
認可は要求の入口で操作の単位を評価し、評価を通った要求だけが業務の処理へ進む。
個々の対象への操作は、その対象を取り出す境界で対象の単位を改めて評価する。

### 根拠
認可を処理の途中に散らすと、評価の漏れや順序の誤りが生まれる。
入口で一度評価し、通った要求だけを内側へ通せば、内側は操作の認可を前提にできる。
入口の評価は操作の単位までなので、到達してよい操作の中で他人の対象に触れる越権は防げない。
対象を取り出す境界で対象の単位も評価すれば、識別子を差し替えて他人の対象を操作する越権を止められる。

### 完了条件
認可が、要求の入口で操作の単位として評価されている。
個々の対象への操作が、その対象を取り出す境界で対象の単位でも評価されている。
評価を通った要求だけが、業務の処理へ進む。
認可の評価が、入口と対象を取り出す境界に限られ、業務の処理の途中に散っていない。

### 禁止事項
認可の評価を、業務の処理の途中へ散らすこと。
対象の単位の認可を省き、識別子の差し替えで他人の対象を操作させること。

### 行動
認可の評価点を入口に置き、通過した要求だけを内側へ渡す。
対象を取り出す境界を洗い出し、対象の単位の評価が抜けている取り出しを是正する。

### 例

入口で操作だけを認可すると、識別子の差し替えによって他人の対象へ到達できる。

```
function handle(request) { authorize(actor, "orders:read"); return getOrder(request.id); }
```

入口では操作を認可し、対象を取り出す境界ではその対象へのアクセスを認可する。

```
function handle(request) { authorize(actor, "orders:read"); const order = getOrder(request.id); authorize(actor, order); return order; }
```

## 認可の判定を port で委譲する

### 要求
認可の判定は port を通して委譲し、業務の処理は判定の結果だけを受け取る。
判定は、役割・属性・関係などの方針モデルで表し、業務から切り離す。
判定できないときは、拒否に倒す。

### 根拠
認可の判定の詳細を業務に埋め込むと、方針の変更が業務へ波及する。
判定を port の向こうへ委譲すれば、方針を業務と独立に変えられる。
方針を役割・属性・関係で表し、判定点を集めれば、規則が散らばらない。

### 完了条件
認可の判定が、port を通して委譲されている。
業務の処理が、判定の結果だけを受け取っている。
判定の方針が、業務から切り離されている。
判定できないとき、拒否になっている。

### 禁止事項
認可の判定の詳細を、業務の処理へ埋め込むこと。
framework の既定の認可を、この概念の要求と照合せずに信頼すること。
判定不能を、許可へ倒すこと。

### 行動
認可の判定を port の向こうへ出し、業務には許可・拒否の結果だけを渡す。
方針は役割・属性・関係で表し、判定不能のときは拒否へ倒す。

### 例

判定条件を業務へ埋め込むと、認可方針の詳細が核へ漏れる。

```
if (user.roles.includes("admin") || user.dept === order.dept) { ... }
```

判定は port へ委譲し、業務は結果だけを受け取る。

```
interface PolicyPort { decide(actor: Actor, action: Action, target: Target): Decision }
```

## 拒否は業務の前で止める

### 要求
拒否された要求を業務の処理の前で止める定めは「入口で評価し、通った要求だけ進める」に従い、拒否の応答は [effect](./effect.md) が定める外部へ公開するエラーの形に従って汎用的に返す。
対象の存在が機微な文脈では、見つからない場合と許されない場合を外から区別させない。
拒否の詳細は応答でなくサーバ側のログに残す。

### 根拠
拒否を業務の処理の中で扱うと、保護対象に触れてから止めることになる。
入口で止めれば、保護対象に触れない。
拒否の応答に内部の手がかりが載ると、攻撃者に探索の足場を与える。
対象の存在を漏らすと、許否の差から対象の有無を列挙できる。
詳細をサーバ側のログに残せば、クライアントに明かさずに調査と監査ができる。

### 完了条件
拒否の応答の形が、[effect](./effect.md) の外部へ公開するエラーの規律に従っている。
対象の存在が機微な文脈で、見つからない場合と許されない場合が外から区別できない。
拒否の詳細が、サーバ側のログに残っている。

### 禁止事項
拒否の詳細を記録に残さず、調査と監査をできなくすること。

### 行動
拒否は入口で止め、応答の形は [effect](./effect.md) に従う。
詳細はサーバ側のログへ残し、対象の存在が機微な文脈では未検出と未許可を同じ応答にする。

### 例

内部情報やスタックトレースを応答へ載せると、対象の存在や実装の詳細が漏れる。

```
if (!found) return "そのIDの注文は存在しません"; return error(stackTrace)
```

クライアントには汎用の応答を返し、詳細はログへ記録する。機微な文脈では未検出と未許可を区別しない。

```
log({ denied: true, actorId, target, reason }); return forbidden()
```
