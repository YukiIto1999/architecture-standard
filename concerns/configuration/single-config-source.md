## 定めた源からまとめて読む

### 要求
設定は定めた源からまとめて読み込み、環境変数を設定や secret の供給源にしない。
設定の源は、project が定める。
設定の源は、決定の記録に残す。
複数の設定層を一つの源として解決する場合は、層の選択、優先順位、未指定と明示値の区別、競合時の扱いを源の契約として定め、解決後の型付き設定だけを内側へ渡す。
container の配備でも源の規律は変わらず、orchestration が渡す設定ファイルの mount を源にし、環境変数を源にしない。

### 根拠
設定の源が散らばると、どこで何が決まるか追えない。
一つの源にまとめれば、設定の全体を一箇所で読める。
設定の源を決定の記録に残せば、採用した源と変更理由を追える。
読み込みの順序だけで優先順位が決まると、別の入口や呼び出し方で同じ設定の結果が変わるため、解決規則も源とともに固定する。
設定をコードから分けて環境から読む点は広く行われる作法と同じだが、その供給を環境変数に置かない。
環境変数は名前空間が平坦で型がない。
ログやダンプに紛れ、子プロセスへ既定で継承され、誰が変えたか追えない。
だから設定や secret の源にしない。

### 完了条件
container の配備で、orchestration が渡す設定ファイルの mount が設定の源になっている。
設定が、定めた源からまとめて読み込まれている。
設定の源が、決定の記録に残されている。
環境変数が、設定や secret の供給源になっていない。
設定が、コードに焼き込まれていない。
複数層の設定が競合する場合と、未指定、空値、明示的な false または 0 を含む場合の解決結果が、源の契約どおりであることを実行テストで確かめられている。

### 禁止事項
環境変数を、設定や secret の供給源にすること。
設定の源を、決定の記録に残さず運用すること。
設定の優先順位を読み込み順序や各 consumer の判定へ分散すること。

### 行動
設定の源を一つに定め、決定の記録に残す。
定めた源から、起動時に設定をまとめて読み込む。
複数層を解決する場合は、競合する値と未指定を入力にして解決規則を検証し、secret の値を診断へ出さずに採用した源を追跡できるようにする。
