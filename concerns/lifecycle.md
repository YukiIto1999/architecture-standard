# lifecycle

## 概要
lifecycle は、プロセスの起動・健全性の宣言・終了を全系で統べる規律である。
principles の [separation](../principles/separation.md) と [data](../principles/data.md) が定める境界と追記の永続化を、全系のプロセスの寿命の扱いとして具象化する。

## 速く起動し、検証に失敗したら止める

### 要求
プロセスは速く起動し、検証に失敗した起動は直ちに止める。
起動の完了は外部から観測できる形で宣言し、起動の経路で永続化の schema の migration を適用しない。

### 根拠
起動が遅いと、入れ替えや回復が遅くなる。
検証に失敗したまま起動すると、不正な状態で動き出す。
起動の完了を観測できれば、入れ替えの判断ができる。
起動の経路で migration を適用すると、複数のインスタンスが競合し、起動が重く危うくなる。

### 完了条件
起動から準備の宣言までの時間が、project が定めた上限に収まっている。
検証に失敗した起動が、直ちに止まる。
起動の完了が、外部から観測できる形で宣言されている。
起動の経路で、migration を適用していない。

### 禁止事項
起動の経路で、migration を適用すること。
検証に失敗したまま、起動を続けること。

### 行動
起動時に設定と前提を検証し、失敗なら止める。
検証は [configuration](./configuration.md) に従う。
migration は、起動と別の手順にする。

## 生存と準備を分けて公開する

### 要求
生存と、処理を受ける準備は別の面で公開する。
生存は自身の回復不能な状態だけで判定し、外部依存の疎通を含めない。
準備は処理を受けられるかで判定し、依存の疎通を含めてよい。
健全性の応答は最小に保ち、過負荷の中でも優先して返す。

### 根拠
生存に外部依存の疎通を含めると、依存の一時的な不調でプロセスが再起動され、かえって不安定になる。
生存を自身の状態だけで判定すれば、再起動は本当に回復不能なときだけになる。
準備を別に公開すれば、依存が整うまで処理を受けない。
健全性の応答が重いと、過負荷で返せず、誤って不健全と判定される。

### 完了条件
生存と準備が、別の面で公開されている。
生存が、自身の回復不能な状態だけで判定されている。
準備が、処理を受けられるかで判定されている。
準備の依存の検査が全インスタンスで同時に失敗するとき、全インスタンスが外れて全停止していない。
健全性の応答が最小で、過負荷でも優先して返る。

### 禁止事項
生存の判定に、外部依存の疎通を含めること。
健全性の応答に、重い処理や大きな応答を載せること。

### 行動
生存は自身の回復不能な状態だけで、準備は依存の疎通を含めて判定し、別の面で公開する。
準備の依存の検査は、全インスタンスが同時に外れて全停止しないよう、全滅時は受け続ける側へ倒す。

### 例
```
// 生存の判定に DB の疎通を含める。DB の一時不調で再起動され不安定になる
GET /healthz -> check(self) && check(database) && check(cache)
// 生存は自身の状態だけ、準備は依存を含めて、別の面で
GET /livez  -> check(self)                          // 回復不能な状態だけ
GET /readyz -> check(self) && check(database)       // 処理を受けられるか
```

## 合図を受けたら受付をやめ、期限内で終える

### 要求
停止の合図を受けたら新しい仕事の受付をやめ、進行中の仕事は期限の中で完了させる。
期限の中で終わらない仕事は再実行できる形で返して止まり、確定の途中で処理を打ち切らない。

### 根拠
合図の後も受付を続けると、停止が終わらない。
受付をやめ進行中だけを期限内で終えれば、安全に止まれる。
期限内で終わらない仕事を再実行できる形で返せば、別のインスタンスが引き継げる。
確定の途中で打ち切ると、状態が不整合になる。

### 完了条件
停止の合図の後、新しい仕事を受け付けず、外部のトラフィックの振り分けから外れている。
進行中の仕事が、期限の中で完了するか、再実行できる形で返されている。
確定の途中で、処理が打ち切られていない。

### 禁止事項
停止の合図の後に、新しい仕事を受け付けること。
期限を設けずに、進行中の仕事を待ち続けること。
確定の途中で、処理を打ち切ること。

### 行動
合図で受付を止め、進行中を期限の中で終える。
終わらない仕事は取り消しを伝え、再実行できる形で返す。
取り消しの協調は [concurrency](./concurrency.md) に従う。

### 例
```
// 合図の後も受付を続け、確定の途中で打ち切る
onSignal(() => exit(0))
// 受付を止め、進行中を期限内で終え、終わらなければ再実行できる形で返す
onSignal(async () => { stopAccepting(); await drain(deadline); })
```

## 突然死に耐える

### 要求
合図のない停止の後も、再実行と再配送で回復できるように作る。
重要な状態はプロセス内に持たず、専用の永続化へ外出ししてプロセスを捨てて作り直せるようにする。
回復の経路は、毎回の起動で通す。

### 根拠
プロセスは、合図なく落ちうる。
優雅な停止だけに頼ると、突然死で状態が失われる。
プロセス内に溜めた状態は突然死で失われるので、重要な状態を専用の永続化へ外出しすれば、プロセスは捨てて作り直せる。
回復の前提を冪等性と追記の永続化で満たせば、再実行と再配送で回復できる。
回復の経路を毎回の起動で通せば、回復のコードが常に検証される。

### 完了条件
合図のない停止の後も、再実行と再配送で回復できる。
回復の前提が、冪等性と追記の永続化で満たされている。
再実行や再配送での回復に必要な状態が、プロセス内に保持されず専用の永続化へ外出しされている。

### 禁止事項
優雅な停止だけに頼り、突然死で回復できない状態を作ること。
重要な状態をプロセス内に溜め、突然死で失われる形にすること。

### 行動
重要な状態を専用の永続化へ外出しし、プロセス内に溜めない。
冪等性と追記の永続化で、突然死からの回復の前提を満たす。
冪等性と再実行は [resilience](./resilience.md)、追記の永続化は [data](../principles/data.md) に従う。
