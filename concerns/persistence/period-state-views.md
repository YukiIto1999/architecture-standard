## 期間の判定を一か所のビューに定義する

### 要求
期間ごとに、閉じた時刻を返すビューを datastore に一か所で定義し、閉じていない期間では閉じた時刻を空にする。
閉じた時刻は、自身の終わりの業務事実のうち取り消されていないものの時刻、判定の時点までに来た予定の終わり、同じ集約が所有する外側の期間のビューが返す閉じた時刻の中で最も早い時刻とする。
予定の終わりは、始まりの行の値、始まりの行が参照する行の書き換えない値、期間を参照する業務事実のうち取り消されていないものの値から求め、判定の時点がその時刻に達したときだけ閉じた時刻に含める。
判定の時点は、判定を評価する時の時刻とし、トランザクションの開始で固定される時刻にしない。
始まりの行が予定の始まりの時刻を持つ期間は、行を書いた時点から開いているとし、今その状態にあるかは、開いていることと判定の時点が予定の始まりに達したことの両方で判定する。
予定の始まりや終わりに依存する判定を計測に基づいて控えに実体化する場合は、事実の行から決まる予定の時刻を控えに持ち、判定の時点との比較は読むときに行う。
外側の期間とは、期間の始まりの行が、行がどの期間に属するかを示す外部キーで参照する期間である。
外側の期間を別の集約が所有する期間と、二つの集約の両方に属する期間は、外側の閉じた時刻を組み込まず、自身の終わりの業務事実と予定の終わりだけで閉じる。
今開いているかは閉じた時刻が空であることとし、閉じた時刻のビューの上に定義する。
後の判定は前の判定のビューを組み合わせて定義し、条件を書き写さない。
新しい行の値を条件にする検証(新しい回と重なる開いた回がないかなど)は、ビューを読む問い合わせに値を渡して書き、ビューが定める閉じ方を問い合わせに書き写さない。
まだ書いていない行の閉じ方が要る検証は、鍵の下で行を書いた後に、その行をビューで確かめ、満たさなければ確定しない。
書き込みの検証、読み取り、保持期限で消せる行の判定、datastore を直接読む集計は、これらのビューを使う。
ビューに置くのは、事実の行から導く今の状態と値(閉じた時刻、今開いているか、後の業務事実が変えた今の値など)と、それらから導く消せる行の判定であり、認可の方針を置かない。
書き込む行に現れない主体(操作者など)がその操作をしてよいかの判定は、[authorization](../authorization/evaluate-at-entry.md) の「入口で評価し、通った要求だけ進める」に従う認可であり、その方針(停止中の利用者は権限を使えない、など)は、ビューにも datastore の手続きにも置かず、アプリケーションの一か所に定義する。
開いた回を一つまでに限ることは datastore が保証しないので、判定は、開いた回が複数あっても結果を誤らない、存在を確かめる形で書く。
判定ごとに、一つの対象を調べるときと全体の一覧を求めるときに読む行の数を書き出し、一つの対象の判定がその対象の履歴の回数に比例するように索引を置く。

### 根拠
今の状態を記録せずに導く理由は、[data](../../principles/data/derive-state-from-facts.md) に従う。
どの終わりの業務事実がどの期間を閉じるかは事実の意味であり、期間の所有を決める業務の規則と書き込み経路が変わらない限り変わらない。
その意味を datastore のビューとして一か所に置けば、書き込みの検証、読み取り、削除、直接の集計が同じ定義を使い、判定が経路ごとに割れない。
閉じた時刻を返せば、今開いているかと、閉じてから保持期限を過ぎたかを、同じ定義から導ける。
外側の期間の閉じた時刻を内側の判定に組み込めば、外側の終わりで閉じる内側の期間に終わりの業務事実を書き足さずに済む。
別の集約が所有する外側の期間や、二つの集約の両方に属する期間で外側の閉じた時刻を組み込むと、所有する集約の不変条件を検証しないまま内側の期間が閉じたとみなされる。
予定の終わりは書き換えない値から決まり、その時刻に達して閉じることは書き込みを伴わないので、両方の集約に属する期間でも、不変条件はその閉じ方を含めて定まる。
判定の時点をトランザクションの開始に固定すると、鍵を待つ間に予定の終わりに達した期間を開いているとみなす。
予定の始まりや終わりに依存する判定の答えを控えに持つと、事実の行が変わらなくても時刻とともに答えが変わるので、控えを事実の行だけから作り直せない。
認可の方針は、表や書き込み経路を変えずに業務の都合で変わるため、ビューに置くと、方針の変更のたびに datastore の定義を変えることになる。
認可をアプリケーションの一か所に置けば、方針の正本が一つに保たれる。
開いた回が一つまでであることを書き込み経路が守る構成では、判定がその前提に依存すると、書き込み経路の誤りが判定の誤りへ広がる。
導出は対象の履歴を読むので、読む行の数を設計の時点で確かめないと、履歴の増加で性能の目標を後から割り込む。

### 完了条件
期間ごとに、閉じた時刻を返すビューが一つだけ定義されている。
閉じた時刻が、自身の終わりの時刻、来た予定の終わり、同じ集約が所有する外側の期間の閉じた時刻のうち最も早いものになり、別の集約が所有する外側の期間と両方の集約に属する期間では外側の閉じた時刻を含んでいない。
今開いているかの判定が、閉じた時刻のビューの上に定義され、条件を書き写していない。
書き込みの検証、読み取り、保持期限で消せる行の判定、datastore を直接読む集計が、これらのビューを使っている。
認可の方針が、ビューと datastore の手続きになく、アプリケーションの一か所に定義されている。
判定が、開いた回が複数ある行の組でも、単一の開いた回を前提とせずに閉じた時刻と開閉状態を導出している。
判定ごとに読む行の数と、それを支える索引が、決定の記録から追える。

### 禁止事項
ビューを使わずに、状態の判定条件を個々の問い合わせへ書き写すこと。
同じ集約が所有する外側の期間の閉じ方を、内側の判定から外すこと。
別の集約が所有する外側の期間の閉じた時刻を、内側の判定に組み込むこと。
認可の方針を、ビューや datastore の手続きに置くこと。
開いた回が一つまでであることを前提に、最新の一回だけを読んで判定すること。

### 行動
期間ごとに、終わりの業務事実、予定の終わり、同じ集約が所有する外側の期間を特定する。
閉じた時刻を返すビューを、外側の期間のビューを組み込んで定義し、今開いているかをその上に定義する。
書き込みの検証、読み取り、削除、集計が、条件を書き写さずにビューを使っているかを確かめる。
認可の判定を洗い出し、ビューや datastore の手続きにあればアプリケーションの一か所へ移す。
判定ごとに読む行の数を書き出し、一つの対象の判定を支える索引を置く。

### 例

停止中かを問い合わせごとに書き、退会で停止が閉じることを一部の問い合わせだけが考慮すると、読み取りと書き込みの検証で答えが食い違う。

```sql
SELECT s.id
  FROM user_suspensions s
 WHERE s.user_id = :user_id
   AND NOT EXISTS (SELECT 1 FROM user_reinstatements r WHERE r.suspension_id = s.id);
```

登録の期間は利用者のキーの行に始まり退会で閉じ、停止の期間は登録の期間の内側にあり、同じ利用者の集約が所有する。
停止の閉じた時刻は、解除の時刻と、登録の期間の閉じた時刻のうち早いほうである。
今停止中かは、その閉じた時刻が空であることとし、全ての読み取りと書き込みの検証がこのビューを使う。

```sql
CREATE VIEW registration_periods AS
SELECT u.id AS user_id, w.occurred_at AS closed_at
  FROM users u
  LEFT JOIN user_withdrawals w ON w.user_id = u.id;

CREATE VIEW suspension_periods AS
SELECT s.id AS suspension_id, s.user_id,
       CASE
         WHEN r.occurred_at IS NULL THEN g.closed_at
         WHEN g.closed_at IS NULL THEN r.occurred_at
         WHEN r.occurred_at < g.closed_at THEN r.occurred_at
         ELSE g.closed_at
       END AS closed_at
  FROM user_suspensions s
  JOIN registration_periods g ON g.user_id = s.user_id
  LEFT JOIN user_reinstatements r ON r.suspension_id = s.id;

CREATE VIEW suspended_users AS
SELECT user_id, suspension_id FROM suspension_periods WHERE closed_at IS NULL;
```
