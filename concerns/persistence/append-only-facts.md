## 業務事実を保持期間の間は追記で残す

### 要求
業務事実として追記する関係には、契約が保持を求める活動だけを記録する。
この規律の対象は、[data](../../principles/data/fact-state-time.md) が事実の行とする全ての関係であり、業務事実の関係のほかにキーの関係も含む。
事実の行の関係は、保持期間の間、書き込み権限で行の更新と削除を拒み、追記だけを受け付ける形にする。
業務の活動の時刻と記録の時刻が一致する業務では、業務事実の時刻を datastore の既定値で付け、書き込み経路の権限から時刻の列への書き込みを外す。
時刻の既定値は、行を書く文の時点以後の時刻にし、トランザクションの開始で固定される時刻にしない。
参照元の業務事実は、参照先の行が見えること(別の確定なら確定したこと)を確かめた後に、参照先と別の文で書く。
外部キーでつながらない業務事実どうしの前後関係は、集約の鍵の下で書く順序で保ち、その規則を決定の記録に列挙する。
後から活動の時刻を指定して記録する業務では、時刻を書き込み経路から受け取り、前後関係を書き込み経路が確かめる。
保持期間内の取り消しと訂正は、元の行を変えず、元の行を参照する行を追記して表す。
保持期限を過ぎた事実の行の削除は、期限を過ぎた行だけを対象とする専用の経路で行い、通常の書き込み経路の権限から分ける。
専用の経路は、消す行を所有する集約の書き込みパスの一つとして、その集約の鍵を取って削除する。
閉じた期間の行と期間を持たない業務事実のうち、その削除がどの書き込みの検証の結果も変えず、他の書き込みが消せる条件を変えないもの(開いた期間だけを数える判定しか読まない行など)は、集約の判定の対象に当たらないので、鍵を取らずに消してよい。
この条件の他の書き込みは業務の書き込み経路を指し、保持期限の削除どうしの順序は、参照元を先に消す順と外部キーが守る。
専用の経路が消せる行の条件は datastore のビューに定義し、削除の主体には表への削除権限を与えず、そのビューへの削除権限だけを与える。
保持期限は、契約が数え始めを定めればそれに従い、定めなければ、期間なら閉じた時刻から、期間を持たない業務事実なら活動の時刻から数える。
期間の内側で起きる業務事実のうち、その期間が開いている間の判定や今の値に効くもの(返却期限を変える延長など)は、自身の保持期限を過ぎても、その期間が閉じるまで消さない。
保持期限で消すのは、閉じた期間の始まりの行と、期間を持たない業務事実と、参照先を先に消す契約のために置いた結ぶ関係の行である。
終わりの業務事実と、予定した終わりを定める業務事実と、取り消しと訂正の業務事実と、消去のために業務事実から分けた行は、保持期限では参照先の行の削除から連鎖して消す。
終わりの業務事実と、予定した終わりを定める業務事実と、取り消しと訂正の業務事実の関係には、どの主体にも削除権限を与えない。
連鎖して消える行のほかに、他の行から参照されている行は消せる行に含めず、参照元を先に消す。
連鎖して消える行の保持期限は、参照先の行を消せる条件に含める。
保持期限の長さは、移行だけが変更する定義の行に置き、消せる行のビューがそれを読む。
保持期限は、個人情報を含む事実の行と、契約や法令が保持の期限を定める事実の行に定め、どちらにも当たらない事実の行は消さない。
消去の契約による事実の行の削除は、消去のために業務事実から分けた行を対象とする消去の経路だけが行い、その経路の削除権限は消去の対象の関係に限る。
退会の確定のように消去の義務を果たす書き込みが同じ確定でその行を消す場合も、その削除は消去の経路の権限で行う。
履歴を入力とする導出値は、日常の問い合わせで全履歴を走査しないよう、起点と差分の範囲を関係として表す。
契約が保持を求める締めなどの確定値は業務事実の関係へ追記し、技術的な起点だけを要する場合は正本から再構築できる控えの関係へ置く。
保持期間内の区切りより前の業務事実は、削除せず別の保管へ分離してよい。
業務事実を追記する関係の名前は活動を表す名詞とし、情報・データ・履歴・管理・マスタ・記録という語を避ける。
キーの関係は、始まりの業務事実を兼ねる場合もリソースの名詞で名付ける。

### 根拠
事実の行を書き換えない理由は [data](../../principles/data/preserve-facts-and-current-state.md) に従う。
追記だけを受け付ける形にすれば、保持期間の間の不変性を、書き込む側の注意でなく書き込み権限が保証する。
時刻を datastore が付ければ、書き込み経路が時刻を偽れない。
トランザクションの開始で固定される時刻を既定値にすると、鍵を待つ間に確定した参照先より前の時刻が参照元に付く。
参照先が見えることを確かめた後の別の文で参照元を書けば、参照元の時刻は参照先の時刻以後になり、この前後関係は datastore の時計が巻き戻らないことに依存する。
外部キーでつながらない業務事実の前後関係は一つの行の値では比べられないので、書き込み経路が鍵の下で書く順序で保つ。
活動の時刻を後から指定する業務では、既定値がその順序を支えないので、書き込み経路が前後を確かめる必要がある。
訂正を元の行の参照として追記すれば、元の判断と訂正の両方が残り、後から経緯を説明できる。
期限による削除を専用の経路へ分ければ、保持期間の間の不変性と、期限を過ぎた後の消去が矛盾しない。
保持期限の削除が期間の開閉や件数の判定の結果を変える行を消す場合は、所有する集約の鍵を取らなければ、その判定を読む書き込みと競合する。
閉じた期間の行のように、消しても判定の結果が変わらず、他の書き込みが消せる条件を変えない行は、鍵を取らずに消しても競合しない。
消せる行の条件をビューに置き、削除の主体にそのビューだけを許せば、条件に当たらない行の削除を datastore が拒み、削除の手順が条件を書き写さない。
終わりの業務事実を始まりの行の削除から連鎖させ、その関係への削除権限をどの主体にも与えなければ、終わりだけを消す経路そのものがなくなる。
連鎖して消える行の保持期限を参照先の条件に含めなければ、参照先の削除が、期限前の参照元を連鎖で消す。
保持期限の長さを定義の行に置けば、長さの変更が削除の条件の書き換えにならない。
消去の経路の権限を消去の対象の関係に限れば、消去の契約を理由に業務事実そのものを消せない。
追記する業務事実を保持契約のある活動に絞れば、現在値だけでよい変更を履歴へ残さず、現在情報の更新と削除で扱える。
問い合わせが過去の行を毎回すべて走査する形では、保持する業務事実の件数が増えるほど読む行も増える。
区切りの確定値を元の関係と別の関係に持たせれば、導出は最新の区切りの行から先の事実だけを読む形に閉じる。
区切りより前の業務事実を別の保管へ移せば、日常の問い合わせが読む範囲を保ったまま、保持期間の間は事実を失わずに残せる。
曖昧な語は関係の中身を説明せず、名前から業務事実と現在情報の区別を読み取れなくする。

### 完了条件
事実の行の関係が、保持期間内の行の更新と削除を、書き込み権限で拒んでいる。
活動の時刻と記録の時刻が一致する業務で、業務事実の時刻が、行を書く文の時点以後の時刻を返す既定値で付き、書き込み経路の権限が時刻の列への書き込みを含んでいない。
業務事実の前後関係を保つ書き込み経路の規則が、決定の記録に列挙されている。
保持期間内の取り消しと訂正が、元の行を変えず、元の行を参照する追記の行として表されている。
保持期限の削除が、消す行を所有する集約の鍵の下で行われ、鍵を取らない削除が、どの書き込みの検証の結果も変えず、他の書き込みが消せる条件を変えない閉じた期間の行と業務事実に限られている。
削除の主体が、表への削除権限を持たず、消せる行のビューを通してだけ削除でき、ビューの条件に当たらない行の削除が拒まれている。
保持期限の削除の後に、開いた期間の始まりの行と、始まりの行が残る終わりの業務事実と予定した終わりを定める業務事実が残っている。
連鎖して消える行のほかに、他の行から参照されている行が、消せる行のビューに現れない。
保持期限の長さが、移行だけが変更する定義の行にある。
消去の経路の削除権限が、消去のために業務事実から分けた行の関係に限られている。
履歴を入力とする導出値で、日常の問い合わせが起点と必要な差分だけを読んでいる。
起点の確定値が、実在する業務上の確定なら業務事実、技術的な集計なら再構築できる控えとして別の関係に記録されている。
区切りより前の業務事実を分離した場合、保持期間の間は分離先の保管に残っている。
業務事実の関係の名前が活動を表す名詞であり、情報・データ・履歴・管理・マスタ・記録という語を含んでいない。

### 禁止事項
保持期間内の事実の行を、通常の書き込み経路や管理操作から更新または削除できる権限を与えること。
活動の時刻と記録の時刻が一致する業務で、書き込み経路に業務事実の時刻を渡させること。
トランザクションの開始で固定される時刻を、業務事実の時刻の既定値にすること。
参照元の業務事実を、参照先と同じ文で書くこと。
期限を過ぎた業務事実の削除を、保持期間内の行も削除できる権限で動かすこと。
削除の主体に、事実の行の関係への直接の削除権限を与えること。
終わりの業務事実と、予定した終わりを定める業務事実と、取り消しと訂正の業務事実の関係への削除権限を、いずれかの主体に与えること。
消去のために分けた行の関係への削除権限を、消去の経路のほかの主体に与えること。
消去の経路に、消去のために分けた行のほかの事実の行を削除する権限を与えること。
契約が履歴を求めない変更を、追記の履歴として保持すること。
履歴を入力とする導出値の、日常の問い合わせで毎回すべての履歴を読むこと。
技術的な起点を作るために、契約が保持を求めない確定を業務事実として追記すること。
区切りより前の業務事実を、保持期間内に削除して失うこと。
業務事実を追記する関係の名前に、意味を伝えない語を使うこと。

### 行動
状態の列や遷移の行を見たら、その履歴の保持を契約が求めるかを確かめ、求めなければ現在情報の更新と削除へ戻す。
求める活動は業務事実の関係へ切り出し、事実の行の関係の書き込み権限を追記だけに絞る。
活動の時刻と記録の時刻が一致するかを確かめ、一致するなら時刻の列を、行を書く文の時点以後の時刻を返す既定値にして書き込み権限から外す。
参照元の業務事実を参照先と別の文で書き、外部キーでつながらない業務事実の前後関係を決定の記録に列挙する。
消せる行の条件をビューに定義し、削除の主体にそのビューへの削除権限だけを与え、保持期限の長さを定義の行に置く。
保持期限の削除は、参照元から先に、閉じた期間の始まりの行と期間を持たない業務事実を単位に行い、削除が判定の結果を変える行では所有する集約の鍵を取る。
取り消しと訂正は、元の行を参照する行を追記する形にする。
日常の問い合わせが全履歴の読み出しになっていないか確かめ、起点を必要とする箇所を特定する。
契約が求める実在の確定値と、再構築できる技術的な集計を分け、それぞれの関係と後続の差分から導出する。
日常の問い合わせから古い期間の業務事実を分ける必要がある場合は、保持期間内なら別の保管へ分離し、保持期限を過ぎていれば期限を過ぎた行の削除の経路へ送る。
業務事実を追記する関係の名前を、この規律に沿って付け直す。

### 例

支払いの取り消しの保持を監査の契約が求める業務で、状態の列を上書きすると、取り消す前の支払いが失われる。

```sql
CREATE TABLE payments (
  id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  amount NUMERIC(12, 2) NOT NULL,
  status VARCHAR(20) NOT NULL
);
```

支払いと取り消しを別の業務事実として追記し、取り消しは元の支払いを参照する。
時刻は datastore が、行を書く文の時点以後の時刻を返す既定値で付け、その関数は languages が定めるので、例では既定値を省く。
書き込み権限は時刻を除く列の追記だけに絞る。

```sql
CREATE TABLE payments (
  id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  amount NUMERIC(12, 2) NOT NULL,
  paid_at TIMESTAMP WITH TIME ZONE NOT NULL
);
CREATE TABLE payment_cancellations (
  payment_id BIGINT PRIMARY KEY REFERENCES payments (id) ON DELETE CASCADE,
  reason_code VARCHAR(20) NOT NULL,
  cancelled_at TIMESTAMP WITH TIME ZONE NOT NULL
);
GRANT INSERT (amount) ON payments TO application_writer;
GRANT INSERT (payment_id, reason_code) ON payment_cancellations TO application_writer;
```

保持期限で消す主体が表への削除権限を持つと、期限内の行も消せ、取り消しだけを消すと支払いが取り消されていない状態に戻る。
支払いは期間を持たない業務事実なので、支払った時刻から保持期限を数え、消せる行の条件をビューに置き、削除の主体にはそのビューへの削除権限だけを与える。
期限の長さは移行だけが変更する定義の行にあり、取り消しは支払いの削除から連鎖して消えるので、取り消しの時刻から数えた期限も支払いを消せる条件に含める。
判定の時点を返す関数は languages が定めるので、例では標準 SQL の `CURRENT_TIMESTAMP` で表す。

```sql
CREATE TABLE retention_periods (
  target VARCHAR(50) PRIMARY KEY,
  days INTEGER NOT NULL CHECK (days > 0)
);
CREATE VIEW purgeable_payments AS
SELECT p.id
  FROM payments p
 WHERE p.paid_at < CURRENT_TIMESTAMP - (
         SELECT r.days FROM retention_periods r WHERE r.target = 'payments'
       ) * INTERVAL '1' DAY
   AND NOT EXISTS (
         SELECT 1 FROM payment_cancellations c
          WHERE c.payment_id = p.id
            AND c.cancelled_at >= CURRENT_TIMESTAMP - (
                  SELECT r.days FROM retention_periods r WHERE r.target = 'payment_cancellations'
                ) * INTERVAL '1' DAY
       );
GRANT SELECT, DELETE ON purgeable_payments TO data_purger;
```

ポイントの増減の保持を契約が求める業務で、残高を毎回すべての増減から導くと、履歴が伸びるほど読み出しが重くなる。

```sql
CREATE TABLE point_events (
  id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  user_id BIGINT NOT NULL REFERENCES users (id),
  delta INTEGER NOT NULL,
  occurred_at TIMESTAMP WITH TIME ZONE NOT NULL
);
```

ポイントの業務に締めと確定残高の保持契約がある場合は、その確定を繰り返し起きる業務事実として追記し、最新の締めより後だけを導出の対象にする。
計測で残高の実体化が必要と示された場合は、区切りとは別の導出値として、増減と区切りから再構築できる形で置く。

```sql
CREATE TABLE point_closings (
  id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  user_id BIGINT NOT NULL REFERENCES users (id),
  closed_at TIMESTAMP WITH TIME ZONE NOT NULL,
  balance INTEGER NOT NULL,
  UNIQUE (user_id, closed_at)
);
CREATE TABLE point_balances (
  user_id BIGINT PRIMARY KEY REFERENCES users (id),
  balance INTEGER NOT NULL
);
```
