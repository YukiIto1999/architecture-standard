# tools

tools は、何を使うか、どう選ぶかを定める採用の正本である。
principles・concerns・structure・languages の上位規律に従属し、上位規律を再定義しない。
上位の各層は、性質の要求を定め、機構の置き場として tools を指す。
採用は、市場・ライセンス・保守・実測の変化で変わり、この変更理由だけを tools に集める。
tools は、採用だけを書く。
未採用の候補と比較の経緯は、標準に含めない。

## エントリの書式

各エントリは、用途・採用・判断基準・撤回条件の4行を基本にする。

- 用途は、満たす性質を一文で書く。
- 採用は、用途を満たす機構の組を一意に名指しし、代替候補を併記しない。
- 判断基準は、選定の決め手を書く。
- 撤回条件は、撤回する条件と再評価のトリガーを書く。

## 選定の共通基準

1. ライセンスとリリースポリシーが、1 顧客 1 配備([structure/deploy](../structure/deploy/layout.md) の配備の単位)と整合すること。
2. 無償で利用でき、判断基準を満たす部品を優先すること。
3. 撤回条件と再評価のトリガーを、必ず付けること。
4. 性能は対象の規模で評価する。小規模で無視できる差が、規模が大きくなると選定を左右する。
5. 既存のデファクトの道具との挙動の互換と、周辺の対応の充実は、乗り換えと導入の費用を下げる。

## タスク実行の正本

検証と release の手順は、単一の正本として root のタスク定義に集約する。
外部の検証サービスがファイルの置き場を強制する場合、その置き場には正本を呼ぶ最小の起動だけを置く。
タスクを編成する orchestrator の採用は、[build](./build.md) が定める。

## 判定の枠

tools は、採用と判断基準で判定する。
対象が採用と同じ機構を使っているかを照合し、判断基準の前提が崩れていないかを確かめる。
逸脱は、標準の単一性([README](../README.md))に従い project の ADR に記録する。
