# tools

tools は、言語横断の開発道具、自運用基盤、外部 Web サービスについて、何を、どう選び、どう使うかを定める採用の正本です。

上位の設計原則である [principles](../principles/)、横断規律である [concerns](../concerns/)、構造設計である [structure](../structure/) が満たすべき性質を要求するのに対し、tools はその性質を満たすための具体的な技術選定と実装パターンを定義します。

## 設計思想

ライセンス、市場動向、保守体制、性能実測の変化に伴う、言語横断の道具・自運用基盤・外部 Web サービスの技術選定や差し替えの変更理由は、すべて tools 層だけに集約します。
上位層は tools の個別製品に依存せず、tools 側が上位規律を満たす責務を負います。未採用の候補や比較の経緯などの検討資料は標準本体に含めず、決定された採用のみを記述します。

## 構成

| 区分 | 場所 | 中身 |
|---|---|---|
| 言語横断の開発道具 | [build](./build/README.md) | task の編成、共有ライブラリの取得、契約の生成、署名と検査の道具 |
| 自運用基盤 | [platforms](./platforms/README.md) | セルフホストする基盤の採用 |
| 外部 Web サービス | [services](./services/README.md) | 外部 Web サービスの採用方針 |

提供形態の違いに基づき、tools は以上の3つの区分に分割されています。
各区分のディレクトリ配下に置かれた `README.md` が、所属するツールファイルの正本台帳を兼ねています。
特定の言語 ecosystem に属する採用物と、言語機構による実現は tools に置かず、[languages](../languages/) が定めます。
ツールファイルの書式と選定の共通基準は、languages のツールファイルにも適用します。

## ツールファイルの書式

採用物ごとに一つのファイルを置き、用途・採用・判断基準・撤回条件の4行を基本にする。
一つの採用物が複数の用途を持つ場合は、用途ごとの H2 の下に4行を置く。
その採用物を主駆動とする規律の H2 は、entry の後ろに置き、要求・根拠・完了条件・禁止事項・行動の必須の5節で書く。

- 用途は、満たす性質を一文で書く。
- 採用は、用途を満たす機構の組を一意に名指しし、代替候補を併記しない。
- 判断基準は、選定の決め手を書く。
- 撤回条件は、撤回する条件と再評価のトリガーを書く。

## 選定の共通基準

1. ライセンスとリリースポリシーが、[structure/deploy](../structure/deploy/layout.md) の配備の単位と整合すること。
2. 無償で利用でき、判断基準を満たす部品を優先すること。
3. 撤回条件と再評価のトリガーを、必ず付けること。
4. 性能は対象の規模で評価する。小規模で無視できる差が、規模が大きくなると選定を左右する。
5. 既存のデファクトの道具との挙動の互換と、周辺の対応の充実は、乗り換えと導入の費用を下げる。
6. 標準を運用する側が上流の保守を担う機構を採用に記すときは、その機構でなければ満たせない不足を判断基準の文に書き、版を固定できる入手経路を採用の文に書き、保守の停止と、同じ用途を満たす機構の出現を撤回条件の再評価のトリガーに含めること。
7. 版は、上流が現に開発している最新の系に追随すること。旧い系へ据え置くのは、上位規律が要求する機構が新しい系に無いことを実証した場合に限る。安定版へ達していない系を採ってよいのは、その系が機能の追加を終えて残る変更が不具合の修正に限られる段階にあり、上位規律が要求する機構が揃っていて、安定版の到達を撤回条件の再評価のトリガーへ接続できる場合に限る。機能の追加が続く段階の系は採らない。

## 判定の枠

tools は、採用と判断基準で判定する。
対象が採用と同じ機構を使っているかを照合し、判断基準の前提が崩れていないかを確かめる。
逸脱は、[README](../README.md) の標準の単一性に従い project の決定の記録に残す。
