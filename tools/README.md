# tools

tools は、システムを具現化するために何を、どう選び、どう使うかを定める採用と実現の正本です。

上位の設計原則である [principles](../principles/)、横断規律である [concerns](../concerns/)、構造設計である [structure](../structure/) が満たすべき性質を要求するのに対し、tools はその性質を満たすための具体的な技術選定と実装パターンを定義します。

## 設計思想

ライセンス、市場動向、保守体制、性能実測の変化に伴う技術選定や差し替えの変更理由は、すべて tools 層だけに集約します。
上位層は tools の個別製品に依存せず、tools 側が上位規律を満たす責務を負います。未採用の候補や比較の経緯などの検討資料は標準本体に含めず、決定された採用のみを記述します。

## 構成

| 区分 | 場所 | 中身 |
|---|---|---|
| 言語 ecosystem | [rust](./rust/)・[csharp](./csharp/)・[typescript](./typescript/) | 言語の採用、実現軸の規律、採用物ごとのツールファイル |
| 言語横断の開発道具 | [build](./build/README.md) | task の編成、共有ライブラリの取得、契約の生成、署名と検査の道具 |
| 自運用基盤 | [platforms](./platforms/README.md) | セルフホストする基盤の採用 |
| 外部 Web サービス | [services](./services/README.md) | 外部 Web サービスの採用方針 |

提供形態の違いに基づき、tools は以下の4つの区分に分割されています。
各区分および各言語 ecosystem のディレクトリ配下に置かれた `README.md` が、所属するツールファイルの正本台帳を兼ねています。

## 言語 ecosystem

言語ごとの実現は、[rust](./rust/)・[csharp](./csharp/)・[typescript](./typescript/) の ecosystem に置きます。
上位規律が定めた形を、各言語の採用機構でどう満たすかだけを定め、上位規律を再定義しません。

### 6つの実現軸と全域規律

コード上で責務が現れる場所に応じて、3言語共通で以下の6つの実現軸と1つの全域規律を定めています。

| ファイル | 分類 | 担う責務 |
|---|---|---|
| `formation` | 実現軸 | 値・型・不変条件のモデリング。ドメインの核となる状態表現 |
| `translation` | 実現軸 | 外界との境界における意味の出し入れ。DTO変換とバリデーション |
| `connection` | 実現軸 | 副作用と依存の注入・受け渡し。データアクセスとクライアント接続 |
| `coordination` | 実現軸 | 非同期処理、並行実行、処理の取り消し・タイムアウト制御 |
| `publication` | 実現軸 | 外部公開面とプロセスの起動・ホスティング |
| `inspection` | 実現軸 | 自動テスト、静的解析、不変条件の検証機構 |
| `conventions` | 全域規律 | 命名規則、コード整形、ドキュメントコメント、型名接尾辞の一貫性 |

具体的なライブラリやツールの採用規律は、これらの軸ファイルではなく、個別のツールファイルに記述されます。

### 言語と役割

| 言語 | 役割 |
|---|---|
| [rust](./rust/) | server・console・worker・desktop と mobile の host・extension が接続する core のプロセスと言語サービス |
| [csharp](./csharp/) | server・console・worker・desktop と mobile の host・extension が接続する core のプロセス |
| [typescript](./typescript/) | viewer・extension・web と ide の host |

言語の間で揃えるのは保証、すなわち満たす性質とその検証であり、実装の形の双子性ではありません。
実装単位と言語の対応を適用時の入力とし、各 ecosystem の README が定める言語の採用のうち使用する各言語の規律を適用する。
自己ホストの surface と、desktop・mobile の host は、core の言語に従う。
web の host の platform は browser であり、言語を持たない。
その bundler と entry は typescript が担う。
言語と基盤の版は各 ecosystem の README が定め、改訂は standard-update で行う。
遵守は、各実現軸の採用機構と規律の完了条件・禁止事項で照合して判定する。

### 言語の単一性

同じ目的の機構は、一つの言語の中で一つに固定する。
言語 ecosystem が機構を定めていない目的では、project が単一の採用を ADR に明記する。
逸脱は、root の [README](../README.md) が定める要件に従う。
機構の採用は、この README の選定の共通基準に従う。

### 言語 ecosystem の書式

各ファイルは、`## 概要` で従う上位規律への参照を述べる。
その下に軸内の規律ごとの `## 規律名` を置き、各規律を必須の5節で書く。末尾に `## 参照` を置く。
conventions.md も同じ書式に従うが、置き場を持たず全ての実現軸に一様に適用する規律である点だけが異なる。
inspection.md は、`## 参照` の直前に `## 規則と検証機構の対応` の付表を置き、規律ごとの検証手段を一覧にする。

- 要求では、言語機構ごとに守る規則を一文単位に分け、命令形で記す。
- 根拠は、上位規律の再導出でなく、その言語の機構で上位規律をどう満たすかを述べる。
- 完了条件は、満たされた状態を観測できる形で示す。
- 禁止事項は、してはならないことを書く。
- 行動は、適用と是正の手順を書く。
- 例は、避けたい書き方と望ましい書き方をその言語の実コードで対比し、規律を明確にするのに役立つときだけ加える。

製品を主駆動とする規律は、軸のファイルでなく採用したツールのファイルに置く。
機構の規律が上位規律と重なるときは、上位規律が正である。
## ツールファイルの書式

採用物ごとに一つのファイルを置き、用途・採用・判断基準・撤回条件の4行を基本にする。
一つの採用物が複数の用途を持つ場合は、用途ごとの H2 の下に4行を置く。
その採用物を主駆動とする規律の H2 は、entry の後ろに置き、軸のファイルと同じ必須の5節で書く。

- 用途は、満たす性質を一文で書く。
- 採用は、用途を満たす機構の組を一意に名指しし、代替候補を併記しない。
- 判断基準は、選定の決め手を書く。
- 撤回条件は、撤回する条件と再評価のトリガーを書く。

## 選定の共通基準

1. ライセンスとリリースポリシーが、[structure/deploy](../structure/deploy/layout.md) の配備の単位と整合すること。
2. 無償で利用でき、判断基準を満たす部品を優先すること。
3. 撤回条件と再評価のトリガーを、必ず付けること。
4. 性能は対象の規模で評価する。小規模で無視できる差が、規模が大きくなると選定を左右する。
5. 既存のデファクトの道具との挙動の互換と、周辺の対応の充実は、乗り換えと導入の費用を下げる。

## 判定の枠

tools は、採用と判断基準で判定する。
対象が採用と同じ機構を使っているかを照合し、判断基準の前提が崩れていないかを確かめる。
逸脱は、[README](../README.md) の標準の単一性に従い project の ADR に記録する。
