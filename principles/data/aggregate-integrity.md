## 整合性を集約境界に閉じる

### 要求
同時に守らなければ不正となる不変条件は、その業務規則を所有する一つの集約の内に閉じ、その集約の判断で検証する。
業務の判断は、アクターの目的と変更理由でモデルに分け、モデルを分けたことだけで集約を増やさない。
集約は、独立した状態と、その状態について同時に守る不変条件を所有するモデルについて、所有の分析で引き、業務規則の所有と整合性の範囲を表す。
独立した状態も不変条件も所有しない値や方針の純粋なモデルは、集約の root にせず、判断を呼ぶ集約や use-case が使う。
一つの業務動作が複数のモデルの判断を要しても、変更する集約が一つなら、その集約だけを確定する。
集約を、table、コンテキスト、トランザクション、一度の datastore の確定のいずれの単位とも同一視せず、それらの単位から機械的に決めない。
異なるアクターの目的や変更理由の集約を、一度に確定する都合だけで一つの集約へまとめない。
集約は小さく保ち、集約どうしは識別子で参照する。
複数の集約にまたがる規則(注文の成立と在庫の確保を必ず同時に確定する要件など)は、どちらの集約の不変条件でもなく、業務動作が要求する確定の範囲であり、use-case が各集約の判断を組み合わせて定める。
複数の集約の変更を同時に確定するか別の確定に分けるかは、部分的な確定が業務上許されないか、即時の整合を要するか、整合させるのがその操作を行う本人の責務か別の利用者やシステムの責務かで判断する。
同時の確定を要さない集約どうしは別の確定とし、時間を置いてよい連携だけをイベントによる結果整合性で表す。
二つの集約がどちらも、同じ記録の集合に即時に守るべき件数の不変条件を持つ場合は、その記録を両方の集約に属するものとし、その記録を書く確定は、属する集約を全て競合制御の下に置いて一緒に確定する。

### 根拠
整合性の判断が複数の箇所へ散らばると、部分更新や競合で不正な状態が生まれる。
同時に守るべき不変条件を一つの集約に集めれば、その集約の判断と競合制御だけで規則を守れる。
集約は、オブジェクトの所有関係でなく、業務規則の整合性の境界を表すために引く。
境界の引き方は、どの状態と不変条件をどのモデルが所有するかの分析で決める。
モデルの分割は責務の分離であり、集約の境界は状態と不変条件の所有で決まる。
モデルごとに集約を引くと、状態を持たない判断にまで競合制御の単位と鍵が増え、規則の所有は明確にならない。
table は永続化の形、コンテキストは語彙と意味の境界、確定の範囲は業務動作ごとの要求であり、それぞれ別の理由で決まる。
集約を table や確定の範囲から決めると、実体の形や同時に変わる都合が境界になり、目的と変更理由の異なる判断を吸収して肥大し、片方の変更がもう片方を壊す。
この理由は [separation](../separation/split-by-change-reason.md) の「変更理由で分ける」に従う。
確定の範囲を集約へ一致させると、同時に確定すべき業務動作のために集約を統合するか、確定を分けてイベントの結果整合性を負うかの二択になる。
統合は目的と変更理由の異なる責務を混ぜ、確定の分割は同時確定が要る動作を部分確定の状態へ晒し、イベントの遅延・重複・順序・中間状態という複雑さを不要に負わせる。
use-case が各集約の純粋な判断を組み、必要な変更を一度に確定すれば、集約を分けたまま、同時に確定すべき動作を部分確定なしで満たせる。
一度に確定する集約が増えると、確定が待つ競合の範囲と失敗の原因が含めた集約の分だけ広がるので、同時の確定は業務が要求する範囲に限る。
同時の確定を要さない連携は別の確定に分ければ、各集約の競合の範囲を広げずに済む。
集約を小さく保つと性能と競合の両面で扱いやすく、大きな集約は更新がぶつかって詰まる。
他の集約を実体でなく識別子で指すと、他の集約の状態と変更理由が自分の不変条件と競合の範囲へ入り込まない。
貸出が利用者の冊数の上限と資料の同時貸出の禁止の両方に数えられるように、一つの記録が二つの集約の件数の不変条件に同時に属する場合は、確定を分けるとどちらに置いても他方の不変条件が結果整合になり、即時に守れない。
その記録を書く確定を、記録が属する集約の競合制御の下で一度に行えば、両方の不変条件を即時に守れる。
一つの操作が多くの集約に属する記録を一度に終わらせる場合も、それらを全て直列化した一つの確定で行えば、途中で止まった操作が、終わった記録と終わっていない記録を混在させない。
即時に整合させるか結果整合に委ねるかは、整合させるのがその操作を行う本人の責務か、別の利用者やシステムの責務かで判断する。
集約が守るのは、業務規則に基づく計算の整合性である。
保存されたデータの整合性ではない。
だから集約は永続化と独立に設計し、確定の範囲と競合制御は [transaction](../../concerns/transaction/README.md) が定める。

### 完了条件
同時に守らなければ不正となる規則が、その規則を所有する単一の集約の内で検証されている。
集約が、独立した状態と同時に守る不変条件を所有するモデルについて引かれ、table・コンテキスト・確定の単位から機械的に決められていない。
モデルの分割が集約の追加と同一視されず、独立した状態も不変条件も持たない値や方針のモデルが集約の root になっていない。
一度に確定する範囲が、業務動作の同時確定の要求から use-case に定められ、含める集約が一つの集約に限られていない。
異なる目的や変更理由の集約が、一度に確定する都合だけで統合されていない。
集約が、ルートと必要最小限の属性に限られている。
他の集約への参照が、実体でなく識別子で表されている。
同時の確定を要さない複数の集約にまたがる連携が、別の確定とイベントによる結果整合性として明示されている。
同時の確定を要する複数の集約が、含めた全ての集約の競合制御の下の一度の確定で書かれ、モデルの統合にも別の確定のイベントにも置き換えられていない。
複数の集約に属する記録を書く確定が、属する集約を全て一緒に競合制御の下に置いている。

### 禁止事項
同時に守るべき判断を、集約の外の各所へ分散させること。
異なるアクターの目的や変更理由の集約を、一度に確定する都合だけで一つの集約へまとめること。
独立した状態も不変条件も持たない値や方針のモデルを、モデルを分けたことだけを理由に集約の root にすること。
集約を、table、コンテキスト、トランザクションの単位と同一視して境界を決めること。
同時に確定すべき業務動作を、複数の集約にまたがるというだけで、別の確定とイベントによる結果整合性へ分けること。
同時の確定を要さない集約を、実装や問い合わせ数の都合だけで一度の確定へ含めること。
所有関係や画面の都合で、集約を大きくすること。
他の集約を、実体への直接参照で抱え込むこと。

### 行動
不変条件を洗い出し、同時に守るべきものを、それを所有するモデルの一つの集約に束ねる。
モデルをアクターの目的と変更理由で分けた後、独立した状態と不変条件を所有するものだけに集約の境界を引き、状態を持たない値や方針のモデルは、集約に含めず判断を呼ばれる側に置く。
集約をルートと最小の属性に絞り、それ以外は別の集約として識別子で参照する。
業務動作ごとに複数の集約の判断を要するかを確かめ、要するなら、部分確定が許されるか、即時の整合を要するか、整合させるのがその操作を行う本人の責務か別の利用者やシステムの責務かで、同時に確定するか別の確定に分けるかを判断する。
同時に確定するなら、use-case が各集約の判断を組んで一度に確定し、含める集約の競合制御は [transaction](../../concerns/transaction/README.md) が定める規律で通す。
別の確定に分けるなら、イベントなどの結果整合性で連携する。
集約の統合を考えたときは、統合する集約の目的と変更理由を列挙し、異なるなら統合せず、確定の範囲だけを広げる。

### 例
注文が顧客を実体で抱えると、集約が大きくなり、更新が衝突しやすい。

```ts
class Order { id: OrderId; lines: OrderLine[]; customer: Customer }
```

他の集約は識別子で参照し、顧客の変更は `Customer` 集約が判断する。

```ts
class Order { id: OrderId; customerId: CustomerId; lines: NonEmpty<OrderLine> }
```

注文の成立と在庫の確保を必ず同時に確定する要件があるとき、注文と在庫を一つの集約へまとめると、販売の変更理由と倉庫の変更理由が同じ集約に混ざる。

```text
OrderWithStock { orderId, lines, stock }
```

在庫の確保を注文と別の確定へ分け、イベントで引き当てると、注文が成立しても在庫が確保されていない状態が観測され、同時に確定する要件を満たさない。

```text
transaction { insert order }
OrderPlaced -> transaction { reserve stock }
```

`Order` と `Inventory` を別の集約のまま、use-case が両方の純粋な判断を組み、両方の競合制御の下で一度に確定する。
どちらかが拒否したときは、どちらの書き込みも確定しない。

```text
Order.place(customer, lines) -> refused(reason) | accepted(order)
Inventory.reserve(stock, lines) -> refused(reason) | accepted(reservation)

use-case placeOrder:
  read customer, stock
  decide Order.place and Inventory.reserve
  if either is refused: end without commit
  write order, reservation
  commit once
```

値引き方針と請求可否を変更理由の異なる純粋なモデルとして分けても、どちらも独立した状態を持たないので、集約にはならない。
変更する集約は `Order` だけであり、二つの方針は競合制御の対象にならない。

```text
DiscountPolicy.apply(order, customerRank) -> discount
BillingPolicy.judge(order, customer) -> billable | notBillable(reason)

use-case confirmOrder:
  read order, customer
  decide DiscountPolicy.apply and BillingPolicy.judge
  if notBillable: end without commit
  write order with discount
  commit once
```
