## 業務事実と現在情報を分けて保持する

### 要求
データごとに、業務・監査・回復・消去の契約から、事実の行として保持するか、現在値だけを持つ現在情報かを決める。
事実の行は、保持期限と消去の契約による削除と、それに伴う従属する記録の連鎖削除のほかは、更新も削除もしない。
事実の行の取り消しと訂正は、書き換えでなく、対象の事実の行を参照する業務事実の追記で表す。
可変属性と現在関係は、現在値を正本とし、変更と消去を通常の更新と削除で行う。
削除を業務事実として残すリソースのキーの行は、それを参照するデータが残る間は存続させる。
残す識別子と参照は、業務・監査・回復の契約が必要とする範囲に限る。
保持期限を過ぎた事実の行と、消去の契約が定める情報は、契約に従って消去する。
保持期限による削除は、閉じた期間の始まりの行とその終わりの業務事実を一緒に消し、開いた期間の始まりの行を消さず、終わりの業務事実だけを消さない。
消去の契約が定める情報は、消去後も保持する事実の行へ複製せず、現在情報の控えを含む全ての保持先で契約に従って消去する。
消去の契約が定める情報を業務事実が伴う場合は、その情報を業務事実と別の記録に置き、業務事実を残したまま消せるようにする。
参照は、参照元が残るべき期間を持つ対象へ向ける。
現在情報の変更または消去とそれに伴う業務事実の追記は、同じ集約の一つのトランザクションで確定し、全ての書き込み経路が同じ競合制御に従う。
導出値は、正本を一つに保ち、保持する場合も正本から再構築できる形にする。
業務事実の履歴から導出値を導く設計では、日常の参照が毎回全履歴を走査しないよう、導出の起点と読む範囲を定める。
実在する業務上の確定を起点に使う場合は業務事実として保持し、計算量を抑えるだけの起点は再構築できる控えとして扱う。

### 根拠
保持を求められていない変更まで追記で残すと、その履歴が消去の契約と衝突し、業務が要求しない保持と複雑さを負う。
現在値だけでよい情報を更新と削除で扱えば、保持する範囲が契約と一致する。
業務・監査・回復の契約が求める出来事を上書きや削除で失うと、判断の根拠を取り戻せない。
だから保持を求められた事実の行は、保持期間の間は不変に保つ。
事実の行を書き換えて状態の変化を表すと、状態と事実を同じ行に置いて削除で表す形になり、起きた活動を事実として残すという前提そのものを失う。
保持期限による消去と、消去の契約による現在情報の削除は、どちらも契約の履行であり、追記の規律からの逸脱ではない。
終わりの業務事実だけを消すと、終わった期間が開いた状態に戻り、開いた期間の始まりの行を消すと、今の状態が失われる。
消去の契約が定める情報を消去後も残す事実の行へ複製すると、現在情報を消しても同じ情報が残り、消去が完了しない。
業務事実に伴う情報のうち消去の契約を負う部分を別の記録に置けば、業務事実の不変性と消去の義務が衝突しない。
削除を業務事実として残すリソースのキーの行を保てば、現在情報を消しても、それを参照する他のデータが意味を失わない。
一方、識別子と参照を無条件に残すと、消去の契約が定める範囲まで残る。
だから残す識別子と参照は、契約が必要とする範囲に絞る。
参照の向きが、参照元が残る期間を決める。
現在情報の変更と業務事実の追記を別々に確定すると、片方だけが残る。
複数の記録にまたがる不変条件は、一つの記録への制約だけでは守れない場合がある。
そのとき書き込み経路ごとに競合制御が異なると、競合する書き込みが経路をまたいで不変条件を破る。
導出値は、捨てても正本から取り戻せる値である。
導出できる値を独立した値として持つと、その値を正本と同期し続ける責任が生まれ、この責任は業務が要求しない複雑さである。
正本として保持する現在情報は、捨てると情報を失うため、導出値と同じ扱いで破棄できない。
全ての現在情報を業務事実から再構築できるようにすると、再構築を必要としない属性まで履歴に残すことになり、消去の契約と衝突する。
導出のたびに履歴を最初から全て読み直すと、追記に伴って処理する事実が増え、導出の負担が大きくなる。
一定の区切りで確定した値を業務事実として残せば、以後の導出はその区切りから先の事実だけで済む。
区切りは業務上の確定であり、追記される業務事実である。
再構築を速めるための技術的な控えは、捨てても事実を失わない最適化であり、区切りとは別に扱う。

### 完了条件
project の決定の記録から、各データを事実の行か現在情報に分類した判断と、保持期間および消去の契約を追える。
事実の行が、保持期間の間、更新も削除もされていない。
事実の行の取り消しと訂正が、対象の事実の行を参照する業務事実の追記で表されている。
可変属性と現在関係が、現在値として更新と削除で扱われている。
契約が履歴を求めない変更が、追記の履歴として保持されていない。
削除を業務事実として残すリソースのキーの行が、それを参照するデータが残る間は存続している。
残る識別子と参照が、業務・監査・回復の契約が必要とする範囲に限られている。
保持期限を過ぎた事実の行と、消去の契約が定める情報が、契約に従って消えている。
保持期限による削除の後に、開いた期間の始まりの行がすべて残り、始まりの行を失った終わりの業務事実も、始まりの行が残る終わりの業務事実の欠けもない。
消去の契約が定める情報が、消去後に事実の行や現在情報の控えを含む他の保持先に残っていない。
現在情報の変更と業務事実の追記が、一つの集約の一つのトランザクションで確定し、全ての書き込み経路が同じ競合制御に従っている。
再構築の対象が導出値に限られ、導出値が正本から再構築できる。
業務事実の履歴から導出値を導く設計で、日常の参照が毎回全履歴の走査にならず、起点が実在する業務上の確定か再構築できる控えかで区別されている。

### 禁止事項
契約が求めない属性の変更履歴、とくに個人情報の全変更履歴を、追記して保持すること。
保持期間内の事実の行を、更新または削除すること。
状態の変化を、事実の行の更新や削除で表すこと。
開いた期間の始まりの行や、終わりの業務事実だけを、保持期限で削除すること。
保持期限を過ぎた事実の行や、消去の契約が定める情報を、不変性や削除フラグを理由に保持し続けること。
消去の契約が定める情報を、消去後も事実の行や他の保持先へ残すこと。
現在情報を一律に業務事実から再構築する対象とし、現在値だけでよい属性の保持まで要求すること。
削除を業務事実として残すリソースのキーの行を、参照するデータが残るまま削除すること。
契約が必要としない識別子や参照を、キーの行の存続を理由に残すこと。
現在情報の変更と業務事実の追記を、別々の確定点で行うこと。
複数の記録にまたがる不変条件を、一部の書き込み経路だけが従う規約で守ること。
導出値を、正本から再構築できない形で保持すること。
業務事実の履歴から導出値を導く設計で、日常の参照のたびに全履歴を走査すること。
計算量を抑える目的だけで、業務に存在しない確定を業務事実として保持すること。
業務上の確定の事実と、技術的な控えを、同じものとして扱うこと。

### 行動
データごとに、業務・監査・回復・消去の契約を確認し、事実の行として保持するものと、現在値だけを持つ現在情報を分ける。
現在情報は更新と削除で扱い、事実の行は保持期間の間だけ不変に保ち、保持期限と消去を契約どおりに実施する。
保持期限による削除は、閉じた期間の始まりの行を単位に行い、終わりの業務事実をそれと一緒に消す。
消去後も保持する事実の行には消去対象の情報を載せず、業務事実に伴う消去対象の情報は別の記録に分け、控えを含む全ての保持先の消去を設計する。
参照先を、参照元が残るべき期間を持つ対象から選ぶ。
現在情報の変更と業務事実の追記を同じ集約の一つのトランザクションに入れ、全ての書き込み経路へ同じ競合制御を適用する。
導出値は正本を一つに決め、再構築の手順を用意する。
履歴からの導出で日常の参照が全履歴の走査になる箇所を特定し、実在する業務上の確定と再構築できる控えを区別して起点を置く。
分類は [fact-state-time](./fact-state-time.md) の「データを事実・状態・時間で分類する」に、今の状態の導き方は [derive-state-from-facts](./derive-state-from-facts.md) の「今の状態を事実の行から導く」に従う。
集約と確定点は [aggregate-integrity](./aggregate-integrity.md)、データ層の制約は [database-integrity](./database-integrity.md) に従う。
関係と参照制約の具体化は [persistence](../../concerns/persistence/README.md) が、書込経路の原子性は [transaction](../../concerns/transaction/README.md) が、個人情報の保持と消去は [privacy](../../concerns/privacy/README.md) が定める。

### 例
全ての属性変更を履歴として追記し、現在値をそこから導くと、退会後もメールアドレスが履歴に残り、消去の契約を果たせない。

```text
add userChange(userId, "email", email, now)
currentEmail(userId) = latest userChange(userId, "email")
withdraw(userId) = add userChange(userId, "withdrawn", true, now)
```

退会が一回限りで、再登録が新しい識別子になり、退会後の個人情報の消去を契約が定める業務では、利用者のキーの行を残し、退会をそれを参照する業務事実として追記し、個人情報の可変属性を同じトランザクションで消す。
注文の受取人のように業務事実に伴う個人情報は、注文と別の記録に置き、注文を残したまま消せるようにする。
注文は別の集約であり、退会の確定では変更しない。
全ての書き込み経路が、利用者の集約に定めた同じ排他に従う。
矢印は参照先を表す。

```text
user(id)
profile(userId -> user, displayName)
email(id, userId -> user, address)
withdrawal(userId -> user, at)
order(id, userId -> user, at)
orderRecipient(orderId -> order, name, address)

withdraw(userId):
  exclusive userAggregate(userId)
  require user(userId) exists and no withdrawal(userId)
  remove profile(userId), email(userId)
  add withdrawal(userId, now)
```

利用者のキーの行と、退会と注文の業務事実は退会後も残り、個人情報だけが消える。

監査の契約が入出金の保持を求める口座で残高を上書きすると、過去の入出金という業務事実が消え、監査も復元もできない。

```text
account.balance = account.balance - amount
```

入出金を業務事実として追記し、残高をその業務事実から導く。
月次の確定残高は業務上の確定として追記し、導出の起点にする。
残高の控えを置く場合は、確定とは別の導出値として扱う。

```text
add ledger(accountId, "withdrawn", amount, at)
balance(accountId) = closing.balance + sum of ledger after closing.at
add closing(accountId, month, balance, at)
store balanceCache(accountId, balance)
```
