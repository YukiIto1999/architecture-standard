## 業務事実と現在情報を分けて保持する

### 要求
データごとに、業務・監査・回復・消去の契約から、保持を求める業務事実か、現在値だけを持つ現在情報かを決める。
同一性を持つ親リソースの識別子は変えず、現在関係と属性を消した後も、参照するデータが残る間は存続させる。
残す識別子と参照は、業務・監査・回復の契約が必要とする範囲に限る。
現在関係と可変属性は、現在値を正本とし、変更と消去を通常の更新と削除で行う。
業務事実は、契約が定める保持期間の間、追記で保存し、更新も削除もしない。
保持期間内の業務事実の取り消しと訂正は、書き換えでなく、打ち消す事実の追記で表す。
保持期限を過ぎた業務事実と、消去の契約が定める情報は、契約に従って消去する。
消去の契約が定める情報は、消去後も保持する業務事実へ複製せず、現在情報の控えを含む全ての保持先で契約に従って消去する。
参照は、参照元が残るべき期間を持つ対象へ向ける。
現在情報の変更とそれに伴う業務事実の追記は、同じ集約の一つのトランザクションで確定し、全ての書き込み経路が同じ競合制御に従う。
導出値は、正本を一つに保ち、保持する場合も正本から再構築できる形にする。
業務事実の履歴から導出値を導く設計では、日常の参照が毎回全履歴を走査しないよう、導出の起点と読む範囲を定める。
実在する業務上の確定を起点に使う場合は業務事実として保持し、計算量を抑えるだけの起点は再構築できる控えとして扱う。

### 根拠
保持を求められていない変更まで追記で残すと、その履歴が消去の契約と衝突し、業務が要求しない保持と複雑さを負う。
現在値だけでよい情報を更新と削除で扱えば、保持する範囲が契約と一致する。
業務・監査・回復の契約が求める出来事を上書きや削除で失うと、判断の根拠を取り戻せない。
だから保持を求められた出来事だけを業務事実として追記し、保持期間の間は不変に保つ。
保持期限による消去と、消去の契約による現在情報の削除は、どちらも契約の履行であり、追記の規律からの逸脱ではない。
消去の契約が定める情報を消去後も残す業務事実へ複製すると、現在情報を消しても同じ情報が残り、消去が完了しない。
親リソースの識別子を変えずに保てば、現在関係や属性を消しても、それを参照する他のデータが意味を失わない。
一方、識別子と参照を無条件に残すと、消去の契約が定める範囲まで残る。
だから残す識別子と参照は、契約が必要とする範囲に絞る。
参照の向きが、参照元が残る期間を決める。
親リソースの識別子への参照は現在情報が消えても残り、現在情報への参照は現在情報とともに消える。
残すべき参照を現在情報へ向けると退会で失われ、消すべき情報を親リソースの識別子へ従属させると退会後も残る。
現在情報の変更と業務事実の追記を別々に確定すると、片方だけが残る。
現在関係と業務事実が両立してはならない組のように、複数の記録にまたがる不変条件は、一つの記録への制約だけでは守れない場合がある。
そのとき書き込み経路ごとに競合制御が異なると、競合する書き込みが経路をまたいで不変条件を破る。
導出値は、捨てても正本から取り戻せる値である。
導出できる値を独立した値として持つと、その値を正本と同期し続ける責任が生まれ、この責任は業務が要求しない複雑さである。
だから導出値は、正本を一つに保ち、保持する場合も正本から再構築できる形にする。
正本として保持する現在情報は、捨てると情報を失うため、導出値と同じ扱いで破棄できない。
全ての現在情報を業務事実から再構築できるようにすると、再構築を必要としない属性まで履歴に残すことになり、消去の契約と衝突する。
導出のたびに履歴を最初から全て読み直すと、追記に伴って処理する事実が増え、導出の負担が大きくなる。
一定の区切りで確定した値を業務事実として残せば、以後の導出はその区切りから先の事実だけで済む。
区切りは業務上の確定であり、追記される業務事実である。
再構築を速めるための技術的な控えは、捨てても事実を失わない最適化であり、区切りとは別に扱う。

### 完了条件
project の決定の記録から、各データを業務事実か現在情報に分類した判断と、保持期間および消去の契約を追える。
親リソースの識別子が変わらず、現在関係と属性を消した後も、参照するデータが残る間は存続している。
残る識別子と参照が、業務・監査・回復の契約が必要とする範囲に限られている。
現在関係と可変属性が、現在値として更新と削除で扱われている。
契約が履歴を求めない変更が、追記の履歴として保持されていない。
業務事実が、契約が求める時刻・理由・遷移を持ち、保持期間の間、追記だけで保存され、更新も削除もされていない。
保持期間内の業務事実の取り消しと訂正が、打ち消す事実の追記で表されている。
保持期限を過ぎた業務事実と、消去の契約が定める情報が、契約に従って消えている。
消去の契約が定める情報が、消去後に業務事実や現在情報の控えを含む他の保持先に残っていない。
残すべき参照が親リソースの識別子を向き、現在情報に従属するデータが現在情報とともに消えている。
現在情報の変更と業務事実の追記が、一つの集約の一つのトランザクションで確定し、全ての書き込み経路が同じ競合制御に従っている。
再構築の対象が導出値に限られ、導出値が正本から再構築できる。
業務事実の履歴から導出値を導く設計で、日常の参照が毎回全履歴の走査にならず、起点が実在する業務上の確定か再構築できる控えかで区別されている。
業務上の確定と、再構築を速める技術的な控えが、別のものとして扱われている。

### 禁止事項
契約が求めない属性の変更履歴、とくに個人情報の全変更履歴を、追記して保持すること。
保持期間内の業務事実を、更新または削除すること。
保持期限を過ぎた業務事実や、消去の契約が定める情報を、不変性や削除フラグを理由に保持し続けること。
消去の契約が定める情報を、消去後も業務事実や他の保持先へ残すこと。
現在情報を一律に業務事実から再構築する対象とし、現在値だけでよい属性の保持まで要求すること。
親リソースの識別子を、参照するデータが残るまま削除すること。
契約が必要としない識別子や参照を、親リソースの存続を理由に残すこと。
残すべき参照を、現在情報へ向けること。
現在情報の変更と業務事実の追記を、別々の確定点で行うこと。
複数の記録にまたがる排他を、一部の書き込み経路だけが従う規約で守ること。
導出値を、正本から再構築できない形で保持すること。
業務事実の履歴から導出値を導く設計で、日常の参照のたびに全履歴を走査すること。
計算量を抑える目的だけで、業務に存在しない確定を業務事実として保持すること。
業務上の確定の事実と、技術的な控えを、同じものとして扱うこと。

### 行動
データごとに、業務・監査・回復・消去の契約を確認し、業務事実として保持するものと、現在値だけを持つ現在情報を分ける。
他のデータが参照して残す対象を特定し、不変の識別子を持つ親リソースとして表す。
現在情報は更新と削除で扱い、業務事実は保持期間の間だけ追記で保存し、保持期限と消去を契約どおりに実施する。
消去後も保持する業務事実には消去対象の情報を載せず、控えを含む全ての保持先の消去を設計する。
参照先を、参照元が残るべき期間を持つ対象から選ぶ。
現在情報の変更と業務事実の追記を同じ集約の一つのトランザクションに入れ、全ての書き込み経路へ同じ競合制御を適用する。
導出値は正本を一つに決め、再構築の手順を用意する。
履歴からの導出で日常の参照が全履歴の走査になる箇所を特定し、実在する業務上の確定と再構築できる控えを区別して起点を置く。
集約と確定点は [aggregate-integrity](./aggregate-integrity.md)、データ層の制約は [database-integrity](./database-integrity.md) に従う。
関係と参照制約の具体化は [persistence](../../concerns/persistence/README.md) が、書込経路の原子性は [transaction](../../concerns/transaction/README.md) が、個人情報の保持と消去は [privacy](../../concerns/privacy/README.md) が定める。

### 例
全ての属性変更を履歴として追記し、現在値をそこから導くと、退会後もメールアドレスが履歴に残り、消去の契約を果たせない。

```text
add userChange(userId, "email", email, now)
currentEmail(userId) = latest userChange(userId, "email")
withdraw(userId) = add userChange(userId, "withdrawn", true, now)
```

退会が一回限りで、再登録が新しい識別子になり、退会後の個人情報の消去を契約が定める業務では、親リソースの識別子と注文の参照を残し、現在関係と属性を消し、退会を業務事実として追記する。
可変属性は変更の契機と消去の単位に従って分け、現在関係に従属させる。
登録の保持も契約が求める場合は、識別子と登録時刻を業務事実として残し、登録時の個人情報は写さない。
注文は別の集約であり、退会の確定では変更しない。
退会は、親リソースを排他してから、有効な現在関係の存在と退会の不在を確かめ、一つのトランザクションで確定する。
全ての書き込み経路が、同じ排他に従う。
矢印は参照先を表す。

```text
user(id)
activeUser(userId -> user)
userProfile(userId -> activeUser, displayName)
userEmail(id, userId -> activeUser, email)
userCredential(userId -> activeUser, passwordHash)
registration(userId -> user, occurredAt)
order(id, userId -> user)
withdrawal(userId -> user, occurredAt)

withdraw(userId):
  exclusive user(userId)
  require activeUser(userId) present and withdrawal(userId) absent
  remove activeUser(userId) with its dependents
  add withdrawal(userId, now)
```

個人情報を持つ属性は現在関係とともに消え、登録と退会の事実および注文は親リソースを参照するので退会後も残る。
登録イベントを保持しても、現在の有効性を毎回登録と退会から計算せず、現在関係の有無を読む。
復帰や同じ識別子での再登録を認める業務は、この一回限りの前提を使えない。
出来事の発生回数と現在関係への影響は、[fact-state-time](./fact-state-time.md) の「データを事実・状態・時間で分類する」に従って別に定める。

監査の契約が入出金の保持を求める口座で残高を上書きすると、過去の入出金という業務事実が消え、監査も復元もできない。

```text
account.balance = account.balance - amount
```

入出金を業務事実として追記し、残高をその業務事実から導く。
月次の確定残高は業務上の確定として追記し、導出の起点にする。
残高の控えを置く場合は、確定とは別の導出値として扱う。

```text
add ledger(accountId, "withdrawn", amount, at)
balance(accountId) = closing.balance + sum of ledger after closing.at
add closing(accountId, month, balance)
store balanceCache(accountId, balance)
```
