# comment

comment は、コメントに関する原則を置く。
コメントは、命名と型で表せないものだけに限る。
ドキュメントコメントは、宣言した型・関数・メンバに付けて契約を述べる。
ドキュメントコメントの最初の一行は、目的を示す。
用法説明と変更経緯は書かない。
記法と節の構成は、言語ごとに [languages](../languages/) に置く。

## 命名と型で表せることはコメントに書かない

### 要求
コメントは、命名・型・コード構造で表せない意図・制約・外部仕様だけを書く。
命名や分割で表せる内容は、コメントでなくコードで表す。

### 根拠
命名と型で表せる内容をコメントに書くと、コードと説明が二重になり、いずれずれる。
コメントは保守も参照もされにくく、コードが変わっても古いまま残り、誤情報になる。
コメントを書きたくなるのは、しばしばコードが不明瞭なことの徴候である。
ブロックの説明はまず関数の抽出で、関数の説明はまず改名で、前提の表明はまず機械検証で、コメントを不要にできないか試す。
名前は無視しにくいが、コメントは無視されやすい。
表せるものは上の層へ寄せる。

### 完了条件
残っているコメントが、命名と型で表せない意図・制約・外部仕様だけを述べている。
コードの内容を言い換えただけのコメントが、残っていない。

### 禁止事項
命名・型・分割で表せる内容を、コメントに書くこと。
コードの内容を、そのまま言い換えるコメントを書くこと。

### 行動
コメントを書く前に、命名改善・関数抽出・型・表明で表せないか確かめる。
表せるなら、コメントでなくコード構造を直す。

### 例
```ts
// i に 1 を足す
i = i + 1;
// コメントは消し、必要なら意図を名前に込める
attemptCount = attemptCount + 1;
```

## 表せない契約・不変条件・理由は必ず残す

### 要求
ドキュメントコメントは、宣言した型・関数・メンバに付け、その契約を述べる。
契約は、事前条件・不変条件・副作用・失敗条件と、名前と型で表せない自明でない理由である。
コメントは、どう動くかでなく、何をするかとなぜそうするかを述べる。

### 根拠
契約は名前と型だけでは表せないので、宣言した要素ごとにドキュメントコメントで契約を明示する。
利用者は、実装を読まずにドキュメントコメントだけで、事前条件・不変条件・副作用・失敗条件を知れる。
ドキュメントコメントが名前の言い換えにしかならない要素は、コメントの巧拙でなく分割の誤りで、独立した契約を持たない徴候である。
そのときはコメントを省かず、要素の分割を見直して契約を持つ単位にする。
契約を書かなければ、その要素の契約は未定義のままで、誤解とバグを生む。
コメントの欠落の代償は、誤ったコメントの代償よりはるかに大きい。
実装コメントは、コードの再述でなく、何をしているかを述べる。

### 完了条件
宣言した型・関数・メンバに、契約を述べるドキュメントコメントがある。
ドキュメントコメントが、事前条件・不変条件・副作用・失敗条件を述べ、名前の言い換えになっていない。
コメントが、どう動くかの逐語でなく、何をなぜするかを述べている。

### 禁止事項
宣言した型・関数・メンバの契約を、未記述のまま放置すること。
名前を言い換えただけのドキュメントコメントを書くこと。
ドキュメントコメントが名前の言い換えにしかならないのを、分割の誤りでなくコメントの問題として放置すること。
コメントで、実装の手順を逐語でなぞること。

### 行動
宣言した型・関数・メンバごとに、事前条件・不変条件・副作用・失敗条件を確認し、ドキュメントコメントで述べる。
ドキュメントコメントが名前の言い換えになる要素は、分割を見直して独立した契約を持つ単位にする。
実装をなぞるコメントは、何をなぜするかの記述へ書き換える。

### 例
```ts
// 名前を言い換えただけで、名前を超える情報がない
/** 候補が素数か返す。 */
function isPrime(candidate: number): boolean { /* ... */ }
// 型で表せない前提と理由を述べる。利用者は実装を読まずに使える
/**
 * 候補の素数判定
 * candidate は呼び出しごとに単調増加であること(過去の値の倍数表を再利用するため)。
 */
function isPrime(candidate: number): boolean { /* ... */ }
```

## 目的を最初の一行で示す

### 要求
ドキュメントコメントの最初の一行は、名前の直訳でなく、利用者が用途を判断できる目的を示す。

### 根拠
最初の一行は、検索や一覧で要素の目的を示す要約として再利用される。
名前の直訳の一行は、署名を超える情報を持たず、利用者の判断を助けない。

### 完了条件
最初の一行が、名前の直訳でなく、利用者が用途を判断できる目的を示している。

### 禁止事項
最初の一行を、名前の直訳で書くこと。

### 行動
最初の一行に、名前の直訳でなく、利用者が用途を判断できる目的を書く。

### 例
```ts
// 名前の直訳で、署名を超える情報がない
/** 素数かどうかを判定する。 */
function isPrime(candidate: number): boolean { /* ... */ }
// 利用者が用途を判断できる目的を一行に示す
/** 候補の素数判定 */
function isPrime(candidate: number): boolean { /* ... */ }
```

## 用法説明と変更経緯を書かない

### 要求
コメントは、対象の意味・責務・制約を述べる。
用法説明・変更経緯・作業メモ・コメントアウトしたコードを残さない。

### 根拠
用法や処理手段をコメントへ逃がすと、命名や型の不備が隠れる。
変更経緯や作業メモは、現在の仕様と混同され、古くなって誤情報になる。
コメントアウトしたコードは、版管理に残るので保持する必要がなく、読み手を惑わせる。

### 完了条件
用法説明・変更経緯・作業メモ・コメントアウトしたコードが、残っていない。
コメントが、対象の意味・責務・制約だけを述べている。

### 禁止事項
「〜するための」「〜に使用する」「〜処理を行う」のような、用法や手段を述べること。
変更理由・修正履歴・暫定対応・旧仕様との差分・作業メモを残すこと。
コメントアウトしたコードを残すこと。

### 行動
用法説明・変更経緯・作業メモ・コメントアウトを検出し、削除するか、意味を表す記述へ書き換える。
履歴や判断の理由が必要なら、コメントでなく決定の記録へ残す。

### 例
```ts
// 2026-06-01 田中が修正。最初は while だったが for に変えた
// 在庫を確認するための処理
function reserve(order: Order) { /* ... */ }
// 経緯と用法を消す。経緯は PR や ADR へ、用法は命名へ
function reserve(order: Order) { /* ... */ }
```
