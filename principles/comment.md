# comment

comment は、実装コメントとドキュメントコメントの境界を定める。
現在のコードの内容はコードで表し、実装コメントには採らなかった理由だけを残す。
ドキュメントコメントは、公開宣言の外部契約と非公開宣言の内部契約を述べる。
変更履歴と古いコードは、現在のソースに残さない。
記法と節の構成は、言語ごとに [tools](../tools/) が定める。

## コードの内容を実装コメントで説明しない

### 要求
現在の処理、責務、順序は、[legibility](./legibility.md) に従い、フォルダ、ファイル、型、関数の構造と命名、コード本体で表す。
実装コメントを、コードの説明に使わない。

### 根拠
コードで読める内容をコメントにも書くと、同じ内容に二つの正本が生まれる。
コードだけを変更すればコメントは古くなり、コメントだけを変更すれば実装を表さなくなる。
説明を足さなければ読めないコードは、コメントが不足しているのでなく、配置、分割、命名、処理の流れのいずれかが不明瞭である。
コメントで不明瞭さを覆うと、コードは第一級の文書でなくなる。

### 完了条件
現在の処理、責務、順序が、実装コメントを読まずに、構造と命名、コード本体から読み取れる。
コードの内容を説明するだけの実装コメントが残っていない。

### 禁止事項
処理の目的、手順、分岐、結果を、コードの言い換えとして実装コメントへ書くこと。
不明瞭な配置、分割、命名、処理の流れを、実装コメントで補うこと。

### 行動
説明の実装コメントを見つけたら、まずコメントを外してコードを読む。
読めなければ、フォルダ、ファイル、型、関数の配置と分割、命名、コード本体の順に直す。
コードだけで読めるようになったら、説明の実装コメントを削除する。

### 例
コードの内容を説明するコメントは、処理の言い換えにすぎない。

```ts
// 注文を一件ずつ検証して、有効なら予約する
for (const order of orders) {
  if (isValid(order)) reserve(order);
}
```

説明を消し、検証済みの注文という意味をコードへ表す。

```ts
for (const order of validOrders(orders)) {
  reserve(order);
}
```

## 実装コメントは採らなかった理由だけを書く

### 要求
実装コメントは、読み手が自然に選ぶ実装を、現在も有効な制約によって採れない場合だけ書く。
採らなかった実装と、それを妨げる制約を、短く具体的に述べる。
複数の境界に及ぶ判断は [documentation](./documentation.md) の決定の記録へ置き、実装コメントには局所の判断に必要な参照だけを残す。

### 根拠
現在のコードは、採られなかった選択肢を表せない。
自然に見える実装を選ぶと壊れる理由がコードの外にあると、後の変更で同じ誤りが繰り返される。
実装コメントをこの理由に限れば、コードから読める内容を重ねず、現在の実装を拘束する情報だけが残る。

### 完了条件
各実装コメントから、自然に見えるどの実装を、なぜ採れないかが分かる。
実装コメントが述べる制約が、現在もコードを拘束している。
コードから読み取れる内容だけを述べる実装コメントがない。

### 禁止事項
現在のコードが何をするか、どう動くかを、実装コメントへ書くこと。
「性能のため」「互換性のため」のように、採らなかった実装と成立しない条件を特定できない理由を書くこと。
現在の実装を拘束しない過去の判断を、実装コメントへ残すこと。

### 行動
実装コメントごとに、読み手が選びうる自然な実装と、それを採れない現在の制約を答える。
答えられなければコメントを削除し、コードの明瞭さで不足を補う。
局所で説明し切れない判断は決定の記録へ移し、必要な箇所から参照する。

### 例
処理内容の説明は実装コメントへ残さない。

```ts
// 順番に送信する
for (const message of messages) await publish(message);
```

自然に見える並行送信を採らない理由は、コードから読み取れない現在の制約なので残す。

```ts
// Promise.all は使わない。受信側が一つ前の版の確定前に次の版を受理しないため
for (const message of messages) await publish(message);
```

## ドキュメントコメントは宣言の契約を書く

### 要求
公開範囲を問わず、宣言した型、関数、メンバにドキュメントコメントを付ける。
公開宣言は境界外の利用側への外部契約を、非公開宣言は同一境界内の呼び出し側への内部契約を述べる。
ドキュメントコメントは、宣言の目的と、該当する事前条件、事後条件、不変条件、副作用、失敗条件を述べる。
最初の一行は、名前の直訳でなく、呼び出し側が用途を判断できる目的を一つの句で示す。

### 根拠
公開宣言は境界外の利用側へ保証を与え、非公開宣言にも同じ境界内の呼び出し側との契約がある。
型と名前だけでは、値の前提、状態の変化、失敗の条件を全て表せない。
契約を宣言の近くに置けば、呼び出し側は実装を読まずに正しく利用できる。
名前の言い換えしか書けない宣言は、独立した契約を持たないか、責務と命名が定まっていない可能性がある。

### 完了条件
公開範囲を問わず、宣言した型、関数、メンバにドキュメントコメントがある。
公開宣言が外部契約を、非公開宣言が内部契約を述べている。
各ドキュメントコメントが、宣言の目的と、該当する契約条件を述べている。
最初の一行から用途を判断でき、名前の言い換えになっていない。
ドキュメントコメントの契約が、現在の宣言と実装に一致している。

### 禁止事項
非公開であることを理由に、宣言の契約を未記述にすること。
公開宣言の契約を、同一境界内だけに通用する内部契約として書くこと。
名前や型から分かる内容だけを、ドキュメントコメントで言い換えること。
該当しない契約項目を埋めるために、意味のない定型文を足すこと。
誤りと分かった契約を、直さずに残すこと。

### 行動
宣言ごとに、目的、前提、保証する結果、不変条件、副作用、失敗条件を確認し、該当するものだけを書く。
公開宣言は境界外の利用側、非公開宣言は同一境界内の呼び出し側が依存してよい保証を書く。
名前の言い換えしか書けなければ、宣言の責務、分割、命名を見直す。
対象の宣言か実装を変えたら、同じ変更で契約を更新する。
契約を実装より先に書く判断は、[verification](./verification.md) の「テストを設計の道具にする」に従う。

### 例
名前を言い換えただけでは、呼び出し側が知らなければならない契約を示せない。

```ts
/**
 * 候補の素数判定
 * @param candidate - 判定する候補
 * @returns candidate が素数なら true
 */
function isPrime(candidate: number): boolean { /* ... */ }
```

前提と再利用する状態を書けば、実装を読まずに正しく呼び出せる。

```ts
/**
 * 直前までの倍数表を再利用する連続した素数判定
 * @param candidate - 直前の呼び出しより大きい候補
 * @returns candidate が素数なら true
 */
function isPrime(candidate: number): boolean { /* ... */ }
```

## 履歴と古いコードを現在の source に残さない

### 要求
変更履歴、旧仕様との差分、作業メモ、未完了の作業注記、コメントアウトしたコードを、現在の source に残さない。
履歴は版管理に、未完了の作業は課題の追跡記録に置く。
現在も自然な実装を妨げる理由は、過去の経緯ではなく現在の制約として、実装コメントか決定の記録に残す。

### 根拠
コードは変わるが、現在のコードと履歴の説明は同じ変更で更新されるとは限らない。
同期を失った説明は、現在の実装と過去の実装を同じ source に並べ、どちらが正しいかを読者へ判断させる。
これは、コメントアウトした古いコードを source に残すことと同じであり、コードを現在の状態を示す第一級の文書でなくする。
版管理は履歴と差分を保持し、課題の追跡記録は未完了の作業を所有するので、source に複製する必要はない。

### 完了条件
source のコメントが、現在の宣言の契約か、現在も有効な採らなかった理由だけを述べている。
変更履歴、旧仕様との差分、作業メモ、未完了の作業注記、コメントアウトしたコードが残っていない。

### 禁止事項
変更日、変更者、変更内容、修正履歴、旧仕様との差分をコメントへ書くこと。
暫定対応や未完了の作業を、追跡可能な課題へ移さずコメントに残すこと。
古いコードをコメントアウトして保持すること。

### 行動
履歴と差分の説明は削除し、必要な事実を版管理から追える状態にする。
未完了の作業は追跡記録へ移し、source から作業注記を削除する。
コメントアウトしたコードは削除する。
過去の理由が現在も実装を拘束するなら、現在の制約として書き直す。

### 例
変更履歴、作業注記、古いコードをsourceへ残すと、現在の実装と過去の写しが同居する。

```ts
// 2026-06-01 に while から for へ変更
// TODO: 入力検証を追加する
// const legacyResult = reserveLegacy(order);
const result = reserve(order);
```

履歴は版管理へ、未完了の作業は課題の追跡記録へ移し、sourceには現在のコードだけを残す。

```ts
const result = reserve(order);
```
