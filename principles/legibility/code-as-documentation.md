## コードを第一級の文書として明瞭に書く

### 要求
コードを、現在のシステムの概念、責務、不変条件、実現方法を表す第一級の文書として書く。
フォルダ、ファイル、型、関数の構造と命名で、全体の責務と局所の処理を結ぶ。
現在の処理と、それを成立させる不変条件を、コードから簡潔に読み取れる形にする。
外から観測する振る舞い、変更の理由、採らなかった理由との役割分担は、[documentation](../documentation/decision-records.md) の「設計判断の理由を決定の記録に残す」に従う。

### 根拠
コードは現在の実現方法を詳細に表すが、明瞭さに労力を払わなければ、概念と責務は読み手に伝わらない。
コードは、書かれる時間より長く読まれる。
コードは頭の中の意図を完全には写せず、長く複雑になるほど意図が写し漏れる。
だから楽にすべき活動は、読むことである。
コードは、他の文書と同じく、明瞭にも不明瞭にもなる。
文書だと決めて労力を払って初めて明瞭になる。
複雑さとは、ある作業のために頭へ入れねばならない情報量と、その情報の得にくさである。
フォルダとファイルは責務を探す目次になり、型と関数は処理を理解する単位になる。
全体の配置と局所のコードがつながっていれば、読み手は関係のない実装を渡り歩かずに目的の処理へ到達できる。
急いで読んだ読み手の最初の推測が正しくなるのが、明瞭なコードである。
名前が副作用のない判定を示唆するのに状態を変える実装は、読み手を誤らせる。
呼び出し側の前提に依存する処理は、検証のために呼び出し側まで読ませる。
説明の実装コメントで不足を補うと、不明瞭な構造が残り、コードとコメントの二つを同期し続けることになる。
明瞭さを高めるには、他者に読ませ、どこで詰まるかを観る。
コードベースは個人でなくチームのものであり、個人の好みよりチームの読みやすさの規約を優先する。

### 完了条件
フォルダとファイルから責務と境界を特定でき、型と関数から処理の単位を特定できる。
概念と不変条件が、それを所有する型、関数、制約、コード本体から読み取れる。
処理の流れ、順序、副作用、失敗条件が、命名、型、分割、配置、コード本体から読み取れる。
読み手の最初の推測が、実際の振る舞いと一致する。

### 禁止事項
コードを文書として扱わず、明瞭さに労力を払わないこと。
責務を探すために、関係のないフォルダ、ファイル、型、関数を読み歩かせること。
名前が示唆しない副作用を持たせること。
呼び出し側の前提に暗黙に依存する処理を書くこと。
個人の好みを、チームの読みやすさより優先すること。

### 行動
フォルダ、ファイル、型、関数、コード本体の順に読み、全体の責務から局所の処理まで迷わず到達できるか確かめる。
分かりにくければ、実装コメントを足さず、配置、分割、命名、型、処理の流れを見直す。
概念、不変条件、責務が文書だけに残っていれば、それを所有するコードへ表し直す。
未実装の要件や入力契約は現在の実装の説明とは分け、コードの観測だけで要件を置き換えない。
名前が示唆する振る舞いと、実際の振る舞いを一致させる。
呼び出し側の前提に依存していれば、依存を断つか契約にする。
他者に読ませ、詰まる箇所を明瞭さの指標にする。

### 例
責務も意味も名前に現れないコードは、読み手に処理の復元を強いる。

```ts
if (u.f & 0x2 && Date.now() - u.t > 86400000) {}
```

責務と意味を構造と名前に表せば、コードだけで読める。

```ts
if (user.isLocked && elapsedSince(user.lockedAt, now) > LOCK_WINDOW) {}
```
