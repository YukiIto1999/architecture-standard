## 名前で意味を表す

### 要求
フォルダ、ファイル、モジュール、型、関数、値の名前は、対象の意味と責務を表す。

### 根拠
名前は、重要なものに注意を集め、重要でない詳細を省く抽象の境界である。
コメントを足さないと意味が分からない名前は、意図を表せていない。
型や構造を偽って示唆する名前は、読み手を誤らせる。
要素の実体が一覧でないのに一覧と名付けると、読み手は誤った前提を持つ。
誤解を招く名前は、意味のない名前より悪い。
読み手は無意味な名前には騙されないが、誤解を招く名前は信じたまま誤る。
名前と中身の食い違いに気づいた読み手は、書き手への信頼を失い、以後のコード全体を疑う防御的な読みに切り替わる。
命名は設計の行為であり、一度では正しくならず、対象の理解が深まるたびに直す機会が生まれる。
名前は書き手の覚え書きでなく読み手への伝達であり、独りよがりな表現より誰にでも伝わる語を選ぶ。
名前は対象の意味を正確に表すほどよいが、説明文になるほど長いのは名前でなく散文である。
業務の概念は、実装の用語でなく業務の語で名付けると、保守する者が業務側に確認できる。

### 完了条件
名前から、対象の意味と責務が読み取れる。
型や構造を偽って示唆する語が、名前に含まれていない。

### 禁止事項
意味をコメントで補う前提の名前を付けること。
実体と異なる型や構造を示唆する語を、名前に含めること。
対象の意味を表さず、複数の用途に使える汎用な名前を付けること。

### 行動
名前を見て、コメントなしで意味が読み取れるか確かめる。
読み取れなければ、コメントの追加でなく命名の修正で直す。
正しい名前がまだ決まらないときは、先に、少なくとも誤解を招かない名前へ直す。
名前は一度で決めず、理解が深まるたびに見直す。
実装の用語で足りなければ、業務の語を使う。

### 例
短縮名では経過日数という意図と日という単位が分からず、実体が Set の集合を `accountList` と呼ぶと異なる型を示唆する。

```ts
let d = 0;
const accountList: Set<Account> = new Set();
```

`elapsedDays` は意味と単位を表し、`accounts` は実体を偽らない。

```ts
let elapsedDays = 0;
const accounts: Set<Account> = new Set();
```
