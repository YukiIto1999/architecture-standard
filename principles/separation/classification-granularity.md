## 分類軸と粒度を階層で揃える

### 要求
同じ module・namespace・package・directory の直下に置く要素は、同じ分類の問いに答え、同程度の抽象度と意味の粒度を持たせる。
同じ architecture level を表す別の tree にも、同じ分類軸を通す。
要素の追加、分割、統合、移動と、既存の概念の意味、責務、制約、関係を変える変更は、兄弟要素と対応する tree の関心と粒度の釣り合いに関わるものとして扱う。

### 根拠
業務概念、技術的な実現手段、処理の一段を同じ階層に並べると、何を基準に探し、どこへ追加すべきかが決まらない。
分類軸が階層ごとに変わると、同じ意味の要素が複数の tree に散り、依存と変更範囲を追えなくなる。
ファイルサイズは物理量であり、要素の ontology、変更理由、抽象度を示さない。
同じ分類の問いへ同程度の解像度で答える兄弟要素は、構造を一覧しただけで意味の地図になる。
概念の分け方と粒度は、兄弟要素との釣り合いで意味を持つので、一つの要素の変更が、兄弟要素と対応する tree の釣り合いを崩す。

### 完了条件
各階層について、兄弟要素を分ける一つの分類の問いを説明できる。
兄弟要素が、同程度の抽象度と意味の粒度を持つ。
同じ architecture level を表す tree 間で、分類軸と概念の対応を追跡できる。
要素の追加、分割、統合、移動と、既存の概念の意味、責務、制約、関係の変更が、兄弟要素と対応する tree の関心と粒度の釣り合いを保っている。

### 禁止事項
業務概念、技術的な実現手段、処理の一段を、同じ分類軸の兄弟として混在させること。
ファイルサイズまたは項目数だけを根拠に、階層を分割または統合すること。
同じ意味の分類を、tree ごとに異なる軸で表すこと。

### 行動
対象の tree ごとに、各階層が答える分類の問いを一文で書く。
兄弟要素について、ontology、変更理由、抽象度、意味の粒度を比較する。
分類の問いに答えない要素は、対応する階層へ移すか、誤った分類自体を改める。
同じ architecture level の別 tree を照合し、概念の欠落、重複、粒度のずれを直す。
要素の追加、分割、統合、移動と、既存の概念の意味、責務、制約、関係を変えるときは、兄弟要素と同じ architecture level の別 tree の関心と粒度との釣り合いを照合する。
崩れる箇所は、同じ変更で整える。
既存の概念の誤りを直すときは、同種の概念と対応する tree に同じ問題がないか探す。
