## 関心を境界の内に隠す

### 要求
モジュールは、変わりやすい内部の決定を隠し、外部へは目的を表す最小の契約だけを公開する。
境界付けられたコンテキストは、内部の用語・判断・責務を内部で完結させ、外部へは境界の契約だけを出す。

### 根拠
内部の判断や表現が外部へ漏れると、外部がその詳細に依存し、変更が境界を越えて波及する。
インタフェースは、提供する機能に対してできるだけ小さく保ち、その裏に多くの機能を隠す。
小さなインタフェースの裏に深い機能を置けば、利用者の学習量と結合の量が同時に減る。
公開する契約は、どんな変更で変わるかを設計の時点で検討し、安定させる。
引数が増え続ける公開面は、破壊的変更を生みやすい構造を自ら作っている。
引数をそのまま別の関数へ受け渡すだけの薄い層は、結合だけ増えて機能を足さないため、責務の分割を見直す合図になる。
契約の不変条件を担う層と、表現を別の意味体系へ変換する層は、それ自体が意味のある公開面なので、この合図に当たらない。
層の外側では文字列や JSON などの素の表現を扱い、境界を越えた内側ではドメイン型だけを扱う。
境界での検証は、[modeling](../modeling/parse-at-boundary.md) の「境界で検証して型に通す」に従う。
上流の都合をそのまま受け入れると下流が歪むため、必要なら境界に隔離層を置き、外部のモデルを自分のモデルへ変換する。

### 完了条件
公開する契約が、内部の表現・永続化構造・判断順序を明かしていない。
外部のモジュールが、内部の型・内部状態へ直接依存していない。
各層が、契約の不変条件を担うか、表現を別の意味体系へ変換するかのいずれかを行っている。
本来の公開面を隠し、その手前へ別の公開面を重ねた層がない。

### 禁止事項
内部の永続化型・内部状態・判断順序を、公開の契約として出すこと。
本来の公開面を隠し、契約の不変条件も表現の変換も持たない層を手前へ重ねて、公開面を増やすこと。
上流の外部モデルを、変換せずに内部へ持ち込むこと。

### 行動
モジュールの公開面を確認し、外部が知る必要のある情報だけが出ているか判定する。
漏れていれば、公開契約を縮め、内部型と境界型を分ける。
外部システムと結ぶ箇所には変換の隔離層を置き、外部の都合を内部へ漏らさない。

### 例
内部の永続化型を公開すると、外部が列名や型に依存し、DB の変更が外へ波及する。

```ts
export interface UserRow { id: number; pw_hash: string; created_at: string }
```

目的を表す最小の契約だけを公開し、永続化型を repository の内側に閉じる。

```ts
export interface UserProfile { id: UserId; displayName: string }
```
