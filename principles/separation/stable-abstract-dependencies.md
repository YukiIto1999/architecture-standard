## 依存を安定と抽象へ向ける

### 要求
依存は、変わりにくいものへ向ける。
低頻度で変わる業務規則を内側に、高頻度で変わる詳細を外側に置き、向きを一方向に保つ。

### 根拠
高頻度で変わる詳細が業務規則を支配すると、詳細の変更が中心の判断を壊す。
依存される側ほど安定しているべきで、安定したものほど抽象であるべきである。
安定とは、既存の依存元から見た振る舞いを変えないことである。
複雑さは変更の少ない基盤の側に引き受けさせ、変更の多い業務の側を単純に保つ。
業務規則と詳細が直接結びつくと向きを固定できないため、両者の間に抽象を置く。
その抽象は、詳細の側ではなく方針の側が所有する。
方針の側がインタフェースを定義し、詳細の側がそれを実装すると、呼び出しの向きと逆にソースの依存が内側へ向く。
データの寿命はアプリケーションより長い。
アプリケーションは永続化方式より変えやすい。
だから業務規則はアプリケーション側に置き、永続化層には事実だけを残す。
具体の差し替えは、実行時に組立点で注入する。

### 完了条件
業務規則と方針が、UI・外部 API・永続化方式などの詳細へ依存していない。
境界をまたぐインタフェースが、それを使う方針の側に置かれている。
依存方向が一方向で、循環がない。

### 禁止事項
業務規則から、UI・DB・HTTP・framework・外部 SDK などの詳細へ直接依存すること。
インタフェースを詳細の側に置き、方針がそれを取りに行くこと。
循環参照や逆向きの参照を作ること。

### 行動
import・参照・組立点の構成・型共有・callback の向きを確認する。
逆向きがあれば、方針の側にインタフェースを定義し、詳細にそれを実装させ、具体は組立点で結び付ける。

### 例
方針が具体の DB クライアントへ依存すると、永続化の変更が中心へ波及する。

```ts
import { DatabaseClient } from "../infra/database";
class PricingPolicy { constructor(private database: DatabaseClient) {} }
```

方針の側が port を所有し、infra の実装を組立点で注入すれば、依存は内側へ向く。

```ts
interface RateRepository { find(id: SkuId): Promise<Rate> }
class PricingPolicy { constructor(private rates: RateRepository) {} }
```
