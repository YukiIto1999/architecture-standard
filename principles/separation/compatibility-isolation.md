## 正本を互換から独立させる

### 要求
契約の境界は、正本の構造を基準に定める。
併存する新旧の契約は、それぞれ独立した構造として扱い、移行と互換の処理を境界へ閉じ込める。
互換のための欠落や旧版の表現によって、内側の型の保証を弱めない。
業務上の不明は、その意味と許される操作を正本のモデルで定め、技術互換のための不要な任意化と区別する。

### 根拠
旧契約や互換対応の都合を正本へ持ち込むと、現在の業務概念が歪む。
同じ名前のフィールドでも、表す意味が違えば別の概念であり、別の型で表す。
申込時点の希望値と、現在運用されている値は、混ぜずに分ける。
互換のための表現を境界へ隔離すれば、正本は現在の概念だけを表せる。

### 完了条件
正本となる構造が、現在の業務概念を表している。
旧契約への対応が、境界に隔離されている。
互換の対象、版、変換箇所、内側へ渡す型、所有者、存続の根拠または撤去条件、検査入口を、既存の決定の記録から辿れる。
宣言した互換構造の参照が境界に閉じ、内側の型が現在の業務上の保証を保っている。

### 禁止事項
正本のモデルへ、互換専用の項目・不要な任意化・旧名称・旧状態を混ぜること。
新旧の意味差を、同一のフィールドや同一の型へ押し込めること。
必要な事実がない入力を、架空の値や業務上の意味を持たない既定値で補って、保証を満たした型として渡すこと。

### 行動
契約項目ごとに、現在の正本概念か、互換のための表現かを確認する。
互換要素が正本に混ざっていれば、独立した構造として境界へ分ける。
互換を導入するときは、その存続根拠または撤去条件と変換の所有者を決定の記録へ対応付け、一時的な移行のための要素を撤去へ進める。
変換で必要な保証を満たせない場合は、境界で未解決の入力として扱い、正本の型を弱めて通さない。

### 例
互換専用の旧項目が正本に同居すると、現在の概念を読み取れない。

```ts
interface Order {
  total: Money;
  amount?: number;
  statusLegacy?: string;
}
```

正本は現在の概念だけにし、旧契約への写像は境界に置く。

```ts
interface Order { total: Money; status: OrderStatus }
```
