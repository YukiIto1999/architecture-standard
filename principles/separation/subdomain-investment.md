## サブドメインの種別で設計投資を配分する

### 要求
境界付けられたコンテキストは、業務の差別化に効く core、業務に必要だが差別化に効かない supporting、業務固有でない generic のいずれかへ分類し、分類と根拠を project の決定の記録へ残す。
この標準の要求は、分類によらずすべてのコンテキストへ適用する。generic では、[structure](../structure/) が generic を名指しで別に定めた規律だけが置き換わる。
generic は既製の機構で満たすことを既定とし、自作する場合も業務の不変条件を置かない。
supporting を generic へ再分類する要否は、準拠の基準にした標準の commit を更新する時点で判定し、判定と根拠を残す。
core を既製の機構へ置き換えない。

### 根拠
設計の手間は、間接と抽象と学習の費用を払って、特定の変更が安くなる状態を買う取引である。
不変条件が複雑で寿命の長い領域では、その変更がほぼ確実に起きるため、払った費用を回収できる。
業務固有でない領域で同じ費用を払うと、起きない変更に備えた分がそのまま損になる。
分類を記録しないと、どの境界に手間をかけるかが個々の判断に散り、費用の高い形が業務固有でない領域まで広がる。
差別化に効く領域を既製の機構へ置き換えると、業務の優位そのものを外部の都合に委ねる。
費用と対価の一般の規律は [construction](../construction/README.md) に従う。

### 完了条件
generic を自作で満たしたコンテキストに、既製の機構で満たせない根拠が記録されている。
各コンテキストに、core・supporting・generic のいずれかの分類と、その根拠が記録されている。
generic に分類したコンテキストで置き換わっている規律が、structure が generic を名指しで定めた規律に限られている。
generic に分類したコンテキストに、業務の不変条件が置かれていない。
supporting の再分類の要否の判定と根拠が、標準の commit を更新した時点ごとに記録されている。

### 禁止事項
コンテキストを分類せずに、境界の内部を作り始めること。
generic に分類したコンテキストへ、業務の不変条件を置くこと。
core に分類したコンテキストを、既製の機構へ置き換えること。
structure が generic を名指しで定めていない規律を、分類を理由に適用外とすること。

### 行動
コンテキストごとに、その領域が業務の差別化に効くか、業務に必要だが差別化に効かないか、業務固有でないかを判定する。
判定と根拠を記録し、要求の適用範囲をその分類から導く。
generic と判定した領域では既製の機構を探し、採れるなら自作しない。
supporting の再分類の要否を、標準の commit を更新する時点で判定して記録する。
