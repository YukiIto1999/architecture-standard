# documentation

documentation は、README・設計文書・決定の記録に関する原則を置く。
コードに焼き込めるものは文書に書かず、文書は最小で高シグナルにし、なぜを決定の記録に残し、種別を分けて読み手を定める。

## コードに焼き込めるものは文書に書かない

### 要求
機械で検証できる制約は、[verification](./verification.md) に従って機械検証へ固定し、文書に重ねて書かない。
要件は、文章でなく、型・テスト・schema など動くものに焼き込む。

### 根拠
コードは主要な文書であり、十分に詳細で正確なのはコードだけである。
動くものに刻まれた要件だけが、毎日読まれ、変更されたら壊れて気づける。
文章の規則は、コードと乖離しても誰も気づかず、古くなって嘘になる。
機械が検証できる規則を文章に置くと、人の記憶とレビューに頼ることになる。
仕様の記述にプログラミング言語を使えば、仕様と実装の継ぎ目が消える。

### 完了条件
コードスタイルや構造の検証できる規則が、型・lint・テスト・CI に落ちている。
要件が、型・テスト・schema など動くものに表されている。
文書に残るのが、コードへ焼き込めない情報に限られている。

### 禁止事項
機械で検証できる規則を、文章の規約として運用すること。
コードで表せる要件を、文章の説明だけに置くこと。

### 行動
文書に書こうとする規則が、型・lint・テスト・CI で検証できないか確かめる。
検証できるなら、文書から外して機械に委ねる。
要件は、型・テスト・schema へ落とせないか検討する。

### 例
```md
<!-- 機械で検証できることを文章で運用している -->
- インデントはスペース4つにする。タブは使わない。
- import の順序を守る。

<!-- 整形と順序は formatter と lint に委ね、文書には残さない -->
（コードスタイルは formatter と lint が検証する。文書には書かない）
```

## 文書は最小で高シグナルにする

### 要求
文書は、最小で高シグナルなものにする。
各行に、その行を消したら読み手が誤るかを問い、誤らないなら消す。

### 根拠
量の多い文書は読まれず、無関係な記述が増えるほど、読み手は全体を無視するようになる。
削除して誤りが生じない行は、情報を足していない。
禁止だけを書くと、代わりに何をすべきかが分からず、読み手は迷う。
常時必要な情報と、必要なときだけの情報を分ければ、読み手は要る分だけ読める。
文書は、最初から完璧を目指すより、実際に起きた誤解から追記して育てる。

### 完了条件
各行が、削除すると読み手が誤る情報を持っている。
禁止に、代替の手段が併記されている。
常時必要な情報と、必要なときだけの情報が分かれている。

### 禁止事項
削除しても誤りが生じない行を、文書に残すこと。
代替を示さずに、禁止だけを書くこと。
無関係な記述を積み、読み手に全体を無視させること。

### 行動
各行に削除テストをかけ、残す価値のない行を消す。
禁止には、代わりに採るべき手段を併記する。
常時必要な情報と、参照時に読む情報を分ける。

### 例
```md
<!-- 削除しても誤りが生じない行、代替のない禁止 -->
- このプロジェクトはとても重要です。
- 変な HTTP クライアントを使わないこと。

<!-- 削除テストに残る行だけにし、禁止には代替を併記する -->
- HTTP は `httpClient` を使う(`fetch` を直接呼ばない。再試行とトレースが入らないため)。
```

## なぜを決定の記録に残す

### 要求
構造に影響する決定を、文脈・決定・帰結とともに残す。
構造に影響する決定は、実装の前に記録する。
覆すときは、古い記録を消さず、置換済みとして印を付ける。

### 根拠
最も追跡が難しいのは、決定の動機である。
動機を知らずに来た者は、決定を盲目的に受け入れるか、盲目的に変えるしかない。
PR は何を変えたかを記録するが、なぜ決めたかは記録しない。
決定・文脈・帰結を残せば、後から判断の経緯を辿れる。
検討した代替案を残すと、なぜそれを採らなかったかが分かる。
古い記録を消すと、当時の判断が失われ、同じ議論を繰り返す。

### 完了条件
構造に影響する決定が、文脈・決定・帰結とともに記録されている。
記録に、検討した代替案と、それを採らなかった理由が含まれている。
覆された決定が、消されず、置換済みとして残っている。
記録した決定の前提や内容が実装で変わった時点で、当該記録が置換済みにされるか、改訂されている。

### 禁止事項
構造に影響する決定を、根拠を残さずに行うこと。
決定を覆すときに、古い記録を書き換えるか消すこと。

### 行動
構造・依存・公開面・非機能特性に影響する決定をしたら、文脈・決定・帰結・代替案を記録する。
覆すときは、新しい記録を足し、古い記録を置換済みとして印を付ける。
標準からの逸脱を採る決定の記録は、root の [README](../README.md) が定める要件に従う。

### 例
```md
<!-- 避けたい形: 決定をコミットメッセージだけに書き、文脈と代替案が残らない -->
（commit: "session を変更". 理由も検討した代替案も残らない）

# ADR 0007: session を外部の session store に保持する

## Status
Accepted

## Context
BFF はトークンを外部に出さない。session を server 側に持つ必要がある。
候補は外部の session store、RDB のセッションテーブル、署名付き Cookie。
RDB は寿命の短いデータで負荷が増える。Cookie は失効と改ざんの運用が重い。

## Decision
session を、TTL つきで外部の session store に、不透明な session id を鍵に保持する。

## Consequences
失効が TTL で自動になり、RDB から負荷を分離できる。
session store の可用性が認証の可用性に直結する。冗長化は別の ADR で決める。
```

## 文書の種別を分け、読み手を定める

### 要求
文書は、学習・手順・参照・説明の種別を分け、混ぜない。
読み手と、その読み手が作業中か学習中かを定めてから書く。
AI が生成する運用文書も、学習・手順・参照・説明の種別に従い、読み手を定める。
検証できない語の扱いは、[verification](./verification.md) に従う。

### 根拠
読み手のニーズは、学びたい・やり遂げたい・調べたい・理解したい、で質的に異なる。
作業中に参照する記述と、作業を離れて理解する記述を混ぜると、どちらも役に立たなくなる。
参照に説明を混ぜると、参照は脱線で曇り、説明も適所で展開できない。
読み手を定めずに書いた文書は、種別が滲み、誰の役にも立たない。
検証できない語は、読み手ごとに別の像を結び、要件が壊れている徴候である。

### 完了条件
文書が、学習・手順・参照・説明のいずれかに分かれ、混ざっていない。
各文書が、想定する読み手と、作業中か学習中かを定めている。

### 禁止事項
参照と説明、手順と学習を、一つの文書に混ぜること。
読み手を定めずに、文書を書くこと。

### 行動
書く文書が、学習・手順・参照・説明のどれかを決める。
想定する読み手と、その読み手が作業中か学習中かを定める。
