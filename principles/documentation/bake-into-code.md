## コードに焼き込めるものは文書に書かない

### 要求
機械検証は、[verification](../verification/machine-enforced-constraints.md) に従う。
機械で検証できる制約を、文書へ重ねて書かない。
コードで表現できる意味を、文書へ書いて補わない。
この規律の対象は説明の文書であり、宣言のドキュメントコメントは [comment](../comment/declaration-contracts.md) の「ドキュメントコメントは宣言の契約を書く」が統べる。

### 根拠
機械検証の規範を documentation で再定義すると、verification が変わっても文書は壊れず、古い規範が残る。
機械で検証できる規則を文章だけで運用すると、人の記憶とレビューに依存する。
文書で補うと、コードが不明瞭なまま残り、意味の正本が文書とコードに分かれる。
文書に書けば足りるという逃げ道があると、ドメインと仕様がコードから読み取れない状態が是正されない。

### 完了条件
機械検証が、verification の規範に従っている。
文書に、機械で検証できる制約が重ねて書かれていない。
文書が、コードで表現できる意味を補っていない。

### 禁止事項
機械検証の規範を、documentation で再定義すること。
機械で検証できる規則を、文章の規約として運用すること。
コードから読み取れない意味を、文書を足して解決すること。

### 行動
機械検証に関する記述を見つけたら、verification への参照に置き換える。
文書に書こうとする規則が、型・lint・構造検査・テスト・計測で検証できないか確かめ、判定できる検査をリポジトリの検証入口から実行する。
検証できるなら、文書から外して機械に委ねる。
文書に書こうとする意味がコードで表現できないか確かめ、できるなら型・命名・構造・宣言の契約へ移す。
コードから意味が読み取れない状態は、文書の不足として扱わず、[legibility](../legibility/code-as-documentation.md) の「コードを第一級の文書として明瞭に書く」の行動に従って直す。

### 例
機械で検証できることを文章だけで運用すると、記述と実際の検査が分かれる。

```md
- インデントはスペース4つにする。タブは使わない。
- import の順序を守る。
```

整形と順序を formatter と lint に委ねれば、文書へ規則を重ねずに済む。文書の側には書かない。
