## コードの意味を文書で代用しない

### 要求
機械検証は、[verification](../verification/machine-enforced-constraints.md) に従う。
現在の概念、責務、不変条件、実現方法をコードで表し、外から観測する振る舞いをテストで保証する。
コードや機械検証で表せる意味と制約を、説明文書だけに置いて代用しない。
読者向けの説明は、[separate-document-types](./separate-document-types.md) の「文書の種別を分け、読み手を定める」に従い、コード、テスト、契約、設定から現在の内容を投影する。
未実装の要件、入力契約、変更先は、[requirements](../requirements/evidence-decision-separation.md) の「根拠と決定状態を分ける」に従い、現在の実装の説明と区別する。
宣言のドキュメントコメントは [comment](../comment/declaration-contracts.md) の「ドキュメントコメントは宣言の契約を書く」に従い、実装コメントとは区別して保持する。

### 根拠
コードや検査とは独立した説明を規範として運用すると、実装や検査を変えても文章は壊れず、古い規範が残る。
機械で検証できる規則を文章だけで運用すると、人の記憶とレビューに依存する。
不明瞭なコードを文書で補うと、ドメインの意味と責務がコードから読み取れない状態を是正できない。
読者向けの投影は実装へ到達する助けになるが、意味を所有するコードや契約とは別の正本にならない。
将来の要求と入力契約は実装に先立つので、現行コードに表れていないことだけでは不要と判断できない。

### 完了条件
機械検証が、verification の規範に従っている。
コードで表せる現在の意味や機械で検証できる制約が、説明文書だけに置かれていない。
読者向けの説明から対応する正本を特定でき、内容が現在の正本と一致している。
未実装の要件と入力契約が、現在の実装の説明と区別して保持されている。

### 禁止事項
機械検証の規範を、documentation で再定義すること。
機械で検証できる規則を、文章の規約として運用すること。
現在のコードで表せる意味を読み取れないままにし、文書を足して解決すること。
コードで表せることを理由に、読者向けの投影、未実装の要件、入力契約、宣言の契約を一律に削除すること。

### 行動
文書に書こうとする現在の意味を、構造、命名、型、コード本体、振る舞いのテストで表せないか確かめ、表せるものはその正本へ移す。
機械で検証できる制約は、verification に従ってリポジトリの検証入口へ組み込み、文章だけで運用しない。
説明文書を残す場合は、読み手の判断に要る内容と正本への対応に絞り、正本の変更と同じ変更で更新する。
入力契約や未実装の要求を削除する前に、現行の事実ではなく確認済みの意図か変更先を表していないか確かめる。
コードから意味が読み取れない状態は、文書の不足として扱わず、[legibility](../legibility/code-as-documentation.md) の「コードを第一級の文書として明瞭に書く」の行動に従って直す。

### 例
機械で検証できることを文章だけで運用すると、記述と実際の検査が分かれる。

```md
- インデントはスペース4つにする。タブは使わない。
- import の順序を守る。
```

整形と順序を formatter と lint に委ねれば、文章だけで規則を運用せずに済む。
文書に導入手順を残す場合は、設定と検証入口へ読み手を案内する。
