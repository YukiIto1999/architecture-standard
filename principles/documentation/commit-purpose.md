## 変更の目的を commit log に残す

### 要求
commit の件名は、その変更を何のために行うかを述べる。
コードと差分から分かる変更内容の列挙ではなく、解消する問題か成立させる目的を書く。
件名の記述の形は、[sentence-endings](./sentence-endings.md) の「文末の形を記述の種類で分ける」に従う。
一つの目的と一つの取り消し理由を持つ小さな commit を、着手と確定の単位にする。
短い件名で変更の Why を伝えられなければ、独立した判断が混ざっていないかを確かめ、目的ごとに変更を分ける。
件名に個人名を含めない。

### 根拠
コードと差分は、現在の内容と何が変わったかを示すが、なぜその変更が必要だったかを示さない。
目的が分かれば、その目的に属する差分と、別の変更へ分ける差分を判断できる。
目的の異なる変更を分ければ、変更単位を一つの理由で取り消せる。
変更を依頼した人や行った人は変更の目的に属さず、件名に書けば目的を読む妨げになり、個人の情報を履歴に固定する。

### 完了条件
commit の件名から、変更を行う直接の目的が分かる。
一つの commit が、一つの目的と一つの取り消し理由を持つ。
変更したファイルや操作の列挙だけで、目的を代用していない。
commit の件名に、個人名がない。

### 禁止事項
変更したファイル、編集操作、変更後の状態だけを列挙し、変更の目的を書かないこと。
複数の目的を、一つの commit へまとめること。
短い件名へ Why を収める代わりに、独立した判断をまとめた長い本文へ理由を退避すること。
commit の件名に、依頼者、作業者、参考にした人の名前を書くこと。

### 行動
着手前に、解消する問題か成立させる目的を一つに定める。
その目的を commit の件名へ書き、目的に属さない差分を別の commit へ分ける。
短い件名で目的を述べられない場合は、無関係な判断を分けて、着手と確定の単位を見直す。
現在も採れない実装の理由は、[comment](../comment/rejected-alternatives.md) の「実装コメントは採らなかった理由だけを書く」に従って判断の所有者へ残す。

### 例
変更内容だけでは、変更が必要だった理由を残せない。

```text
fix: verifier の失敗処理の変更
```

解消する問題を件名に書けば、変更の目的を直接読める。

```text
fix: verifier の異常終了の見逃し防止
```
