## commit の件名に対象と変化を書く

### 要求
commit の件名は、変更の対象と、その対象で何がどう変わったかを述べる。
対象は、読み手が扱う作業や物の名前(テーブル設計、注文の取消、verifier など)で書き、repository の中の置き場所や分類の名前(directory、file、層の名前)で書かない。
何がどう変わったかは、対象に起きた操作(追加、削除、置き換え、分割など)と、それで成り立つ結果(状態の列を置かないこと、異常終了を失敗に数えることなど)の両方が読める語で書き、その結果で変更の目的を表す。
操作は対象に起きたことを表す語で書き、採用、整備、明確化、統一のように評価だけを表す語で代えない。
件名の記述の形は、[sentence-endings](./sentence-endings.md) の「文末の形を記述の種類で分ける」に従う。
一つの対象と一つの変化を持つ小さな commit を、着手と確定の単位にする。
一つの対象と一つの変化で件名を書けなければ、独立した判断が混ざっていないかを確かめ、対象と変化ごとに変更を分ける。
件名に個人名を含めない。

### 根拠
件名は、履歴の一覧で差分を開かずに読まれる。
対象のない件名では、どの作業に効く変更かを知るために差分を開くことになる。
repository の中の置き場所や分類の名前は差分から分かり、その構造を知らない読み手には何に効く変更かを伝えない。
操作だけを書くと変更で何が成り立ったかが分からず、目的だけを抽象的な名詞で書くと何に何をしたかが分からない。
対象と、そこで成り立つ結果を書けば、変更の目的と、取り消すときの範囲を件名から判断できる。
一つの対象と変化で書けない差分は目的の異なる変更を含み、分ければ変更単位を一つの理由で取り消せる。
変更を依頼した人や行った人は変更の内容に属さず、件名に書けば読む妨げになり、個人の情報を履歴に固定する。

### 完了条件
commit の件名から、変更の対象と、その対象に起きた操作と、それで成り立つ結果が分かる。
件名の対象が、repository の中の置き場所や分類の名前でなく、読み手が扱う作業や物の名前で書かれている。
一つの commit が、一つの対象と一つの変化を持つ。
変更したファイルや操作の列挙だけで、変化を代用していない。
commit の件名に、個人名がない。

### 禁止事項
「〜の採用」「〜の整備」「〜の明確化」のような評価だけを表す語で、対象と変化を書かずに目的をまとめること。
directory、file、層の名前を、件名の対象にすること。
変更したファイルや編集操作だけを並べ、何がどう変わったかを書かないこと。
複数の対象や変化を、一つの commit へまとめること。
短い件名に収める代わりに、独立した判断をまとめた長い本文へ変化を退避すること。
commit の件名に、依頼者、作業者、参考にした人の名前を書くこと。

### 行動
着手前に、変更の対象と、その対象で成り立たせる変化を一つに定める。
対象を読み手が扱う作業や物の名前で言えるかを確かめ、言えなければ変更の範囲を見直す。
その対象と変化を commit の件名へ書き、属さない差分を別の commit へ分ける。
現在も採れない実装の理由は、[comment](../comment/rejected-alternatives.md) の「実装コメントは採らなかった理由だけを書く」に従って判断の所有者へ残す。

### 例
評価だけを表す語で目的をまとめると、何に何をしてどうなったかが分からない。

```text
feat: 事実の行から今の状態を導くデータ設計の採用
```

repository の中の分類の名前を対象にすると、その構造を知らない読み手には何に効く変更かが分からない。

```text
feat: data 原則への状態の導出の規律の追加
```

読み手が扱う作業を対象にし、そこで何がどう変わったかを書けば、件名だけで変更が分かる。

```text
feat: テーブル設計で状態の列を置かず事実の行から導く規律の追加
```

操作だけを書くと、変更で何が成り立ったかが分からない。

```text
fix: verifier の失敗処理の変更
```

対象に起きた操作と、それで成り立つ結果を書けば、変更の目的を直接読める。

```text
fix: verifier の異常終了を失敗に数える判定の追加
```
