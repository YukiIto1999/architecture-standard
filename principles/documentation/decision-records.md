## 設計判断の理由を決定の記録に残す

### 要求
構造に影響する決定は、文脈・代替案・帰結とともに記録し、その決定を実現した変更から辿れるようにする。
決定の記録は、対象 project の repository が保持する成果物の外に残す。
記録の置き場は、この要求を満たすものを project が一つ選び、対象 project の README に宣言する(root の [README](../../README.md) の標準の単一性とプロジェクト側の記載形式に従う)。
選ぶ置き場は、決定を実現した変更の履歴を保持する間、保守者が同じ識別子から当時の本文を読めるものとする。置き場や読取権限を変える場合も、この追跡を失わせない。
決定は、実装に着手する前に下し、記録する。
覆すときは、古い記録の内容を書き換えず、置き換えられたことが分かる印を付け、新しい記録から古い記録を指す。
採用した判断を変えずに確定済みの記録を訂正するときも、元の本文を残し、訂正内容とその理由を追記または別の記録で辿れるようにする。採用した判断を変える場合は、訂正と呼ぶ場合も決定を覆す手順に従う。

### 根拠
最も追跡が難しいのは、設計判断の動機である。
動機を知らずに来た者は、決定を盲目的に受け入れるか、盲目的に変えるしかない。
commit log は変更の直接の目的を持つが、判断に至った文脈、代替案、帰結までは保持しない。
決定の記録は当時の判断を示す事実であり、現在の状態の説明ではない。
repository の成果物として置くと、記録が現在の状態を示すものと同じ寿命で扱われ、記録の改訂が現在の説明として読まれる。
決定を実現した変更から辿れれば、記録と、それが効いている差分が結び付く。
置き場が複数あると、同じ判断の記録が分かれ、どれが有効かを判定できない。
検討した代替案を残すと、なぜそれを採らなかったかが分かる。
古い記録を消すと、当時の判断が失われ、同じ議論を繰り返す。
外部の置き場で本文や参照が失われれば、変更の履歴だけが残っていても、その理由を検証できない。
古い記録に印がないと、その記録だけを読んだ者が、覆された決定を有効なものとして受け取る。

### 完了条件
構造に影響する決定が、文脈・代替案・帰結とともに、その決定を実現した変更から辿れる。
決定の記録が、その決定を実装する変更より前に作成されている。
記録に、検討した代替案と、それを採らなかった理由が含まれている。
覆された決定の記録が、消されず、置き換えられたことが分かる印を持ち、新しい記録から指されている。
一つの記録が、一つの判断に対応している。
記録の置き場が一つに定まり、対象 project の repository の外にある。
選んだ置き場が、対象 project の README から辿れる。
置き場の保存期間と読取権限が変更履歴の保持期間を覆い、保守者が変更から当時の本文へ辿れる。
訂正や置き場の移行の後も、元の本文と訂正内容を同じ識別子から読める。

### 禁止事項
構造に影響する決定を、根拠を残さずに行うこと。
決定の記録を、対象 project の repository の成果物として置くこと。
複数の逸脱または判断を、一つの記録へまとめること。
決定を覆すときに、古い記録の内容を書き換えるか消すこと。
確定した判断の本文を、当時の内容を復元できない形で上書きすること。
覆された決定の記録を、印のないまま残すこと。

### 行動
構造・依存・公開面・非機能特性に影響する決定をしたら、文脈・代替案・帰結を記録し、その決定を実現する変更から辿れるようにする。
覆すときは、古い記録へ置き換えられた印を付け、新しい記録に、置き換えた記録への参照を書く。
置き場を選ぶときと移すときは、保存期間、保守者の読取権限、元の本文の保持、既存の識別子からの到達を確認する。
標準からの逸脱を採る決定の記録は、root の [README](../../README.md) が定める要件に従う。

### 例
commit log に変更の直接の目的だけを書くと、判断の文脈と代替案は残らない。

```text
fix: process 間で session を共有する
```

決定の記録は、文脈、採らなかった案とその理由、決定、帰結を持つ。

```text
session を外部の session store に保持する

BFF はトークンを外部に出さないので、session を server 側に持つ必要がある。
候補は外部の session store、RDB のセッションテーブル、署名付き Cookie。
RDB は寿命の短いデータで負荷が増え、Cookie は失効と改ざんの運用が重い。
不透明な session id を鍵に、TTL つきで外部の session store へ保持する。
失効が TTL で自動になり、RDB から負荷を分離できる。
session store の可用性が認証の可用性に直結する。冗長化は別の決定として残す。
```
