# naming

naming は、命名と語彙に関する原則を置く。
名前で意味を表し、業務の語彙を統一する。
識別子は英語で書き、役割と具体で名付ける。
汎用名と略語を制限し、種類ごとに名付け、テスト名で仕様を表す。
casing と接辞の形式の規約は言語ごとに異なるため、[languages](../languages/) に置く。

## 名前で意味を表す

### 要求
名前は、対象がなぜ存在し、何をし、どう使うかを表す。
名前で表せる意味を、コメントへ逃がさない。

### 根拠
名前は、重要なものに注意を集め、重要でない詳細を省く抽象の境界である。
コメントを足さないと意味が分からない名前は、意図を表せていない。
型や構造を偽って示唆する名前は、読み手を誤らせる。
要素の実体が一覧でないのに一覧と名付けると、読み手は誤った前提を持つ。
名前は対象の意味を正確に表すほどよいが、説明文になるほど長いのは名前でなく散文である。
業務の概念は、実装の用語でなく業務の語で名付けると、保守する者が業務側に確認できる。

### 完了条件
名前から、対象の意味・責務・用途が読み取れる。
コメントなしで意味が分かる名前になっている。
型や構造を偽って示唆する語が、名前に含まれていない。

### 禁止事項
意味をコメントで補う前提の名前を付けること。
実体と異なる型や構造を示唆する語を、名前に含めること。
対象の意味を表さず、複数の用途に使える汎用な名前を付けること。

### 行動
名前を見て、コメントなしで意味が読み取れるか確かめる。
読み取れなければ、コメントの追加でなく命名の修正で直す。
実装の用語で足りなければ、業務の語を使う。

### 例
```ts
// 何の日数か、単位は何か分からない
let d = 0;
// 意図(経過)と単位(日)を名前に表す
let elapsedDays = 0;

// 集合を List と名付け、実体と異なる型を示唆する
const accountList: Set<Account> = new Set();
// 型を示唆せず実体を表す
const accounts: Set<Account> = new Set();
```

## 語彙を統一する

### 要求
同じ概念には同じ語を、異なる概念には異なる語を使う。
業務概念は、会話・文書・コードを貫いて、統一した語彙で表す。

### 根拠
同じ概念に取得・参照・取り出しのような複数の語を混ぜると、別物かと読み手が迷う。
同じ語を異なる概念へ流用すると、意味が二重になり誤読を生む。
語を変えただけで意味の変わらない区別は、情報を増やさない。
情報・データのような語は、冠詞と同じく意味のないノイズであり、意味のある区別を作らない。
業務概念と型と名前を一致させると業務と実装の対応が保たれ、語彙の改訂はモデルの改訂になる。

### 完了条件
同一の概念が、コード・schema・DB・UI・文書で同じ語で表されている。
一つの概念に複数の語、一つの語に複数の概念が、混在していない。
語を変えただけで意味の変わらない区別が、残っていない。

### 禁止事項
同義の語・略称・旧名称・表示名・物理名を混在させること。
一つの語を、異なる概念へ流用すること。
情報・データのようなノイズ語で、意味のない区別を作ること。

### 行動
対象概念の既存の名称を、コード・schema・DB・UI・文書から横断検索する。
正式な語を決め、同一の概念を統一し、意味が異なるものは語を分ける。

### 例
```ts
// 同じ概念に異なる語、区別に意味がない
getUserInfo();
getUserData();
// 返すもので区別し、語を一つに統一する
getUserProfile();
getUserActivityLog();
```

## 識別子を英語で書く

### 要求
型・関数・変数・モジュール・テストの名前を、英語で書く。
業務概念を表す語も、英語で定める。

### 根拠
識別子の言語が混ざると、語彙の対応が崩れ、検索と補完と通読を妨げる。
日本語やローマ字の識別子は、英語の予約語や API と並んだとき表記が不揃いになり、誤読を招く。
業務概念に英語の語を一つ定めれば、その語が会話の日本語と実装の識別子を結ぶ。
テスト名も識別子であり、英語の一文で書けば、検証対象と条件と期待結果が他の名前と同じ語彙で並ぶ。

### 完了条件
型・関数・変数・テストの名前が、すべて英語である。
日本語やローマ字の識別子が、残っていない。
業務概念を表す語が、英語で定まっている。

### 禁止事項
識別子に、日本語やローマ字を使うこと。

### 行動
業務概念を表す英語の語を決め、その語で識別子を書く。
日本語やローマ字の識別子を見つけたら、英語へ直す。

### 例
```ts
// 日本語やローマ字の識別子。英語の予約語や API と並ぶと不揃いになる
const 注文 = getOrder(id);
function chumonWoKakutei(order: Order) {}
// 業務概念を英語の語で定め、識別子を英語で書く
const order = getOrder(id);
function placeOrder(order: Order) {}
```

## 役割と具体で名付ける

### 要求
名前は、対象が何であるかでなく、何の役割を果たすかを表す。
意味範囲の広い汎用語や、技術都合の語で名付けない。

### 根拠
意味範囲の広い名前は、異なる役割の処理を際限なく吸収し、肥大した型や関数を生む。
Manager・Util・Helper のような語は、何をするかを伝えず、肥大の残渣や寄せ集めの兆候になる。
Int・Flag・Info・Data のような技術都合の語は、業務上の意味範囲を伝えない。
何をするか一意に答えられない名前は、答えられるまで構造を見直す合図である。
インタフェースの実装に妥当な名前を付けられないのは、責務が多すぎる兆候である。

### 完了条件
名前が、対象の役割または動作を一意に表している。
Manager・Util・Helper・Info・Data・Flag のような語が、寄せ場として使われていない。
インタフェースと実装が、役割の分かる名前で名付けられている。

### 禁止事項
意味範囲の広い汎用語や、Manager・Util・Helper を寄せ場として使うこと。
Int・Flag・Info・Data・Update のような技術都合の語で、業務概念を名付けること。

### 行動
名前が役割または動作を一意に表すか確かめる。
何をするか一意に言えなければ、言えるまで構造を分け、名前を具体にする。
技術都合の語があれば、業務の語または役割の語へ置き換える。

### 例
```ts
// 技術都合で大雑把。何をするか不明
class UrlManager {}
class CustomerUtils { static getNumber() {} }
// 役割と具体で名付ける。動作が一意になる
class UrlBuilder {}
class CustomerNumberGenerator { next(): CustomerNumber {} }
```

## 汎用名・略語・一時名を制限する

### 要求
意味の薄い汎用名・未定義の略語・一時しのぎの名前を、本実装に残さない。

### 根拠
汎用名は複数の用途に使えるため、情報量が低い。
temp のような名前は、その値の本当の目的を理解していない兆候である。
num のような曖昧な語は、総数か特定の一件かを区別しない。
過度な略語や単一文字名は、検索を困難にし、誤読と誤入力を招く。
型やスコープを名前へ埋め込む符号化は、名前を読みにくくする。
似て非なる名前を近くに置くと、取り違えを生む。

### 完了条件
data・info・item・temp・num・manager のような汎用名が、意味を補わずに使われていない。
未定義の略語と、本実装に残る一時名がない。
型やスコープを名前へ埋め込む符号化が残っていない。

### 禁止事項
意味の薄い汎用名を、意味を補わずに使うこと。
未定義の略語・母音抜き・過度な短縮を使うこと。
temp・work・tmp・new・old のような一時名を、本実装に残すこと。
型やスコープを、名前へ埋め込むこと。

### 行動
汎用名・略語・一時名を検出し、対象の意味を表す具体名へ変える。
総数と特定の一件のように、意味が異なるものは別の名前に分ける。

### 例
```ts
// 汎用名・略語・番号での区別、および型を名前に埋め込む
let temp = base + tax;
let num = customers.length;
const [file1, file2] = sources;
let nameString = user.name;
// 役割を表す具体名にし、型は名前から外す
let totalPriceWithTax = base + tax;
let customerCount = customers.length;
const [sourceFile, destinationFile] = sources;
let name = user.name;
```

## 種類ごとに名付ける

### 要求
真偽値は肯定形で真偽が読める名前にし、集合は複数性を表し、関数は動作と副作用の有無を表し、型は名詞にし、状態と種別を区別する。

### 根拠
真偽値の否定形は、否定されると二重否定になり読みづらい。
状態か真偽か分からない名前は、条件式の意味を曖昧にする。
集合に単数の名前を付けると、単数の値と取り違える。
値を返す問い合わせと、状態を変える命令を一つの関数に混ぜると、呼び出しの副作用が読めない。
問い合わせは、何度呼んでも答えが変わらない参照透過であるべきである。
フラグや裸の数値で状態と種別を表すと、その値の意味を知らないと読めない。

### 完了条件
真偽値が肯定形で、真偽が名前から読み取れる。
集合の名前が、複数性と要素の意味を表している。
関数名が、動作または問い合わせと、副作用の有無を表している。
型名が、対象の概念を表す名詞または名詞句になっている。
状態と種別が、フラグや裸の数値でなく、状態名と名前付きの列挙で区別されている。

### 禁止事項
否定形や二重否定になる真偽値の名前を使うこと。
関数の名前が、問い合わせか命令かを偽ること。
状態をフラグで、種別を裸の数値で表すこと。

### 行動
真偽値を肯定形へ、集合を複数形へ、型名を名詞へ直す。
副作用のある命令と、値を返す問い合わせを分ける。
状態は状態を表す名前に、種別は名前付きの列挙にする。

### 例
```ts
// 否定形・真偽不明・命令と問い合わせの混在
if (!notDone) {}
if (status) {}
const balance = account.withdraw(amount);   // 取得と副作用が混ざる
// 肯定形・真偽が明確・命令と問い合わせを分ける
if (isComplete) {}
if (isPaymentAccepted) {}
account.withdraw(amount);                    // 命令
const balance = account.balance();           // 問い合わせ
```

## テスト名は仕様を表す

### 要求
テスト名は、検証対象・条件・期待結果を表す。
失敗したテストの名前だけで、どの仕様が壊れたかが分かるようにする。

### 根拠
テストは検証であると同時に、仕様の文書である。
番号や正常系・異常系だけの名前は、何を検証しているかを伝えない。
検証対象と条件だけ、あるいは期待結果だけでは、失敗の意味が分からない。
三つを含めれば、コードを読まずに名前だけで失敗の意味が分かる。
テスト名が対象を主語とする一文として読めると、名前だけで仕様が伝わる。

### 完了条件
テスト名から、検証対象・条件・期待結果が読み取れる。
番号や、正常系・異常系だけの名前が残っていない。
テスト名が、仕様を表す一文として読める。

### 禁止事項
test1・チェックのような、検証内容が分からない名前を使うこと。
検証対象・条件・期待結果のいずれかを欠いた名前を使うこと。

### 行動
テスト名に、検証対象・条件・期待結果の三つを含める。
名前だけで失敗の意味が分かるか確かめ、分からなければ仕様を表す名前へ直す。

### 例
```ts
// 何の仕様か、失敗で何が壊れたか分からない
test("test1", () => {});
test("process", () => {});
// 検証対象・条件・期待結果を表す
test("withdrawing more than the balance fails and leaves the balance unchanged", () => {});
```
