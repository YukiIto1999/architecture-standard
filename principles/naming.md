# naming

naming は、命名と語彙に関する原則を置く。
名前で意味を表し、業務の語彙を統一する。
識別子は英語で書き、役割と具体で名付ける。
汎用名と略語を制限し、種類ごとに名付ける。
参照範囲で名前の可変性を見積もり、最初の命名を丁寧にして乱れを早期に直し、テスト名で仕様を表す。
casing と接辞の形式の規約は言語ごとに異なるため、[languages](../languages/) に置く。

## 名前で意味を表す

### 要求
フォルダ、ファイル、モジュール、型、関数、値の名前は、対象の意味と責務を表す。
名前で表せる意味を、コメントへ逃がさない。

### 根拠
名前は、重要なものに注意を集め、重要でない詳細を省く抽象の境界である。
コメントを足さないと意味が分からない名前は、意図を表せていない。
型や構造を偽って示唆する名前は、読み手を誤らせる。
要素の実体が一覧でないのに一覧と名付けると、読み手は誤った前提を持つ。
誤解を招く名前は、意味のない名前より悪い。
読み手は無意味な名前には騙されないが、誤解を招く名前は信じたまま誤る。
名前と中身の食い違いに気づいた読み手は、書き手への信頼を失い、以後のコード全体を疑う防御的な読みに切り替わる。
命名は設計の行為であり、一度では正しくならず、対象の理解が深まるたびに直す機会が生まれる。
名前は書き手の覚え書きでなく読み手への伝達であり、独りよがりな表現より誰にでも伝わる語を選ぶ。
名前は対象の意味を正確に表すほどよいが、説明文になるほど長いのは名前でなく散文である。
業務の概念は、実装の用語でなく業務の語で名付けると、保守する者が業務側に確認できる。

### 完了条件
名前から、対象の意味と責務が読み取れる。
コメントなしで意味が分かる名前になっている。
型や構造を偽って示唆する語が、名前に含まれていない。

### 禁止事項
意味をコメントで補う前提の名前を付けること。
実体と異なる型や構造を示唆する語を、名前に含めること。
対象の意味を表さず、複数の用途に使える汎用な名前を付けること。

### 行動
名前を見て、コメントなしで意味が読み取れるか確かめる。
読み取れなければ、コメントの追加でなく命名の修正で直す。
正しい名前がまだ決まらないときは、先に、少なくとも誤解を招かない名前へ直す。
名前は一度で決めず、理解が深まるたびに見直す。
実装の用語で足りなければ、業務の語を使う。

### 例
短縮名では経過日数という意図と日という単位が分からず、実体が Set の集合を `accountList` と呼ぶと異なる型を示唆する。

```ts
let d = 0;
const accountList: Set<Account> = new Set();
```

`elapsedDays` は意味と単位を表し、`accounts` は実体を偽らない。

```ts
let elapsedDays = 0;
const accounts: Set<Account> = new Set();
```

## 語彙を統一する

### 要求
同じ概念には同じ語を、異なる概念には異なる語を使う。
業務概念は、会話・文書・コードを貫いて、統一した語彙で表す。
統一の範囲は、一つの境界付けられたコンテキストの内とする。
語の定義には、その語が通用するコンテキストを添える。

### 根拠
同じ概念に取得・参照・取り出しのような複数の語を混ぜると、別物かと読み手が迷う。
動作の語も統一の対象であり、同じ動作には同じ動詞を使い、手元の計算か外部への取得かのような処理の実態に即して動詞を選ぶ。
同じ語を異なる概念へ流用すると、意味が二重になり誤読を生む。
一つの実装が異なる目的に使われるなら、外から見れば別の概念であり、実装を共有したまま別の名前の要素に分ける。
語を変えただけで意味の変わらない区別は、情報を増やさない。
情報・データのような語は、冠詞と同じく意味のないノイズであり、意味のある区別を作らない。
業務概念と型と名前を一致させると業務と実装の対応が保たれ、語彙の改訂はモデルの改訂になる。
語の意味は用法と文脈が決めるため、同じ語でもコンテキストが違えば意味も伴う規則も異なり、それは別の概念である。
コンテキストを越えて一つの意味を全域に強制すると、各コンテキストのモデルが互いの都合で歪む。

### 完了条件
同一の概念が、コード・schema・DB・UI・文書で同じ語で表されている。
一つのコンテキストの内で、一つの概念に複数の語、一つの語に複数の概念が、混在していない。
語の定義に、その語が通用するコンテキストが添えられている。
語を変えただけで意味の変わらない区別が、残っていない。

### 禁止事項
同義の語・略称・旧名称・表示名・物理名を混在させること。
一つの語を、異なる概念へ流用すること。
コンテキストを越えて、一つの語に一つの意味を強制すること。
情報・データのようなノイズ語で、意味のない区別を作ること。

### 行動
対象概念の既存の名称を、コード・schema・DB・UI・文書から横断検索する。
正式な語を決め、同一の概念を統一し、意味が異なるものは語を分ける。
語の意味は、その語を使うコンテキストごとに確かめ、コンテキストが違えば別の概念として扱う。

### 例
同じ概念を `Info` と `Data` で分けても意味の違いがない。`User` を共通の語にし、返すものを `Profile` と `ActivityLog` で区別する。

```ts
getUserInfo();
getUserData();
getUserProfile();
getUserActivityLog();
```

## 識別子を英語で書く

### 要求
型・関数・変数・モジュール・テストの名前を、英語で書く。
業務概念を表す語も、英語で定める。

### 根拠
識別子の言語が混ざると、語彙の対応が崩れ、検索と補完と通読を妨げる。
日本語やローマ字の識別子は、英語の予約語や API と並んだとき表記が不揃いになり、誤読を招く。
業務概念に英語の語を一つ定めれば、その語が会話の日本語と実装の識別子を結ぶ。
テスト名も識別子であり、英語の一文で書けば、検証対象と条件と期待結果が他の名前と同じ語彙で並ぶ。
命名規則の多くは、コードを英語の文として自然に読めるようにするための規則である。

### 完了条件
型・関数・変数・テストの名前が、すべて英語である。
日本語やローマ字の識別子が、残っていない。
業務概念を表す語が、英語で定まっている。

### 禁止事項
識別子に、日本語やローマ字を使うこと。

### 行動
業務概念を表す英語の語を決め、その語で識別子を書く。
日本語やローマ字の識別子を見つけたら、英語へ直す。

### 例
日本語やローマ字の識別子は、英語の予約語や API と並ぶと不揃いになる。業務概念に対応する英語の語を定め、識別子に使う。

```ts
const 注文 = getOrder(id);
function chumonWoKakutei(order: Order) {}
const order = getOrder(id);
function placeOrder(order: Order) {}
```

## 役割と具体で名付ける

### 要求
名前は、対象が何であるかでなく、何の役割を果たすかを表す。
意味範囲の広い汎用語や、技術都合の語で名付けない。

### 根拠
意味範囲の広い名前は、異なる役割の処理を際限なく吸収し、肥大した型や関数を生む。
対象が何であるかで名付けると機能を集める方向に、何をするかで名付けると分割する方向に、書き手は誘導される。
Manager・Util・Helper のような語は、何をするかを伝えず、肥大の残渣や寄せ集めの兆候になる。
Int・Flag・Info・Data のような技術都合の語は、業務上の意味範囲を伝えない。
呼ばれる時点や初期条件を写した名前は、役割でなく文脈を表し、抽象を壊す。
目的や意味を込めすぎた名前は、目的が変わるたびに改名を強いる。
機能追加のたびに接続の語を継ぎ足す名前は、名前が内部構造へ密結合した兆候である。
型や構造をそのまま説明する名前は、構造と名前の二重管理になり、食い違ったときどちらが正しいか判断できない。
何をするか一意に答えられない名前は、答えられるまで構造を見直す合図である。
インタフェースの実装に妥当な名前を付けられないのは、責務が多すぎる兆候である。

### 完了条件
名前が、対象の役割または動作を一意に表している。
Manager・Util・Helper・Info・Data・Flag のような語が、寄せ場として使われていない。
インタフェースと実装が、役割の分かる名前で名付けられている。

### 禁止事項
意味範囲の広い汎用語や、Manager・Util・Helper を寄せ場として使うこと。
Int・Flag・Info・Data・Update のような技術都合の語で、業務概念を名付けること。
呼ばれる時点や初期条件で、名付けること。
機能追加のたびに、接続の語を名前へ継ぎ足すこと。

### 行動
名前が役割または動作を一意に表すか確かめる。
何をするか一意に言えなければ、言えるまで構造を分け、名前を具体にする。
技術都合の語があれば、業務の語または役割の語へ置き換える。

### 例
技術都合の大雑把な名前では、役割や動作が分からない。構築と番号生成という具体の役割で名付け、動作を一意にする。

```ts
class UrlManager {}
class CustomerUtils { static getNumber() {} }
class UrlBuilder {}
class CustomerNumberGenerator { next(): CustomerNumber {} }
```

## 汎用名・略語・一時名を制限する

### 要求
意味の薄い汎用名・未定義の略語・一時しのぎの名前を、本実装に残さない。

### 根拠
汎用名は複数の用途に使えるため、情報量が低い。
temp のような名前は、その値の本当の目的を理解していない兆候である。
num のような曖昧な語は、総数か特定の一件かを区別しない。
過度な略語や単一文字名は、検索を困難にし、誤読と誤入力を招く。
型やスコープを名前へ埋め込む符号化は、名前を読みにくくする。
似て非なる名前を近くに置くと、取り違えを生む。

### 完了条件
data・info・item・temp・num・manager のような汎用名が、意味を補わずに使われていない。
未定義の略語と、本実装に残る一時名がない。
型やスコープを名前へ埋め込む符号化が残っていない。

### 禁止事項
意味の薄い汎用名を、意味を補わずに使うこと。
未定義の略語・母音抜き・過度な短縮を使うこと。
temp・work・tmp・new・old のような一時名を、本実装に残すこと。
型やスコープを、名前へ埋め込むこと。

### 行動
汎用名・略語・一時名を検出し、対象の意味を表す具体名へ変える。
総数と特定の一件のように、意味が異なるものは別の名前に分ける。
複数形の複数形が要る場面では、集合そのものに名前のある概念を定義する。

### 例
汎用名、略語、番号による区別は役割を隠し、型を埋め込んだ名前は宣言と重複する。役割を表す具体名に変え、型は名前から外す。

```ts
let temp = base + tax;
let num = customers.length;
const [file1, file2] = sources;
let nameString = user.name;
let totalPriceWithTax = base + tax;
let customerCount = customers.length;
const [sourceFile, destinationFile] = sources;
let name = user.name;
```

## 種類ごとに名付ける

### 要求
真偽値は、肯定形で真偽が読める名前にする。
集合は、複数性を表す名前にする。
関数は、動作と外部から観測できる業務状態を変えるかを名前に表す。
問い合わせは、外部から観測できる業務状態を変えない。
命令は、外部から観測できる業務状態を変える意図を名前に表す。
型は、名詞で名付ける。
状態と種別は、フラグや裸の数値でなく、名前のある形で区別する。

### 根拠
真偽値の否定形は、否定されると二重否定になり読みづらい。
状態か真偽か分からない名前は、条件式の意味を曖昧にする。
集合に単数の名前を付けると、単数の値と取り違える。
複数形にするかは、名前が内容物そのものを表すか、関連する対象や文脈を表すかで判断する。
内容物を表す名前は複数形が、文脈を表す名前は単数形が、読み手の予想と一致する。
広く使われる設計パターンの命名は、内容物と複数性の対応を含めてそのまま踏襲する。
値を返す問い合わせと、外部から観測できる業務状態を変える命令を一つの関数に混ぜると、呼び出しの結果が読めない。
問い合わせは外部から観測できる業務状態を変えないが、外部状態を読む問い合わせの結果は読み取り対象の変化に応じて変わりうるため、参照透過とは限らない。
問い合わせのためのキャッシュ更新や計測は、外部から観測できる業務状態を変えない限り、この規則に反しない。
フラグや裸の数値で状態と種別を表すと、その値の意味を知らないと読めない。

### 完了条件
真偽値が肯定形で、真偽が名前から読み取れる。
集合の名前が、複数性と要素の意味を表している。
関数名が、動作または問い合わせと、外部から観測できる業務状態を変えるかを表している。
問い合わせの実行前後で、外部から観測できる業務状態が変わっていない。
型名が、対象の概念を表す名詞または名詞句になっている。
状態と種別が、フラグや裸の数値でなく、状態名と名前付きの列挙で区別されている。
複数形の採否が、内容物か文脈かの基準で説明できる。

### 禁止事項
否定形や二重否定になる真偽値の名前を使うこと。
関数の名前が、問い合わせか命令かを偽ること。
問い合わせで、外部から観測できる業務状態を変えること。
状態をフラグで、種別を裸の数値で表すこと。

### 行動
真偽値を肯定形へ、集合を複数形へ、型名を名詞へ直す。
外部から観測できる業務状態を変える命令と、その状態を変えずに値を返す問い合わせを分ける。
外部状態を読む問い合わせは、参照透過であることを判定条件にしない。
キャッシュ更新や計測を、外部から観測できる業務状態の変更と区別する。
状態は状態を表す名前に、種別は名前付きの列挙にする。

### 例
否定形や真偽が不明な名前は条件を誤読させる。値を返す操作で業務状態まで変えると、命令と問い合わせの区別も失われる。

```ts
if (!notDone) {}
if (status) {}
const balance = account.withdraw(amount);
```

真偽値は肯定形で名付け、状態を変える命令と、状態を変えずに値を返す問い合わせを分ける。

```ts
if (isComplete) {}
if (isPaymentAccepted) {}
account.withdraw(amount);
const balance = account.balance();
```

## 参照範囲で可変性を見積もる

### 要求
名前を付けるとき、その名前が後から変えられるかを、外部からの参照範囲で見積もる。
参照が広く改名が難しい名前ほど、最初に時間をかけて決める。

### 根拠
名前の変えやすさは、層の上下でなく、どれだけ広く参照されるかで決まる。
公開契約・schema・永続データ・URL に現れる名前は、利用側を巻き込まないと変えられない。
局所の名前は機械的な改名で安全に変えられるが、読み手には名前を覚え直す認知の負担が残る。
認知の負担は改名をやめる理由でなく、改善の効果と比べる要素である。
名前の改善がシステムの理解を進めるなら、改名は積極的に行う。
公開面そのものの安定の設計は、[separation](./separation.md) の関心を境界の内に隠すに従う。

### 完了条件
参照範囲の広い名前が、命名の時点で検討を経て決まっている。
改名の判断が、参照範囲と改善の効果の比較で説明できる。

### 禁止事項
参照範囲を確かめずに、公開契約や永続データの名前を仮のまま公開すること。
認知の負担だけを理由に、誤解を招く名前の改名を退けること。

### 行動
命名の時点で、その名前がどこまで参照されるかを確かめる。
参照が広い名前は精密に決め、局所の名前は誤解を招かない形で早く付けて見直す。

### 例
公開 schema に仮の名前を出すと、利用側を巻き込まずには変えられない。

```json
{ "usrNm": "..." }
```

参照の広い名前は名付けの時点で決める。局所の変数は後から安全に変えられる。

```json
{ "userName": "..." }
```

## 最初の命名を丁寧にし、乱れを早期に直す

### 要求
新しい領域の最初の命名は、既存の規則と語彙に照らして丁寧に決める。
規則に反する名前は、見つけたら早期に直す。

### 根拠
最初の命名は後続の書き手に模倣され、コード全体の命名慣習の起点になる。
命名規則の目的は、新しく加わる書き手が名付けに迷わないことである。
不適切な名前は、放置すると派生する名前を巻き込みながら広がり、時間が経つほど直す費用が増える。

### 完了条件
新しい領域の名前が、既存の規則と語彙に沿っている。
規則に反する名前が、派生を生む前に直されている。

### 禁止事項
規則に反する名前を、慣習として定着するまで放置すること。

### 行動
新しい領域では、最初の命名を既存の命名規則と語彙への照合で決める。
乱れを見つけたら、参照範囲を確かめて早期に改名する。

### 例
最初の乱れた命名は模倣され、派生しながら慣習になる。最初の名前を既存の規則と語彙に照らして決め、乱れは派生する前に直す。

```ts
function getUserInfo() {}
function getUserInfo2() {}
function findUserProfile() {}
```

## テスト名は仕様を表す

### 要求
テスト名は、検証対象・条件・期待結果を表す。
失敗したテストの名前だけで、どの仕様が壊れたかが分かるようにする。

### 根拠
テストは検証であると同時に、仕様の文書である。
番号や正常系・異常系だけの名前は、何を検証しているかを伝えない。
検証対象と条件だけ、あるいは期待結果だけでは、失敗の意味が分からない。
三つを含めれば、コードを読まずに名前だけで失敗の意味が分かる。
テスト名が対象を主語とする一文として読めると、名前だけで仕様が伝わる。

### 完了条件
テスト名から、検証対象・条件・期待結果が読み取れる。
番号や、正常系・異常系だけの名前が残っていない。
テスト名が、仕様を表す一文として読める。

### 禁止事項
test1・チェックのような、検証内容が分からない名前を使うこと。
検証対象・条件・期待結果のいずれかを欠いた名前を使うこと。

### 行動
テスト名に、検証対象・条件・期待結果の三つを含める。
名前だけで失敗の意味が分かるか確かめ、分からなければ仕様を表す名前へ直す。

### 例
汎用的なテスト名では、何の仕様が壊れたかを失敗時に特定できない。検証対象、条件、期待結果をテスト名に表す。

```ts
test("test1", () => {});
test("process", () => {});
test("withdrawing more than the balance fails and leaves the balance unchanged", () => {});
```
