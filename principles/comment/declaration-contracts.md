## ドキュメントコメントは宣言の契約を書く

### 要求
公開範囲を問わず、宣言した型、関数、メンバにドキュメントコメントを付ける。
公開宣言は境界外の利用側への外部契約を、非公開宣言は同一境界内の呼び出し側への内部契約を述べる。
ドキュメントコメントは、宣言の目的と、該当する事前条件、事後条件、不変条件、副作用、失敗条件を述べる。
宣言の署名が持つ引数、型引数、戻り値は、名前や型から自明に見えても省かず、型が表さない役割か前提を述べ、その記法は [languages](../../languages/) が定める。
最初の一行は、名前の直訳でなく、呼び出し側が用途を判断できる目的を一行で示す。
ドキュメントコメントの記述の形は、[documentation](../documentation/sentence-endings.md) の「文末の形を記述の種類で分ける」に従う。

### 根拠
公開宣言は境界外の利用側へ保証を与え、非公開宣言にも同じ境界内の呼び出し側との契約がある。
型と名前だけでは、値の前提、状態の変化、失敗の条件を全て表せない。
契約を宣言の近くに置けば、呼び出し側は実装を読まずに正しく利用できる。
名前の言い換えしか書けない宣言は、独立した契約を持たないか、責務と命名が定まっていない可能性がある。
署名の要素を全て述べれば、記述と署名を一対一で照合でき、記述の欠けと署名との食い違いを見つけられる。

### 完了条件
公開範囲を問わず、宣言した型、関数、メンバにドキュメントコメントがある。
公開宣言が外部契約を、非公開宣言が内部契約を述べている。
各ドキュメントコメントが、宣言の目的と、該当する契約条件を述べている。
宣言の署名が持つ引数、型引数、戻り値が、型が表さない役割か前提とともに全て述べられている。
最初の一行から用途を判断でき、名前の言い換えになっていない。
ドキュメントコメントの契約が、現在の宣言と実装に一致している。

### 禁止事項
非公開であることを理由に、宣言の契約を未記述にすること。
公開宣言の契約を、同一境界内だけに通用する内部契約として書くこと。
名前や型から分かる内容だけを、ドキュメントコメントで言い換えること。
名前や型から自明に見えることを理由に、引数、型引数、戻り値の記述を省くこと。
該当しない契約項目を埋めるために、意味のない定型文を足すこと。
誤りと分かった契約を、直さずに残すこと。

### 行動
宣言ごとに、目的、前提、保証する結果、不変条件、副作用、失敗条件を確認し、該当するものだけを書く。
署名の引数、型引数、戻り値を記述と一対一で照合し、欠けを埋める。
公開宣言は境界外の利用側、非公開宣言は同一境界内の呼び出し側が依存してよい保証を書く。
名前の言い換えしか書けなければ、宣言の責務、分割、命名を見直す。
対象の宣言か実装を変えたら、同じ変更で契約を更新する。
契約を実装より先に書く判断は、[verification](../verification/tests-as-design.md) の「テストを設計の道具にする」に従う。

### 例
名前を言い換えただけでは、呼び出し側が知らなければならない契約を示せない。

```ts
/**
 * 候補の素数判定
 * @param candidate - 判定する候補
 * @returns candidate が素数なら true
 */
function isPrime(candidate: number): boolean { /* ... */ }
```

前提と再利用する状態を書けば、実装を読まずに正しく呼び出せる。

```ts
/**
 * 直前までの倍数表を再利用する連続した素数判定
 * @param candidate - 直前の呼び出しより大きい候補
 * @returns candidate が素数なら true
 */
function isPrime(candidate: number): boolean { /* ... */ }
```
