## テストを振る舞いの安全網にする

### 要求
テストは、外から見た振る舞いを検証し、小さく速いテストを厚く、外部に依存する遅いテストを薄く保つ。
テストの単位は、内部構造でなくuse-caseの境界に揃える。
配分の尺度と値は、project が決めて記録に残す。
遅いテストを薄くするのは、小さく速いテストで同じ性質を確かめられる重複を除くことであり、件数の削減を目標にしない。
実依存や実際の組合せでしか確かめられない性質と、他のテストが確かめていない振る舞いの検証は、遅いことを理由に削除・統合または置換しない。
テストを減らす操作は、削除・統合、通常の実行からの除外、別の検証への置換を区別し、いずれもそのテストだけが確かめている性質、振る舞い、入力の区分を特定してから行う。
不安定なテストの隔離は減らす操作に含めず、[テストの信頼性を保つ](./test-reliability.md) に従う。
削除・統合と置換は、残す検証がその違反を検出することを確かめてから行い、通常の実行から除くテストは、実行する契機と通常の実行へ戻す条件を定めて残す。
被覆した箇所や検出した変異の重複は、減らす候補を見つける手掛かりとし、それだけを減らす根拠にしない。
レガシーを変えるときは、現在の振る舞いを観測して固定するテストを先に置く。
現在の振る舞いを固定するテストは `Observed` を記録するものであり、その振る舞いが `Intended` であることを証明しない。
テストの緑は、テストが覆う既知の契約に対して回帰が検出されていないことだけを示すものとして扱う。
テストの緑を、仕様全体を満たすことの証明として扱わない。
対象を選んで状態を変える操作のテストは、選んだ対象の変化とともに、選ばれなかった対象が変わらないことを確かめる。

### 根拠
テストは振る舞いの安全網になり、変更しても壊れていないことを継続的に確かめられる。
型検査の緑は形の整合を示すだけで、振る舞いの保存はテストでしか確かめられない。
公開面が変わらず、参照がすべて静的に追跡でき、振る舞いのテストが緑なら、既知の契約に対する回帰が検出されていないと判断できる。
この結果は、仕様全体を満たすことの証明にはならない。
変更の規模は、差分の行数でなく、安全を確かめるのに要る検証の水準で測る。
検証の水準は、関数や型の内側、ファイルや境界、コンテキストを跨ぐ変更へと、段階的に上がる。
内部実装に依存したテストは、振る舞いが正しくても壊れ、保守の重荷になる。
テストの対象は、クラスやメソッドという構造でなく、入力から外から確認できる結果までの作業の単位である。
テストの重みは、アクターがドメインに触れるuse-caseの境界に置く。
内側の要素は型と契約の静的な保証に委ね、個別のテストを最小にする。
検証の総量は変わらず、静的な保証が広がるほど、テストで確かめる範囲は狭められる。
単位が上がるほど内部のロジックはテストから隠され、構造の変更にテストが耐える。
外から確認できる結果は、戻り値・状態の変化・外部への呼び出しの三種であり、置き換えによる呼び出しの検証が要るのは、外部への呼び出しが結果そのものであるときだけである。
状態の変化を選んだ対象の変化だけで確かめると、選ぶ条件の誤りで対象外まで変える欠陥が緑のまま残る。
変えるものだけを述べた仕様は変えないものを保証しないため、状態の変化の検証は、変えないものも結果に含める。
異なる結果を一つのテストで確かめると、最初の失敗で以降の確認が実行されず、名前もどの結果の仕様かを表せない。
テストは必要な資源の大きさで分け、単一プロセスで動く小さなテストを厚くする。
小さく速いテストは、変更の直後に回帰を知らせ、失敗した振る舞いを絞り込めるので、短く有益なフィードバックになる。
外部通信や DB を要するテストは遅く脆いので、依存を分け、小さく速いテストで確かめられる性質をそちらへ寄せる。
テストダブルで確かめられるのは、境界のこちら側の呼び出しと結果の扱いであり、相手が実際に返す結果や守る制約ではない。
実依存や実際の組合せでしか成り立たない性質は、小さなテストへ寄せても保証が移らず、それらを使うテストが担い続ける。
遅いテストを件数や比率だけを理由に除くと、そのテストだけが確かめていた性質や振る舞いの回帰が検出されなくなる。
性質を寄せた先が同じ違反を検出しなければ、寄せた分だけ保証が減る。
同じ箇所を通り同じ変異を検出するテストでも、別の入力の区分や実際の欠陥を確かめていることがあり、被覆や変異の検出の重複だけで除くと、その欠陥を露見させるテストを失う。
通常の実行から除いたテストは検証として残るが、実行する契機がなければ、除いた範囲の回帰はいつまでも検出されない。
現在の振る舞いを観測して固定するテストが先にあれば、レガシーの変更も安全網の下で進められる。
ただし、既知の欠陥または疑わしい挙動を仕様として正当化しないよう、確認済みの契約とは別に記録する必要がある。

### 完了条件
変更対象の振る舞いが、外から見た仕様としてテストされている。
テストが、内部実装でなく外から見た振る舞いに依存している。
一つのテストが、一つの結果だけを確認している。
対象を選んで状態を変える操作のテストが、選ばれなかった対象を少なくとも一つ用意し、それが変わらないことを確かめている。
小さく速いテストが厚く、外部依存の遅いテストが薄く、配分の尺度と値が project の記録で確かめられる。
実依存や実際の組合せでしか確かめられない性質のそれぞれに、その性質を実依存や実際の組合せで確かめるテストが対応している。
削除・統合または置換したテストだけが確かめていた性質について、その性質を破る変更を残す検証が検出した記録がある。
減らす操作として通常の実行から除いたテストに、実行する契機と通常の実行へ戻す条件が定められている。
テストの単位が、内部構造でなくuse-caseの境界に揃っている。
テストの緑が、テストが覆う既知の契約に対する回帰未検出の結果として扱われている。
現在の振る舞いを固定したテストが、確認済みの契約、既知の欠陥、疑わしい挙動のいずれを観測したものか区別されている。

### 禁止事項
内部実装の細部にテストを結びつけ、振る舞いが正しくても壊れる状態にすること。
戻り値か状態の変化で確かめられる振る舞いを、置き換えた依存への呼び出しの検証で確かめること。
対象を選んで状態を変える操作を、選んだ対象の変化だけで確かめること。
外部依存の遅いテストを厚くし、小さく速いテストを薄くすること。
遅いテストの件数や比率を整えるために、そのテストだけが確かめている性質や振る舞いの検証を削除・統合または置換すること。
被覆した箇所や検出した変異の重複だけを根拠に、テストを削除または統合すること。
減らす操作として、実行する契機を定めずにテストを通常の実行から除くこと。
テストダブルで確かめた責務を、実依存との結合の保証として扱うこと。
公開面が変わらずテストが緑であることから、仕様全体を満たしたと断定すること。
現在の振る舞いを固定したことから、その振る舞いが意図された仕様だと断定すること。

### 行動
変更対象の振る舞いを、使う側の視点でテストに表す。
検証する結果を戻り値・状態の変化・外部への呼び出しから特定し、結果ごとにテストを分ける。
同じ一つの結果への複数の確認は、分けずにまとめてよい。
対象を選んで状態を変える操作では、選ばれない対象を同じ置き場に用意し、操作の後に変わらないことを、選んだ対象の変化と同じ一つの結果の確認としてまとめる。
外部依存を分け、実依存を要しない性質をテストダブルで小さく速いテストに落とす。
実依存や実際の組合せでしか確かめられない性質は、それらを使う薄いテストとして残す。
テストを減らす前に、そのテストだけが確かめている性質、振る舞い、入力の区分を特定し、削除・統合、通常の実行からの除外、別の検証への置換のどれを行うかを決める。
削除・統合と置換では、[テストの信頼性を保つ](./test-reliability.md) に従い、その性質を破る変更を残す検証が検出することを確かめてから、元のテストを除く。
通常の実行から除くテストには、実行する契機と、通常の実行へ戻す条件(たとえば、残した検証が見逃した違反をそのテストが検出したとき)を定める。
レガシーは、現在の振る舞いを固定するテストを置いてから変える。
固定した振る舞いを、確認済みの契約、既知の欠陥、疑わしい挙動に分ける。
変更に着手する前に、どの水準の検証で安全を確かめられるかを見積もる。
緑になったテストが覆う既知の契約を特定し、仕様全体の充足は別に照合する。

### 例
内部の呼び出し回数を検証するテストは、振る舞いが正しくてもリファクタリングで壊れる。

```ts
expect(service.repository.saveCalls).toBe(1);
```

外から観測できる登録結果を検証すれば、実装を変えてもテストは壊れない。

```ts
const found = await service.register(input);
expect(found.status).toBe("registered");
```
