## 重要な制約を機械検証に固定する

### 要求
命名・配置・依存方向・公開面・境界・アーキテクチャ特性の制約は、機械で検証できる形に固定する。
重要な制約を、文書・口頭・レビューの指摘だけで運用しない。
実行可能な仕様は実装と同じ検査経路に載せ、別成果物として置く場合は両者の継ぎ目を検証する。

### 根拠
人の記憶やレビューの善意に頼ると、制約の違反が継続的に見逃される。
違反がコンパイルエラーやビルド失敗のような具体的な結果を生む形にして、初めて制約は守られる。
型検査・lint・依存の境界検査・アーキテクチャテストに固定し、リポジトリの検証入口から実行すれば、違反が継続的に検出される。
依存の向きやレイヤー越境は、規約のコメントでなく、実行できるテストとして強制する。
アーキテクチャ特性は、主観でなく客観の尺度で測る適応度関数にし、リポジトリの検証入口に組み込む。
計測するだけでは足りず、違反が出力を生んでフローを止めることが、ただの監視との違いである。
良い設計とは型が付く設計であり、型が付けば多くの制約を型検査が担える。
コードスタイルの細則は、人の合意でなく、単一の formatter と linter に委ねる。
単一の整形に委ねると、レビューから見た目の雑音が消え、本質的な指摘が際立つ。
整形の論争そのものが消え、合意の費用が要らなくなる。
検証のゲートは、コードの出自が人か生成かを問わず、一律に適用される。
規則を満たすことと問題を解くことは別であり、機械検証を通ることは設計の正しさを保証しない。
機械検証が届くのは静的に追跡できる参照だけであり、追跡できない参照は影響を測れない無限の依存として扱う。
自動テストの一式は、機能と同時に作る欠陥検出器になる。
実行可能な仕様を実装と同じ経路で検査すれば、両者の不整合を同じ結果として検出できる。
仕様が実装と別の成果物なら、同じ検査経路に載せても、仕様と実装を対応付ける継ぎ目は残る。

### 完了条件
公開 API・境界名・依存方向・公開面・配置・境界違反・アーキテクチャ特性が、型・lint・構造検査・テスト・計測のいずれかで検証され、リポジトリの検証入口から実行されている。
検証のゲートが、コードの出自が人か生成かを問わず、一律に適用されている。
依存方向やレイヤー越境が、実行できるテストとして強制されている。
手作業のレビューでしか検出できない、要求に列挙した制約が残っていない。
コードスタイルの細則が、formatter と linter に委ねられている。
実行可能な仕様と実装が同じ検査経路に載り、別成果物である場合は両者の対応が検証されている。

### 禁止事項
重要な制約を、文書・口頭・レビュー指摘だけで運用すること。
機械で検証できる制約を、人手のレビューに委ねること。
違反しても何も起きない、結果を生まない検証を置くこと。
検証規則を、無効化の注記で局所的に回避すること。
実行可能であることを理由に、別成果物である仕様と実装の継ぎ目が消えたとみなすこと。

### 行動
制約ごとに、型・lint・import 境界・アーキテクチャテスト・計測のどれで検証できるかを判断し、判定できる検査をリポジトリの検証入口へ組み込む。
検証手段がなければ、ルール・テスト・設定を足して検証可能にする。
同じ規則への無効化が繰り返されるなら、違反箇所の免除でなく、規則の適用範囲を見直す。
規則への不遵守が繰り返されるなら、違反の側だけでなく、規則の側の妥当性も疑う。
繰り返し問題になる判断は、個人の判断のままにせず、明文の規則へ昇格させ、機械検証へ近づける。
静的に追跡できない参照を見つけたら、追跡できる形へ直す。
実行可能な仕様を実装と同じ検査経路に載せ、別成果物なら両者の対応も検査する。

### 例
「domain は infra に依存しない」と文書に書くだけでは違反を防げない。依存の層を契約として宣言し、上位から下位だけへ依存できることと推移依存を検査する。違反はリポジトリの検証入口で失敗させ、言語ごとの手段は tools の inspection に置く。

```text
contract: layered
layers:
    interfaces
    domain
    data
```
