# requirements

requirements は、要件の確定に関する原則を置く。
目的から要件を導き、判断を左右する主張の根拠と決定状態を分けて記録し、検証できる形で要件と制約を定める。
確定した制約と振る舞いの検証は [verification](./verification.md) に従う。

## 目的から要件を導く

### 要求
解くべき問題は、観測された事実と解釈を分けて定める。
要件は、候補の手段からでなく、目的から例を挙げて導く。

### 根拠
事実と解釈の混同は、存在しない問題を解かせる。
候補の手段を先に固定すると、目的に合わない構造が要件の顔をして残る。
手段に何のためかを問うて上位の目的へ遡ると、同じ目的を満たす別の手段を比較できる。
技術の語を除いても通じる問題の記述は、解き方を縛らずに、解くべきことだけを固定する。
目的から挙げた具体例は、抽象の語で合意するより先に、認識の食い違いを表面化させる。

### 完了条件
問題の記述が、観測された事実と、事実への解釈に分かれている。
問題の記述から技術の語を除いても、意味が通る。
要件のそれぞれが、どの目的に仕えるかを一言で言える。
要件に、目的から挙げた具体例が添えられている。

### 禁止事項
候補の手段を、目的を問わずに要件として固定すること。
観測されていない解釈を、事実として問題の記述に書くこと。

### 行動
要件に手段の名が現れたら、何のためかを問うて上位の目的へ遡る。
遡った目的から具体例を挙げ、例が示す振る舞いを要件へ降ろす。
この往復を、手段への固定が外れるまで繰り返す。
導いた要件は、「検証できる形で要件と制約を定める」に従い、観測できる形へ直す。

### 例
「一覧の結果をキャッシュする」では手段が要件として固定され、目的を問えない。繰り返しの閲覧を待たせないという目的へ遡り、具体例から観測できる要件へ降ろす。

```text
「一覧の結果をキャッシュする」

目的  繰り返しの閲覧を待たせない
例    同じ条件の一覧を、続けて開き直す
要件  同一条件の一覧の再表示が、初回の表示より速い
```

## 根拠と決定状態を分ける

### 要求
判断または変更を左右する主張は、根拠の状態と決定の状態を分けて記録する。
根拠の状態は、一次資料または明示された契約に基づく `Known`、列挙した `Known` から論理的に導いた `Derived`、現行のコード・テスト・実行結果を示す `Observed`、未確認の `Assumed`、現時点で判断できない `Unknown` とする。
意図を述べる主張には、確認済みの意図を示す `Intended` または明示的に決めた変更先を示す `Target` を、根拠の状態とは別に付ける。

### 根拠
現行実装は現在そう動くことを示すが、本来そうあるべきことまでは示さない。
一般的な慣習や領域知識は、対象システム固有の契約を補完しない。
根拠と意図を一つの分類へ混ぜると、観測した挙動を仕様と誤認したり、決定した目標を既存の事実として扱ったりする。
判断を左右する主張だけに状態を付ければ、全ての文を分類する負担を増やさず、推論の弱い継ぎ目を追跡できる。

### 完了条件
判断または変更を左右する主張に、根拠の状態が付いている。
`Known` と `Observed` に出典または観測箇所があり、`Derived` に導出元の主張がある。
意図または変更先を述べる主張に、`Intended` または `Target` が根拠の状態と別に付いている。
`Assumed` と `Unknown` が、未確認のまま確定した判断へ使われていない。

### 禁止事項
`Observed` を `Intended` とみなすこと。
一般的な慣習、一般的な領域知識、エージェントの推測を `Known` とみなすこと。
`Assumed` または `Unknown` だけを根拠に、違反、変更内容、完了を確定すること。
`Target` を、現行の事実または確認済みの意図として扱うこと。

### 行動
判断または変更を左右する主張を抽出し、根拠の状態を付ける。
`Known` と `Observed` には file・行・一次資料・コマンド結果のいずれかを添え、`Derived` には導出元を列挙する。
意図が必要な主張は、確認して `Intended` とするか、変更の決定として `Target` を定める。
確認できない主張は `Unknown` のまま残し、その主張に依存する判断を止める。

## 検証できる形で要件と制約を定める

### 要求
要件と完了条件は、観測できる尺度と閾値で定める。
検証できないものは、要件として置かない。

### 根拠
検証できない要件は、満たされたかを判定できず、合意したつもりの食い違いを残す。
要件は、人か機械が有限の手間で満たしたかを確認できるときだけ、検証できる。
「使いやすい」「速い」「直感的」のような曖昧な語は、定量化されるまで要件にならない。
曖昧な品質の語は、尺度と閾値と測定法の三つに分けて、観測できる述語へ直す。
型と契約による静的な保証と、テストによる動的な検証は、同じ検証行為の二つの形である。
境界での実行時の検証も、この検証行為の一形態である。
判定できる要件は、型・構造検査・テスト・計測に落とし、リポジトリの検証入口から実行して機械に判定させる。
受け入れの基準は、振る舞いの定義として、実行できるテストに写す。
最適化や改善は、推測でなく計測に基づいて、効いたかを事実で確かめる。

### 完了条件
要件と完了条件が、観測できる尺度と閾値で書かれている。
曖昧な質的表現が、尺度・閾値・測定法に分けて定量化されている。
受け入れの基準が、実行できるテストに写されている。
改善が、計測の前後の比較で確かめられている。

### 禁止事項
「使いやすい」「速い」「適切に」のような検証できない語で、要件を定めること。
満たされたかを判定できない条件を、完了条件として置くこと。
計測せずに、最適化の効果を主張すること。

### 行動
要件に検証できない語があれば、尺度・閾値・測定法に分けて観測できる条件へ言い換える。
その条件を、型・テスト・計測のどれで判定するかを決める。
最適化は、計測で支配的な箇所を特定してから、その箇所だけ行い、前後を比較する。
検証できない共有事項は、規則にせず、説明の文書として扱う。
文書の種別は [documentation](./documentation.md) に従う。

### 例
「検索は高速であること」では、満たしたかを判定できない。応答時間の 99 パーセンタイルという尺度、1000 件のデータで 200ms 未満という閾値、5 分間の窓での計測という測定法に分ける。

```text
「検索は高速であること」

尺度  検索 API の応答時間の 99 パーセンタイル
閾値  1000 件のデータで 200ms 未満
測定法 5 分間の窓で計測し、リポジトリの検証入口と本番監視の両方で判定する
```
