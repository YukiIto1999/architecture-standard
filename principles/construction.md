# construction

construction は、実装の構成に関する原則を置く。
値を不変に扱い、関数を全域にし、判断と集合を構造化し、パターンを統一し、単純な形を既定にし、投機的な要素を作らない。
副作用をどこに置くかは [separation](./separation.md) に従う。

## 値を不変に扱い、変換の連なりで組む

### 要求
値は不変に扱い、状態の変化は新しい値の生成として表す。
処理は、合成できて置換できる変換の連なりとして構成する。

### 根拠
値は変わらず、変化とは別の値になることである。
場所の内容を上書きする様式は、記憶が限られた時代の前提に依る。
共有された可変の値を書き換えると、参照しているすべての箇所が知らぬ間に変わる。
破壊的な更新は、処理順序に依存する不具合と、意図しない共有状態の変更を生む。
変更を新しい値の生成として表すと、元の値はそのまま残り、過去の状態を保てる。
旧版から新版を作る操作は、構造の大半を共有する仕組みにすれば、丸ごと複製せずに済む。
読み取り専用で渡すデータに可変のコレクションを露出すると、外から書き換えられて不変性が崩れる。
処理を入力から出力を返す変換として書き、前段の出力を次段の入力へ連ねると、各段を独立に読め、差し替えられる。
変換の合成が安全なのは、各段が不変の値を入出力するからである。

### 完了条件
業務の意味を持つ値・境界を越える値・共有される値が、不変な構造で扱われている。
変更が、破壊的更新でなく、新しい値の生成として表されている。
公開するデータが、外から書き換えられない読み取り専用の形で渡されている。
各変換が、入力から出力を返し、共有の中間状態を書き換えない。

### 禁止事項
共有されたオブジェクトを、暗黙に破壊的更新すること。
読み取り専用で渡すデータに、可変のコレクションを露出すること。
中間状態を、複数の箇所から変更できる構造にすること。

### 行動
代入・破壊的メソッド・共有参照の書き換えの箇所を確認する。
破壊的更新が不要なら、新しい値を返す形へ置き換える。
処理を、入力から出力への変換に切り出し、連ねて組む。

### 例
```ts
// 共有配列を破壊的に変更する。呼び出し側が持つ配列も変わる
function addLine(order: Order, line: OrderLine): void { order.lines.push(line); }

// 新しい値を返す。元の order は変わらない
function addLine(order: Order, line: OrderLine): Order {
  return { ...order, lines: [...order.lines, line] };
}
```

## 関数を全域にする

### 要求
関数は、引数の型が取りうるすべての値に対して、例外を投げずに結果を返す全域関数にする。
一部の入力で失敗する部分関数は、引数の型を狭めるか、戻り値の型を広げて全域にする。

### 根拠
一部の入力で例外を投げる部分関数は、呼び出し側に見えない失敗の経路を残す。
失敗を避けるには、そもそも不正な入力を渡せないよう引数の型を狭めるのが第一の手段である。
空でないことが前提の関数には、空を許す型でなく、空でないことを表す型を渡す。
それができない失敗は、成功か失敗の値として戻り値の型に現す。
例外では表さない。
戻り値を弱めると呼び出し側に毎回の失敗処理を強いるが、引数を狭めると失敗の場合がそもそも消える。
全域な関数は、同じ入力に同じ出力を返す参照透過な計算として、置き換えても意味が変わらない。
持っている表現でなく、持っていたい表現に対して関数を書き、型にコードを導かせる。

### 完了条件
関数が、引数の型の全域で、例外を投げずに結果を返す。
前提条件のある関数が、その前提を満たす型を引数に取っている。
想定された失敗が、戻り値の型に成功か失敗の値として現れている。

### 禁止事項
一部の入力で例外を投げる部分関数を、全域のように見せること。
前提条件を、引数の型でなく、関数の中の検査と例外で守ること。

### 行動
関数が、引数の型のどの値で失敗するかを確認する。
失敗するなら、引数の型を前提を満たす型へ狭めるか、戻り値を成功か失敗の型へ広げる。

### 例
```ts
// 空配列で例外を投げる部分関数。失敗が型に現れない
function head<T>(xs: T[]): T { if (xs.length === 0) throw Error("empty"); return xs[0]; }

// 引数の型を「空でない配列」に狭め、全域にする
function head<T>(xs: NonEmpty<T>): T { return xs[0]; }   // どの NonEmpty でも必ず返る
```

Rust では先頭要素を型で保証する構造体、C# では要素数をコンストラクタで検証する型で、同じ絞り込みができる。

## 業務判断を型と多態で構造化する

### 要求
業務上の判断は、裸の条件分岐に散らすのでなく、型・多態・状態・方針として表す。
種別や状態のデータの場合分けは、判別子つきの直和に対する網羅した分岐で書く。
組立点で実装を差し替える方針の振る舞いは、方針の型への多態で表す。
分岐を呼び出し側に露出させない。

### 根拠
構造化されていない条件分岐に業務の意味を載せると、同じ判断が各所に重複し、概念が埋もれる。
複合した条件式は、意図を表す名前の判定へ抽出すると、何を判断しているかが読める。
判別子つきの直和を網羅で分岐すると、場合の追加が型検査で漏れなく検出され、分岐が複数の箇所にあっても漏れが残らない。
網羅の検査が働かない裸の値の分岐は、種別が増えるたびに、すべての分岐を人が探して直すことになる。
状態によって振る舞いが変わり遷移を持つものは、[modeling](./modeling.md) の直和で状態の形を表し、状態ごとの型に振る舞いを移して、状態自身に遷移を持たせる。
入れ替え可能な算法は、方針として切り出して組立点で差し替える。
多態はこの方針の表現に使う。
繰り返し現れる業務規則は、満たすかを判定する仕様として切り出し、かつ・または・否定で合成する。
深いネストは、特殊な場合を早期の return で先に弾き、本筋を平らに保つ。

### 完了条件
業務条件・状態遷移・権限判断・集約規則が、型・多態・状態・方針・直和で表されている。
同じ業務判断が、複数の箇所に重複して書かれていない。
場合分けが網羅され、漏れを型検査が検出する。
ネストが浅く、特殊な場合の検査が早期の return で分かれている。

### 禁止事項
構造化されていない条件分岐やループに、業務条件・状態遷移・権限判断を重複して書くこと。
条件式の羅列で、業務概念を隠すこと。
網羅の検査が働かない、裸の値による種別の分岐を書くこと。

### 行動
分岐が何の業務概念を表すかを確認する。
複合した条件式は、意図を表す名前の判定へ抽出する。
裸の値による種別の分岐は、判別子つきの直和と網羅した分岐に変える。
実装を差し替える振る舞いは、方針の型へ切り出し、具体は組立点で結び付ける。
状態をフラグでなく型で表し、深いネストは、特殊な場合を早期の return で弾いて平らにする。

### 例
```ts
// 網羅の検査が働かない裸の値の分岐。種別の追加漏れに気づけない
function fee(account: { type: string }): Money {
  if (account.type === "gold") return goldFee();
  else if (account.type === "silver") return silverFee();
  else return basicFee();
}

// 判別子つきの直和と網羅した分岐。分岐が複数の箇所にあっても、場合の追加漏れを型検査が全箇所で検出する
type Account = { type: "gold" } | { type: "silver" } | { type: "basic" };
function fee(account: Account): Money {
  switch (account.type) {
    case "gold": return goldFee();
    case "silver": return silverFee();
    case "basic": return basicFee();
  }
}
```

Rust では enum と網羅 match、C# では閉じた sealed 階層と switch 式で、同じ網羅ができる。
組立点で差し替える方針は、多態で表す。

```ts
// 手数料の方針を差し替え可能にする。実装は方針の型に閉じ、組立点で注入する
interface FeePolicy { fee(order: Order): Money }
class StandardFeePolicy implements FeePolicy { fee(order: Order): Money { return standardFee(order); } }
class CampaignFeePolicy implements FeePolicy { fee(order: Order): Money { return campaignFee(order); } }
```

## 集合処理を名前のある操作で表す

### 要求
集合の絞り込み・変換・集計・整列は、裸のループでなく、名前のある高水準の操作で表す。
業務的な意味を持つ集合は、操作を備えた一つの型に閉じ込める。

### 根拠
裸のループは、何をしているかを読み手が本体を追って復元しなければならない。
一つのループが絞り込みと集計のように複数のことを同時に行うと、意図が溶けて読めなくなる。
絞り込み・変換・集計を名前のある操作で書き、前段の結果を次段へ渡すと、何をするかが名前から読める。
集合を扱うロジックが各所に散ると、同じ集計が重複し、規則の変更が漏れる。
集合とその操作を一つの型に閉じ込めると、集合に対する規則がそこに集まり、他の責務と混ざらない。

### 完了条件
集合の絞り込み・変換・集計・整列が、名前のある操作として表されている。
一つの操作が、一つのことだけを行っている。
業務的な意味を持つ集合が、操作を備えた一つの型に閉じ込められている。
集合に対する同じ判断が、各所に重複していない。

### 禁止事項
業務の意味を持つ集合処理を、裸のループとして各所に散らすこと。
一つのループに、複数の集合操作を混ぜること。
集合に対する規則を、集合の外の各所に書くこと。

### 行動
ループが何の集合操作かを確認し、絞り込み・変換・集計・整列の名前のある操作へ置き換える。
一つのループが複数のことをしていれば、操作ごとの段に分ける。
業務的な意味を持つ集合は、操作を備えた型へ閉じ込める。

### 例
```ts
// 裸のループ。絞り込みと集計が混ざり、何の計算か本体から読み取る必要がある
let total = 0;
for (const line of order.lines) { if (line.taxable) total += line.amount; }

// 名前のある操作の連なりで意図を表す
const total = order.lines.filter(line => line.taxable).reduce((subtotal, line) => subtotal + line.amount, 0);
```

## 同じ目的に同じパターンを使う

### 要求
同じ目的の処理には、同じ実装パターンを使う。
エラー処理・入出力変換・依存の渡し方・状態の更新・テストの構造を、一つの流儀に揃える。

### 根拠
流儀が分かれると、読み手は同種の処理のたびに別の解釈をやり直す。
パターンを統一すれば、一度学んだ構造を同種の処理へそのまま当てられる。
操作の結果が、名前や文脈から予測できると、読み手は驚かず誤読しない。
名前が示す動作と実装が食い違うと、読み手の予測を裏切り、驚きという代償を生む。
標準が定めていない書き方の一貫性は、スタイル規約よりプロジェクト、プロジェクトよりモジュールの局所で優先する。
似て非なるものを似せると、見かけの親しさが誤った予測を生むため、はっきり別物にする方がよい。

### 完了条件
同種の処理・エラー処理・入出力変換・依存の渡し方・状態更新・テストが、同じ構造で実装されている。
操作の結果が、名前と文脈から予測できる。
例外的な実装に、明確な理由がある。

### 禁止事項
同種の問題に、複数の流儀を併存させること。
名前が示す動作と、実装を食い違わせること。
個人の好みや局所の都合で、別のパターンを足すこと。
似て非なるものを、似せて紛らわしくすること。

### 行動
変更対象と同種の実装を検索し、既存の標準パターンを確認する。
差異があれば標準へ寄せ、標準自体を変える必要があれば、影響範囲の全体へ適用する。

### 例
```ts
// 同じ「走査して変換」を場所ごとに違う流儀で書く
const ys = []; for (let i = 0; i < xs.length; i++) ys.push(f(xs[i]));
const zs = xs.reduce((a, x) => (a.push(g(x)), a), []);

// 同じ目的には同じ操作を一つ選び、局所の一貫性を保つ
const ys = xs.map(f);
const zs = xs.map(g);
```

## 単純な形を既定にする

### 要求
要求されたものを作る形が複数あるときは、変更理由と処理の流れを読み手が追跡できる単純な形を既定にする。
間接・抽象・汎用化は、その場で説明できる対価があるときだけ足す。

### 根拠
単純性は、他の価値と交換してよい一項目でなく、判断の既定である。
形の良し悪しは、変更理由と処理の流れを読み手が追跡できるかの一点で判定できる。
要求されていないものを作らない規律は、何を作るかを定める。
この規律はその先の、要求されたものをどう作るかの選択を定める。
対価を説明できない間接・抽象・汎用化は、追跡の段数だけを増やし、変更のたびに読み手へ負担を課す。

### 完了条件
採った形で、変更理由と処理の流れを読み手が追跡できる。
残した間接・抽象・汎用化のそれぞれに、その場で説明できる対価がある。

### 禁止事項
対価を説明できない間接・抽象・汎用化を足すこと。
単純な形を検討せずに、複雑な形を選ぶこと。

### 行動
要求を満たす複数の形を比べ、変更理由と処理の流れを追跡できる単純な形を選ぶ。
間接・抽象・汎用化を足すときは、その対価をその場で説明する。
説明できなければ、足さずに単純な形のまま作る。

## 投機的で説明できない要素を作らない

### 要求
各行・各分岐・各依存・各データ構造を、現に要求された責務・制約・判断のいずれかに対応させる。
将来を見越した未要求の要素は作らない。

### 根拠
念のための分岐・将来用のフィールド・使われない抽象は、要求された機能のためでなく、想像された未来のために置かれる。
投機的な機能は、作る手間に加え、ほかの機能の実装を遅らせ、以後の全ての変更を重くし、誤って作れば直す手間まで生む。
要求されていない要素を足すより、要求された範囲を過不足なく作り切る方が、変更を楽に保つ。
投機的な要素だけを作らないのであり、品質への労力を惜しむのではない。
あらゆるインタフェース・型・関数は、学ぶ負担という費用を伴い、取り除く複雑さが加える複雑さを上回るときだけ元が取れる。
失敗の場合を後から処理するより、意味を定義し直して失敗の場合がそもそも生じないようにする方が、分岐が減る。
誤りを後から検査で防ぐより、誤りにくい型と構造にする方が、防御そのものが要らなくなる。
主要な設計判断は、最初の案で決めず、根本的に異なる複数の案を比べてから選ぶ。

### 完了条件
追加または変更した各要素が、現に要求された責務・制約・判断のいずれかに対応している。
使われていないクラス・メソッド・フィールド・引数が残っていない。

### 禁止事項
要件に対応しない分岐・使われない抽象・不要な依存・将来用のフィールド・根拠のない設定を残すこと。
呼び出し元のないメソッドや、使われない一般化を残すこと。
存在理由の説明を、コメントだけに逃がすこと。

### 行動
変更差分の各要素について、必要性・利用箇所・制約・代替案を確認する。
呼び出し元のない要素や、加える複雑さに見合わない一般化は、削除する。
失敗の場合を、そもそも生じない構造へ寄せられないか検討する。
主要な設計判断では、異なる複数の案のインタフェースを書いて比べる。
