# legibility

legibility は、コードによる意図表現に関する原則を置く。
コードを第一級の文書として書き、自明にし、可読性と視認性を両立する。
意図は、コード・命名・コメント・文書の順で伝え、上の層で表せるものを下の層へ逃がさない。
命名は [naming](./naming.md)、コメントは [comment](./comment.md)、文書は [documentation](./documentation.md) に従う。

## コードを第一級の文書として書く

### 要求
コードを、システムの主要な文書として書く。
人が読んで理解できるよう、明快に書く努力を払う。

### 根拠
十分に詳細で正確な文書は、コードだけである。
コードは、書かれる時間より長く読まれる。
だから楽にすべき活動は、読むことである。
コードは、他の文書と同じく、明快にも意味不明にもなる。
文書だと決めて労力を払って初めて明快になる。
複雑さとは、ある作業のために頭へ入れねばならない情報量と、その情報の得にくさである。
明快さを高めるには、他者に読ませ、どこで詰まるかを観る。
コードベースは個人でなくチームのものであり、個人の好みよりチームの読みやすさの規約を優先する。

### 完了条件
処理の意図・責務・順序・失敗条件が、命名・型・関数分割・配置から読み取れる。
理解の正本が、コード外の説明だけに依存していない。

### 禁止事項
コードを文書として扱わず、明快さに労力を払わないこと。
仕様理解の正本を、外部文書だけに置くこと。
個人の好みを、チームの読みやすさより優先すること。

### 行動
読み手が上から追って、何を・なぜ・どの順で行うか分かるか確かめる。
分かりにくければ、命名・型・関数分割・配置を見直す。
他者に読ませ、詰まる箇所を明快さの指標にする。

### 例
```ts
// 計算機向け。何を判定しているか読み手が復元しなければならない
if (u.f & 0x2 && Date.now() - u.t > 86400000) {}

// 人向け。意図が名前と型に現れ、上から読める
if (user.isLocked && elapsedSince(user.lockedAt, now) > LOCK_WINDOW) {}
```

## コードを自明にする

### 要求
コードは、読み手が凝視や推論をせずに振る舞いと意味を理解できる、自明な状態にする。
読み手が抱く疑問に、コードかコメントが自然に答えるようにする。

### 根拠
理解していないのに理解したと思わせるコードは、誤解していると分かっているコードより危うい。
急いで読んだ読み手の最初の推測が正しくなるのが、自明なコードである。
複雑さは読み手の側にあり、他者が複雑だと感じたなら、そのコードは実際に複雑である。
読み手の練習不足のせいにせず、書き手が自明さに責任を持つ。
不明瞭にする要因は、コードに書かれていない情報を読み手に要求する。
名前が副作用のない判定を示唆するのに状態を変える隠れた副作用は、読み手を誤らせる。
呼び出し側の前提に依存する処理は、検証のために呼び出し側まで読ませる。
自明でない性能最適化は、なぜそう書くかを読み手に自力で再構成させる。

### 完了条件
読み手の最初の推測が、実際の振る舞いと一致する。
名前が示唆する振る舞いと、実際の振る舞いが一致している。
呼び出し側の文脈に依存する暗黙の前提が、残っていない。
自明でない最適化や前提に、理由の補足がある。

### 禁止事項
名前が示唆しない隠れた副作用を持たせること。
呼び出し側の前提に暗黙に依存する処理を書くこと。
自明でない最適化を、理由の補足なしに残すこと。

### 行動
名前が示唆する振る舞いと、実際の振る舞いが一致するか確かめる。
呼び出し側の前提に依存していれば、依存を断つか、前提を明示する。
自明でない最適化や前提は、なぜそう書くかを補う。

### 例
```ts
// 名前は判定を示唆するが、内部で状態を変える隠れた副作用がある
function isReady(job: Job): boolean { job.checkedAt = now(); return job.deps.length === 0; }

// 判定は副作用を持たない。状態変更が要るなら別の名前と関数に分ける
function isReady(job: Job): boolean { return job.deps.length === 0; }
```

## 可読性と視認性を両立する

### 要求
処理の流れを追える可読性と、構造・まとまり・境界を見分けられる視認性を、同時に満たす。
分割は、機能の凝集を表すときに行い、行数を減らすためだけには行わない。

### 根拠
局所的に読めても全体の構造が見えないコードは、変更時の見通しを失わせる。
最良のモジュールは、多くの機能を提供しつつインタフェースが小さい。
分割しすぎると各部の機能が痩せ、インタフェースが複雑になり、何も隠さなくなる。
一方を理解するのにもう一方を読まねばならない二つの部分は、絡み合っており、分割が裏目に出ている。
密に関連する部分は、一箇所にまとめると最も理解しやすい。
行数や一機能のような数値の規則だけで分割すると、絡み合った浅い断片を量産する。

### 完了条件
ファイル・関数・型・ブロックの大きさ、ネストの深さ、複雑さのしきい値は [languages](../languages/) に置き、値がそのしきい値に収まっている。
責務の境界と、空行やブロックなどの視覚的な区切りが一致している。
分割された各部が、互いを読まずに独立して理解できる。

### 禁止事項
[languages](../languages/) のしきい値を超える大きさ・ネスト・複雑さを残すこと。
互いを読まねば理解できない、絡み合った断片へ分割すること。
視認性のためだけに、責務のない空のラッパーを作ること。

### 行動
大きさ・ネスト・複雑さを [languages](../languages/) のしきい値で確認する。
関心が自然に分かれて各部が独立に読めるなら分割し、行き来が要るならまとめる。
読みにくい箇所は、責務単位に沿って分け、構造と表示上のまとまりを一致させる。

### 例
```ts
// 行数を減らすためだけの分割。三つを頭に載せないと意味が追えず、絡み合っている
function a(c: number) { return b(c) === c; }
function b(c: number) { return d(c); }
function d(c: number) { /* ... */ }

// 自然な単位で一つにまとめる。独立して読める単位だけを切り出す
function isPrime(candidate: number): boolean { /* ... */ }
```
