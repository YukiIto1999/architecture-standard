# legibility

legibility は、コードによる意図表現に関する原則を置く。
コードを第一級の文書として明瞭に書き、全体と局所を構造で結び、可読性と視認性を両立し、宣言を使用へ近接させる。
現在の処理は、構造と命名、コード本体で表す。
実装コメントと文書を、不明瞭なコードの補足に使わない。
命名は [naming](./naming.md)、コメントは [comment](./comment.md)、文書は [documentation](./documentation.md) に従う。

## コードを第一級の文書として明瞭に書く

### 要求
コードを、システムの主要な文書として書く。
フォルダ、ファイル、型、関数の構造と命名で、全体の責務と局所の処理を結ぶ。
現在の処理は、コードから簡潔に読み取れる形にする。

### 根拠
十分に詳細で正確な文書は、コードだけである。
コードは、書かれる時間より長く読まれる。
コードは頭の中の意図を完全には写せず、長く複雑になるほど意図が写し漏れる。
だから楽にすべき活動は、読むことである。
コードは、他の文書と同じく、明瞭にも不明瞭にもなる。
文書だと決めて労力を払って初めて明瞭になる。
複雑さとは、ある作業のために頭へ入れねばならない情報量と、その情報の得にくさである。
フォルダとファイルは責務を探す目次になり、型と関数は処理を理解する単位になる。
全体の配置と局所のコードがつながっていれば、読み手は関係のない実装を渡り歩かずに目的の処理へ到達できる。
急いで読んだ読み手の最初の推測が正しくなるのが、明瞭なコードである。
名前が副作用のない判定を示唆するのに状態を変える実装は、読み手を誤らせる。
呼び出し側の前提に依存する処理は、検証のために呼び出し側まで読ませる。
説明の実装コメントで不足を補うと、不明瞭な構造が残り、コードとコメントの二つを同期し続けることになる。
明瞭さを高めるには、他者に読ませ、どこで詰まるかを観る。
コードベースは個人でなくチームのものであり、個人の好みよりチームの読みやすさの規約を優先する。

### 完了条件
フォルダとファイルから責務と境界を特定でき、型と関数から処理の単位を特定できる。
処理の流れ、順序、副作用、失敗条件が、命名、型、分割、配置、コード本体から読み取れる。
読み手の最初の推測が、実際の振る舞いと一致する。

### 禁止事項
コードを文書として扱わず、明瞭さに労力を払わないこと。
責務を探すために、関係のないフォルダ、ファイル、型、関数を読み歩かせること。
名前が示唆しない副作用を持たせること。
呼び出し側の前提に暗黙に依存する処理を書くこと。
個人の好みを、チームの読みやすさより優先すること。

### 行動
フォルダ、ファイル、型、関数、コード本体の順に読み、全体の責務から局所の処理まで迷わず到達できるか確かめる。
分かりにくければ、実装コメントを足さず、配置、分割、命名、型、処理の流れを見直す。
名前が示唆する振る舞いと、実際の振る舞いを一致させる。
呼び出し側の前提に依存していれば、依存を断つか契約にする。
他者に読ませ、詰まる箇所を明瞭さの指標にする。

### 例
責務も意味も名前に現れないコードは、読み手に処理の復元を強いる。

```ts
if (u.f & 0x2 && Date.now() - u.t > 86400000) {}
```

責務と意味を構造と名前に表せば、コードだけで読める。

```ts
if (user.isLocked && elapsedSince(user.lockedAt, now) > LOCK_WINDOW) {}
```

## 可読性と視認性を両立する

### 要求
処理の流れを追える可読性と、構造・まとまり・境界を見分けられる視認性を、同時に満たす。
分割は、機能の凝集を表すときに行い、行数を減らすためだけには行わない。

### 根拠
局所的に読めても全体の構造が見えないコードは、変更時の見通しを失わせる。
最良のモジュールは、多くの機能を提供しつつインタフェースが小さい。
分割しすぎると各部の機能が痩せ、インタフェースが複雑になり、何も隠さなくなる。
一方を理解するのにもう一方を読まねばならない二つの部分は、絡み合っており、分割が裏目に出ている。
密に関連する部分は、一箇所にまとめると最も理解しやすい。
行数や一機能のような数値の規則だけで分割すると、絡み合った浅い断片を量産する。
長さそのものは悪ではないが、長いコードは複雑さを内包している可能性が高く、注意のシグナルである。
編集環境の進歩は長いコードを読む負担を軽くしたが、それは長くてよい理由にならない。
一望で把握できる項目の数には限界があり、同一の階層へ項目を並べすぎると構造が読めない。

### 完了条件
ファイル・関数・型・ブロックの大きさ、ネストの深さ、複雑さが、[tools](../tools/) の定めるしきい値に収まっている。
責務の境界と、空行やブロックなどの視覚的な区切りが一致している。
分割された各部が、互いを読まずに独立して理解できる。

### 禁止事項
[tools](../tools/) のしきい値を超える大きさ・ネスト・複雑さを残すこと。
互いを読まねば理解できない、絡み合った断片へ分割すること。
視認性のためだけに、責務のない空のラッパーを作ること。
しきい値に収まっていることを、短くする理由の消滅と扱うこと。

### 行動
大きさ・ネスト・複雑さを [tools](../tools/) のしきい値で確認する。
関心が自然に分かれて各部が独立に読めるなら分割し、行き来が要るならまとめる。
読みにくい箇所は、責務単位に沿って分け、構造と表示上のまとまりを一致させる。
しきい値は極端を止める背止めとして扱い、収まっていることを目標にしない。
より短く明確にできないかを常に問う。
列挙や階層が長すぎるなら、意味のある中間の単位で束ねる。

### 例
行数を減らすためだけに分けると、三つの関数を同時に把握しなければ意味を追えない。

```text
a(candidate) -> b(candidate)
b(candidate) -> d(candidate)
```

自然な単位は一つにまとめ、独立して読める単位だけを切り出す。

```text
isPrime(candidate)
```

## 宣言と使用を近接させる

### 要求
変数と補助的な処理の宣言は、最初に使う箇所の近くに置く。
スコープは、必要な最小の範囲に絞る。

### 根拠
短さを求める理由は、画面に収めることでなく、スコープを狭めて誤用と干渉の余地を減らすことにある。
宣言と使用が離れるほど、読み手が保持する文脈が増える。
スコープが広いほど、値の変更点と参照点の組み合わせが増え、追跡が難しくなる。

### 完了条件
宣言から最初の使用までの距離が短い。
各宣言のスコープが、使用の範囲を超えていない。

### 禁止事項
使用から離れた場所へ、宣言をまとめて置くこと。
必要より広いスコープで宣言すること。

### 行動
宣言を最初の使用の直前へ移す。
広いスコープの宣言は、使用範囲に合わせて絞るか、関数へ切り出す。

### 例
宣言を冒頭へ集めると使用までの距離が開き、前処理の間も値へ干渉できる。

```ts
function summarize(orders: Order[]) {
  let total = 0;
  const normalized = normalize(orders);
  total = normalized.reduce((sum, order) => sum + order.amount, 0);
  return total;
}
```

宣言を使用の直前に置けば、スコープを最小にできる。

```ts
function summarize(orders: Order[]) {
  const normalized = normalize(orders);
  const total = normalized.reduce((sum, order) => sum + order.amount, 0);
  return total;
}
```
