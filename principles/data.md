# data

data は、データと状態に関する原則を置く。
整合性を集約境界に閉じ、データを意味で分類し、事実を追記して現在状態を導き、整合性をデータ層の制約で守る。
論理と物理の分離は [modeling](./modeling.md)、正本と互換の独立は [separation](./separation.md)、状態の命名は [naming](./naming.md) に従う。
関係と制約による永続データの設計は、concerns の [persistence](../concerns/persistence.md) が具象化する。

## 整合性を集約境界に閉じる

### 要求
同時に守らなければ不正となる不変条件は、一つの集約の内に閉じ、その確定をひとつのトランザクションに一致させる。
集約は小さく保ち、集約どうしは識別子で参照する。

### 根拠
整合性の判断が複数の箇所へ散らばると、部分更新や競合で不正な状態が生まれる。
同時に守るべき不変条件を一つの境界に集めれば、その境界の内だけで整合を保てる。
集約は、オブジェクトの所有関係でなく、整合性の境界を表すために引く。
境界の引き方は、どの不変条件をどのトランザクションで守るかの分析で決める。
集約を小さく保つと性能と競合の両面で扱いやすく、大きな集約は更新がぶつかって詰まる。
他の集約を実体でなく識別子で指すと、一度の更新で複数の集約を変える誘惑が断たれる。
一つのトランザクションでは一つの集約だけを変え、複数の集約にまたがる整合はイベントによる結果整合性で表す。
即時に整合させるか結果整合に委ねるかは、整合させるのがその操作を行う本人の責務か、別の利用者やシステムの責務かで判断する。
集約が守るのは、業務規則に基づく計算の整合性である。
保存されたデータの整合性ではない。
だから集約は永続化と独立に設計し、その確定点をトランザクション境界に一致させる。

### 完了条件
同時に守らなければ不正となる規則が、単一の集約の内で検証されている。
トランザクション境界が、その整合性の範囲と一致している。
集約が、ルートと必要最小限の属性に限られている。
他の集約への参照が、実体でなく識別子で表されている。
複数の集約にまたがる整合が、イベントや workflow による結果整合性として明示されている。

### 禁止事項
同時に守るべき判断を、controller・handler・repository・UI・外部サービス呼び出しへ分散させること。
一つのトランザクションで、複数の集約を変更すること。
所有関係や画面の都合で、集約を大きくすること。
他の集約を、実体への直接参照で抱え込むこと。

### 行動
不変条件を洗い出し、同時に守るべきものを一つの集約に束ねる。
集約をルートと最小の属性に絞り、それ以外は別の集約として識別子で参照する。
複数の集約にまたがる規則は、即時整合が要るかを問い、整合させるのがその操作を行う本人の責務か別の利用者やシステムの責務かで判断し、要らなければイベントで結果整合性にする。

### 例
```ts
// 大きすぎる集約。注文が顧客を実体で抱え、更新が衝突しやすい
class Order { id: OrderId; lines: OrderLine[]; customer: Customer }

// 集約は小さく、他の集約は識別子で参照する
class Order { id: OrderId; customerId: CustomerId; lines: NonEmpty<OrderLine> }
// 顧客の変更は Customer 集約の別トランザクションで行い、必要ならイベントで連携する
```

## データを事実・状態・時間で分類する

### 要求
データを、事実・イベント・現在状態・識別子・時間軸に分けて捉える。
現在の値だけでなく、保持すべき事実・履歴・発生時刻・適用時刻を、それぞれ区別して表す。

### 根拠
現在の値だけでデータを持つと、履歴・発生事実・時点に依存する意味が失われる。
変わらない事実と、変わる現在状態は、別のものとして分ける。
日時の属性を持つもの、「〜する」と言えるものはイベントであり、業務上の価値はイベントの側にある。
日時を持たず状態として残るものはリソースであり、現在状態はイベントから導かれる。
識別子は、不変の代理キーと、生成時の不変な属性だけを持ち、変わりうる属性は置かない。
事実が実世界で真である時刻と、それをシステムが記録した時刻は、別の時間軸である。
実世界の時刻に基づく分析を、記録や処理の時刻と混同すると、集計が狂う。
リソースに更新日時を付けたくなるのは、その裏に隠れたイベントが存在する兆候である。

### 完了条件
事実・イベント・現在状態・識別子・時刻の分類が、型か schema の区別として表れている。
イベント・現在状態・導出値・識別子が、混同されていない。
識別子が、不変の代理キーと生成時の属性に限られている。
発生時刻と記録時刻の両方を要する対象で、二つの時刻が別の属性として保存されている。

### 禁止事項
現在の値だけで業務の意味を表すこと。
更新履歴・発生事実・時点依存の意味を、同じものへ混在させること。
識別子に、変わりうる属性を持たせること。
隠れたイベントを、更新日時や削除フラグで覆い隠すこと。

### 行動
対象データが、事実・イベント・現在状態・識別子・時刻のどれかを分類する。
「〜する」と言えるか、日時を持つかで、イベントとリソースを見分ける。
関係と制約への落とし方は、[persistence](../concerns/persistence.md) が具象化する。

## 事実は追記し、現在状態は導出する

### 要求
事実は不変なものとして追記し、上書きや削除で消さない。
現在の状態は、保持した事実から導く。
取り消しや差し戻しは、現在値の書き換えでなく、打ち消す事実の追記で表す。
導出のコストが履歴の長さに比例して増えないよう、一定の区切りで確定した値を事実として残し、導出の起点をそこに置いて有界に保つ。

### 根拠
破壊的な更新は、業務上必要な事実や判断の根拠を消す。
状態を表す値は最新のものしか持てず、過去の遷移を上書きすると、その事実が失われる。
事実を追記で残せば、現在の状態をいつでも事実から導け、監査・復元・原因分析に耐えられる。
リソースの状態の違いは、削除フラグでなく、区分や状態を表すイベントで表す。
履歴と世代は別のものとして扱い、過去の記録はイベントで、未来に向けた変更は世代で表す。
事実を追記し続けると、現在状態を導く処理は履歴の長さに比例して重くなる。
一定の区切りで確定した値を事実として残せば、以後の導出はその区切りから先の事実だけで済む。
区切りは業務上の確定であり、追記される事実である。
再構築を速めるための技術的な控えは、捨てても事実を失わない最適化であり、区切りとは別に扱う。

### 完了条件
監査・復元・分析の対象とする事実・遷移・時刻・理由が、追記で保存されている。
状態の遷移が、現在値の上書きでなく、事実の追記として残っている。
現在の状態が、保持した事実から導ける。
履歴から現在状態を導く設計で、導出の起点が確定した区切りの事実で有界に保たれている。
業務上の確定と、再構築を速める技術的な控えが、別のものとして扱われている。
破壊的更新を行う箇所に、失う情報が不要だと説明できる根拠が、project の ADR に残っている。

### 禁止事項
業務事実・監査対象・復元対象を、無条件に上書きまたは削除すること。
状態の遷移を、過去の遷移を消す形の現在値更新で表すこと。
履歴が必要な値を、現在値だけで保持すること。
履歴から現在状態を導く設計で、導出の起点を区切らず、コストを履歴の長さに比例して増やし続けること。
業務上の確定の事実と、技術的な控えを、同じものとして扱うこと。

### 行動
永続化の対象ごとに、後から必要になる履歴・監査項目・復元要件を確認する。
状態を持つ値を見たら、その遷移を事実の追記として残すべきか判断する。
履歴から現在状態を導く箇所で、導出のコストが履歴に比例して増えないか確認する。
増えるなら、一定の区切りで確定値を事実として残し、導出の起点をそこに置く。
追記の形での関係への落とし方は、[persistence](../concerns/persistence.md) が具象化する。

### 例
口座の残高を、現在値の上書きと、事実の追記で比べる。

```ts
// 残高を上書きする。過去の入出金という事実が消え、監査も復元もできない
account.balance = account.balance - amount;

// 入出金を事実として追記し、現在の残高は事実から導く
ledger.append({ kind: "withdrawn", amount, at });         // 追記される事実
const balance = ledger.events.reduce(applyToBalance, 0);  // 事実から導出

// 区切りは業務上の確定で、追記される事実。捨てない
ledger.append({ kind: "monthlyClosed", balance, month });
// 技術的な控えは導出を速めるだけの最適化。捨てても事実を失わない
cache.set(accountId, balance);
```

## 整合性をデータ層の制約で守る

### 要求
データの整合性は、アプリケーションの規約でなく、データ層の制約で守る。
論理設計を正規化で整え、一つの事実を一箇所に置く。

### 根拠
アプリケーションの規約だけで整合性を守ると、別経路の書き込みや不具合でデータが壊れる。
データの寿命はアプリケーションより長く、壊れたデータは復旧が難しい。
正規化は、一つの事実を一箇所に置き、更新時の異常と冗長を取り除く規律である。
一つの事実が複数の箇所にあると、片方だけ更新して矛盾が生まれる。
関係は真である命題の集合であり、制約はその命題が偽になる更新をデータ層で拒む。
データ層の制約は、人手のレビューより確実に整合性違反を弾く。

### 完了条件
関係の形として表せる整合性が、データ層の制約で守られている。
事実が正規化され、同じ事実が複数の箇所に重複していない。

### 禁止事項
業務上の整合性を、アプリケーションの規約だけで保証すること。
整合性のために必要な制約を、性能や手間を理由に外すこと。
一つの事実を、複数の箇所に重複して持つこと。

### 行動
既存のスキーマから、制約で表せるのに規約だけで守っている整合性を洗い出す。
守るべき整合性を、データ層の制約で表せる形にする。
制約の種類・任意項目の扱い・物理の最適化の判断は、[persistence](../concerns/persistence.md) が具象化する。
