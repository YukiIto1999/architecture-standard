# separation

separation は、分割と依存に関する原則を置く。
何を同じ境界に入れ、何を分け、結合をどう弱め、依存をどちらへ向けるかを定める。

## 変更理由で分ける

### 要求
モジュールは、変更を要求するアクターと変更の理由が一致する単位で分ける。
処理の手順・技術層・framework・ファイル種別では分けない。

### 根拠
変更理由の異なる関心を同居させると、片方の修正がもう片方を壊し、確認すべき範囲が広がる。
変更を要求するアクターは、人間の利用者に限らず、他システムや、同じ利用者のライフサイクル上の異なる状態も含む。
アクターの区切りはコードからは決まらず、境界付けられたコンテキストとドメインの捉え方に従うモデリングの判断である。
だから分割の判定には、コードの照合だけでなく、要件の整理とモデリングが先に要る。
アクターの混在は、個々のコード片よりも、全体の設計と共通化の判断に現れる。
同時に変わる要素だけを同じ境界に置けば、修正の影響は境界の内に収まる。
分割の軸は、処理の段階ではなく、変わりそうな決定に置く。
変わりそうな決定を洗い出し、その一つひとつを別のモジュールに隠すと、決定の変更が一つのモジュールに封じ込まれる。
入力から出力への処理の流れでモジュールを割ると、データ形式や整列順の決定が複数のモジュールに漏れ、一つの変更が全体へ波及する。
同じ理由で変わる要素をまとめる凝集は、単一のタスクに全要素が貢献する形が最も強い。
同時刻に動くから、表面のカテゴリが同じだから、という理由でまとめた凝集は弱く、後で分け直しになる。
人は目に見える実体に思考を引かれ、実体の単位が正しい境界に見えてしまう。
実体をそのまま境界にすると、その実体に関わるあらゆる目的の属性と判断を吸収して肥大し、変更理由が混ざる。
特定のアクターを持たない汎用処理は、あらゆるアクターに開かれ、無限の責任を負う。
だから汎用の置き場は、最小に保つ。
重複の判定は、コードの見た目でなく、表している知識と意図で行う。
見た目が同じでも別の知識を表す一致は、偶然であって重複でない。

### 完了条件
各モジュールの変更理由と隠している決定が説明できる。
変更理由の異なる処理・型・設定・画面・永続化構造が、同一モジュールに混在していない。
一つの仕様変更で書き換わる範囲が、一つのモジュールに収まる。
新しいアクターの追加が、既存のアクターの実装に影響しない。
重複の判定が、コードの見た目でなく、表している知識と意図の一致で行われている。

### 禁止事項
処理の段階・技術層・framework・ファイル種別・目に見える実体だけを理由に、境界を決めること。
共通化を理由に、変更理由の異なる要素をまとめること。
別の知識を表す見た目の一致を、重複として共通化すること。
無関係な処理を、util や helper のような共通の置き場へ寄せ集めること。

### 行動
変更対象の利用者・変更契機・変更頻度・変更時に読む仕様を調べる。
変わりそうな決定として、データ形式・整列順・外部仕様・アルゴリズムを列挙し、各決定を一つのモジュールに隠す。
境界の候補が目に見える実体の単位なら、その実体に関わる目的を列挙し、目的ごとに分け直す。
同時に変わる要素だけを同じ境界に残し、別の理由で変わる要素を分ける。
変更に着手する前に、その変更がどのアクターのどのユースケースに属するかを答え、答えられなければモデリングへ戻る。
アクターが混在した実装を分けるときは、まず同一の実装を複製し、アクターごとに要件の違いを書き分けてから、残った偶然の一致を消す。
共通の置き場へ足す前に、対応するアクターかコンテキストへの配置や、既存の型への操作の追加で吸収できないかを先に検討する。
切り出した要素は、対応する概念の名前で検索して到達できる場所に置き、独立した再実装を防ぐ。
使われない項目が null で埋まるモデルを見つけたら、アクターの混在を疑って分け、不正な状態の排除は [modeling](./modeling.md) に従う。

### 例
処理の手順で割った分割と、変わりそうな決定を隠す分割を比べる。

```ts
// 入力→変換→整列→出力 の手順で割ると、行の格納形式をどのモジュールも知ってしまう
class InputReader { /* 行を配列に読む。配列の形を知る */ }
class Shifter     { /* 同じ配列の形を知る */ }
class Sorter      { /* 同じ配列の形を知る */ }
// 格納形式を変えると、3 モジュールすべてが書き換わる

// 行の格納という決定を 1 モジュールに隠すと、形式変更がそこに封じ込まれる
class LineStore { add(line: Line): void; get(i: number): Line }  // 格納形式を隠す
class Shifter   { constructor(private lines: LineStore) {} }     // 形式を知らない
class Sorter    { constructor(private lines: LineStore) {} }     // 形式を知らない
```

## 関心を境界の内に隠す

### 要求
モジュールは、変わりやすい内部の決定を隠し、外部へは目的を表す最小の契約だけを公開する。
境界付けられたコンテキストは、内部の用語・判断・責務を内部で完結させ、外部へは境界の契約だけを出す。

### 根拠
内部の判断や表現が外部へ漏れると、外部がその詳細に依存し、変更が境界を越えて波及する。
インタフェースは、提供する機能に対してできるだけ小さく保ち、その裏に多くの機能を隠す。
小さなインタフェースの裏に深い機能を置けば、利用者の学習量と結合の量が同時に減る。
公開する契約は、どんな変更で変わるかを設計の時点で検討し、安定させる。
引数が増え続ける公開面は、破壊的変更を生みやすい構造を自ら作っている。
引数をそのまま別の関数へ受け渡すだけの薄い層は、結合だけ増えて機能を足さないため、責務の分割を見直す合図になる。
層の外側では文字列や JSON などの素の表現を扱い、境界を越えた内側ではドメインの型だけを扱う。
境界での検証は、[modeling](./modeling.md) の「境界で検証して型に通す」に従う。
上流の都合をそのまま受け入れると下流が歪むため、必要なら境界に隔離層を置き、外部のモデルを自分のモデルへ変換する。

### 完了条件
公開する契約が、内部の表現・永続化構造・判断順序を明かしていない。
外部のモジュールが、内部の型・内部状態へ直接依存していない。
受け流すだけの薄い層がなく、各モジュールが目的の機能を内に持っている。

### 禁止事項
内部の永続化型・内部状態・判断順序を、公開の契約として出すこと。
受け流すだけの薄い層を重ね、結合だけを増やすこと。
上流の外部モデルを、変換せずに内部へ持ち込むこと。

### 行動
モジュールの公開面を確認し、外部が知る必要のある情報だけが出ているか判定する。
漏れていれば、公開契約を縮め、内部型と境界型を分ける。
外部システムと結ぶ箇所には変換の隔離層を置き、外部の都合を内部へ漏らさない。

### 例
```ts
// 内部の永続化型を公開すると、外部が列名や型まで知り、DB 変更が外へ波及する
export interface UserRow { id: number; pw_hash: string; created_at: string }

// 目的を表す最小の契約だけを公開し、永続化型は repository の内側に閉じる
export interface UserProfile { id: UserId; displayName: string }
```

## 結合を距離に見合う強さにする

### 要求
結合はゼロにできないものとして扱い、その強さを要素間の距離に見合う形にする。
近い要素には強い結合を許し、遠い要素ほど弱い結合へ下げる。

### 根拠
結合はシステムを束ねる糊であり、最小化ではなくバランスの対象である。
強い結合と遠い距離が重なると、一つの変更が遠くまで波及して全体が複雑になる。
弱い結合と近い距離が重なると、無関係なものが密集して局所が複雑になる。
結合の強さは共有する知識の種類で決まり、内部実装の共有が最も強く、引数で渡す値が弱く、名前による参照が最も弱い。
距離は要素間の隔たりで決まり、同じ関数の中が最も近く、同じ型やモジュールの中、別のモジュール、別のパッケージや別のシステム、の順に遠くなる。
関連の強いものを近くへ置く要求は、変数からリポジトリまで、あらゆる規模で同じ一つの欲求である。
複数の階層を上下する長い参照の連なりは、距離に見合わない強い結合の兆候である。
長い参照の連なりの多くは、参照される構造自体が過剰な木である兆候であり、構造の見直しで消える。
結合の痛みは、共有する知識の強さと、要素間の距離に、対象の変わりやすさを重ねて決まり、三つのどれかを下げれば残りが高くても痛みは減る。
一方の変更で他方も直さねば正しさが保てない関係は、特定の値の意味への依存・引数の位置への依存・アルゴリズムの重複として現れる。
これらは、名前付きの定数・キーワード引数・一箇所への抽出によって、より弱い形へ下げられる。
ファイルやディレクトリの名前と配置に振る舞いを結び付けると、参照を静的に追跡できない暗黙の結合が生まれる。
めったに変わらない要素なら、強い結合でも痛みは小さい。
複数の境界が一つの概念を共有する結合は、概念への属性の追加が受け手のすべてへ波及するため、距離や変わりやすさによらず弱いほどよい。

### 完了条件
遠い境界を越える結合が、引数で渡す値か、名前による参照に限られている。
近接する要素以外で、内部実装・グローバル状態・特定値の意味・引数位置への依存が残っていない。
何をするかを指示するフラグ引数で、呼び出し先の分岐を外から操作していない。

### 禁止事項
別モジュールの内部状態や private へ直接到達すること。
複数のモジュールが、可変のグローバル状態を共有すること。
単一インスタンスや静的アクセサで包んだ可変状態を、共有されたグローバル状態の禁止の外と扱うこと。
合成データ構造を丸ごと渡し、受け手が一部しか使わないこと。
処理の切り替えフラグを渡し、呼び出し先の分岐を外から制御すること。
ファイルやディレクトリの名前と配置に、プログラムの振る舞いを結び付けること。

### 行動
境界を越える結合ごとに、共有している知識の種類と要素間の距離と変わりやすさを確かめる。
距離が遠いのに強い結合があれば、引数の値渡しや名前による参照へ下げる。
意味を持つ裸の値は名前付きの定数や型へ、引数の位置依存は名前による対応づけへ、重複したアルゴリズムは一箇所へ移す。
境界をまたいで同じ概念を共有する箇所は、本当に同じ概念か、受け手に不要な属性まで渡していないかを確かめ、違うなら別の概念として名前ごと分ける。
結合の強さが読めないときは、意図的な破壊的変更で影響範囲を測り、計測の後に元へ戻す。

### 例
```ts
// フラグで呼び出し先の分岐を外から操作する。呼び出し先の中身が外に漏れている
function save(order: Order, validate: boolean) { /* if (validate) ... */ }

// 目的ごとに分け、フラグによる結合をなくす
function save(order: Order) {}
function saveDraft(order: Order) {}
```

```ts
// 特定値の意味に依存する。2 の意味を知らないと読めず、各所の 2 が一緒に変わる
if (user.role === 2) { /* 管理者 */ }

// 名前へ下げる。意味が型に乗り、変更が定義の一箇所に収まる
if (user.role === Role.Admin) {}
```

## 依存を安定と抽象へ向ける

### 要求
依存は、変わりにくいものへ向ける。
低頻度で変わる業務規則を内側に、高頻度で変わる詳細を外側に置き、向きを一方向に保つ。

### 根拠
高頻度で変わる詳細が業務規則を支配すると、詳細の変更が中心の判断を壊す。
依存される側ほど安定しているべきで、安定したものほど抽象であるべきである。
安定とは、既存の依存元から見た振る舞いを変えないことである。
複雑さは変更の少ない基盤の側に引き受けさせ、変更の多い業務の側を単純に保つ。
業務規則と詳細が直接結びつくと向きを固定できないため、両者の間に抽象を置く。
その抽象は、詳細の側ではなく方針の側が所有する。
方針の側がインタフェースを定義し、詳細の側がそれを実装すると、呼び出しの向きと逆にソースの依存が内側へ向く。
データの寿命はアプリケーションより長い。
アプリケーションは永続化方式より変えやすい。
だから業務規則はアプリケーション側に置き、永続化層には事実だけを残す。
具体の差し替えは、実行時に組立点で注入する。

### 完了条件
業務規則と方針が、UI・外部 API・永続化方式などの詳細へ依存していない。
境界をまたぐインタフェースが、それを使う方針の側に置かれている。
依存方向が一方向で、循環がない。

### 禁止事項
業務規則から、UI・DB・HTTP・framework・外部 SDK などの詳細へ直接依存すること。
インタフェースを詳細の側に置き、方針がそれを取りに行くこと。
循環参照や逆向きの参照を作ること。

### 行動
import・参照・組立点の構成・型共有・callback の向きを確認する。
逆向きがあれば、方針の側にインタフェースを定義し、詳細にそれを実装させ、具体は組立点で結び付ける。

### 例
```ts
// 方針が具体の DB クライアントへ依存し、永続化の変更が中心へ波及する
import { DatabaseClient } from "../infra/database";
class PricingPolicy { constructor(private database: DatabaseClient) {} }

// 方針が port を所有し、詳細がそれを実装する。依存は内側へ向く
interface RateRepository { find(id: SkuId): Promise<Rate> }   // domain が定義し所有
class PricingPolicy { constructor(private rates: RateRepository) {} }
// RateRepository の実装は infra に置き、組立点で注入する
```

## 副作用を境界に集める

### 要求
業務の計算・変換・判定は、副作用を持たない純粋な核に集める。
入出力・永続化・時刻・乱数・外部通信は、核を包む薄い殻で行う。

### 根拠
副作用が業務判断に混ざると、テストの再現性と実装の置換性が失われる。
純粋な核は判断を値として返し、殻はその値に基づいて入出力を行う。
不純な殻は純粋な核を呼べるが、純粋な核は不純な処理を呼ばない。
処理は、入力を読む・判断する・結果を書く、の三段に並べ、中央の判断を純粋に保つ。
現在時刻や乱数のような外界との界面は、引数やインタフェースへ追い出し、テストで差し替えられるようにする。
判断と入出力が同じ関数に混ざると、テストに実物の入出力かモックが要り、検証が重くなる。

### 完了条件
業務の計算・変換・判定の関数が、I/O・時刻・乱数・外部通信を行わず、必要な値を引数で受け取る。
副作用の実装が、核を包む殻と組立点に置かれている。
核の単体テストに、モックや実物の入出力が要らない。

### 禁止事項
業務の計算の途中で、永続化・現在時刻の取得・乱数生成・外部通信・可変グローバル状態を参照すること。
判断と入出力を、同じ関数に混ぜること。
テストのために副作用を、隠れた状態で差し替えること。

### 行動
処理の中の副作用の発生箇所を洗い出す。
純粋な判断と変換を関数へ切り出し、判断は値として返させ、入出力は殻へ移す。
時刻・乱数・外部依存は、引数かインタフェースで渡す。

### 例
```ts
// 判断の途中で時刻を取得し書き込みもする。実行のたびに結果が変わり、テストに実物が要る
function expireIfStale(token: Token): void {
  if (token.expiresAt < Date.now()) repository.markExpired(token.id);
}

// 判断を純粋な核に、時刻と書き込みを殻に分ける
function decideExpiry(token: Token, now: Instant): "expire" | "keep" {
  return token.expiresAt < now ? "expire" : "keep";   // 純粋。値を返すだけ
}
// 殻側で時刻を取り、判断の結果に応じて書き込む
// const now = clock.now(); if (decideExpiry(token, now) === "expire") repository.markExpired(token.id);
```

## 正本を互換から独立させる

### 要求
契約の境界は、正本の構造を基準に定める。
併存する新旧の契約は、それぞれ独立した構造として扱い、移行と互換の処理を境界へ閉じ込める。

### 根拠
旧契約や互換対応の都合を正本へ持ち込むと、現在の業務概念が歪む。
同じ名前のフィールドでも、表す意味が違えば別の概念であり、別の型で表す。
申込時点の希望値と、現在運用されている値は、混ぜずに分ける。
互換のための表現を境界へ隔離すれば、正本は現在の概念だけを表せる。

### 完了条件
正本となる構造が、現在の業務概念を表している。
旧契約への対応が、境界に隔離されている。

### 禁止事項
正本のモデルへ、互換専用の項目・不要な任意化・旧名称・旧状態を混ぜること。
新旧の意味差を、同一のフィールドや同一の型へ押し込めること。

### 行動
契約項目ごとに、現在の正本概念か、互換のための表現かを確認する。
互換要素が正本に混ざっていれば、独立した構造として境界へ分ける。

### 例
```ts
// 互換のための旧項目が正本に同居し、現在の概念が読めなくなる
interface Order {
  total: Money;
  amount?: number;        // v1 互換、今は使わない
  statusLegacy?: string;  // 旧状態の名残
}

// 正本を現在の概念だけにし、互換は境界で吸収する
interface Order { total: Money; status: OrderStatus }
// 旧契約への写像 toV1Response(order): OrderV1 は境界に置く
```
