# modeling

modeling は、業務の意味を型で表すための原則を置く。
意味を型に封じ、不正な状態を表現できなくし、境界で検証し、論理と物理を分ける。
語彙と命名は [naming](./naming.md) に従う。

## 業務の意味を型に封じる

### 要求
業務上の意味・単位・制約を持つ値は、専用の型または値オブジェクトに封じる。
裸の文字列・数値・真偽値で業務概念を表さない。
同じ構造でも意味が違えば、互いに代入できないようにする。
値に対する業務判断の構造化は、[construction](./construction.md) の「業務判断を型と多態で構造化する」に従う。

### 根拠
裸のプリミティブは、意味と制約がコードに現れず、取り違えと誤用を招く。
同じ string の住所と郵便番号は、引数を入れ替えても型検査を通り、誤りが実行時まで残る。
専用の型にすれば、取り違えを型検査で弾ける。
値オブジェクトは、等価性を識別子でなく値で定め、不変に保ち、生成時に不変条件を検証する。
検証を生成時に寄せると、生成された値は以後つねに妥当で、利用側で再検証しなくてよい。
許可された操作だけを型のメソッドとして公開すると、業務上ありえない演算を型が拒む。
金額どうしの加算は許し、金額への乗算は許さない、という区別を型に持たせる。
操作を外部のユーティリティへ出すと、規則の変更時に同期が漏れ、静かな不具合を生む。
値に名前を付ける定数化や列挙は、値の変更を一箇所に集めるが、値を解釈する判断は使う側に残したままである。
判断を型の操作として封じて初めて、値の使い方の変更まで一箇所に収まる。
判断を持つ側が型を作る責任を負い、利用側の目的を知らない汎用のライブラリは、値の公開に留めてよい。
構造を型として固定するほど約束は強く、実行時のデータへ遅らせるほど約束は薄れる。

### 完了条件
識別子・金額・数量・期間・状態・権限・単位付きの値が、専用の型または値オブジェクトで表されている。
その型が、生成または変換の時点で不変条件を検証する。
同じ意味の値が、コード全体で同じ型に統一されている。
同じ構造でも意味の異なる値が、互いに代入できない。
値オブジェクトが不変で、変更が新しい値の生成として表されている。
許可された操作が、型の契約として公開されている。

### 禁止事項
裸の文字列・数値・真偽値だけで業務の意味を表すこと。
意味や単位の異なる値を、同じプリミティブ型または同じ汎用の型として交換可能にすること。
値オブジェクトの操作を外部のユーティリティへ出し、型の外に散らすこと。
生成後に検証する前提の、未初期化の値オブジェクトを作ること。
意味が同じものへ別名を与えるだけで、精密にしたと見なすこと。

### 行動
プリミティブの値が業務の意味・単位・制約を持つか、他の値と取り違え可能かを確認する。
持つ場合は、専用の型・値オブジェクト・単一ケースの型へ置き換え、検証を生成時に寄せる。
構築子を非公開にし、検証を通す生成関数だけを公開する。
汎用のライブラリが値の公開に留めた判断は、判断を持つ利用側で専用の型に封じる。
同種の値を横断検索し、同じ意味が同じ型で表されているか確かめる。
プリミティブに見える値が、複数の要素や判断を伴い始めたら、専用の型へ昇格させる合図として扱う。

### 例
裸の `string` は取り違えても型検査を通り、検証も使う各所に散る。

```ts
function register(email: string, zip: string, country: string) { /* ... */ }
register(zip, email, country);
```

業務の意味を専用の型に封じ、構築子を隠して生成時に一度だけ検証する。等価性は値で定める。

```ts
class EmailAddress {
  private constructor(readonly value: string) {}
  static parse(value: string): EmailAddress | Error {
    return /^\S+@\S+\.\S+$/.test(value) ? new EmailAddress(value) : new Error("invalid email");
  }
  equals(other: EmailAddress): boolean { return this.value === other.value; }
}
function register(email: EmailAddress, zip: ZipCode, country: CountryCode) { /* ... */ }
```

列挙に名前を付けるだけでは、キャンセル可否の判断が使う側に散る。

```ts
if (order.status === OrderStatus.Paid || order.status === OrderStatus.Preparing) { /* ... */ }
```

判断を型の操作に封じれば、可否の規則の変更が型の一箇所に収まる。

```ts
if (order.canCancel()) { /* ... */ }
```

Rust では newtype と非公開フィールド、C# では record と検証付きファクトリで、同じ封入ができる。

## 不正な状態を表現できなくする

### 要求
不正な状態は、後付けの検査で弾くのではなく、型として構築できない形にする。
排他的な場合分けは、判別子つきの直和で表し、各場合にその場合でだけ意味を持つデータを持たせる。

### 根拠
複数のフラグや任意項目で状態を持つと、業務上ありえない組み合わせが表現可能になる。
接続中なのにセッション ID がある、という状態が型として作れてしまえば、いつか必ず生まれる。
モデルの本体は、データの列挙でなく、状態を貫いて成り立つ制約である。
欠けている制約は、正常の列挙からは見つかりにくく、どうすれば壊せるかを問う思考実験で現れる。
各状態に、その状態でだけ意味を持つデータを束ねると、ありえない組み合わせは型として存在しなくなる。
排他的な「いずれか」の規則は、両方必須でも両方任意でもなく、取りうる場合を列挙した直和で表す。
直和で表すと、取りうる場合が型として枚挙され、業務上ありうる場合だけが構築できる形になる。
一つの直和の場合ごとに処理が完全に分かれ、共有される処理がないなら、それは一つの型でなく、初めから別の型に分ける合図である。
対象が存在しないことと、対象は存在するが要素が零であることは、別の意味であり、別の表現で表す。
制約は後から足すのでなく、初めから正しく構築する。
状態ごとの振る舞いと遷移の置き場は、[construction](./construction.md) に従う。

### 完了条件
状態が、フラグや任意項目の組み合わせでなく、判別子つきの直和で表されている。
各場合が、その場合でだけ意味を持つデータだけを持っている。
場合分けの網羅の判定は、[construction](./construction.md) の「業務判断を型と多態で構造化する」に従う。
業務上ありえない値の組み合わせが、型として構築できない。

### 禁止事項
複数の任意項目やフラグで状態を表し、ありえない組み合わせを構築可能にすること。
排他的な選択を、両方任意の項目で表すこと。
場合分けの網羅を、既定の分岐や例外で誤魔化すこと。

### 行動
どうすれば不正な値や矛盾した状態を作れるかを列挙し、防ぐべき制約を洗い出す。
状態を表す型に、同時に成り立たない項目が同居していないか確認する。
同居していれば、取りうる場合を列挙し、判別子つきの直和へ組み替える。
各場合に、その場合でだけ意味を持つデータだけを移す。
場合を扱う処理を全場合の網羅で書き、既定の分岐に逃がさない。

### 例
すべての状態の項目を一つの型に任意で持たせると、接続中の `sessionId` や切断済みの `lastPing` のような不正な組み合わせを作れる。

```ts
interface Connection {
  state: "connecting" | "connected" | "disconnected";
  sessionId?: string; lastPing?: [Date, number]; whenDisconnected?: Date;
}
```

各状態にその状態固有のデータだけを束ねれば、ありえない組み合わせは型として存在しない。

```ts
type Connection =
  | { state: "connecting"; whenInitiated: Date }
  | { state: "connected"; sessionId: string; lastPing?: [Date, number] }
  | { state: "disconnected"; whenDisconnected: Date };
```

「連絡先は email か住所のいずれかを持つ」規則は、両方を任意にせず、取りうる場合を列挙する。どちらも無い状態は型として作れない。

```ts
type ContactInfo =
  | { kind: "emailOnly"; email: EmailAddress }
  | { kind: "postalOnly"; postal: Address }
  | { kind: "emailAndPostal"; email: EmailAddress; postal: Address };
```

Rust ではデータを持つ enum、C# では sealed な階層型とパターンマッチで、同じ排他表現ができる。

## 境界で検証して型に通す

### 要求
入力の検証は、システムの境界で、データを使う前に一度だけ行う。
検証の結果は真偽でなく検証済みの型で表し、型を新設するかの判定は「知識の増加を型に残す」に従う。

### 根拠
真偽だけを返す検証は、検査で得た知識を捨てるため、内側で同じ検査を繰り返す羽目になる。
検証済みの型へ変換すれば、得た知識が型に残り、以後はその型が妥当性を保証する。
未検証の値と検証済みの値を別の型にすると、検証を通さずに内側へ入る経路が型として塞がれる。
検証を処理のあちこちに撒くと、不正な入力を一括で拒む力が失われ、途中まで処理してから失敗する。
境界で検証相と実行相を分ければ、入力に由来する失敗は境界に閉じ、内側は妥当な値だけを扱う。
証明責任はできるだけ境界へ寄せ、境界より内へ持ち込みすぎない。

### 完了条件
外部から入る値が、境界で検証済みの型へ変換されてから内側へ渡っている。
内側の処理が、未検証の生の値を受け取っていない。
検証が、入力ごとに境界で一度だけ行われている。
検証の失敗が境界で型として表現され、後段へ伝播していない。

### 禁止事項
検証を真偽値だけで表し、検証済みであることを型に残さないこと。
未検証の生の値を、検証済みの値と同じ型で内側へ流すこと。
検証を処理の各所に撒き、データを使い始めてから検証すること。

### 行動
外部入力を受ける箇所を特定し、そこで生の表現を検証済みの型へ変換する。
構築の一点化は、「業務の意味を型に封じる」の行動に従う。
内側の関数の引数を、検証済みの型に変える。

### 例
真偽値を返す検証では型が `string` のまま残り、内側で何度も検査し直すことになる。

```ts
function isValidEmail(value: string): boolean { /* ... */ }
if (isValidEmail(input)) { send(input); }
```

検証済みの `EmailAddress` へ変換すれば、以後の処理は妥当性を型によって前提にできる。

```ts
function parseEmail(value: string): EmailAddress | Error { /* ... */ }
const email = parseEmail(input);
if (email instanceof Error) return reject(email);
send(email);
```

Rust と C# では Result 型で、検証の失敗を値として返す。
失敗しうる変換の連なりの形は、concerns の [effect](../concerns/effect.md) が具象化する。

## 知識の増加を型に残す

### 要求
parse・解決・検証・正規化・変換の段が、新しい不変条件、許可される操作、失敗の範囲、または lifecycle の保証を得るなら、その保証を出力の型に残す。
段の前後で保証が変わらない場合は、段ごとの型を新設しない。

### 根拠
検証して得た知識を元の弱い型へ戻すと、後段が同じ検査を繰り返し、未検証の値との取り違えを許す。
処理済みかを boolean や optional field で持つ形は、互いに矛盾する組み合わせを作れる。
一方、処理の名前が違うだけで保証が変わらない段まで別型にすると、変換と学習の費用だけが増える。
型を分ける根拠は、振る舞い、制約、lifecycle、許可される操作、保証される不変条件の差である。

### 完了条件
各段の入力が既に保証することと、出力が新たに保証することを説明できる。
後段が、前段で確認済みの制約を再検査していない。
型の違いが、振る舞い、制約、lifecycle、許可される操作、不変条件の少なくとも一つの違いに対応している。

### 禁止事項
検証後も未検証の入力型を使い続けること。
処理段階を、同じ値の boolean flag または optional field の組み合わせで表すこと。
保証が変わらない処理段ごとに、名前だけが異なる型を作ること。
型を増やすこと自体を目的にすること。

### 行動
各段について、入力の保証、増えた知識、失われる情報、起こり得る失敗、外部への効果を列挙する。
増えた保証を後段で利用する必要があれば、その保証を持つ型を出力する。
保証が変わらなければ同じ型を保ち、処理の関数だけを分ける。
失われる情報が後で必要なら、変換前の値を正本として残すか、必要な情報を出力へ明示する。

## 論理設計と物理設計を分ける

### 要求
業務の意味を表す論理モデルと、性能・格納・通信のための物理表現を、別の構造として扱う。
両者の間に変換の境界を置き、依存は物理から論理への一方向に保つ。
境界のデータ変換は、読み書きに必要な双方向を持てるようにする。

### 根拠
論理と物理を混同すると、格納形式や転送形式の都合が業務概念を歪める。
論理モデルは振る舞いと不変条件を表し、永続化モデルは格納構造を表す。
両者を分ければ、業務の意味と性能の都合を独立に変えられる。
一方向に保つ対象は依存であり、書き込み時に論理データを物理表現へ変換しても、論理モデルが物理表現を参照しなければ依存は逆転しない。
データは、メモリ上の表現と、バイト列としての符号化を、別の関心事として扱う。
同じ論理データでも、符号化形式が変われば全く違うバイト表現になる。
データはコードより長く生きるため、表現の進化は符号化の層の責務にする。
索引・分割・非正規化・キャッシュは物理の最適化であり、論理モデルには現れない。
場所やレコードは計算機の都合であり、業務の意味を持たない。

### 完了条件
論理モデルが、業務の意味だけで説明できる。
物理モデルが、性能・格納・通信の制約への最適化として説明できる。
論理モデルが、永続化方式・wire 形式・キャッシュ構造を知らない。
両者の変換が、両者の間の境界に置かれている。
物理側が論理側へ依存し、論理側が物理側を参照していない。
境界が、読み書きに必要な向きへデータを変換している。

### 禁止事項
DB の物理構造・索引・wire 形式・キャッシュ構造を、そのまま業務モデルとして扱うこと。
性能最適化を理由に、論理概念を曖昧にすること。
論理モデルに、永続化や転送の都合を持ち込むこと。
データ変換の向きと依存の向きを同一視し、書き込みに必要な変換を禁じること。

### 行動
対象の構造が、論理概念か物理表現かを判定する。
混同していれば、論理のモデルと物理の表現を分け、変換境界を明示する。
物理側だけが論理側を参照するよう依存を揃える。
読み込みでは物理表現を論理モデルへ、書き込みでは論理モデルを物理表現へ、境界で変換する。

### 例
DB の列がそのままドメインに現れると、業務の意味と格納の都合が混ざる。

```ts
class Order { id: string; created_at: string; status_code: number }
```

論理側の `Order` は業務の意味と不変条件だけを持ち、物理側の `OrderRow` がテーブルとカラムに対応する。物理側から論理側に依存し、境界で読み書きの両方向へ変換するため、`Order` は `OrderRow` を知らない。

```ts
class Order {
  constructor(readonly id: OrderId, readonly lines: NonEmpty<OrderLine>) {}
}

interface OrderRow { id: string; created_at: string; status_code: number }

class OrderRepository {
  private toDomain(row: OrderRow): Order { /* ... */ }
  private toRow(order: Order): OrderRow { /* ... */ }
}
```
