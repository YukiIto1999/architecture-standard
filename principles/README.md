# principles

principles は、ソフトウェア設計の判断の土台となる原則を置く。
concerns・structure・languages は、この原則の上に立つ。
原則は言語に依存しない。
言語ごとの実現は languages が、概念ごとの規律は concerns が担う。

## 目的

設計の目的は、変更を楽に、安全に、局所的にすることである。
すべての原則はこの一点への手段である。
原則を適用して変更がかえって難しく危うくなるなら、その適用が誤っている。

## 読み方

各原則は、`## 原則名` の下に必須の5節と任意の例で書く。
節の順序は全原則で同じにする。

- 要求は、守る規則を命令の一文で書く。
- 根拠は、なぜ守るかを述べ、判定の対象には含めない。
- 完了条件は、満たされた状態を観測できる形で示す。
- 禁止事項は、してはならないことを書く。
- 行動は、検出から是正までの手順を書く。
- 例は、避けたい書き方と望ましい書き方を対で示し、原則を明確にするのに役立つときだけ加える。
  差と帰結はコメントで述べ、記号は使わず、望ましい形を後に置く。
  型システムの機構が言語間で異なる例には、他言語での同等手段を一行添える。

遵守は、要求で意図を捉え、完了条件と禁止事項で照合して判断する。
根拠は理解のための記述であり、判定には使わない。

## 適用姿勢

要求した範囲は、最小実装で止めず、過不足なく作り切る。
未要求の投機的な要素は作らない。
投機的な要素を作らない原則は [construction](./construction.md) に従う。
粒度は、全体と局所、具象と抽象を往復して決める。
類推を入り口に使い、判断は具体で下す。

## 意図伝達の階層

意図は、コード・命名・コメント・文書の順で伝える。
上の層で表せるものを、下の層へ逃がさない。
命名で表せることをコメントに書かない。
コードで表せることを文書に頼らない。

## 原則間の関係

原則は互いに協調する。
恒常的に矛盾する組み合わせは置かない。
個別の事例で二つの原則が衝突することがある。
その解決は、変更容易性を保つ側を優先する。
採った判断とその根拠は、project が記録として残す。
標準は単一である。
条件付きの例外を原則の側に作らない。
事例ごとの逸脱は、それを採る project が明記する。
