## 業務判断を型と多態で構造化する

### 要求
業務上の判断は、裸の条件分岐に散らすのでなく、型・多態・状態・方針として表す。
分岐を書く前に、分類する業務の対象と、その分類軸を定める。
区分は、業務の対象を一つの分類軸で互いに排他的な場合へ分けたもので、各場合が業務での意味と名前を持つ。
区分の型は、分類軸と取りうる場合と各場合の意味を所有する。
業務の値や事実から場合を決める分類条件は、一か所に定める。
区分によって変わる判断は、その判断の変更理由を持つ責務に、業務の名前を持つ操作として置く。
操作は、区分を含む引数の型と業務の結果を表す戻り値の型で宣言し、場合ごとの分岐をその内側に置く。
分岐を呼び出し側に露出させず、呼び出し側が場合を判別したり、場合の意味を組み立てたりしなくてよい形にする。
独立した責務の判断は、区分の型へ集めず、それぞれの責務が区分を使って持つ。
種別や状態のデータの場合分けは、判別子つきの直和に対する網羅した分岐で書く。
直和へ新しい場合を追加するときは、網羅した分岐へ新しい arm を足し、意味の変わらない既存の場合の arm の本文を書き換えない。
既存の場合の意味を改めるときは、場合の追加と分け、影響する判断と分類条件を新しい意味に合わせて改める。
組立点で実装を差し替える方針の振る舞いは、方針の型への多態で表す。
業務概念を型で表すときは、継承を直和や方針の型を宣言する手段に限り、振る舞いの再利用には合成と委譲を使う。
業務の分類を表さない技術的な条件分岐や一時的な値には、専用の区分を作らない。

### 根拠
区分に基づく業務の判断は、対象をある分類軸で場合に分け、場合ごとに結果を変える形を取る。
どの軸で分け、各場合が何を意味し、何が変わるかは業務の知識であり、型と操作に置かなければ、呼び出し側の条件式の中にだけ現れる。
構造化されていない条件分岐に業務の意味を載せると、同じ判断が各所に重複し、概念が埋もれる。
複合した条件式は、意図を表す名前の判定へ抽出すると、何を判断しているかが読める。
場合に名前を付けるだけでは、場合の意味を解釈する判断が呼び出し側に残り、各所の分岐が重複したままである。
区分の型と、業務の名前を持つ判断の操作が、場合の意味と場合ごとの結果を所有すれば、呼び出し側は場合の名前も数も知らずに結果を使える。
操作の引数と戻り値の型が、呼び出し側の渡すものと受け取る業務の結果を定めるので、場合の増減や各場合の結果の変更は、操作の内側に収まる。
判別子つきの直和を網羅で分岐すると、場合の追加が型検査で漏れなく検出され、分岐が複数の箇所にあっても漏れが残らない。
網羅の検査が働かない裸の値の分岐は、種別が増えるたびに、すべての分岐を人が探して直すことになる。
網羅の検査が保証するのは、宣言した場合がすべて扱われることだけである。
業務の対象がちょうど一つの場合へ入るか、場合の境界が業務の定義に合うか、外部の入力が宣言した場合へ変換されるかは、網羅しても確かめられない。
分類条件に重なりや抜けがあれば、すべての arm が網羅されていても、対象は誤った場合の arm へ流れる。
外部の入力から場合への変換は、[modeling](../modeling/parse-at-boundary.md) の「境界で検証して型に通す」に従う。
既存の分岐へ場合を追加する変更は、既定の分岐に流れていた既存の入力の挙動を静かに変えうる。
型と多態で構造化された判断は、変更の差分が追加に寄り、修正が最小に留まる。
新しい場合には新しい arm が要るが、既存の場合の意味が変わらなければ、既存の arm の本文を保てるので、既存の場合の振る舞いを変えずに拡張できる。
一方、既存の場合の意味を改める変更は、その意味を所有する判断と分類条件を変更の対象にする。
新しい場合が既存の場合に入っていた対象の一部を引き取るときは、既存の arm の本文が変わらなくても、既存の場合に入る対象の範囲が変わるので、分類条件の変更として確かめる。
仕様の変更の大きさと修正の費用が釣り合う構造が、費用の面で優れた構造である。
区分によって変わる判断が複数の責務にまたがるとき、すべてを区分の型へ集めると、区分の型がすべての責務の変更理由を吸収して肥大する。
判断を変更理由ごとの責務に置き、区分の型を共有の語彙として使えば、一つの判断の変更が他の判断へ波及しない。
責務の分け方は、[separation](../separation/split-by-change-reason.md) の「変更理由で分ける」に従う。
実装の継承は基底の変更を派生へ暗黙に伝播させ、置換可能性を壊しやすい。
状態は、対象をライフサイクルの軸で分けた区分の一つである。
状態によって振る舞いが変わり遷移を持つものは、[modeling](../modeling/README.md) の直和で状態の形と状態固有のデータを表し、状態ごとの型に振る舞いを移して、状態自身に遷移を持たせる。
入れ替え可能な算法は、方針として切り出して組立点で差し替える。
多態はこの方針の表現に使う。
方針は業務の対象を分けた区分でなく、組立点が選ぶ算法であり、区分とは別の対象である。
繰り返し現れる業務規則は、満たすかを判定する仕様として切り出し、かつ・または・否定で合成する。
深いネストは、特殊な場合を早期の return で先に弾き、本筋を平らに保つ。

### 完了条件
区分ごとに、分類する業務の対象、分類軸、各場合の業務での意味を説明できる。
業務条件・状態遷移・権限判断・集約規則が、型・多態・状態・方針・直和で表されている。
区分によって変わる判断が、業務の名前を持つ操作に置かれ、呼び出し側に場合の判別と場合の意味の組み立てが現れていない。
同じ業務判断が、複数の箇所に重複して書かれていない。
場合分けが網羅され、漏れを型検査が検出する。
業務の値や事実から場合を決める分類条件が一か所に定められ、分類対象の入力領域で重なりと欠落がないことが、業務の定義から分類処理とは独立して導く期待値と境界の値の検証で確かめられている。
区分の型が独立した責務の判断を集めておらず、各判断が変更理由を持つ責務の側に置かれている。
ネストが浅く、特殊な場合の検査が早期の return で分かれている。
場合の追加が、場合の定義と新しい arm の追加で完結し、意味の変わらない既存の場合の arm の本文を書き換えていない。
新しい場合が既存の場合の対象を引き取る追加では、分類条件と境界の値のテストが改められている。
既存の場合の意味を改める変更が、その意味を所有する判断と分類条件へ反映され、意味の変わらない場合の arm の本文を書き換えていない。
繰り返し現れる業務規則が、満たすかを判定する仕様として切り出されている。

### 禁止事項
構造化されていない条件分岐やループに、業務条件・状態遷移・権限判断を重複して書くこと。
条件式の羅列で、業務概念を隠すこと。
網羅の検査が働かない、裸の値による種別の分岐を書くこと。
場合に名前を付けるだけで、場合ごとの判断を呼び出し側の分岐に残すこと。
呼び出し側に、場合の判別や場合の意味の組み立てを書かせること。
型検査の網羅だけを根拠に、分類条件の妥当性を確かめたとみなすこと。
独立した責務の判断まで、一つの区分の型へ集めること。
業務の分類を表さない技術的な条件分岐や一時的な値まで、専用の区分へ置き換えること。
新しい場合へ対応するために、意味の変わらない既存の場合の arm の本文を書き換えること。
振る舞いの再利用を目的に、実装の継承を使うこと。

### 行動
分岐が何の業務概念を表すかを確認し、分ける業務の対象と分類軸、場合ごとに変わる判断を書き出す。
複合した条件式は、意図を表す名前の判定へ抽出する。
裸の値による種別の分岐は、判別子つきの直和と網羅した分岐に変える。
場合ごとに変わる判断は、その判断の変更理由を持つ責務の、業務の名前を持つ操作へ移し、呼び出し側の分岐を操作の呼び出しに置き換える。
業務の値や事実から場合を決める分類条件を一か所に定め、場合の境界の値で、重なりと抜けがないことを確かめる。
新しい場合の定義と新しい arm を足し、意味の変わらない既存の arm の本文が変わっていないことを確かめる。
新しい場合が既存の場合の対象を引き取るときは、分類条件を改め、境界の値のテストを足す。
既存の場合の意味を改めるときは、影響する判断と分類条件を改め、意味の変わらない場合の arm の本文が変わっていないことを確かめる。
区分ごとに、判断の変更理由を確かめ、理由の異なる判断は、区分の型へ集めずそれぞれの責務に置く。
実装を差し替える振る舞いは、方針の型へ切り出し、具体は組立点で結び付ける。
繰り返し現れる業務規則は、満たすかを判定する仕様へ切り出し、かつ・または・否定で合成する。
状態をフラグでなく型で表し、深いネストは、特殊な場合を早期の return で弾いて平らにする。
場合の追加の差分で追加と修正の比率を確かめ、意味の改定を伴わない修正が多いなら、判断の構造化を見直す。

### 例
会員区分を裸の文字列で受けて呼び出し側で分岐すると、各区分の送料の意味が呼び出し側の条件式にだけ現れ、綴りの誤りと区分の追加が既定の分岐へ静かに流れる。

```ts
function checkoutTotal(subtotal: Money, tier: string, parcel: Parcel): Money {
  if (tier === "gold") return subtotal;
  if (tier === "silver") return subtotal.plus(reducedShippingFee(parcel));
  return subtotal.plus(standardShippingFee(parcel));
}
```

請求書の表示のように同じ会員区分で判断を変える処理が増えるたびに、同じ条件を複製することになり、更新の漏れを型検査は指せない。

会員を年間購入額の軸で分けた会員区分を型にし、購入額から区分を決める分類条件を `memberTierOf` に、区分で変わる送料の判断を `shippingFee` に置く。

```ts
type MemberTier = { kind: "gold" } | { kind: "silver" } | { kind: "basic" };

function memberTierOf(annualPurchase: Money): MemberTier {
  if (annualPurchase.isAtLeast(goldThreshold)) return { kind: "gold" };
  if (annualPurchase.isAtLeast(silverThreshold)) return { kind: "silver" };
  return { kind: "basic" };
}

function shippingFee(tier: MemberTier, parcel: Parcel): Money {
  switch (tier.kind) {
    case "gold": return Money.zero;
    case "silver": return reducedShippingFee(parcel);
    case "basic": return standardShippingFee(parcel);
    default: {
      const remainingTier: never = tier;
      return remainingTier;
    }
  }
}

function checkoutTotal(subtotal: Money, tier: MemberTier, parcel: Parcel): Money {
  return subtotal.plus(shippingFee(tier, parcel));
}
```

`checkoutTotal` は、会員区分の名前も数も、各区分の送料の求め方も、区分を決める購入額の閾値も知らない。
`shippingFee` の引数の型は渡せる会員区分を宣言した三つに限り、戻り値の型は送料という業務の結果を返すので、呼び出し側は区分を判別せずに結果を足せる。
新しい区分 `platinum` を追加すると、`shippingFee` の arm の不足を型検査が指し、`checkoutTotal` は変わらない。
gold の送料を改める変更で変わるのは、gold の arm だけである。
請求書の表示や特典の付与のように会員区分で変わる独立した判断は、`shippingFee` へ足さず、それぞれの責務が `MemberTier` を引数に受ける操作として持つ。

`shippingFee` の網羅が保証するのは、宣言した三つの区分がすべて扱われることだけである。
購入額がちょうど閾値のときの区分と閾値の順序は、`memberTierOf` が定める業務の定義であり、境界の値のテストと定義の照合で確かめる。
`platinum` が gold の購入額の一部を引き取るときは、gold の arm の本文が変わらなくても、`memberTierOf` を改め、境界の値のテストを足す。

閉じた直和と網羅的な分岐を持つ言語機構であれば、同じ区分を表せる。
組立点で差し替える方針は、業務の対象を分ける区分でなく算法の選択であり、多態で表して実装を方針の型に閉じる。

```ts
interface FeePolicy { fee(order: Order): Money }
class StandardFeePolicy implements FeePolicy { fee(order: Order): Money { return standardFee(order); } }
class CampaignFeePolicy implements FeePolicy { fee(order: Order): Money { return campaignFee(order); } }
```
