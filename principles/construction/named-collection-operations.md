## 集合処理を名前のある操作で表す

### 要求
業務の意味を持つ集合は、集合全体の制約と業務の操作を持つ一つの型に閉じ込める。
業務の意味を持つ集合とは、集合全体の制約を持つか、業務上の名前で呼ぶ集計・絞り込み・整列を持つ集合である。
集合全体の制約は、要素の妥当性とは別に、集合の型の構築と更新で守る。
集合の型が公開する操作の名前は、実現手段でなく業務上の問いを表し、利用側は内部の配列を取り出して集合の解釈を書き直さない。
集合の絞り込み・変換・集計・整列は、裸のループでなく、名前のある高水準の操作で表す。
業務の意味も制約も持たない技術的な一時の配列は、専用の型を作らず、高水準の操作のまま扱う。
集合の型が内部に持つ配列は、書き換えられない形で保ち、不変の扱いは [immutable-transformations](./immutable-transformations.md) の「値を不変に扱い、変換の連なりで組む」に従う。

### 根拠
業務の集合には、要素一つでは決まらない意味と規則がある。
同じ商品の明細を重ねない規則や課税対象の合計のように、規則は要素でなく集合全体に対して成り立つ。
一つ一つの要素が妥当でも、集合全体が妥当とは限らない。
同じ商品の明細を重ねない契約では、各明細が妥当でも、同じ商品の明細が二行ある集合は不正である。
この制約は要素の型では守れず、集合の型の構築と更新が検査して初めて守られる。
構築された集合が以後つねに妥当なら、利用側は集合の制約を再検査しなくてよい。
集合を裸の配列で渡すと、集合の解釈を知る責任が利用側へ移り、利用の箇所ごとに絞り込み・集計・判定が書かれる。
裸のループは、何をしているかを読み手が本体を追って復元しなければならない。
一つのループが絞り込みと集計のように複数のことを同時に行うと、意図が溶けて読めなくなる。
絞り込み・変換・集計を名前のある操作で書き、前段の結果を次段へ渡すと、何をするかが名前から読める。
ただし、ループを高水準の操作の連鎖へ書き換えるだけでは、読みやすさは増しても、集計の知識の置き場は変わらない。
同じ連鎖が利用側の各所に書かれれば、課税対象の合計のような同じ集計が重複し、規則の変更が漏れる。
置き場と名前を持たない知識は、放置すると急速に重複していく。
本質的に順序を持たない規則を、変数への代入の積み重ねで書くと、記述の順序が正しさの条件に加わる。
条件を満たす候補を列挙して選ぶ宣言の形は、この順序への依存を消す。
集合とその操作を一つの型に閉じ込めると、集合に対する規則がそこに集まり、他の責務から分けられる。
利用側は課税対象の合計という業務上の問いを名前で呼ぶだけで済み、絞り込みと集計の手順を知らずに済む。
高水準の操作の連鎖は、その型の内部で業務の操作を実現する部品として残る。
内部の配列を書き換えられる形で公開すると、構築で守った制約を外から崩せる。
業務の意味も制約も持たない技術的な一時の配列には、守る規則がなく、専用の型は読む型を増やす費用だけを生む。

### 完了条件
業務の意味を持つ集合が、集合全体の制約と業務の操作を持つ一つの型に閉じ込められている。
集合全体の制約が、要素の妥当性の検査とは別に、集合の型の構築と更新で検査されている。
集合の型が内部に持つ配列が、書き換えられる形で公開されていない。
集合の型が公開する操作の名前が、実現手段でなく業務上の問いを表している。
利用側が、集合の内部の配列を取り出して、絞り込み・集計・判定を書き直していない。
集合の絞り込み・変換・集計・整列が、裸のループでなく名前のある操作として表されている。
高水準の各操作が、絞り込み・変換・集計・整列のうち一つだけを行っている。
集合に対する同じ判断が、各所に重複していない。

### 禁止事項
業務の意味を持つ集合処理を、裸のループとして各所に散らすこと。
一つのループに、複数の集合操作を混ぜること。
集合に対する規則を、集合の外の各所に書くこと。
ループを高水準の操作の連鎖へ書き換えただけで、同じ連鎖を利用側の各所に残し、集合の規則を型へ移したと見なすこと。
要素の妥当性の検査だけで、集合全体の制約を検査せずに済ませること。
集合の型が、内部の配列を書き換えられる形で公開すること。
業務の意味も制約も持たない技術的な一時の配列へ、専用の型を求めること。

### 行動
ループと配列の利用箇所ごとに、業務の意味を持つ集合か、技術的な一時の配列かを確かめる。
業務の意味を持つ集合は、要素の妥当性と集合全体の制約を分けて洗い出し、集合全体の制約を型の構築と更新に置く。
利用側が集合に対して行っている絞り込み・集計・判定・整列を洗い出し、業務上の問いの名前を付けて、集合の型の操作へ移す。
集合の型の内部と技術的な一時の配列では、ループが何の集合操作かを確認し、絞り込み・変換・集計・整列の名前のある操作へ置き換える。
一つのループが複数のことをしていれば、操作ごとの段に分ける。
順序と無関係な規則が順序依存で書かれていれば、候補の列挙と選択の形へ直す。
集合の内部の配列を取り出す箇所は、保存・表示・送信のような境界への出力に限り、それ以外は集合の型の操作へ置き換える。

### 例
裸のループは、絞り込みと集計を混ぜ、何を計算するかを本体から復元することになる。

```ts
let taxableTotal = Money.zero;
for (const line of order.lines) {
  if (line.isTaxable()) {
    taxableTotal = taxableTotal.plus(line.amount);
  }
}
```

名前のある操作へ置き換えると意図は読めるが、`order.lines` が裸の配列のままなら、同じ連鎖が画面・請求・帳票の各所に複製される。
同じ商品の明細を重ねない規則も、どこにも置かれない。

```ts
const taxableTotal = order.lines
  .filter((line) => line.isTaxable())
  .reduce((subtotal, line) => subtotal.plus(line.amount), Money.zero);
```

明細の集合を型にし、同じ商品を重ねないという集合全体の制約を構築で検査し、課税対象の合計を業務上の問いの名前で公開する。
各明細が妥当でも、重複の検査は明細の型では書けない。
利用側は、課税対象の判定と集計の手順と内部の配列を知らずに済む。

```ts
class OrderLines {
  private constructor(private readonly lines: readonly OrderLine[]) {}

  static of(lines: readonly OrderLine[]): OrderLines | Error {
    if (new Set(lines.map((line) => line.productId.value)).size !== lines.length) {
      return new Error("duplicated product");
    }
    return new OrderLines([...lines]);
  }

  taxableTotal(): Money {
    return this.lines
      .filter((line) => line.isTaxable())
      .reduce((subtotal, line) => subtotal.plus(line.amount), Money.zero);
  }
}

const taxableTotal = order.lines.taxableTotal();
```

絞り込みと集計の連鎖は型の内部に残り、利用側が呼ぶのは業務上の名前だけになる。
閉じた型に制約と操作を持たせられる言語機構と、名前のある高水準の操作があれば、同じ封入ができる。
