# verification

verification は、検証に関する原則を置く。
重要な制約を機械検証に固定し、目的から要件を導き、検証できる形で定め、テストを設計の道具にし、テストを振る舞いの安全網にする。

## 重要な制約を機械検証に固定する

### 要求
命名・配置・依存方向・公開面・境界・アーキテクチャ特性の制約は、機械で検証できる形に固定する。
重要な制約を、文書・口頭・レビューの指摘だけで運用しない。

### 根拠
人の記憶やレビューの善意に頼ると、制約の違反が継続的に見逃される。
違反がコンパイルエラーやビルド失敗のような具体的な結果を生む形にして、初めて制約は守られる。
型検査・lint・依存の境界検査・アーキテクチャテスト・CI に固定すれば、違反が継続的に検出される。
依存の向きやレイヤー越境は、規約のコメントでなく、実行できるテストとして強制する。
アーキテクチャ特性は、主観でなく客観の尺度で測る適応度関数にし、CI に組み込む。
計測するだけでは足りず、違反が出力を生んでフローを止めることが、ただの監視との違いである。
良い設計とは型が付く設計であり、型が付けば多くの制約を型検査が担える。
コードスタイルの細則は、人の合意でなく、単一の formatter と linter に委ねる。
単一の整形に委ねると、レビューから見た目の雑音が消え、本質的な指摘が際立つ。
整形の論争そのものが消え、合意の費用が要らなくなる。
検証のゲートは、コードの出自が人か生成かを問わず、一律に適用される。
規則を満たすことと問題を解くことは別であり、機械検証を通ることは設計の正しさを保証しない。
機械検証が届くのは静的に追跡できる参照だけであり、追跡できない参照は影響を測れない無限の依存として扱う。
自動テストの一式は、機能と同時に作る欠陥検出器になる。

### 完了条件
公開 API・境界名・依存方向・公開面・配置・境界違反・アーキテクチャ特性が、型・lint・テスト・CI のいずれかで検証されている。
検証のゲートが、コードの出自が人か生成かを問わず、一律に適用されている。
依存方向やレイヤー越境が、実行できるテストとして強制されている。
手作業のレビューでしか検出できない、要求に列挙した制約が残っていない。
コードスタイルの細則が、formatter と linter に委ねられている。

### 禁止事項
重要な制約を、文書・口頭・レビュー指摘だけで運用すること。
機械で検証できる制約を、人手のレビューに委ねること。
違反しても何も起きない、結果を生まない検証を置くこと。
検証規則を、無効化の注記で局所的に回避すること。

### 行動
制約ごとに、型・lint・import 境界・アーキテクチャテスト・CI のどれで検証できるかを判断する。
検証手段がなければ、ルール・テスト・設定を足して検証可能にする。
既存の違反は、いったん固定して新規の違反だけを赤にし、徐々に減らす。
同じ規則への無効化が繰り返されるなら、違反箇所の免除でなく、規則の適用範囲を見直す。
規則への不遵守が繰り返されるなら、違反の側だけでなく、規則の側の妥当性も疑う。
繰り返し問題になる判断は、個人の判断のままにせず、明文の規則へ昇格させ、機械検証へ近づける。
静的に追跡できない参照を見つけたら、追跡できる形へ直す。

### 例
```text
# 「domain は infra に依存しない」を文書に書くだけでは守られない
# 依存の層を契約として宣言し、違反を CI で赤にする。推移依存も検出する
contract: layered
layers:                       # 上位だけが下位に依存できる
    interfaces
    domain
    data
# 言語ごとの手段は languages の inspection に置く
```

## 目的から要件を導く

### 要求
解くべき問題は、観測された事実と解釈を分けて定める。
要件は、候補の手段からでなく、目的から例を挙げて導く。

### 根拠
事実と解釈の混同は、存在しない問題を解かせる。
候補の手段を先に固定すると、目的に合わない構造が要件の顔をして残る。
手段に何のためかを問うて上位の目的へ遡ると、同じ目的を満たす別の手段を比較できる。
技術の語を除いても通じる問題の記述は、解き方を縛らずに、解くべきことだけを固定する。
目的から挙げた具体例は、抽象の語で合意するより先に、認識の食い違いを表面化させる。

### 完了条件
問題の記述が、観測された事実と、事実への解釈に分かれている。
問題の記述から技術の語を除いても、意味が通る。
要件のそれぞれが、どの目的に仕えるかを一言で言える。
要件に、目的から挙げた具体例が添えられている。

### 禁止事項
候補の手段を、目的を問わずに要件として固定すること。
観測されていない解釈を、事実として問題の記述に書くこと。

### 行動
要件に手段の名が現れたら、何のためかを問うて上位の目的へ遡る。
遡った目的から具体例を挙げ、例が示す振る舞いを要件へ降ろす。
この往復を、手段への固定が外れるまで繰り返す。
導いた要件は、検証できる形で要件と制約を定めるに従い、観測できる形へ直す。

### 例
```text
# 手段が要件として固定されている。目的を問えない
「一覧の結果をキャッシュする」

# 何のためかを問うて目的へ遡り、例を挙げて要件へ降ろす
目的  繰り返しの閲覧を待たせない
例    同じ条件の一覧を、続けて開き直す
要件  同一条件の一覧の再表示が、初回の表示より速い
```

## 検証できる形で要件と制約を定める

### 要求
要件と完了条件は、観測できる尺度と閾値で定める。
検証できないものは、要件として置かない。

### 根拠
検証できない要件は、満たされたかを判定できず、合意したつもりの食い違いを残す。
要件は、人か機械が有限の手間で満たしたかを確認できるときだけ、検証できる。
「使いやすい」「速い」「直感的」のような曖昧な語は、定量化されるまで要件にならない。
曖昧な品質の語は、尺度と閾値と測定法の三つに分けて、観測できる述語へ直す。
型と契約による静的な保証と、テストによる動的な検証は、同じ検証行為の二つの形である。
境界での実行時の検証も、この検証行為の一形態である。
判定できる要件は、型・テスト・CI・計測に落として機械に判定させる。
受け入れの基準は、振る舞いの定義として、実行できるテストに写す。
最適化や改善は、推測でなく計測に基づいて、効いたかを事実で確かめる。

### 完了条件
要件と完了条件が、観測できる尺度と閾値で書かれている。
曖昧な質的表現が、尺度・閾値・測定法に分けて定量化されている。
受け入れの基準が、実行できるテストに写されている。
改善が、計測の前後の比較で確かめられている。

### 禁止事項
「使いやすい」「速い」「適切に」のような検証できない語で、要件を定めること。
満たされたかを判定できない条件を、完了条件として置くこと。
計測せずに、最適化の効果を主張すること。

### 行動
要件に検証できない語があれば、尺度・閾値・測定法に分けて観測できる条件へ言い換える。
その条件を、型・テスト・計測のどれで判定するかを決める。
最適化は、計測で支配的な箇所を特定してから、その箇所だけ行い、前後を比較する。
検証できない共有事項は、規則にせず、説明の文書として扱う。
文書の種別は [documentation](./documentation.md) に従う。

### 例
```text
// 検証できない要件。満たされたかを判定できない
「検索は高速であること」

// 尺度・閾値・測定法に分け、計測で判定する
尺度  検索 API の応答時間の 99 パーセンタイル
閾値  1000 件のデータで 200ms 未満
測定法 5 分間の窓で計測し、CI と本番監視の両方で判定する
```

## テストを設計の道具にする

### 要求
テストは、使う側から見た振る舞いを検証し、実装より先にインタフェースを定める道具として書く。

### 根拠
テストを実装より先に書くと、呼び出し側から見たインタフェースを先に決めさせられる。
テストはその要素の最初の利用者であり、外から何が見える必要があるかを明らかにする。
テストを書く段階で下す判断は、主にインタフェースの判断であり、実装の判断はその後に分ける。
テストが書きにくいときは、どう書くかの前に、なぜ書きにくいかを問い、設計を見直す。
テストを書きにくくする真因は、対象の長さでなく、乱数・現在時刻・外部資源のような隠れた依存である。
テストの書きにくさは設計を見直す契機になるが、書きやすさは設計の良さを保証しない。
テストを先に書くと、対象が肥大する前に外形が固まり、長く複雑になる前に分割の圧が働く。
書かれた後の対象へテストを足すには、失われた意図の復元が要り、先に書くより高くつく。
テストが書かれていることより、必要な時に書ける構造であることを優先する。
テストと同じく、契約の記述を実装より先に書くことも、外から見た形を先に定める設計の道具になる。
内部品質は原因であり、速度は結果であって、設計を駆動するテストが将来の変更コストを下げる。
テストは設計フィードバックの一手段であり、テストの都合だけのために不要な間接層を足さない。

### 完了条件
変更対象の振る舞いが、使う側から見た仕様としてテストされている。
テストを書く段階の判断が、主にインタフェースの判断になっている。
テストの書きにくさが、設計を見直す契機として扱われている。

### 禁止事項
実装の判断とインタフェースの判断を、テストを書く段階で混ぜること。
テストの都合だけのために、不要な間接層を足すこと。

### 行動
変更対象の振る舞いを、使う側の視点でテストに先に表す。
テストが書きにくければ、なぜかを問い、インタフェースか責務の配置を見直す。
実装の設計判断は、テストが通った後のリファクタリングで行う。
一行の計算でも、独立に検証したい値の作り方は関数として切り出してよい。
先に書いた契約の記述が素直に書けない要素は、分割かインタフェースを見直す。

### 例
```ts
// 実装を先に書き、後からテストを実装に合わせる。インタフェースは実装の都合に従う
class Service { /* ... */ }
// テストを先に書き、使う側から見た形をテストが定める
const result = await register({ email, name });   // 呼び出し側から見た契約を先に決める
expect(result.status).toBe("registered");
```

## テストを振る舞いの安全網にする

### 要求
テストは、外から見た振る舞いを検証し、小さく速いテストを厚く、外部に依存する遅いテストを薄く保つ。
期待値は、検証対象のロジックと独立に定める。

### 根拠
テストは振る舞いの安全網になり、変更しても壊れていないことを継続的に確かめられる。
型検査の緑は形の整合を示すだけで、振る舞いの保存はテストでしか確かめられない。
公開面を変えず、参照がすべて静的に追跡でき、振る舞いのテストが緑なら、内部の変更は安全とみなせる。
通っているテストが検証として働いている保証はなく、壊して赤になることが実効性の証拠である。
変更の規模は、差分の行数でなく、安全を確かめるのに要る検証の水準で測る。
検証の水準は、関数や型の内側、ファイルや境界、コンテキストを跨ぐ変更へと、段階的に上がる。
内部実装に依存したテストは、振る舞いが正しくても壊れ、保守の重荷になる。
テストの対象は、クラスやメソッドという構造でなく、入力から外から確認できる結果までの作業の単位である。
テストの重みは、アクターがドメインに触れるユースケースの境界に置く。
内側の要素は型と契約の静的な保証に委ね、個別のテストを最小にする。
検証の総量は変わらず、静的な保証が広がるほど、テストで確かめる範囲は狭められる。
単位が上がるほど内部のロジックはテストから隠され、構造の変更にテストが耐える。
外から確認できる結果は、戻り値・状態の変化・外部への呼び出しの三種であり、置き換えによる呼び出しの検証が要るのは、外部への呼び出しが結果そのものであるときだけである。
異なる結果を一つのテストで確かめると、最初の失敗で以降の確認が実行されず、名前もどの結果の仕様かを表せない。
期待値を検証対象と同じロジックで導くと、実装の誤りが期待値へ複製され、常に合格する同語反復に陥る。
何も検証しないテストは、緑の表示で誤った安心を与えながらバグを通す。
テストは必要な資源の大きさで分け、単一プロセスで動く小さなテストを厚くする。
外部通信や DB を要するテストは遅く脆いので、依存を分け、小さく速いテストに寄せる。
同じ条件で通ったり落ちたりする不安定なテストは、信頼を失い、一度無視され始めると資産でなくなる。
不安定さの主因は隔離の不足・非同期・外部依存・時刻・資源の漏れであり、固定の待機は環境の速度差がそのまま不安定さになる。
現在の振る舞いを観測して固定するテストが先にあれば、レガシーの変更も安全網の下で進められる。
例だけを並べるより、満たすべき性質を書いて入力を多数生成すると、見落とした場合が見つかる。

### 完了条件
変更対象の振る舞いが、外から見た仕様としてテストされている。
テストが、内部実装でなく外から見た振る舞いに依存している。
期待値が、検証対象と別の方法で求めた値として書かれている。
一つのテストが、一つの結果だけを確認している。
小さく速いテストが厚く、外部依存の遅いテストが薄い。
不安定なテストが、隔離され、速やかに直されている。
テストの単位が、内部構造でなくユースケースの境界に揃っている。
安全網として頼るテストが、意図的に壊すと失敗することを確かめられている。

### 禁止事項
内部実装の細部にテストを結びつけ、振る舞いが正しくても壊れる状態にすること。
期待値を、検証対象と同じロジックで計算すること。
検証対象のロジックを、アサーションで再利用すること。
戻り値か状態の変化で確かめられる振る舞いを、置き換えた依存への呼び出しの検証で確かめること。
外部依存の遅いテストを厚くし、小さく速いテストを薄くすること。
不安定なテストを放置し、失敗を無視する習慣を作ること。
固定の待機で、非同期の完了を待つこと。

### 行動
変更対象の振る舞いを、使う側の視点でテストに表す。
検証する結果を戻り値・状態の変化・外部への呼び出しから特定し、結果ごとにテストを分ける。
同じ一つの結果への複数の確認は、分けずにまとめてよい。
期待値は、手計算や仕様の定めなど検証対象と別の方法で求め、値として書き込む。
定数や列挙値の共有は、それが検証の対象に含まれるかで判断する。
外部依存を分け、テストダブルで小さく速いテストに落とす。
不安定なテストは隔離して原因を断ち、固定の待機を状態の観測へ置き換える。
レガシーは、現在の振る舞いを固定するテストを置いてから変える。
安全網として頼る前に、対象のテストを意図的に壊して、失敗することを確かめる。
例だけで場合を尽くせない検証は、満たすべき性質を書いて入力を多数生成する形にする。
変更に着手する前に、どの水準の検証で安全を確かめられるかを見積もる。
同じ振る舞いへ入力だけが異なる検証は、パラメータ化した一つのテストにまとめる。

### 例
```ts
// 内部実装に依存する。リファクタで壊れるが、振る舞いは正しい
expect(service.repository.saveCalls).toBe(1);

// 外から見た振る舞いを検証する。実装を変えても壊れない
const found = await service.register(input);
expect(found.status).toBe("registered");
```

```ts
// 期待値を検証対象と同じ式で導く。式が誤っていても期待値も同じに誤り、常に合格する
expect(shippingFee(2300, 4)).toBe(Math.ceil(2300 / 1000) * 50 + 4 * 10);

// 期待値は別の方法で求めた値を書く。式の誤りで失敗し、検証として働く
expect(shippingFee(2300, 4)).toBe(190);
```
