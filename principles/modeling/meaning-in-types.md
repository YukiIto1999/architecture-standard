## 業務の意味を型に封じる

### 要求
業務上の意味・単位・制約を持つ値は、専用の型または値オブジェクトに封じる。
裸の文字列・数値・真偽値で業務概念を表さない。
同じ構造でも意味が違えば、互いに代入できないようにする。
値に対する業務判断の構造化は、[construction](../construction/decisions-as-types.md) の「業務判断を型と多態で構造化する」に従う。

### 根拠
裸のプリミティブは、意味と制約がコードに現れず、取り違えと誤用を招く。
同じ string の住所と郵便番号は、引数を入れ替えても型検査を通り、誤りが実行時まで残る。
専用の型にすれば、取り違えを型検査で弾ける。
値オブジェクトは、等価性を識別子でなく値で定め、不変に保ち、生成時に不変条件を検証する。
検証を生成時に寄せると、生成された値は以後つねに妥当で、利用側で再検証しなくてよい。
許可された操作だけを型のメソッドとして公開すると、業務上ありえない演算を型が拒む。
金額どうしの加算は許し、金額への乗算は許さない、という区別を型に持たせる。
操作を外部のユーティリティへ出すと、規則の変更時に同期が漏れ、静かな不具合を生む。
値に名前を付ける定数化や列挙は、値の変更を一箇所に集めるが、値を解釈する判断は使う側に残したままである。
判断を型の操作として封じて初めて、値の使い方の変更まで一箇所に収まる。
判断を持つ側が型を作る責任を負い、利用側の目的を知らない汎用のライブラリは、値の公開に留めてよい。
構造を型として固定するほど約束は強く、実行時のデータへ遅らせるほど約束は薄れる。

### 完了条件
識別子・金額・数量・期間・状態・権限・単位付きの値が、専用の型または値オブジェクトで表されている。
その型が、生成または変換の時点で不変条件を検証する。
同じ意味の値が、コード全体で同じ型に統一されている。
同じ構造でも意味の異なる値が、互いに代入できない。
値オブジェクトが不変で、変更が新しい値の生成として表されている。
許可された操作が、型の契約として公開されている。

### 禁止事項
裸の文字列・数値・真偽値だけで業務の意味を表すこと。
意味や単位の異なる値を、同じプリミティブ型または同じ汎用の型として交換可能にすること。
値オブジェクトの操作を外部のユーティリティへ出し、型の外に散らすこと。
生成後に検証する前提の、未初期化の値オブジェクトを作ること。
意味が同じものへ別名を与えるだけで、精密にしたと見なすこと。

### 行動
プリミティブの値が業務の意味・単位・制約を持つか、他の値と取り違え可能かを確認する。
持つ場合は、専用の型・値オブジェクト・単一ケースの型へ置き換え、検証を生成時に寄せる。
構築子を非公開にし、検証を通す生成関数だけを公開する。
汎用のライブラリが値の公開に留めた判断は、判断を持つ利用側で専用の型に封じる。
同種の値を横断検索し、同じ意味が同じ型で表されているか確かめる。
プリミティブに見える値が、複数の要素や判断を伴い始めたら、専用の型へ昇格させる合図として扱う。

### 例
裸の `string` は取り違えても型検査を通り、検証も使う各所に散る。

```ts
function register(email: string, zip: string, country: string) { /* ... */ }
register(zip, email, country);
```

業務の意味を専用の型に封じ、構築子を隠して生成時に一度だけ検証する。等価性は値で定める。

```ts
class EmailAddress {
  private constructor(readonly value: string) {}
  static parse(value: string): EmailAddress | Error {
    return /^\S+@\S+\.\S+$/.test(value) ? new EmailAddress(value) : new Error("invalid email");
  }
  equals(other: EmailAddress): boolean { return this.value === other.value; }
}
function register(email: EmailAddress, zip: ZipCode, country: CountryCode) { /* ... */ }
```

列挙に名前を付けるだけでは、キャンセル可否の判断が使う側に散る。

```ts
if (order.status === OrderStatus.Paid || order.status === OrderStatus.Preparing) { /* ... */ }
```

判断を型の操作に封じれば、可否の規則の変更が型の一箇所に収まる。

```ts
if (order.canCancel()) { /* ... */ }
```

Rust では newtype と非公開フィールド、C# では record と検証付きファクトリで、同じ封入ができる。
