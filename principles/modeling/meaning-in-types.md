## 業務の意味を型に封じる

### 要求
業務の値の制約・正規化・区別・計算・比較・許される操作は、その値を所有する業務モデルの構築と操作が守ってよい。
値を所有する業務モデルは、アクターの責務と変更理由で分けた既存のモデルであり、分け方は [separation](../separation/split-by-change-reason.md) の「変更理由で分ける」に従う。
各 field に制約があることだけを理由に、専用の値型を必須にしない。
独立した値とは、所有するモデルの外で単独に受け渡され、計算され、比較され、業務上の意味が通る値である。
専用の値型は、独立した意味と操作を持つ値、複数のモデルや境界を越えて同じ意味・単位・区別を維持すべき値、同じ検証や計算を複数のモデルが必要とする値に使う。
値型は、その値の計算・比較・変換と許される操作を引き受け、入力と結果の型で業務上の意味を表す。
計算式・比較の規則・端数と単位の扱い・不変条件は、利用側に書かず、値型か所有する業務モデルの操作として一箇所に置く。
独立した意味・単位・操作を持つ値を、裸の文字列・数値・真偽値で表さない。
取り違えの危険とは、同じ構造で意味の異なる値が、モデルや境界を越えて受け渡され、入れ替えても型検査を通ることである。
取り違えの危険がある値は、互いに代入できない型で区別する。
業務モデルが private に持つ値の区別は、そのモデルの構築と操作で守る。
業務モデルは、private に持つ値を検証前の形で公開せず、構築と更新で不変条件を保つ。
型の要否と内部の形は、型が保証する意味・制約・区別・操作で決め、フィールドの数や、単一の値を包むかどうかでは決めない。
複数の要素にまたがる不変条件を持つ値型は、要素を直接持つ一つの型で表し、不正な組を構築できず意味と操作を表せるなら、要素ごとの専用の型を求めない。
計算や比較を持たない識別子のような値は、複数のモデルや境界を越えて受け渡され、検証・正規化・取り違えの防止を型が担うときに専用の型へ封じる。
これらのいずれも伴わない値には、専用の型を求めない。
値型が引き受ける計算・比較・変換は、その値自身の意味に属するものに限り、異なるアクターが変更を求める判断を値型へ集めない。
値に対する業務判断の構造化は、[construction](../construction/decisions-as-types.md) の「業務判断を型と多態で構造化する」に従う。
値の集まりに対する集合処理は、[construction](../construction/named-collection-operations.md) の「集合処理を名前のある操作で表す」に従う。

### 根拠
値の制約・正規化・区別は、守る主体が一箇所に決まっていれば、型の形に依らずその主体が守れる。
値が一つの業務モデルの private な状態にだけ存在するなら、そのモデルの構築が検証し、操作が正規化と不変条件を保てるので、外からは検証前の値に触れられない。
この場合に各 field へ専用の型を足しても保証は増えず、読む型と変換が増えるだけである。
業務モデルは、アクターの目的と変更理由で分けた単位であり、その単位が値の規則を所有すると、規則の変更はそのモデルに収まる。
独立して受け渡される値を裸のプリミティブで表すと、意味と制約と計算の規則がコードに現れず、受け手ごとに再検査と再実装が生まれ、取り違えと誤用を招く。
値の意味は、何と足せて何と比べられ、どの単位で表し、端数をどう丸めるかという計算と比較の規則として現れる。
その規則を型に置かず利用側が書くと、同じ計算式が各所で別々に再実装され、端数の扱いや単位の解釈が食い違っても型検査を通る。
同じ数値型の単価・数量・税率は、引数を入れ替えても型検査を通り、誤りが実行時まで残る。
専用の型にすれば、取り違えを型検査で弾け、計算の入力と結果の型が業務上の意味を表す。
金額に数量を掛けると金額になり、金額どうしの乗算は書けない、という区別が、演算の署名に現れる。
値オブジェクトは、等価性を識別子でなく値で定め、不変に保ち、生成時に不変条件を検証する。
検証を生成時に寄せると、生成された値は以後つねに妥当で、利用側で再検証しなくてよい。
許可された操作だけを型のメソッドとして公開すると、業務上ありえない演算を型が拒み、利用側は計算の手順と内部表現を知らずに済む。
操作を外部のユーティリティへ出すと、規則の変更時に同期が漏れ、静かな不具合を生む。
値に名前を付ける定数化は、値の変更を一箇所に集めるが、その値を使う計算と比較は利用側に残したままである。
計算と比較を型の操作として封じて初めて、値の使い方の変更まで一箇所に収まる。
識別子のように計算を持たない値でも、複数のモデルや境界を越えて受け渡され、型が検証・正規化・取り違えの防止を担うなら、専用の型は利用側の再検査と誤用を減らす。
同じ検証や正規化が複数のモデルに現れるなら、それは独立した値の規則であり、値型へ集めれば規則の変更が一箇所に収まる。
検証・正規化・区別・操作のいずれも生まない型は、名前を増やすだけで保証を増やさない。
計算・比較・制約・取り違えのいずれも伴わない値や、一つのモデルの構築と操作が守れる private な値は、型を増やす費用に見合う保証を得られない。
型が足す保証は、内部のフィールドの数でなく、守る意味・制約・区別・操作で決まる。
一つの値に閉じた制約は、その値を表す型か所有するモデルが守り、開始が終了を超えない期間のように複数の要素にまたがる不変条件は、要素を直接持つ型の構築が守る。
開始日と終了日を別々の型で包んでも、組の検査は期間の構築に残るので、要素の型が足す保証は、その要素に固有の制約と取り違えの防止に限られる。
値の計算を型へ集める目的は、同じ意味の計算を利用側に重複させないことであり、異なる目的の判断を一つの値へ寄せる根拠にならない。
金額の単位・端数・加減と比較は金額自身の意味だが、値引きの方針と請求の可否は、変更を求めるアクターと理由が異なる。
各判断を金額の型へ足すと、型がすべてのアクターの変更理由を吸収して肥大し、一つの判断の変更が他の判断へ波及する。
計算や比較の規則を持つ側が型を作る責任を負い、利用側の目的を知らない汎用のライブラリは、値の公開に留めてよい。
構造を型として固定するほど約束は強く、実行時のデータへ遅らせるほど約束は薄れる。

### 完了条件
独立した意味と操作を持つ値、複数のモデルや境界を越えて同じ意味・単位・区別を維持すべき値(金額・数量・税率・期間・メールアドレス・識別子など)が、専用の型または値オブジェクトで表されている。
値型が、生成または変換の時点で不変条件を検証する。
同じ意味の値が、コード全体で同じ型に統一されている。
取り違えの危険がある値が、互いに代入できない。
値オブジェクトが不変で、変更が新しい値の生成として表されている。
値の計算・比較・変換が、値型か所有する業務モデルの操作として公開され、その入力と結果の型が業務上の意味を表している。
許可された操作が型の契約として公開され、業務上ありえない演算を型が拒む。
利用側が、値の内部表現を取り出して、型の操作と同じ計算や比較を書き直していない。
同じ計算式と比較の規則が、複数の箇所に重複していない。
業務モデルが private に持つ値の制約・正規化・区別が、そのモデルの構築と更新で守られ、検証前の値が公開されていない。
要素の組に成り立つ不変条件を持つ値型が、要素を持つ一つの型の構築で守られ、不正な組を構築できない。
専用の型のそれぞれが、検証・正規化・区別・計算・比較・許可される操作のいずれかの保証を担っている。
値型の操作が、その値自身の意味に属し、異なるアクターの判断を集めていない。

### 禁止事項
独立した意味・単位・操作を持つ値を、裸の文字列・数値・真偽値だけで表すこと。
取り違えの危険がある意味や単位の異なる値を、同じプリミティブ型または同じ汎用の型として交換可能にすること。
各 field に制約や正規化があることだけを理由に、専用の値型を必須にすること。
値の計算式と比較の規則を、利用側の各所に書くこと。
値の内部表現を取り出して、型の操作が所有する計算や比較を利用側で再実装すること。
値オブジェクトの操作を外部のユーティリティへ出し、型の外に散らすこと。
生成後に検証する前提の、未初期化の値オブジェクトを作ること。
業務モデルが private に持つ値を、検証を経ずに外から設定できる形で公開すること。
検証・正規化・区別・操作のいずれも担わず、意味が同じものへ別名を与えるだけの型を、精密にしたと見なすこと。
内部のフィールドの数や、単一の値を包むかどうかだけを、型の適否の基準にすること。
モデルの構築と操作が守れる private な値へ、保証を増やさない専用の型を求めること。
計算・比較・制約・取り違えのいずれも伴わない値へ、専用の型を求めること。
値の計算を型へ集めることを理由に、異なるアクターの判断を値型へ吸収すること。

### 行動
値ごとに、所有する業務モデルと、その外で独立に受け渡されるかを確かめる。
所有するモデルの外で独立に受け渡され、計算され、比較される値、複数のモデルが同じ検証や計算を要する値、モデルや境界を越えて取り違えの危険がある値を探す。
これらに当たる値は、その保証を担う専用の型・値オブジェクトへ置き換え、検証を生成時に寄せる。
構築子を非公開にし、検証を通す生成関数だけを公開する。
当たらず一つのモデルが private に持つ値は、そのモデルの構築と更新の操作に制約と正規化を置き、検証前の値を公開しない。
型の内部は、保証に必要な要素をそのまま持つ形にし、複数の要素にまたがる不変条件は、要素を持つ一つの型の構築に置く。
要素に専用の値型を足す前に、要求で定めた値型の必要性を、その要素について確かめる。
その値に対して利用側が行う計算・比較・変換・端数処理を洗い出し、同じ式が複数の箇所に現れていないか確かめる。
洗い出した計算と比較を値型か所有する業務モデルの操作へ移し、入力と結果の型で業務上の意味を表す。
利用側で値の内部表現を取り出している箇所を探し、保存・表示・送信のような境界への出力でなければ、型の操作へ置き換える。
値型へ足そうとする操作が別のアクターの判断なら、型へ足さず、その変更理由を持つ責務へ置く。
汎用のライブラリが値の公開に留めた判断は、判断を持つ利用側で専用の型に封じる。
同種の値を横断検索し、同じ意味が同じ型で表されているか確かめる。
同じ検証・正規化・計算が複数のモデルに現れたとき、またはプリミティブに見える値が複数の要素や判断を伴い始めたときは、値型へ昇格させる合図として扱う。
計算も比較も持たない値は、複数のモデルや境界を越えて検証・正規化・取り違えの防止を型が担うかを確かめ、担わなければ専用の型を作らない。
足した型が保証を一つも増やしていなければ、その型を外す。

### 例
裸の数値で金額・数量・税率を渡すと、引数を入れ替えた呼出しも型検査を通る。
税率が百分率の整数であることと端数の切り捨ては関数の本体にしか現れず、同じ業務上の計算を別の箇所が書けば、食い違っても気づけない。

```ts
const percentBase = 100;

function lineTotal(unitPrice: number, quantity: number, taxPercent: number): number {
  return Math.floor((unitPrice * quantity * (percentBase + taxPercent)) / percentBase);
}

const total = lineTotal(unitPrice, taxPercent, quantity);
const qualifiesForFreeShipping = total >= freeShippingThreshold;
```

金額の型が、不変条件の検証と、数量・税率との計算と、金額どうしの比較を持つ。
この例では非負の円の整数を任意精度で扱い、数量と税率も検証済みの非負整数の型で受け、百分率による端数の切り捨てを金額の操作に閉じる。
利用側は内部表現と計算式を知らずに済み、数量と税率を取り違えた呼出しや金額どうしの乗算は、型検査が拒む。

```ts
const percentBase = 100n;

class Money {
  private constructor(private readonly yen: bigint) {}

  static readonly zero = new Money(0n);

  static ofYen(yen: bigint): Money | Error {
    if (yen < 0n) {
      return new Error("invalid amount");
    }
    return new Money(yen);
  }

  times(quantity: Quantity): Money {
    return new Money(this.yen * quantity.count);
  }

  plus(other: Money): Money {
    return new Money(this.yen + other.yen);
  }

  withTax(rate: TaxRate): Money {
    return new Money((this.yen * (percentBase + rate.percent)) / percentBase);
  }

  isAtLeast(threshold: Money): boolean {
    return this.yen >= threshold.yen;
  }

  equals(other: Money): boolean {
    return this.yen === other.yen;
  }
}

const total = unitPrice.times(quantity).withTax(taxRate);
const qualifiesForFreeShipping = total.isAtLeast(freeShippingThreshold);
```

期間は、複数のモデルが含む・重なるの問いを共有する独立した値なので値型にし、開始日と終了日をそのまま持つ一つの型でよい。
開始が終了を超える組を構築で拒み、含むかの問いを操作として持てば、開始日と終了日を別々の専用の型で包まなくても、制約と操作の保証を満たす。
開始日と終了日は期間の業務上の属性として読み出せ、範囲の判定は `includes` だけが持つ。
`CalendarDate` は、日付の妥当性と順序の比較を担う型とする。

```text
Period { start: CalendarDate, end: CalendarDate }
Period.of(start, end) -> invalid | Period
  invalid when start is after end
Period.includes(day) -> boolean
  start <= day and day <= end
```

顧客の表示名は `Customer` だけが private に持ち、長さの検証と正規化を `Customer` の構築と更新が守る。
検証前の表示名は `Customer` の外に現れないので、`DisplayName` の専用の型を足さなくても保証は変わらず、各 field を包む型と変換が増えない。
顧客識別子は他のモデルへ渡されて注文識別子などと取り違えうるので、`CustomerId` は型で区別する。

```text
Customer { id: CustomerId, private displayName: text }
Customer.of(id, displayName) -> invalid | Customer
  normalized = trim(displayName)
  invalid when normalized is empty or longer than 50
  Customer { id, displayName = normalized }
Customer.rename(displayName) -> Customer.of(id, displayName)
Customer.label() -> displayName
```

意味ごとに型を分け、構築を検証へ限り、計算を型の操作として持てる言語機構があれば、同じ封入ができる。
