# standard-feedback

プロジェクトで `architecture-standard` を適用または監査している最中に、規律の矛盾・不成立・欠落・曖昧さに実測で突き当たった際、標準の所有リポジトリ（`YukiIto1999/architecture-standard`）へ改訂提案を還流するための Skill である。

## 発火条件（Trigger）

以下のいずれかの事象を実測で確認したときに発火する。

- **規律の矛盾**: 2 つ以上の標準文書間で要求が衝突している。
- **不成立**: 指定された言語やエコシステムの制約上、標準の完了条件を達成できない。
- **欠落**: 業務や設計で不可欠な境界や関心事について、標準本文に該当規定が存在しない。
- **曖昧さ**: 規律の解釈が複数に割れ、設計や実装の判断を一意に決定できない。

## 前提

- 標準本文の直接編集は行わない。
- プロジェクト側の `docs/revision` への記録は従来どおり行い、本 Skill はその記録を標準側へ届ける送信路として動作する。
- 起票・検索には GitHub MCP（`github-operations`）を使用する。

## 手順

1. **実測証跡の固定**:
   感情や推測を排し、対象規律の相対パス・見出し、発生した `file:line`、コンパイルエラーやテスト失敗のコマンド出力を客観的事実として記録する。
2. **重複起票の防止（事前検索）**:
   `YukiIto1999/architecture-standard` のオープンな Issue を検索し、同一の規律や条文を対象とした既存 Issue が存在しないか確認する。
   - 既存 Issue が存在する場合: 新規起票を行わず、該当 Issue へ今回の実測証跡と補足提案をコメントとして追記する。
   - 存在しない場合: 新規 Issue を作成する。
3. **Issue 本文の作成と送信**:
   以下の固定フォーマットに従って Issue を起票または追記する。

### Issue 記述フォーマット

```markdown
## 対象規律
- ファイル: `<standard-root からの相対パス>`
- 条文 / 見出し: `## <見出し名>`

## 実測証跡
- 対象プロジェクト: `<プロジェクト名>`
- 該当箇所: `<file:line>`
- 観測事実・コマンド結果:
\`\`\`text
<エラー出力や衝突の客観的証拠>
\`\`\`

## 提案
<標準側でどのような改訂・追記・例外規定を行うべきかの一文>
```

## Non-goals

- プロジェクト側で勝手なローカル解釈や独自ルールを決定して標準を書き換えること。
- 証拠のない不満や主観的な要望を起票すること。
- 重複する同一条文の Issue を乱立させること。
