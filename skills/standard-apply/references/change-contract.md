# 変更契約を固定して最小の段で止める

設計、実装、構造改善、移行のモードで、設計本文または編集の前に読む。

設計案または編集を作る前に、次を一つの変更契約として固定する。

- 依頼が求める外から観測できる結果と、明示された適用外。
- 選んだ process と標準本文が、その結果へ課す必須条件。
- 対象 project の既存契約、検証入口、安全、互換性を保つために必要な条件。

設計要素、変更 file、追加する型・抽象・設定・依存・fallback は、変更契約のいずれかの条件へ直接結びつくものだけを含める。
新しい要素を加える前に、変更不要、不要な既存要素の削除、標準に適合する既存要素の再利用または修正、標準が明示する機構、言語または実行環境の標準機構、導入済みで標準が許す依存、必要最小限の新規実装の順に判定する。
各段は変更契約の全条件を満たすかで判定し、満たした最初の段で止める。
必須条件の一つでも Unknown なら、その段を満たすと判定しない。
最も早く成立しうる段として暫定記録し、未確認契約が閉じるまで段の選択を保留する。
後の候補を比較、設計、実装しない。
閉じた探索で既存要素を確認できない場合は、その段で条件充足を立証できないと記録し、「既存要素がない」「再利用不能」と不存在を断定しない。
選んだ段、または選択を保留した暫定段と、それより前の各段では満たせない変更契約の条件を記録してから設計または編集へ進む。
後の段を候補、代替案、将来案として挙げない。
「この段で止め、後続の段は検討しない」のように、後段へ触れる文も最終応答へ書かない。
どの条件のためかを示せない要素は追加しない。
ここでいう最小は行数の最小化ではない。
受入条件、標準の必須規律、安全、互換性、必要な検証を削らず、それらを満たす追加だけに閉じることである。
提示された source に型、呼出元、戻り値、失敗契約がなければ、標準の必須規律が要求する結果を先に固定する。
観測した契約ではその結果を満たせない場合、具体的な独自型や失敗値を発明せず、必要な契約変更と確認対象を未確定の必須条件として残す。
受入条件にないことを理由に標準の安全条件を削ったり、既存契約を維持できると仮定したりしない。
受入条件に completion、success、failure、state など意味と authority を要する語があれば、依頼文や対象 source の局所的な読みだけで意味を固定しない。
同じ語または型を手掛かりに、対象 project の明示された要件と宣言の契約、state authority、writer、caller、既存 test を、source から実演された link に沿って material evidence が揃うまで追い、変更契約と検証へ反映する。
caller を一つ読んだだけで追跡を止めず、authority または既存 test を確認できなければ、その語の意味と検証条件を未確認にする。
future または task の終了と、domain の terminal state または永続化された authority の更新を同じ completion とみなさない。
完了、join、回収のように終了を表す語は、その終了を観測した経路の範囲でだけ使い、親の return や固定の成功値を task の join とも domain の完了とも説明せず、task の回収を domain の完了と説明しない。
Accepted な契約が persisted state を authority とする場合、全 record の terminal state を確認できて初めて domain completion と判定する。
標準の言語実現が並行処理の構造(permit を待つ場所など)を定める場合は、その構造を設計の必須構造とし、変えず、token、deadline、失敗値の具体的な入力契約だけを Unknown に残し、それらを発明しない。
project の判断の意味は、現在の標準本文が定める情報の正本に沿って、source、宣言の契約、test、設定、変更理由、Why not と、README または直接リンクされた要件や文書から回収する。
入力契約と未実装の要件の確認を、現在の実装の観測で代替しない。
外部 ADR の置き場の宣言がないことだけでは、契約の authority や判断の意味を Unknown としない。
直接参照された外部資料には利用できる読取手段を使い、記録が示す採否、対象、決定内容と現在の実装との対応を読む。
採否は特定の文字列との一致だけで判定せず、覆された記録や下書きを現在の契約へ昇格させない。
検索結果が空でも契約の不存在とはせず、観測した caller、受入語、authority 型や直接リンクの範囲で必要な根拠を追う。
既存 test は内部実装名でなく、対象 source を呼ぶ一段上の公開 caller の exact symbol を手掛かりに、manifest または明示契約から確認した test root で探す。
最初の search に一致がなくても test 契約の不存在とはせず、caller の rename、route、明示 link をたどって狭く再検索する。
読んだ test 内で caller が返す値または状態、authority の型を検査しているかを確かめる。
test root を確認できなければ慣例から推測せず Unknown にする。
設計本文を書く前に、受入条件の意味を持つ明示契約、state authority と既存 test の追跡を gate として閉じる。
source、caller、契約、変更理由、Why not、直接リンクされた資料を追っても material evidence が得られない契約は Unknown と記録し、空の search や一つの caller から不在を断定せずに設計を続ける。
並行処理の cancellation は、子の失敗時に sibling を取り消して drain する契約と、caller からの cancellation または deadline を子へ伝播する契約を別々の必須条件にする。
後者の起点または現行契約を確認できなければ、外部 cancellation と deadline の伝播を未確定の必須条件として残す。
未観測の関数または module に、state authority の更新、失敗翻訳、cleanup などの責務を割り当てない。
「既存の未変更の責務」と書けるのは、その責務を担う実装または明示契約を直接確認した場合だけである。
確認できなければ、必要な責務と owner を別々に Unknown とし、その責務を前提に受入条件を満たすとは報告しない。
失敗または cancellation を caller へ伝える契約が未確定なら、それらを成功と同じ戻り値へ畳む疑似コードを書かない。
実装形の疑似コードは省き、必要な契約変更、確認する caller、伝播の受入条件だけを残す。
未確定の必須失敗契約が一つでも残る設計では、戻り値型、`join` loop、error branch を含む code fence を最終応答へ置かない。
契約が確定するまで、制御構造は prose と遷移だけで示す。
設計だけの依頼では、変更契約を満たす構造、既存機構の使い方、観測する検証までを応答で決める。
決定の記録、設計書、報告 file への記録を依頼されていなければ file を作らず、実装も編集しない。
未観測の契約に依存する分岐や、隣接する migration の設計へ広げない。
検証は対象入力または setup、観測する値、合格となる期待結果を指定する。
task の終了数や実行中 counter は並行度と task 回収だけを検証し、persisted state が authority なら domain completion の検証には使わない。
persisted state を completion authority とする Accepted な契約では、並行度、task 回収、domain authority の terminal state を検証一覧の別々の case にする。
domain authority の case は、識別できる複数の入力を公開 caller へ渡し、返った時点で同じ識別子の authority を読み、全件が契約上の terminal state であることを期待結果にする。
writer、reader、persistence の具体的な呼出しを確定できなければ、その実現だけを同じ case に未確定と書き、case を検証一覧から省かない。
domain authority の case がなければ設計を完了と報告しない。
架空の seam、helper、型は補わず、検証可能または完了と書かない。
尺度と閾値の列挙だけを検証設計と扱わない。
受入条件ごとに少なくとも一つの具体的な case を上の三要素で閉じられなければ、設計を完了としない。
検証入口を設計・変更する場合は、承認対象と必要保証の対応を入力に [process/verification](../../../process/verification.md) の実行計画を具体化する。
一走行の資源保護の上限による停止、進捗のない反復の停止、有効な進捗からの再開、累積の費用と方法の見直しの記録、非影響変更による証跡の再利用、影響する入力・設定・検証器の変更による失効、T1・T2 の選択の記録の保存、分析と上限・取消・終了 status を共有しない全量回帰の完走、全量回帰で見つかった選択の見逃しと cache の失効の不備の区別と入力への還元を、それぞれ対象入力、観測、期待結果で判定できる case にする。
有効な進捗のある修正と再開は、累積の消費だけでは止まらない case にする。
製品受入の検査の不成立・未実行と、mutation 分析の未実行・中断・未分類・生の status を別の case に分け、分析の未完了だけでは受入不成立にも製品の欠陥にもならないことを判定できるようにする。
mutation 分析の全件消化、未検出 0 件、score の閾値は受入条件にしない。
分析で確認した実装の仕様違反と具体的な受入検査の不足は、通常の修正へ返る case を置く。
設計した停止・再開条件と、それを実装して実測した結果を区別し、実行計画を記述したことだけで上限内の完了や受入の成立を確認済みとしない。
作業中に見つけた隣接課題は、変更契約の成立、安全、互換性を左右する場合だけ未確定条件へ含める。
それ以外は、監査または別件報告を依頼されていなければ最終応答へ追加しない。
現在のモードで変更契約に対して実測できる条件を確かめ、未実装・未実行を分け、依頼全体の完了とは区別する。
依頼が一つのモードに限定されている場合は、その範囲の結果と未確認事項を報告して終了し、実装など別のモードへ広げない。
依頼が複数のモードを含む場合は、完了したモードの成果と証拠を次のモードへ渡し、実行可能な残件を進める。
最終応答の各節、設計要素、参照 file を一つずつ除いたとき、変更契約の条件または未確認事項の根拠が失われるか確かめる。
失われないものは応答から除く。
